# Backend

`backend/` holds the Lambda code (ADR 0002, 0006). It is a separate npm package with its own lockfile. `backend/src/observability` gives every handler structured JSON logs and business metrics ([Powertools for AWS Lambda](https://docs.powertools.aws.dev/lambda/typescript/)): `createObservability()` returns a `logger`, `count(metric, n, metadata)` and `gauge(metric, value, unit)` (a level a scheduled check measures), and `withObservability(obs, handler)` adds the request ID to every log line and flushes metrics after each invocation. Metrics go out as CloudWatch embedded metric format in namespace `SupplyCheckout`, with `Region` as their only dimension; per-team detail goes in metadata, never a dimension.

It also has the HTTP API's handlers in `backend/src/api` (see [Data API](infrastructure.md#data-api)), transactional email in `backend/src/email` (templates, the SES mailer, and the bounce and complaint handler; see [Transactional email](infrastructure.md#transactional-email)), the user pool's triggers for Google and Apple users in `backend/src/identity` (a guard that keeps them to their provider, one that sets `email_verified` from the provider's claim and keeps a linked user's to the address Cognito verified, and one that links a first Google or Apple sign-in to an existing account with the same verified email) (see [Sign-in](infrastructure.md#sign-in)), and the data-access module, `backend/src/data`:

- **Team-scoped access.** Every read and write of a team's data takes a `TeamContext`. Every function that can issue one lives in `src/data/team-context.ts`, and the issuer itself isn't exported. `authorizeTeam(db, userId, teamId)` checks the MEMBER item; the authorizer calls it with the user ID from the verified token. `createTeam`, `acceptInvite`, `teamContextForStripeCustomer` and `teamContextForEmailEvent` issue a context for the new owner, the new member, the billing webhook and the email-events handler (which may only mark an invite failed, with `markInviteFailed`). `acceptInvite` takes the caller's verified email, and its transaction re-checks that the stored invite is for that email, unexpired and unused. Each function checks the role (viewer, contributor, owner, system) before it writes. A MEMBER item's `email` is the member's verified address, copied at create or join and kept current by `setOwnMemberEmail` (`supply-checkout-xv3k`): the account handler calls it (`keepMemberEmail`) in each team the caller is in, on a session for that team after the membership check, on `GET /me` whenever the verified address differs from the stored one and on `POST /me/email/verify` once a native user's new address is verified (a linked user's counts at the token refresh that follows, and the `/me` after it picks it up). It sets only the caller's own item, only if it still exists, never with an unverified address, and not in a closed team; a failure is logged with the team ID and error name only and doesn't fail the request. So the members list and team-closed notices use the address the member has now. When an address stops counting as verified (a change not yet confirmed with a code), the member item keeps the last verified address until a new one is verified. The `Db` handle from `createDb` is opaque: it exposes no DynamoDB client.
- **At least one owner.** The team item keeps an `owners` count. Every change to an owner membership updates it in the same transaction, and a decrease is conditioned on `owners > 1`; when only that condition fails, `setMemberRole` and `removeMember` throw `LastOwnerError` (the API's 409 `reason: "last_owner"`). Owner actions on other members also re-check the caller's own MEMBER item at write time.
- **Member cap.** The team item also keeps a `members` count, set to 1 by `createTeam` and moved in the same transaction as every membership added (`acceptInvite`) or removed (`removeMember`, which covers leaving). Both counts live on the META item, so one Update moves them (`teamCounts` in `src/data/model.ts`; DynamoDB allows one operation per item in a transaction). Adding is conditioned on `members < cap`, so two accepts racing for the last place can't both join: the loser gets `TeamFullError` (the API's 429 `quota_exceeded`, `reason: "team_full"`) or a `ConflictError` to retry, and keeps the invite. `memberCap(team)` (`model.ts`) decides the cap: `MEMBERS_PER_TRIAL_TEAM` (10) unless the team's status is `active` or `past_due`, then `MEMBERS_PER_TEAM` (100). It's the one place seat billing (bead `supply-checkout-l50`) changes when paid seats must be enforced. `createInvite` also refuses an invite when members plus live invites already fill the cap; that reads before it writes, and the accept is the enforcement. A team from before the count has no `members`: the next add or remove counts its MEMBER items (`src/data/member-count.ts`) and sets the count on the condition that it's still absent, so a change that commits in between makes it fail and retry rather than leave a wrong count. The `members` backfill (`src/data/backfill.ts`, run by the owner with `npm run backfill`, [infrastructure](infrastructure.md#backfills)) sets it on every such team, on the same condition.
- **Roles on every route.** Each route in `src/api/routes.ts` names the least role that may call it (`minRole`), and the handlers check it with `requireRole` (`src/api/roles.ts`) before anything runs; the data layer checks again before each write. `test/roles.test.ts` calls every team route as an owner, a contributor, a viewer and an outsider, `test/members-api.test.ts` covers the members routes (listing, role changes, removal, leaving, the last owner, two owners at once), and `test/invites-api.test.ts` the invites routes.
- **Invites.** `src/data/invites.ts`. Owners invite an address with a role (`createInvite`): a random 32-byte token goes in the emailed link, and only its SHA-256 is stored (on `GSI1`); the invite expires in 7 days (`expiresAt`, also the TTL). An address that's already a member's, or already has a live invite to the team, is refused. The address must be a bare addr-spec (`mailAddress` in `src/data/model.ts`: lowercase ASCII, a dot-atom local part, a DNS domain), because SES reads a recipient as an RFC 5322 address and a display name or list could deliver somewhere other than the address that was checked; the mailer refuses anything else too. (Matching a signed-in user to their invites still uses the looser `normalizeEmail`.) Each invite, new or re-sent, moves three counters in the same transaction: the team's for the UTC day (`TEAM#<teamId>` / `LIMIT#INVITES#<day>`, 50), the team's for that address (`TEAM#<teamId>` / `LIMIT#INVITES#<day>#<key>`, 3, so one team can't use up the address's allowance), and the address's from every team together (`INVITELIMIT#<key>` / `LIMIT#INVITES#<day>`, 15), each expiring after two days. The key (`inviteLimitKey`) is the SHA-256 of the address less any `+tag`, and for Gmail less the dots, so one mailbox can't be reached under many spellings. Past any, `LimitReachedError` (429), with one message for both so an owner can't tell what other teams sent. `resendInvite` replaces the invite in one transaction (the old one deleted, on the condition that its token hash hasn't changed): a new ID and token, so the old link stops working and a late bounce for the old message can't mark the new one, the same address and role, a fresh expiry and no failure fields. The account handler sends the email after the write (`sendInviteEmail`); if SES won't take it, `markInviteNotSent` marks the invite `inviteStatus: "failed"`, `failureReason: "not_sent"`, next to the `bounced` and `complained` the email-events handler records. `removeMember` first deletes every invite to the team for the member's address, so someone removed can't rejoin with an invite they hadn't used; when someone leaves, the account handler also passes the address Cognito has verified for them now (`verifiedEmail`), so invites to it go even if their member item has none or an older one (`supply-checkout-u0vv`). Invite emails quote the team name and defang anything in it that a mail client could turn into a link (`teamLabel` in `src/email/templates.ts`).
- **One way in.** Outside `src/data`, ESLint (`backend/eslint.config.js`) bans any `@aws-sdk/*dynamodb*` package or path inside one, and any file under `data/` except `data/index.js`. This covers static imports, re-exports, `import()` and `require`. Tests are exempt, to inspect stored items.
- **Region-ready** ([ADR 0010](adr/0010-multi-region-active-active.md)). Every team gets `homeRegion` when it's created, from `AWS_REGION`. `writeRegionFor` in `src/data/region.ts` is the one function that decides where a team's writes go; in the MVP it always returns the local region.
- **Documents.** `src/data/documents.ts` serves the app's document model (`products/<key>`, `sheets/<id>`: get, set, deep-merge update, delete, list) on the same items the typed functions use. Every write reads the item and puts the new one on the condition that its version (and a product's `stock`) hasn't changed, so each write is one stream record with a new version. A product write keeps the stored `stock` and refuses a body `stock` that differs from it, so stock moves only through the stock commands and the CSV import, which record a movement for each change ([commands.md](api/commands.md)). A stored `stock` that isn't a number (legacy) is no count: a write drops it, so the item can still be edited and stays untracked. Deleting a product that tracks stock is one transaction with a `delete` movement taking its stock to 0, so the history still adds up if the key is used again. A product's `price` and `cost`, and a sheet line's, must be amounts in whole cents (ADR 0014), but only where the write changes them: a legacy value the product or line already had, carried over unchanged, doesn't block the write and is rounded to cents ("rounded when next saved"). Only DynamoDB's own item-size refusal (`Item size has exceeded the maximum allowed size`, matched from the start of the message) is 413 `quota_exceeded`; any other `ValidationException` is a 500. The data API requires `expectedVersion` on every write (ADR 0006) and answers 409 `aborted` if the document is at another version or changes before the put; there's no retry, so two people editing one sheet line can't overwrite each other.
- **Inventory commands.** `src/data/commands.ts` has checkout, return and stock adjust, each one `TransactWriteItems` in the team's partition: an operation record (`OP#<operationId>`, only if new, kept 7 days for replaying retries), the sheet line (counts added on the server, only while the sheet is open and returned stays at or below out), the product's stock (`ADD`, when it tracks stock), and a movement record (`MOVE#<key>#<time>#<operationId>`), the stock history the nightly drift check reconciles. `addLines` adds a receipt's lines for a client to a sheet (up to 40, in one update of the sheet, with the operation record, and no stock or movement). A failed condition cancels the whole transaction; the command reads again and retries a few times before answering 409. The client contract is [docs/api/commands.md](api/commands.md).
- **CSV inventory import.** `src/data/imports.ts` (with the bounded CSV reader in `src/data/csv.ts`) imports a spreadsheet of items (`name`, `barcode`, `price`, `cost`, `stock`, `pack_size`, ADR 0014) for assisted onboarding, owners only. All or nothing, for more rows than one transaction holds (100 items): it validates every cell and every row against the whole inventory first, and any problem means nothing is written (a dry run returns that preview). Then one transaction stages the job (`IMPORT#<importId>`, only if new) and its whole plan in chunk records (`IMPORT#<importId>#CHUNK#<n>`, 49 rows each), and the rows commit in batches, each its own transaction: the product puts (conditional on the version and stock just read), a movement (`reason: "import"`) for each stock change, and the job's count of committed rows, conditional on it not having moved. A batch is at most one chunk and as many rows as fit in 2.5 MB, measured from the items as they are when it commits (as DynamoDB gets them, maps with a `constructor` key included), so it stays under DynamoDB's 4 MB transaction limit even if items grew after staging; if DynamoDB still refuses a batch as too large (its two messages, matched from the start: a transaction over 4 MB, an item over 400 KB), it's retried with half the rows, and a single row it still refuses answers 413 and logs DynamoDB's error name and the start of its message, never item data; a batch DynamoDB cancels with a `ValidationError` reason carrying its item-size message answers 413 too; any other `ValidationException` is a 500; rows whose item would pass the 350,000-byte document limit are refused before staging. If the commit stops part-way, the same file again with the same `importId`, from any owner of the team, carries on from the first row not committed with the staged plan, so an import rolls forward to complete rather than being left half done; a finished one replays its summary. Only two things stop a staged import for good, and both answer 409 saying to choose the file again (a new import, which re-plans and leaves already-imported rows unchanged): its records expired, or a key it planned to create was taken meanwhile by an item with another barcode. A row matches an existing item by barcode, or by name when either side has no barcode, and a re-import sets values (stock included), so importing a file twice changes nothing. New items get keys from their barcode (as `keyOf` in `src/format.js` makes them) or a hash of their name, so two imports of one file at once still make one item per row. Limits: 1,000 rows, 300 KB, 50 columns; job records expire after 7 days. The client contract is `POST /teams/{teamId}/imports` in [openapi.yaml](api/openapi.yaml). While a job is committing it's also in GSI1's `IMPORTS#COMMITTING` partition (sort key `<createdAt>#<importId>`), and the commit that finishes it removes it, as does a stop no retry gets past (a row too large, a key taken); `listStuckImports` reads that partition for the scheduled stuck-import check (`src/ops/`, "Imports stuck" in [journeys.md](journeys.md)), which has no team context and can read only the keys and progress.
- **Operators** ([ADR 0015](adr/0015-platform-operator-role.md)). `src/data/operator.ts` is everything a platform operator may do: list and search teams and read one team's account record and owners (`listOpsTeams`, `listOpsOwners`, `getOpsTeam`, from GSI3's projection only), comp a team or end its comp (`setComp`, `endComp`: the `comp*` attributes and `version` of the `META` item, at the version the operator read, with the audit item and the request's idempotency record in the same transaction), and read the operator audit (`listOperatorAudit`). It takes an `Operator` (the verified `sub`), never a `TeamContext`: ESLint keeps `team-context.ts` out of it, and keeps the context issuers out of `src/operator/`, the ops function (`backend/test/lint.test.ts`). `createTeam`, `acceptInvite` and `setMemberRole` keep GSI3 current: a team's `META` item and its owners' `MEMBER#` items are in it, nothing else. `liveComp` (`model.ts`) is the entitlement rule: while a comp's `compUntil` is ahead, `memberCap`, the live-update audience and `/me` treat the team as active on it. Owners read what operators did with `listSupportActions` (`audit.ts`), which asks only for `OWNER_OPERATOR_AUDIT_ATTRIBUTES`. `test/ops-api.test.ts` runs the ops handler against the in-memory table behind a check that mirrors the operator-access role (`test/ops-policy.ts`), and the in-memory table returns only GSI3's projected attributes, as DynamoDB does; `test/ops-ddb.test.ts` runs the same functions against DynamoDB Local.
- **Closing a team.** `closeTeam` (`src/data/teams.ts`, owners only, `POST /teams/{teamId}/close`) takes the team's name as typed to confirm it (ignoring case and surrounding spaces) and, in one transaction conditioned on the caller still being an owner, sets `closedAt`, `closedBy` and `purgeAfter` (`CLOSED_TEAM_RETENTION_DAYS`, 30, later) on the META item, puts it in GSI1's `TEAMS#CLOSED` partition (sort key `<purgeAfter>#<teamId>`), and writes a `team.closed` audit event; then it deletes the team's invites. Closing a closed team changes nothing. When account deletion closes a team its caller is alone in, the META update is also conditioned on `members = 1`, so someone who joined meanwhile keeps an open team (409, and the retry then finds the caller is its only owner). An invite's transaction checks that the team isn't closed (`attribute_not_exists(closedAt)` on META), so one in flight can't land after the closure deleted the invites. `authorizeTeam` reads `closedAt` into the context (`ctx.closed`), and `writable` refuses every write to a closed team with `TeamClosedError` (403 `permission_denied`, `reason: "team_closed"`) except what passes `whileClosed`: `removeMember` (leaving and removing), `revokeInvite`, `revokeInvitesForEmail` and `closeTeam` itself. System contexts (billing, email events) aren't held to it. Reads keep working, so owners can export. Adding a member (`teamCounts`) is conditioned on `attribute_not_exists(closedAt)`, and `acceptInvite` refuses a closed team as an expired invite. The last owner may leave a closed team: the owner decrement's condition is then `attribute_exists(closedAt)` instead of `owners > 1`. `liveUpdateRecipients` returns nobody for a closed team, and `closedAt` is in `LIVE_AUDIENCE_ATTRIBUTES`. After a closure through `POST /teams/{teamId}/close`, the account handler emails every owner (`sendTeamNotice`, the `teamClosed` template) the day the purge will delete the team, so a closure one owner didn't make doesn't go unnoticed. This is best effort: it counts owners emailed in `TeamClosedNotices`, and owners not emailed in `TeamClosedNoticeFailures` (SES refused, no address, or the owners couldn't be listed), and logs only the team ID, counts and SES error names; any failure alarms (Team closure emails failing). A closure made by account deletion, where the caller is the team's only member, sends no email. The Stripe subscription isn't cancelled yet: billing (`supply-checkout-x0l`) will do that from `closedAt`. `removeMember` audits every removal in its own transaction (`member.left` or `member.removed`, target the user ID, `detail.reason` `account_deleted` when the account is being deleted).
- **Reopening a team.** `reopenTeam` (`src/data/teams.ts`, `POST /teams/{teamId}/reopen`) takes the team's name typed as for closing and, in one transaction, removes `closedAt`, `closedBy`, `purgeAfter` and the `TEAMS#CLOSED` index keys from the META item and bumps its version, writing a `team.reopened` audit event (`detail`: when it was closed and by whom). The update is conditioned on the closure it read (same `closedAt` and `purgeAfter`), on `purgeAfter` being more than `REOPEN_CUTOFF_MINUTES` (60) away, so a team the hourly purge may already be deleting can't come back (`TeamDeletingError`, 409 `aborted` with `reason: "team_deleting"`), on the team not being marked `purging` (the purge's mark before it deletes anything, also `TeamDeletingError`), and on `owners > 0`. For an owner it also checks, in the transaction, that their MEMBER item still says owner, so only an owner who is still in the closed team can reopen it (one who left gets 403 `not_member` from the route). System contexts (billing, email events) are refused (`ForbiddenError`); operators reopen through their own path, `reopenOpsTeam` in `src/data/operator.ts`, run by the operator reopen function (`src/operator/reopen-handler.ts`, [Operators](infrastructure.md#operators)), since operators never get a `TeamContext` (ADR 0015). It allows a reopen until 5 minutes before the purge rather than 60, audits it as `ops.team.reopen` for the owners' support actions, and has no daily limit or owner email. A team can be reopened `REOPENS_PER_TEAM_PER_DAY` (3) times a UTC day: the same transaction moves `LIMIT#REOPENS#<day>` in the team's partition (TTL 2 days) and the fourth is 429 `quota_exceeded`. Every reopening and every closure after one emails every owner, so this bounds how often an owner can send those emails by cycling, without ever silencing a closure notice. Reopening an open team changes nothing. Afterwards `authorizeTeam` issues open contexts again, the operators' index (GSI3 projects `closedAt`) shows the team open so operators can comp it again, and the META change makes the live-update publisher reread the audience, so members get live updates again. What the closure undid stays undone: invites deleted at closing and people who left or were removed while it was closed. The account handler counts `TeamsReopened` and emails every owner (`teamReopened` template) the same best-effort way as a closure (`TeamReopenedNotices`, `TeamReopenedNoticeFailures`, only IDs, counts and SES error names logged). The Stripe subscription isn't touched: when billing (`supply-checkout-x0l`) cancels it at closing, reopening will need to resume it.
- **Purging closed teams.** `listTeamsToPurge` reads GSI1's `TEAMS#CLOSED` partition for teams whose `purgeAfter` has passed, and `purgeTeam` (`src/data/team-purge.ts`) deletes one: each member's team-switcher row (named by the MEMBER item's sort key), every item in `TEAM#<teamId>`, the Stripe link (only if it's still this team's), and the META item last, on the condition it's still closed, which also takes it out of the index. It re-reads the META item first and skips a team that isn't closed or isn't due, then marks it `purging`, on the condition it's still closed and due, before deleting anything: `reopenTeam` refuses a team with the mark, and the two are conditional writes to the same item, so a team is never reopened part-deleted whatever the clocks say. Every step is idempotent, so a run that stops part-way is finished by the next. It deletes MEMBER items without moving the counts because the META item goes too. It names only `TEAM_PURGE_ATTRIBUTES` (`schema.ts`), the attributes its IAM policy allows. The scheduled function is `src/ops/team-purge-handler.ts` (hourly, [Observability](observability.md)); each run sends the `ClosedTeamsOverdue` gauge, the teams more than 24 hours past their `purgeAfter` that it didn't delete, for the Deletion overdue alarm. It counts them with `countTeamsDueBefore` (a `Select: COUNT` query on the same index partition) at the start of the run, less the overdue teams the run cleared, so the gauge isn't capped at the listing's 100 and isn't thrown by the index's eventual consistency. Once a team is marked, and before it deletes anything, the purge writes the team's deletion record (`beforeDelete`, below); a team whose record can't be written is left for the next run.
- **Importing artifact data.** `src/data/artifact-import.ts` and `npm run import-artifact` (`scripts/import-artifact.ts`, supply-checkout-ig9) copy a claude.ai artifact's data into a team, once: the family business's items and sheets from before AWS. The owner exports it in the artifact (Export, "Everything (JSON)", `allJson` in `src/export.js`) and runs the script with their SSO profile, naming the team and one of its owners (`npm run ops -- team <teamId>` lists them). It's a script rather than a route because it runs once for one customer: a route would put a large-upload endpoint and a web dialog in front of every team for good, where the script adds no IAM, no API surface and no app code. It still acts through a `TeamContext` from `authorizeTeam` for that owner, so it's refused unless they're an owner of an open team, and it touches only that team's partition. Like the backfills, `index.ts` doesn't export it.
  - **Checks first.** It reads the whole file before any write (at most 20 MB, 5,000 items, 5,000 sheets, each sheet under the 350,000-byte document limit) and checks every field's type and size, with every problem listed by position, key or sheet ID, never by name or client. Each sheet's lines must add up to the totals the artifact exported with it, by the app's rule (used × price each, summed in whole cents, ADR 0014). Then it matches the file against the team: an item or sheet already there with the same content is skipped, and one there with other content, or a team item with the same barcode under another key, is a conflict. Two items in the file with one barcode are refused, as the CSV import refuses them. Field names, keys and IDs from the file are printed quoted, with control characters escaped. Any problem or conflict: nothing is written. Without `--apply` it stops there (a dry run).
  - **Mapping (ADR 0014).** Keys and sheet IDs stay the same. Money (`price`, `cost`, on items and lines) is rounded to cents, as the artifact already rounds it for display, so totals don't move. A `stock` that isn't a number means the item doesn't track stock, as the app reads it. `packSize` and `cost` are kept when valid. The marks of recent saves (`ops`) and the export's `totals` and `preparedBy` aren't stored. `createdBy` holds a claude.ai user ID, which means nothing on AWS, so it's dropped and the name the artifact showed (`preparedBy`) goes in `createdByName`, as for a sheet made without a signed-in user. Unknown fields are left out, and the report names them.
  - **Writes.** Each document is created only if its key is still free, in one transaction with a check that the team still exists and is open, so a team closed part-way through isn't written to. An item that tracks stock is created in one transaction with an `import` movement from 0 to its count, by the owner, so its stock history adds up. Then it reads the team's items and sheets back and checks every stock count and every sheet's totals against the file, and exits 1 on any difference. It's resumable rather than all or nothing: every write is a whole document, so a run that stops part-way leaves only complete documents, and running it again adds the rest; over a finished import it writes nothing. The report has counts, sums, keys and sheet IDs, never names, clients, emails or user IDs. Tests: `test/artifact-import.test.ts`, with a fictional export made by the artifact's own exporter (`test/fixtures/artifact-export.json`).

- **Deletion records.** `src/deletions/records.ts` (supply-checkout-0ic7). Deleted data lives on in the table's backups, so each deleted account and each purged team gets one small S3 object, `users/<userId>.json` or `teams/<teamId>.json`, holding the ID, the time and, for an account, the teams its deletion closed: never an email, name or item. The bucket keeps each under Object Lock (compliance mode) for `DELETION_RECORD_RETENTION_DAYS` (400), longer than any backup can be kept. The account handler writes the user's once nothing can refuse the deletion and before their rows and Cognito user go; the purge writes the team's before it deletes anything. Each is written once (`If-None-Match`), so a retry keeps the first. `src/data/restore.ts` and `npm run restore` (`scripts/restore.ts`) read every version of them (`ListObjectVersions`, so a record overwritten with junk still counts; `--records-before` leaves out versions written after a suspected compromise) to delete the same data again from a restored table, and copy a restored table back into the live one ([Put a restored table back into service](backups.md#put-a-restored-table-back-into-service)). Like the backfills, `index.ts` doesn't export `restore.ts`: no Lambda runs it.
- **Watching the operator audit.** `src/ops/operator-audit-watch-handler.ts` reads the table's stream (filtered by its event source mapping to `MODIFY` and `REMOVE` records of `OPAUDIT#` partitions, `INSERT`s of `AUDIT#` items, and its heartbeat item) and counts every change to an operator audit item that isn't a TTL expiry, and every new entry set to expire early, in `OperatorAuditChanged`, for the P1 "Operator audit changed" alarm, and each heartbeat in `OperatorAuditWatchHeartbeat`, for the P2 "Operator audit watch silent" alarm ([Operators](infrastructure.md#operators)). It logs keys and event names only. The lint config bans `ReturnValuesOnConditionCheckFailure`, `ALL_OLD` and `ALL_NEW` in the operator code (`src/operator/`, `src/data/operator.ts`), since no IAM condition limits what a failed condition returns.
- **Deleting an account.** `DELETE /me` (`src/api/account-handler.ts`, with `src/data/accounts.ts`), typing `DELETE` to confirm. It's refused, with nothing changed, while the caller is the only owner of an open team that has other members (409 `last_owner`, naming up to three of the teams). Otherwise: `startAccountDeletion` puts `USER#<userId>` / `DELETING` (TTL 30 days), and `createTeam` and `acceptInvite` carry a `ConditionCheck` on it in their transactions, so no membership can be added once the deletion has listed the user's teams (403 "This account is being deleted"). The caller leaves every team with `removeMember` (so the counts move and it's audited), closing first any open team they're the only member of; every invite to their verified email is deleted (`deleteInviteForEmail`, each on a session tagged with that invite's team, the same entitlement as accepting it); `deleteUserRows` deletes what's left in their partition (stale switcher rows) except the mark and the `LIMIT#…` rate-limit counters, which expire by TTL so deleting and recreating an account can't reset a daily limit; and last the Cognito user is deleted with Cognito's `DeleteUser` and the caller's own access token (`cognitoDeleteUser` in `src/api/cognito-user.ts`), which needs no IAM permission and can only delete the caller. Every step is idempotent, so a retry after a failure part-way (the teams are left in parallel, each on its own) carries on. If leaving any team fails (a last-owner refusal after the pre-check, a join that stopped a closure, a conflict), the mark is taken away before the error is returned, so the user isn't blocked from joining teams for its 30 days; a retry marks the account again before it lists the teams. What stays: audit events in teams the user was in keep their user ID (never their email) until the audit trail's TTL or the team's purge, and invites they sent keep their user ID as `invitedBy` until they expire. The log line has only IDs and counts.
- **Live-update audience.** `liveUpdateRecipients(db, teamId)` (`src/data/live-audience.ts`) is who gets a team's live-update notices ([ADR 0016](adr/0016-per-member-live-update-channels.md)): the user IDs of its current members, or none if the team doesn't exist, an owner closed it, or its status has ended (`ENDED_STATUSES` in `model.ts`) and it has no live comp (`liveComp`, ADR 0015). Closure wins over a comp. Like `authorizeTeam`, it reads by team ID without a `TeamContext` (the stream consumer has no caller), and it names only `LIVE_AUDIENCE_ATTRIBUTES` (`schema.ts`), the attributes the consumer's IAM policy allows. `audienceChangeFromStream` tells the consumer which team's `META` or `MEMBER#` item a stream record changed, so it rereads that team's members.
- **Keys.** As in ADR 0005, except sheets: `SHEET#<sheetId>` instead of `SHEET#<date>#<id>`, because the date is editable and a key can't change. Date order comes from `GSI1` (`TEAM#<teamId>#SHEETS`, `<date>#<sheetId>`), which one update can change. `GSI1` also finds invites by the SHA-256 hash of their token, and `GSI2` (`INVITEE#<SHA-256 of the email>`, `INVITE#<inviteId>`) finds them by the invitee's email. `USER#<userId>` / `LIMIT#TEAMS#<date>` counts the teams a user created that day (TTL two days); `USER#<userId>` / `EMAIL_CODE_SENT` holds the SHA-256 of the address the user's last code went to (`POST /me/email/code`, TTL two days), and `USER#<userId>` / `VERIFIED_EMAIL` the SHA-256 of the address they last proved with that code through `POST /me/email/verify` (`src/data/verified-email.ts`), which the pre token generation trigger reads before it records a linked user's address (see "Sign-in" in infrastructure.md); `USER#<userId>` / `DELETING` marks an account being deleted (TTL 30 days); GSI1's `TEAMS#CLOSED` partition lists closed teams by when they're due to be purged; `TEAM#<teamId>` / `LIMIT#INVITES#<date>` and `TEAM#<teamId>` / `LIMIT#INVITES#<date>#<key>` and `INVITELIMIT#<key>` / `LIMIT#INVITES#<date>` count invites (see Invites).
