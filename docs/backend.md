# Backend

`backend/` holds the Lambda code (ADR 0002, 0006). It is a separate npm package with its own lockfile. `backend/src/observability` gives every handler structured JSON logs and business metrics ([Powertools for AWS Lambda](https://docs.powertools.aws.dev/lambda/typescript/)): `createObservability()` returns a `logger`, `count(metric, n, metadata)` and `gauge(metric, value, unit)` (a level a scheduled check measures), and `withObservability(obs, handler)` adds the request ID to every log line and flushes metrics after each invocation. Metrics go out as CloudWatch embedded metric format in namespace `SupplyCheckout`, with `Region` as their only dimension; per-team detail goes in metadata, never a dimension.

It also has the HTTP API's handlers in `backend/src/api` (see [Data API](infrastructure.md#data-api)), transactional email in `backend/src/email` (templates, the SES mailer, and the bounce and complaint handler; see [Transactional email](infrastructure.md#transactional-email)), the user pool's triggers for Google and Apple users in `backend/src/identity` (a guard that keeps them to their provider, one that sets `email_verified` from the provider's claim and keeps a linked user's to the address Cognito verified, and one that links a first Google or Apple sign-in to an existing account with the same verified email) (see [Sign-in](infrastructure.md#sign-in)), and the data-access module, `backend/src/data`:

- **Team-scoped access.** Every read and write of a team's data takes a `TeamContext`. Every function that can issue one lives in `src/data/team-context.ts`, and the issuer itself isn't exported. `authorizeTeam(db, userId, teamId)` checks the MEMBER item; the authorizer calls it with the user ID from the verified token. `createTeam`, `acceptInvite`, `teamContextForStripeCustomer` and `teamContextForEmailEvent` issue a context for the new owner, the new member, the billing webhook and the email-events handler (which may only mark an invite failed, with `markInviteFailed`). `acceptInvite` takes the caller's verified email, and its transaction re-checks that the stored invite is for that email, unexpired and unused. Each function checks the role (viewer, contributor, owner, system) before it writes. The `Db` handle from `createDb` is opaque: it exposes no DynamoDB client.
- **At least one owner.** The team item keeps an `owners` count. Every change to an owner membership updates it in the same transaction, and a decrease is conditioned on `owners > 1`; when only that condition fails, `setMemberRole` and `removeMember` throw `LastOwnerError` (the API's 409 `reason: "last_owner"`). Owner actions on other members also re-check the caller's own MEMBER item at write time.
- **Member cap.** The team item also keeps a `members` count, set to 1 by `createTeam` and moved in the same transaction as every membership added (`acceptInvite`) or removed (`removeMember`, which covers leaving). Both counts live on the META item, so one Update moves them (`teamCounts` in `src/data/model.ts`; DynamoDB allows one operation per item in a transaction). Adding is conditioned on `members < cap`, so two accepts racing for the last place can't both join: the loser gets `TeamFullError` (the API's 429 `quota_exceeded`, `reason: "team_full"`) or a `ConflictError` to retry, and keeps the invite. `memberCap(team)` (`model.ts`) decides the cap: `MEMBERS_PER_TRIAL_TEAM` (10) unless the team's status is `active` or `past_due`, then `MEMBERS_PER_TEAM` (100). It's the one place seat billing (bead `supply-checkout-l50`) changes when paid seats must be enforced. `createInvite` also refuses an invite when members plus live invites already fill the cap; that reads before it writes, and the accept is the enforcement. A team from before the count has no `members`: the next add or remove counts its MEMBER items (`src/data/member-count.ts`) and sets the count on the condition that it's still absent, so a change that commits in between makes it fail and retry rather than leave a wrong count.
- **Roles on every route.** Each route in `src/api/routes.ts` names the least role that may call it (`minRole`), and the handlers check it with `requireRole` (`src/api/roles.ts`) before anything runs; the data layer checks again before each write. `test/roles.test.ts` calls every team route as an owner, a contributor, a viewer and an outsider, `test/members-api.test.ts` covers the members routes (listing, role changes, removal, leaving, the last owner, two owners at once), and `test/invites-api.test.ts` the invites routes.
- **Invites.** `src/data/invites.ts`. Owners invite an address with a role (`createInvite`): a random 32-byte token goes in the emailed link, and only its SHA-256 is stored (on `GSI1`); the invite expires in 7 days (`expiresAt`, also the TTL). An address that's already a member's, or already has a live invite to the team, is refused. The address must be a bare addr-spec (`mailAddress` in `src/data/model.ts`: lowercase ASCII, a dot-atom local part, a DNS domain), because SES reads a recipient as an RFC 5322 address and a display name or list could deliver somewhere other than the address that was checked; the mailer refuses anything else too. (Matching a signed-in user to their invites still uses the looser `normalizeEmail`.) Each invite, new or re-sent, moves three counters in the same transaction: the team's for the UTC day (`TEAM#<teamId>` / `LIMIT#INVITES#<day>`, 50), the team's for that address (`TEAM#<teamId>` / `LIMIT#INVITES#<day>#<key>`, 3, so one team can't use up the address's allowance), and the address's from every team together (`INVITELIMIT#<key>` / `LIMIT#INVITES#<day>`, 15), each expiring after two days. The key (`inviteLimitKey`) is the SHA-256 of the address less any `+tag`, and for Gmail less the dots, so one mailbox can't be reached under many spellings. Past any, `LimitReachedError` (429), with one message for both so an owner can't tell what other teams sent. `resendInvite` replaces the invite in one transaction (the old one deleted, on the condition that its token hash hasn't changed): a new ID and token, so the old link stops working and a late bounce for the old message can't mark the new one, the same address and role, a fresh expiry and no failure fields. The account handler sends the email after the write (`sendInviteEmail`); if SES won't take it, `markInviteNotSent` marks the invite `inviteStatus: "failed"`, `failureReason: "not_sent"`, next to the `bounced` and `complained` the email-events handler records. `removeMember` first deletes every invite to the team for the member's address, so someone removed can't rejoin with an invite they hadn't used. Invite emails quote the team name and defang anything in it that a mail client could turn into a link (`teamLabel` in `src/email/templates.ts`).
- **One way in.** Outside `src/data`, ESLint (`backend/eslint.config.js`) bans any `@aws-sdk/*dynamodb*` package or path inside one, and any file under `data/` except `data/index.js`. This covers static imports, re-exports, `import()` and `require`. Tests are exempt, to inspect stored items.
- **Region-ready** ([ADR 0010](adr/0010-multi-region-active-active.md)). Every team gets `homeRegion` when it's created, from `AWS_REGION`. `writeRegionFor` in `src/data/region.ts` is the one function that decides where a team's writes go; in the MVP it always returns the local region.
- **Documents.** `src/data/documents.ts` serves the app's document model (`products/<key>`, `sheets/<id>`: get, set, deep-merge update, delete, list) on the same items the typed functions use. Every write reads the item and puts the new one on the condition that its version (and a product's `stock`) hasn't changed, so each write is one stream record with a new version. A product write keeps the stored `stock` and refuses a body `stock` that differs from it, so stock moves only through the stock commands and the CSV import, which record a movement for each change ([commands.md](api/commands.md)). The data API requires `expectedVersion` on every write (ADR 0006) and answers 409 `aborted` if the document is at another version or changes before the put; there's no retry, so two people editing one sheet line can't overwrite each other.
- **Inventory commands.** `src/data/commands.ts` has checkout, return and stock adjust, each one `TransactWriteItems` in the team's partition: an operation record (`OP#<operationId>`, only if new, kept 7 days for replaying retries), the sheet line (counts added on the server, only while the sheet is open and returned stays at or below out), the product's stock (`ADD`, when it tracks stock), and a movement record (`MOVE#<key>#<time>#<operationId>`), the stock history the nightly drift check reconciles. `addLines` adds a receipt's lines for a client to a sheet (up to 40, in one update of the sheet, with the operation record, and no stock or movement). A failed condition cancels the whole transaction; the command reads again and retries a few times before answering 409. The client contract is [docs/api/commands.md](api/commands.md).
- **CSV inventory import.** `src/data/imports.ts` (with the bounded CSV reader in `src/data/csv.ts`) imports a spreadsheet of items (`name`, `barcode`, `price`, `cost`, `stock`, `pack_size`, ADR 0014) for assisted onboarding, owners only. All or nothing, for more rows than one transaction holds (100 items): it validates every cell and every row against the whole inventory first, and any problem means nothing is written (a dry run returns that preview). Then one transaction stages the job (`IMPORT#<importId>`, only if new) and its whole plan in chunk records (`IMPORT#<importId>#CHUNK#<n>`, 49 rows each), and the rows commit in batches, each its own transaction: the product puts (conditional on the version and stock just read), a movement (`reason: "import"`) for each stock change, and the job's count of committed rows, conditional on it not having moved. A batch is at most one chunk and as many rows as fit in 2.5 MB, measured from the items as they are when it commits (as DynamoDB gets them, maps with a `constructor` key included), so it stays under DynamoDB's 4 MB transaction limit even if items grew after staging; if DynamoDB still refuses a batch as too large, it's retried with half the rows; rows whose item would pass the 350,000-byte document limit are refused before staging. If the commit stops part-way, the same file again with the same `importId`, from any owner of the team, carries on from the first row not committed with the staged plan, so an import rolls forward to complete rather than being left half done; a finished one replays its summary. Only two things stop a staged import for good, and both answer 409 saying to choose the file again (a new import, which re-plans and leaves already-imported rows unchanged): its records expired, or a key it planned to create was taken meanwhile by an item with another barcode. A row matches an existing item by barcode, or by name when either side has no barcode, and a re-import sets values (stock included), so importing a file twice changes nothing. New items get keys from their barcode (as `keyOf` in `src/format.js` makes them) or a hash of their name, so two imports of one file at once still make one item per row. Limits: 1,000 rows, 300 KB, 50 columns; job records expire after 7 days. The client contract is `POST /teams/{teamId}/imports` in [openapi.yaml](api/openapi.yaml). While a job is committing it's also in GSI1's `IMPORTS#COMMITTING` partition (sort key `<createdAt>#<importId>`), and the commit that finishes it removes it, as does a stop no retry gets past (a row too large, a key taken); `listStuckImports` reads that partition for the scheduled stuck-import check (`src/ops/`, "Imports stuck" in [journeys.md](journeys.md)), which has no team context and can read only the keys and progress.
- **Operators** ([ADR 0015](adr/0015-platform-operator-role.md)). `src/data/operator.ts` is everything a platform operator may do: list and search teams and read one team's account record and owners (`listOpsTeams`, `listOpsOwners`, `getOpsTeam`, from GSI3's projection only), comp a team or end its comp (`setComp`, `endComp`: the `comp*` attributes and `version` of the `META` item, at the version the operator read, with the audit item and the request's idempotency record in the same transaction), and read the operator audit (`listOperatorAudit`). It takes an `Operator` (the verified `sub`), never a `TeamContext`: ESLint keeps `team-context.ts` out of it, and keeps the context issuers out of `src/operator/`, the ops function (`backend/test/lint.test.ts`). `createTeam`, `acceptInvite` and `setMemberRole` keep GSI3 current: a team's `META` item and its owners' `MEMBER#` items are in it, nothing else. `liveComp` (`model.ts`) is the entitlement rule: while a comp's `compUntil` is ahead, `memberCap`, the live-update audience and `/me` treat the team as active on it. Owners read what operators did with `listSupportActions` (`audit.ts`), which asks only for `OWNER_OPERATOR_AUDIT_ATTRIBUTES`. `test/ops-api.test.ts` runs the ops handler against the in-memory table behind a check that mirrors the operator-access role (`test/ops-policy.ts`), and the in-memory table returns only GSI3's projected attributes, as DynamoDB does; `test/ops-ddb.test.ts` runs the same functions against DynamoDB Local.
- **Live-update audience.** `liveUpdateRecipients(db, teamId)` (`src/data/live-audience.ts`) is who gets a team's live-update notices ([ADR 0016](adr/0016-per-member-live-update-channels.md)): the user IDs of its current members, or none if the team doesn't exist or its status has ended (`ENDED_STATUSES` in `model.ts`). Like `authorizeTeam`, it reads by team ID without a `TeamContext` (the stream consumer has no caller), and it names only `LIVE_AUDIENCE_ATTRIBUTES` (`schema.ts`), the attributes the consumer's IAM policy allows. `audienceChangeFromStream` tells the consumer which team's `META` or `MEMBER#` item a stream record changed, so it rereads that team's members.
- **Keys.** As in ADR 0005, except sheets: `SHEET#<sheetId>` instead of `SHEET#<date>#<id>`, because the date is editable and a key can't change. Date order comes from `GSI1` (`TEAM#<teamId>#SHEETS`, `<date>#<sheetId>`), which one update can change. `GSI1` also finds invites by the SHA-256 hash of their token, and `GSI2` (`INVITEE#<SHA-256 of the email>`, `INVITE#<inviteId>`) finds them by the invitee's email. `USER#<userId>` / `LIMIT#TEAMS#<date>` counts the teams a user created that day (TTL two days); `TEAM#<teamId>` / `LIMIT#INVITES#<date>` and `TEAM#<teamId>` / `LIMIT#INVITES#<date>#<key>` and `INVITELIMIT#<key>` / `LIMIT#INVITES#<date>` count invites (see Invites).

```bash
cd backend
npm ci
npm run lint        # tsc type-check and ESLint, including the DynamoDB ban
npm test            # vitest; the access-pattern tests need DynamoDB Local
```

`test/data-api.test.ts`, `test/commands-api.test.ts`, `test/imports-api.test.ts` and `test/account-api.test.ts` run the data and account handlers against an in-memory table that refuses calls outside the partitions the request's session tags allow, as the IAM policies do; they have the isolation negative tests. The access-pattern tests (and `test/documents.test.ts`, `test/commands.test.ts`, which includes concurrent checkouts on one line, and `test/imports.test.ts`, which imports 200 and 1,000 rows) run every entity in ADR 0005 against [DynamoDB Local](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/DynamoDBLocal.html), each test file in a fresh table. They're skipped unless `DYNAMODB_ENDPOINT` is set. `npm run test:ddb` (`scripts/test-ddb.ts`) runs everything against DynamoDB Local locally: it starts CI's image (read from `ci.yml`) with Docker, colima's docker context or Podman on a free port, runs vitest (extra arguments go to vitest), and always removes the container. With no runtime it says how to get one (`brew install colima docker && colima start` on macOS).
