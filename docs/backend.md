# Backend

`backend/` holds the Lambda code (ADR 0002, 0006). It is a separate npm package with its own lockfile. `backend/src/observability` gives every handler structured JSON logs and business metrics ([Powertools for AWS Lambda](https://docs.powertools.aws.dev/lambda/typescript/)): `createObservability()` returns a `logger`, `count(metric, n, metadata)` and `gauge(metric, value, unit)` (a level a scheduled check measures), and `withObservability(obs, handler)` adds the request ID to every log line and flushes metrics after each invocation. Metrics go out as CloudWatch embedded metric format in namespace `SupplyCheckout`, with `Region` as their only dimension; per-team detail goes in metadata, never a dimension.

It also has the HTTP API's handlers in `backend/src/api` (see [Data API](infrastructure.md#data-api)), transactional email in `backend/src/email` (templates, the SES mailer, and the bounce and complaint handler; see [Transactional email](infrastructure.md#transactional-email)), which the account handler also uses for security notices to the caller's own verified address after `POST /me/password` and `POST /me/mfa/totp/verify` (`noticeAccount`, best effort, see [Sign-in](infrastructure.md#sign-in)), and the security notices function in `backend/src/identity` (`security-notices-handler.ts`) for the same changes, and email changes, made directly against Cognito, from CloudTrail through EventBridge (its records, `NOTICE#<kind>` and `NOTICE_ADDRESS` in the user's partition, are in `data/security-notices.ts`; it also keeps `TOTP_ON`, when two-step sign-in was turned on, in `data/two-step.ts`, which the account handler writes too and the billing routes compare with a session's `auth_time`), the user pool's triggers for Google and Apple users in `backend/src/identity` (a guard that keeps them to their provider, one that sets `email_verified` from the provider's claim and keeps a linked user's to the address Cognito verified, and one that links a first Google or Apple sign-in to an existing account with the same verified email), and the post confirmation trigger every pool has, which with the pre token generation trigger records a new account's `NOTICE_ADDRESS` (`notice-address.ts`, GET /me's rule) (see [Sign-in](infrastructure.md#sign-in)), and the data-access module, `backend/src/data`:

- **Team-scoped access.** Every read and write of a team's data takes a `TeamContext`. Every function that can issue one lives in `src/data/team-context.ts`, and the issuer itself isn't exported. `authorizeTeam(db, userId, teamId)` checks the MEMBER item; the authorizer calls it with the user ID from the verified token. `createTeam`, `acceptInvite`, `teamContextForStripeCustomer` and `teamContextForEmailEvent` issue a context for the new owner, the new member, the billing webhook and the email-events handler (which may only mark an invite failed, with `markInviteFailed`). `acceptInvite` takes the caller's verified email, and its transaction re-checks that the stored invite is for that email, unexpired and unused. Each function checks the role (viewer, contributor, owner, system) before it writes. A MEMBER item's `email` is the member's verified address, copied at create or join and kept current by `setOwnMemberEmail` (`supply-checkout-xv3k`): the account handler calls it (`keepMemberEmail`) in each team the caller is in, on a session for that team after the membership check, on `GET /me` whenever the verified address differs from the stored one and on `POST /me/email/verify` once a native user's new address is verified (a linked user's counts at the token refresh that follows, and the `/me` after it picks it up). It sets only the caller's own item, only if it still exists, never with an unverified address, and not in a closed team; a failure is logged with the team ID and error name only and doesn't fail the request. So the members list and team-closed notices use the address the member has now. When an address stops counting as verified (a change not yet confirmed with a code), the member item keeps the last verified address until a new one is verified. The `Db` handle from `createDb` is opaque: it exposes no DynamoDB client.
- **At least one owner.** The team item keeps an `owners` count. Every change to an owner membership updates it in the same transaction, and a decrease is conditioned on `owners > 1`; when only that condition fails, `setMemberRole` and `removeMember` throw `LastOwnerError` (the API's 409 `reason: "last_owner"`). Owner actions on other members also re-check the caller's own MEMBER item at write time.
- **Member cap.** The team item also keeps a `members` count, set to 1 by `createTeam` and moved in the same transaction as every membership added (`acceptInvite`) or removed (`removeMember`, which covers leaving). Both counts live on the META item, so one Update moves them (`teamCounts` in `src/data/model.ts`; DynamoDB allows one operation per item in a transaction). Adding is conditioned on `members < cap`, so two accepts racing for the last place can't both join: the loser gets `TeamFullError` (the API's 429 `quota_exceeded`, `reason: "team_full"`) or a `ConflictError` to retry, and keeps the invite. `acceptInvite` compares the link's token with the stored hash (`timingSafeEqual`) before any of its checks, so without the link every refusal is `NotFoundError` and nothing says whether the team is full; and a team closed or deleted between its checks and its write is `NotFoundError` too, not `TeamFullError`. `memberCap(team)` (`model.ts`) decides the cap: `MEMBERS_PER_TRIAL_TEAM` (10) unless the team's status is `active` or `past_due`, then `MEMBERS_PER_TEAM` (100). Paid seats don't cap it: the subscription's seat quantity follows the billed members instead (Seats, below). `createInvite` also refuses an invite when members plus live invites already fill the cap; that reads before it writes, and the accept is the enforcement. A team from before the count has no `members`: the next add or remove counts its MEMBER items (`src/data/member-count.ts`) and sets the count on the condition that it's still absent, so a change that commits in between makes it fail and retry rather than leave a wrong count. The `members` backfill (`src/data/backfill.ts`, run by the owner with `npm run backfill`, [infrastructure](infrastructure.md#backfills)) sets it on every such team, on the same condition.
- **Roles on every route.** Each route in `src/api/routes.ts` names the least role that may call it (`minRole`), and the handlers check it with `requireRole` (`src/api/roles.ts`) before anything runs; the data layer checks again before each write. `test/roles.test.ts` calls every team route as an owner, a contributor, a viewer and an outsider, `test/members-api.test.ts` covers the members routes (listing, role changes, removal, leaving, the last owner, two owners at once), and `test/invites-api.test.ts` the invites routes.
- **Invites.** `src/data/invites.ts`. Owners invite an address with a role (`createInvite`): a random 32-byte token goes in the emailed link, and only its SHA-256 is stored (on `GSI1`); the invite expires in 7 days (`expiresAt`, also the TTL). An address that's already a member's, or already has a live invite to the team, is refused. Two creates for one address at the same moment can't both get through that check: each writes the team's guard for the address (`TEAM#<teamId>` / `INVITEGUARD#<hashEmail>`, `inviteId` naming the latest invite) in the invite's transaction, on the condition that it's absent or still names the invite the create read (one that's gone or expired). Nothing else deletes a guard; one naming an invite that's gone is stale and the next invite replaces it, and it expires with its invite. `resendInvite` moves it to the new invite the same way, and refuses (409) an address that has become a member's since the invite was made. The address must be a bare addr-spec (`mailAddress` in `src/data/model.ts`: lowercase ASCII, a dot-atom local part, a DNS domain), because SES reads a recipient as an RFC 5322 address and a display name or list could deliver somewhere other than the address that was checked; the mailer refuses anything else too. (Matching a signed-in user to their invites still uses the looser `normalizeEmail`.) Each invite, new or re-sent, moves four counters in the same transaction: the team's for the UTC day (`TEAM#<teamId>` / `LIMIT#INVITES#<day>`, 50), the team's for that address (`TEAM#<teamId>` / `LIMIT#INVITES#<day>#<key>`, 3, so one team can't use up the address's allowance), the inviting user's for that address from every team they own (`USER#<userId>` / `LIMIT#INVITES#<day>#<key>`, 3, so one account owning many teams can't either), and the address's from every team together (`INVITELIMIT#<key>` / `LIMIT#INVITES#<day>`, 15), each expiring after two days. The key (`inviteLimitKey`) is the SHA-256 of the address less any `+tag`, and for Gmail less the dots, so one mailbox can't be reached under many spellings. Past any, `LimitReachedError` (429), with one message for all of them so an owner can't tell what other teams sent. `resendInvite` replaces the invite in one transaction (the old one deleted, on the condition that its token hash hasn't changed): a new ID and token, so the old link stops working and a late bounce for the old message can't mark the new one, the same address and role, a fresh expiry and no failure fields. The account handler sends the email after the write (`sendInviteEmail`); if SES won't take it, `markInviteNotSent` marks the invite `inviteStatus: "failed"`, `failureReason: "not_sent"`, next to the `bounced` and `complained` the email-events handler records. `removeMember` first deletes every invite to the team for the member's address, so someone removed can't rejoin with an invite they hadn't used; when someone leaves, the account handler also passes the address Cognito has verified for them now (`verifiedEmail`), so invites to it go even if their member item has none or an older one (`supply-checkout-u0vv`). Invite emails quote the team name and defang anything in it that a mail client could turn into a link (`teamLabel` in `src/email/templates.ts`).
- **One way in.** Outside `src/data`, ESLint (`backend/eslint.config.js`) bans any `@aws-sdk/*dynamodb*` package or path inside one, and any file under `data/` except `data/index.js`. This covers static imports, re-exports, `import()` and `require`. Tests are exempt, to inspect stored items.
- **Region-ready** ([ADR 0010](adr/0010-multi-region-active-active.md)). Every team gets `homeRegion` when it's created, from `AWS_REGION`. `writeRegionFor` in `src/data/region.ts` is the one function that decides where a team's writes go; in the MVP it always returns the local region.
- **Documents.** `src/data/documents.ts` serves the app's document model (`products/<key>`, `sheets/<id>`: get, set, deep-merge update, delete, list) on the same items the typed functions use. Every write reads the item and puts the new one on the condition that its version (and a product's `stock`) hasn't changed, so each write is one stream record with a new version. A product write keeps the stored `stock` and refuses a body `stock` that differs from it, so stock moves only through the stock commands and the CSV import, which record a movement for each change ([commands.md](api/commands.md)). A stored `stock` that isn't a number (legacy) is no count: a write drops it, so the item can still be edited and stays untracked. Deleting a product that tracks stock is one transaction with a `delete` movement taking its stock to 0, so the history still adds up if the key is used again. A product's `price` and `cost`, and a sheet line's, must be amounts in whole cents (ADR 0014), but only where the write changes them: a legacy value the product or line already had, carried over unchanged, doesn't block the write and is rounded to cents ("rounded when next saved"). Only DynamoDB's own item-size refusal (`Item size has exceeded the maximum allowed size`, matched from the start of the message) is 413 `quota_exceeded`; any other `ValidationException` is a 500. The data API requires `expectedVersion` on every write (ADR 0006) and answers 409 `aborted` if the document is at another version or changes before the put; there's no retry, so two people editing one sheet line can't overwrite each other.
- **Inventory commands.** `src/data/commands.ts` has checkout, return and stock adjust, each one `TransactWriteItems` in the team's partition: an operation record (`OP#<operationId>`, only if new, kept 7 days for replaying retries), the sheet line (counts added on the server, only while the sheet is open and returned stays at or below out), the product's stock (`ADD`, when it tracks stock; a stock adjust's `uncount` removes it, recorded as taking it to 0; a count or uncount sent with `expectedStock` is refused, 409 `stock_changed`, when the stock moved from it), and a movement record (`MOVE#<key>#<time>#<operationId>`), the stock history the nightly drift check reconciles. `addLines` adds a receipt's lines for a client to a sheet (up to 40, in one update of the sheet, with the operation record, and no stock or movement); a line whose product is company equipment goes on its own `<productKey>:bought` line with `purchased: true`, priced by the server from the receipt price and the team's equipment markup unless the reviewer typed a price, with a condition check per line that the product's kind is still what was read and one that the markup is unchanged (ADR 0017, section 2a). `markLost` records company equipment lost or broken (the line's `lost` and any `lostCharge`, a `lost` movement with `delta: 0`, no stock change). `quickTake` checks out onto the team's open ad hoc sheet, or starts the next one, `adhoc-<n>`, pointing the team's `ADHOC` item (`src/data/adhoc.ts`) at it in the same transaction, on the condition that `ADHOC` is unchanged since the read, so two first takes at once end on one sheet (ADR 0017, section 4). `moveLine` moves a whole line from the open ad hoc sheet to an open job sheet: the line comes off the ad hoc sheet on the condition that the sheet's version is the one read, its counts are added to the job sheet's line, and a `move` movement with `delta: 0` records it, all in one transaction (section 5). A failed condition cancels the whole transaction; the command reads again and retries a few times before answering 409. The client contract is [docs/api/commands.md](api/commands.md).
- **Team settings.** `src/data/settings.ts` keeps the team's `SETTINGS` item (ADR 0017, section 2a): `equipmentMarkup`, the percentage `addLines` adds to the receipt price of equipment bought for a client. Owners write it with an expected version, and a changed markup is audited in the same transaction (who, when, old and new); `getTeamSettings` returns it to owners only and an empty `settings` to anyone else. Document writes (`documents.ts`) check the equipment fields on products and sheet lines, and refuse to close a sheet while equipment is out (`EquipmentOutError`, 409 `equipment_out`). They also keep the `ADHOC` item in step with the ad hoc sheets: no document write creates a sheet whose ID starts `adhoc-` or sets a sheet's `kind`; closing or deleting the open ad hoc sheet clears the pointer, and reopening a finished one points at it (refused with `AdhocOpenError`, 409 `adhoc_open`, while another is open), each in the sheet write's transaction.
- **Receipt reading** ([ADR 0008](adr/0008-receipt-reading-bedrock.md), [infrastructure](infrastructure.md#receipt-reading)). `POST /teams/{teamId}/receipts/read` is served by `src/api/receipts-handler.ts` (entry `src/api/receipts.ts`, the `receipts` function). It checks the caller as the data API does (access token, `sub`, the path's team, membership on a team-scoped role session, at least contributor), then the photo (`receiptImage`: a JPEG or PNG as base64 whose first bytes match its type, 100 bytes to `MAX_RECEIPT_IMAGE_BYTES`), before anything is spent. Then it counts the read (`src/data/usage.ts`, `supply-checkout-wxx`), refusing a closed or ended team: first against the caller's per-user rate limit, `takeReceiptRate`, from all their teams together (`RECEIPT_RATE_LIMITS`: 10 a UTC minute, 60 an hour, 200 a day; `RECEIPTRATE#<userId>` / `RECEIPTS#<MINUTE|HOUR|DAY>#<stamp>`, `count` and a TTL a day after the window), all three windows in one transaction so a refused read counts in none of them, retried a few times on a `TransactionConflict` (then refused for a second); past any, 429 `rate_limited` with `Retry-After`, the seconds until the last full window ends. The team's allowance is read first, because the rate depends on it: A user's reads for trial teams also count in a fourth window in the same transaction, `RECEIPTS#TRIALDAY#<day>`: at most `RECEIPT_TRIAL_READS_PER_USER_PER_DAY` (30, provisional) a UTC day from all their trial teams, a mitigation for one account making many trial teams to collect 25 reads in each (refused with `rate_limited` and `Retry-After` to the next UTC day; when that's the only full window, the message says today's free trial scans are used up, `TRIAL_DAY_USED`, rather than "a lot in a short time"). It doesn't stop a farm of many accounts: an account-wide trial circuit breaker and a Bedrock spend budget are still follow-ups. Then against the team's allowance with `takeReceipt`: `receiptAllowance` reads the `META` item's status and comp, and a team that pays (`PAID_STATUSES`) or has a live comp gets `RECEIPTS_PER_TEAM_PER_MONTH` (200) a UTC month at `TEAM#<teamId>` / `USAGE#<month>`, any other team `RECEIPTS_PER_TRIAL` (25) in all at `TEAM#<teamId>` / `USAGE#TRIAL`, which never resets (its reads also count in the month's counter, unlimited there, so operators see every team's reads per month). Both numbers are provisional until pricing is decided (`supply-checkout-akz`). Past it, 429 `receipt_limit`, with the trial's or the month's message. Each counter is one conditional update, so reads at once can't go past it. A read the model service refused before doing work it bills for is given back (`refundReceipt`, never below zero): only a throttle (429, `model_busy`) or a 503, with no token usage (`ReceiptReadError.refundable`, set in `failureFor`). Anything else still counts: a timeout, a bad reply, a photo Bedrock refused, any other status (a 500, 408 or 424) and a network or other non-API error, since any of them may have been billed. The rate counters are never given back. A team that subscribes mid-month has that month's trial reads counted against its 200, since trial reads also count in the month's counter. `GET /teams/{teamId}/receipts/usage` (contributors and owners, `getReceiptQuota`) answers the team's `usage`: `period` (`month` or `trial`), `month`, `used`, `limit` and `remaining`, which a read's answer also carries. Then it reads up to 500 products for matching, and calls `readReceipt` (`src/receipts/reader.ts`) with a 25-second deadline. The prompt is built on the server (`src/receipts/prompt.ts`): the fixed instructions (the app's `RECEIPT_PROMPT` rules, which a test keeps word for word the same, less "reply with only JSON"), then the inventory as `i1 | name | price` lines (names on one line, with no `|`), with the prompt-cache breakpoint after it, then the photo. The reply's shape is `RECEIPT_SCHEMA`, sent as structured output (`output_config.format`), and `checkResult` checks it again: at most 200 lines, a line without a name dropped, text trimmed to 300 characters, quantities and amounts in range, a date only if it's a real `YYYY-MM-DD`, and `match` turned from the prompt's `iN` id into the product's key (or null), so the model can only point at the team's own items. A reply that isn't `end_turn` (a refusal, or cut short at 4,096 tokens) or isn't JSON of that shape is 502 `invalid_output`; a throttle is 429 `model_busy`; the deadline is 504 `model_timeout`; a photo Bedrock refuses (400) is 400 `image_rejected`; anything else from Bedrock is 503 `unavailable`. Logged, in the one `Request` line: the photo's size, the inventory's count, the model's milliseconds, the token counts (input, output, cache read and write), the stop reason and the number of lines, or the failure's kind and a fixed name for its error (`APIError:403`, `SyntaxError`). Never the photo, the prompt, the inventory, the reply or an error's message. Metrics: `ReceiptReads` (every model call), `ReceiptReadFailures`, `ReceiptTokens` (team ID in metadata), the `ReceiptReadLatency` gauge in milliseconds, and `ReceiptRateLimited`, `ReceiptLimitReached` (team ID and `period` in metadata), and `ReceiptTrialsNearLimit` and `ReceiptPaidTeamsNearLimit` (a trial or a paying team's read reaching 80% of its allowance, once per allowance; team ID in metadata). Split by period rather than a dimension, so the alarm watches only trials. The `Request` line also has `allowance` (the period) and `refused` (`rate_limited` or `receipt_limit`), and `refunded` when a read was given back. The function's role session is tagged with the team and the caller's `sub` (`receiptScopedDbs` in `src/api/team-db.ts`, one session per team and user).
- **CSV inventory import.** `src/data/imports.ts` (with the bounded CSV reader in `src/data/csv.ts`) imports a spreadsheet of items (`name`, `barcode`, `kind`, `price`, `cost`, `stock`, `pack_size`, ADR 0014 and 0017: company equipment has no price) for assisted onboarding, owners only. All or nothing, for more rows than one transaction holds (100 items): it validates every cell and every row against the whole inventory first, and any problem means nothing is written (a dry run returns that preview). Then one transaction stages the job (`IMPORT#<importId>`, only if new) and its whole plan in chunk records (`IMPORT#<importId>#CHUNK#<n>`, 49 rows each), and the rows commit in batches, each its own transaction: the product puts (conditional on the version and stock just read), a movement (`reason: "import"`) for each stock change, and the job's count of committed rows, conditional on it not having moved. A batch is at most one chunk and as many rows as fit in 2.5 MB, measured from the items as they are when it commits (as DynamoDB gets them, maps with a `constructor` key included), so it stays under DynamoDB's 4 MB transaction limit even if items grew after staging; if DynamoDB still refuses a batch as too large (its two messages, matched from the start: a transaction over 4 MB, an item over 400 KB), it's retried with half the rows, and a single row it still refuses answers 413 and logs DynamoDB's error name and the start of its message, never item data; a batch DynamoDB cancels with a `ValidationError` reason carrying its item-size message answers 413 too; any other `ValidationException` is a 500; rows whose item would pass the 350,000-byte document limit are refused before staging. If the commit stops part-way, the same file again with the same `importId`, from any owner of the team, carries on from the first row not committed with the staged plan, so an import rolls forward to complete rather than being left half done; a finished one replays its summary. Only two things stop a staged import for good, and both answer 409 saying to choose the file again (a new import, which re-plans and leaves already-imported rows unchanged): its records expired, or a key it planned to create was taken meanwhile by an item with another barcode. A row matches an existing item by barcode, or by name when either side has no barcode, and a re-import sets values (stock included), so importing a file twice changes nothing. New items get keys from their barcode (as `keyOf` in `src/format.js` makes them) or a hash of their name, so two imports of one file at once still make one item per row. Limits: 1,000 rows, 300 KB, 50 columns; job records expire after 7 days. The client contract is `POST /teams/{teamId}/imports` in [openapi.yaml](api/openapi.yaml). While a job is committing it's also in GSI1's `IMPORTS#COMMITTING` partition (sort key `<createdAt>#<importId>`), and the commit that finishes it removes it, as does a stop no retry gets past (a row too large, a key taken); `listStuckImports` reads that partition for the scheduled stuck-import check (`src/ops/`, "Imports stuck" in [journeys.md](journeys.md)), which has no team context and can read only the keys and progress.
- **Operators** ([ADR 0015](adr/0015-platform-operator-role.md)). `src/data/operator.ts` is everything a platform operator may do: list and search teams and read one team's account record and owners (`listOpsTeams`, `listOpsOwners`, `getOpsTeam`, from GSI3's projection only), comp a team or end its comp (`setComp`, `endComp`: the `comp*` attributes and `version` of the `META` item, at the version the operator read, with the audit item and the request's idempotency record in the same transaction), and read the operator audit (`listOperatorAudit`). It takes an `Operator` (the verified `sub`), never a `TeamContext`: ESLint keeps `team-context.ts` out of it, and keeps the context issuers out of `src/operator/`, the ops function (`backend/test/lint.test.ts`). `createTeam`, `acceptInvite` and `setMemberRole` keep GSI3 current: a team's `META` item and its owners' `MEMBER#` items are in it, nothing else. `liveComp` (`model.ts`) is the entitlement rule: while a comp's `compUntil` is ahead, `memberCap`, the live-update audience and `/me` treat the team as active on it. Owners read what operators did with `listSupportActions` (`audit.ts`), which asks only for `OWNER_OPERATOR_AUDIT_ATTRIBUTES`. `test/ops-api.test.ts` runs the ops handler against the in-memory table behind a check that mirrors the operator-access role (`test/ops-policy.ts`), and the in-memory table returns only GSI3's projected attributes, as DynamoDB does; `test/ops-ddb.test.ts` runs the same functions against DynamoDB Local. A team's Stripe subscription and latest invoices for `GET /ops/teams/{teamId}` come from `src/operator/stripe-detail.ts`, on the ops function's own restricted Stripe key, for the customer on the team's index entry; it never throws, answering `{ error: "unavailable" }` when the key or Stripe isn't there (`test/ops-api.test.ts` runs it against a fake Stripe client).
- **Closing a team.** `closeTeam` (`src/data/teams.ts`, owners only, `POST /teams/{teamId}/close`) takes the team's name as typed to confirm it (ignoring case and surrounding spaces) and, in one transaction conditioned on the caller still being an owner, sets `closedAt`, `closedBy` and `purgeAfter` (`CLOSED_TEAM_RETENTION_DAYS`, 30, later) on the META item, puts it in GSI1's `TEAMS#CLOSED` partition (sort key `<purgeAfter>#<teamId>`), and writes a `team.closed` audit event; then it deletes the team's invites. Closing a closed team changes nothing. When account deletion closes a team its caller is alone in, the META update is also conditioned on `members = 1`, so someone who joined meanwhile keeps an open team (409, and the retry then finds the caller is its only owner). An invite's transaction checks that the team isn't closed (`attribute_not_exists(closedAt)` on META), so one in flight can't land after the closure deleted the invites. `authorizeTeam` reads `closedAt` into the context (`ctx.closed`), and `writable` refuses every write to a closed team with `TeamClosedError` (403 `permission_denied`, `reason: "team_closed"`) except what passes `whileClosed`: `removeMember` (leaving and removing), `revokeInvite`, `revokeInvitesForEmail` and `closeTeam` itself. System contexts (billing, email events) aren't held to it. Reads keep working, so owners can export. Adding a member (`teamCounts`) is conditioned on `attribute_not_exists(closedAt)`, and `acceptInvite` refuses a closed team as an expired invite. The last owner may leave a closed team: the owner decrement's condition is then `attribute_exists(closedAt)` instead of `owners > 1`. `liveUpdateRecipients` returns nobody for a closed team, and `closedAt` is in `LIVE_AUDIENCE_ATTRIBUTES`. After a closure through `POST /teams/{teamId}/close`, the account handler emails every owner (`sendTeamNotice`, the `teamClosed` template) the day the purge will delete the team, so a closure one owner didn't make doesn't go unnoticed. This is best effort: it counts owners emailed in `TeamClosedNotices`, and owners not emailed in `TeamClosedNoticeFailures` (SES refused, no address, or the owners couldn't be listed), and logs only the team ID, counts and SES error names; any failure alarms (Team closure emails failing). A closure made by account deletion, where the caller is the team's only member, sends no email. The Stripe subscription isn't cancelled yet: billing (`supply-checkout-x0l`) will do that from `closedAt`. `removeMember` audits every removal in its own transaction (`member.left` or `member.removed`, target the user ID, `detail.reason` `account_deleted` when the account is being deleted).
- **Reopening a team.** `reopenTeam` (`src/data/teams.ts`, `POST /teams/{teamId}/reopen`) takes the team's name typed as for closing and, in one transaction, removes `closedAt`, `closedBy`, `purgeAfter` and the `TEAMS#CLOSED` index keys from the META item and bumps its version, writing a `team.reopened` audit event (`detail`: when it was closed and by whom). The update is conditioned on the closure it read (same `closedAt` and `purgeAfter`), on `purgeAfter` being more than `REOPEN_CUTOFF_MINUTES` (60) away, so a team the hourly purge may already be deleting can't come back (`TeamDeletingError`, 409 `aborted` with `reason: "team_deleting"`), on the team not being marked `purging` (the purge's mark before it deletes anything, also `TeamDeletingError`), and on `owners > 0`. For an owner it also checks, in the transaction, that their MEMBER item still says owner, so only an owner who is still in the closed team can reopen it (one who left gets 403 `not_member` from the route). System contexts (billing, email events) are refused (`ForbiddenError`); operators reopen through their own path, `reopenOpsTeam` in `src/data/operator.ts`, run by the operator reopen function (`src/operator/reopen-handler.ts`, [Operators](infrastructure.md#operators)), since operators never get a `TeamContext` (ADR 0015). It allows a reopen until 5 minutes before the purge rather than 60, audits it as `ops.team.reopen` for the owners' support actions, and has no daily limit or owner email. A team can be reopened `REOPENS_PER_TEAM_PER_DAY` (3) times a UTC day: the same transaction moves `LIMIT#REOPENS#<day>` in the team's partition (TTL 2 days) and the fourth is 429 `quota_exceeded`. Every reopening and every closure after one emails every owner, so this bounds how often an owner can send those emails by cycling, without ever silencing a closure notice. Reopening an open team changes nothing. Afterwards `authorizeTeam` issues open contexts again, the operators' index (GSI3 projects `closedAt`) shows the team open so operators can comp it again, and the META change makes the live-update publisher reread the audience, so members get live updates again. What the closure undid stays undone: invites deleted at closing and people who left or were removed while it was closed. The account handler counts `TeamsReopened` and emails every owner (`teamReopened` template, which also says what happens to billing, worded for either outcome since it goes out before the billing worker's resync) the same best-effort way as a closure (`TeamReopenedNotices`, `TeamReopenedNoticeFailures`, only IDs, counts and SES error names logged). Stripe isn't called: the same update sets `stripeResyncFor` to the closure it ends (so does `reopenOpsTeam`), and the seat sync queued after the reopen has the billing worker resync the subscription, resuming one the closure set to cancel (`src/billing/reopening.ts`, `createReopenResync`; `finishReopenResync` in `src/data/billing.ts` removes the marker, on the condition it's still that closure; [infrastructure](infrastructure.md#billing), "Reopening a subscribed team").
- **Purging closed teams.** `listTeamsToPurge` reads GSI1's `TEAMS#CLOSED` partition for teams whose `purgeAfter` has passed, and `purgeTeam` (`src/data/team-purge.ts`) deletes one: each member's team-switcher row (named by the MEMBER item's sort key), every item in `TEAM#<teamId>`, the Stripe link (only if it's still this team's), and the META item last, on the condition it's still closed, which also takes it out of the index. It re-reads the META item first and skips a team that isn't closed or isn't due, then marks it `purging`, on the condition it's still closed and due, before deleting anything: `reopenTeam` refuses a team with the mark, and the two are conditional writes to the same item, so a team is never reopened part-deleted whatever the clocks say. Every step is idempotent, so a run that stops part-way is finished by the next. It deletes MEMBER items without moving the counts because the META item goes too. It names only `TEAM_PURGE_ATTRIBUTES` (`schema.ts`), the attributes its IAM policy allows. The scheduled function is `src/ops/team-purge-handler.ts` (hourly, [Observability](observability.md)); each run sends the `ClosedTeamsOverdue` gauge, the teams more than 24 hours past their `purgeAfter` that it didn't delete, for the Deletion overdue alarm. It counts them with `countTeamsDueBefore` (a `Select: COUNT` query on the same index partition) at the start of the run, less the overdue teams the run cleared, so the gauge isn't capped at the listing's 100 and isn't thrown by the index's eventual consistency. Once a team is marked, and before it deletes anything, the purge writes the team's deletion record (`beforeDelete`, below), then deletes the team's Stripe customer (`deleteStripeCustomer`); a team whose record can't be written is left for the next run. When Stripe can't delete the customer, the purge queues its deletion instead (`queueStripeCustomerDeletion` in `src/data/stripe-deletions.ts`, one item per team in the `PURGE#STRIPE_DELETIONS` partition naming only `STRIPE_DELETION_ATTRIBUTES`) and still purges the team; each run then retries the queue (`listStripeCustomerDeletions`, oldest first, and `removeStripeCustomerDeletion` once Stripe has deleted it) and sends its gauges (`supply-checkout-8jc.42`). Only a queue entry that can't be written leaves the team for the next run. Re-applying deletions after a restore (`src/data/restore.ts`) queues each re-purged team's customer the same way. Before purging, each run ends closed teams' Stripe subscriptions: `listClosedTeamsToEnd` (the same index partition) lists closed teams with a subscription and no `stripeCancelledFor` equal to their `closedAt`, `closedTeamToEnd` re-reads one, and `markSubscriptionEnding` records it, conditioned on the same `purgeAfter`; `markSubscriptionSetAside` records one it won't end or retry (another customer's subscription, one Stripe doesn't have, or one Stripe refused with an error retrying won't change) as `stripeSetAsideFor`, with why in `stripeSetAsideReason`, on the same condition, and the listing leaves those out so they can't fill its limit. `listSetAsideTeams` counts the teams set aside for their current closure (every page of the same partition) for the purge's `ClosedTeamsSetAside` gauge, so their alarm stays on until a person removes `stripeSetAsideFor` (`supply-checkout-8jc.36`). A team set aside for its current closure isn't purged until then (`supply-checkout-8jc.37`): `listTeamsToPurge` leaves it out, `purgeTeam` holds it (`held` in its result) and its mark's condition refuses one set aside since the read, and a mark refused that way re-reads the team so it's reported as held. Held teams still count in `ClosedTeamsOverdue`, and `listSetAsideTeams` also counts those past the overdue line, which the purge logs. Both `listTeamsToPurge` and `purgeTeam` take a `heldDueBefore` cutoff: a held team whose `purgeAfter` is at or before it is listed and purged anyway (the mark's condition allows it by the same value), and `purgeTeam`'s result has `forced`, with its Stripe IDs and set-aside reason. The purge passes its run's time less `HELD_PURGE_GRACE_DAYS` (14, `src/ops/names.ts`), and logs and counts each forced purge (`HeldTeamsPurged`, `supply-checkout-8jc.40`). A customer Stripe says is already deleted is counted in `StripeCustomersAlreadyDeleted` ([infrastructure](infrastructure.md#billing), "Closing a subscribed team").
- **Importing artifact data.** `src/data/artifact-import.ts` and `npm run import-artifact` (`scripts/import-artifact.ts`, supply-checkout-ig9) copy a claude.ai artifact's data into a team, once: the family business's items and sheets from before AWS. The owner exports it in the artifact (Export, "Everything (JSON)", `allJson` in `src/export.js`; the customer's steps are in [Moving to the web app](moving-to-the-web-app.md)) and runs the script with their SSO profile, naming the team and one of its owners (`npm run ops -- team <teamId>` lists them). It's a script rather than a route because it runs once for one customer: a route would put a large-upload endpoint and a web dialog in front of every team for good, where the script adds no IAM, no API surface and no app code. It still acts through a `TeamContext` from `authorizeTeam` for that owner, so it's refused unless they're an owner of an open team, and it touches only that team's partition. Like the backfills, `index.ts` doesn't export it.
  - **Checks first.** It reads the whole file before any write (at most 20 MB, 5,000 items, 5,000 sheets, each sheet under the 350,000-byte document limit) and checks every field's type and size, with every problem listed by position, key or sheet ID, never by name or client. Each sheet's lines must add up to the totals the artifact exported with it, by the app's rule (used × price each, summed in whole cents, ADR 0014). Then it matches the file against the team: an item or sheet already there with the same content is skipped, and one there with other content, or a team item with the same barcode under another key, is a conflict. Two items in the file with one barcode are refused, as the CSV import refuses them. Field names, keys and IDs from the file are printed quoted, with control characters escaped. Any problem or conflict: nothing is written. Without `--apply` it stops there (a dry run).
  - **Mapping (ADR 0014).** Keys and sheet IDs stay the same. Money (`price`, `cost`, on items and lines) is rounded to cents, as the artifact already rounds it for display, so totals don't move. A `stock` that isn't a number means the item doesn't track stock, as the app reads it. `packSize` and `cost` are kept when valid. The marks of recent saves (`ops`) and the export's `totals` and `preparedBy` aren't stored. `createdBy` holds a claude.ai user ID, which means nothing on AWS, so it's dropped and the name the artifact showed (`preparedBy`) goes in `createdByName`, as for a sheet made without a signed-in user. Unknown fields are left out, and the report names them.
  - **Writes.** Each document is created only if its key is still free, in one transaction with a check that the team still exists and is open, so a team closed part-way through isn't written to. An item that tracks stock is created in one transaction with an `import` movement from 0 to its count, by the owner, so its stock history adds up. Then it reads the team's items and sheets back and checks every stock count and every sheet's totals against the file, and exits 1 on any difference. It's resumable rather than all or nothing: every write is a whole document, so a run that stops part-way leaves only complete documents, and running it again adds the rest; over a finished import it writes nothing. The report has counts, sums, keys and sheet IDs, never names, clients, emails or user IDs. Tests: `test/artifact-import.test.ts`, with a fictional export made by the artifact's own exporter (`test/fixtures/artifact-export.json`).

- **Billing** ([ADR 0009](adr/0009-billing-stripe.md), [infrastructure](infrastructure.md#billing)). `src/billing/` holds the Stripe side: the catalog of plans and prices (`catalog.ts`, provisional pending `supply-checkout-akz`), the Stripe client with its key read from Secrets Manager and checked to be of the configured mode (`stripe.ts`, `names.ts`), and the price lookup by lookup key (`prices.ts`). `npm run stripe-catalog` (`scripts/stripe-catalog.ts`) makes Stripe's products and prices match the catalog. The `billing` function (`src/api/billing-handler.ts`, `billing-db.ts`) serves `POST /teams/{teamId}/billing/checkout`: owners only, it makes and links the team's Stripe customer once (`linkStripeCustomer`, `src/data/billing.ts`) and starts a Checkout Session for the plan, with a seat for each billed member (`countBilledMembers`; the client sends no seat count), keeping the team's free trial without a card. The data layer's `stripeCustomerId` and `stripeSubscriptionId` on the `META` item are the team's customer and subscription; only billing code writes them (and `plan`, `seats`, `status`, `billingInterval`, `currentPeriodEnd`, `cancelAtPeriodEnd`). Stripe's webhook (`src/billing/webhook-handler.ts`) verifies, queues and answers; the worker (`src/billing/worker.ts`, `worker-db.ts`, `worker-handler.ts`) applies each event with the data layer's `stripeCustomerTeam`, `teamContextForStripeCustomer`, `getBillingTeam`, `applySubscription` (conditioned on the team existing, not closed or purging, and the customer's and subscription's being the team's), `listOwnerContacts`, `claimBillingNotice` and `markWebhookProcessed`, all in `src/data/billing.ts`. Closing a team doesn't call Stripe: the purge, and the worker for a closed team's live subscription, end it with `endSubscriptionForClosedTeam` (`src/billing/closing.ts`: cancel at the period's end, or at once if nothing is being paid for, with an idempotency key per closure), and the purge deletes a purged team's customer with `deleteStripeCustomer`. A team whose subscription ended without a live comp is read-only (`isReadOnlyForBilling` in `model.ts`; `authorizeTeam` sets `ctx.subscriptionEnded`, and `writable` throws `SubscriptionEndedError` unless the write is allowed `whileClosed` or `whileEnded`: `setOwnMemberEmail` and `linkStripeCustomer`). Tests: `test/billing-api.test.ts` (with a fake Stripe, against the in-memory table behind the billing-access role's mirror), `test/billing-webhook.test.ts` (signatures made with Stripe's own test helper), `test/billing-worker.test.ts` (behind the billing-worker role's mirror, `test/billing-policy.ts`), `test/billing-ddb.test.ts` (the conditional writes on DynamoDB Local), `test/billing-stripe.test.ts`, `test/billing-db.test.ts`, `test/billing-closing.test.ts` and `test/stripe-catalog.test.ts`; the purge's side is in `test/account-deletion-api.test.ts`.
- **Seats** (`supply-checkout-l50`, [infrastructure](infrastructure.md#billing)). Who takes a paid seat is one list, `BILLED_ROLES` in `src/data/seats.ts` (owners and editors, `contributor`; viewers are free), with `isBilledRole` and `countBilledMembers(db, ctx)`, a strongly consistent query of the team's `MEMBER#` items that reads only their keys and role (`MEMBER_SEAT_ATTRIBUTES`, with `Select` `SPECIFIC_ATTRIBUTES`); the billing worker and Checkout both use it. `listTeamsToReconcile(db)` lists the open teams with a Stripe customer from GSI3's `OPS#TEAMS` partition, naming only `SEAT_RECONCILE_ATTRIBUTES`. `src/billing/seat-queue.ts` is the seat sync message on its own queue (`parseSeatSync`, `sqsSeatSyncQueue`), with no data imports, so the functions that only send syncs bundle nothing that reads a team; `src/billing/seats.ts` is the rest, `createSeatSync`, which the billing worker runs for a seat sync and after each Stripe event about a subscription (`worker-handler.ts` takes only seat syncs from the seat sync queue, by its ARN, and only Stripe events from the billing queue). It finds the team from the customer's link, skips teams and subscriptions it mustn't change, and sets the seat item's quantity to `seatQuantity(countBilledMembers(...))` with proration and an idempotency key made from the team, the message, the SQS delivery, the item and the quantities (`seatUpdateKey`); a count over `MEMBERS_PER_TEAM` changes nothing and counts `SeatQuantityDrift`. The account handler queues a sync after each membership change that commits, and the ops handler after an operator reopens a team, both best effort (`queueSeatSync`, `SeatSyncQueueFailures`). As a team with a Stripe customer closes, the account handler queues a message with reason `closed` instead (`queueClosedSync`), which isn't a seat sync: the worker sets the closed team's subscription to cancel at the period's end within seconds (`endAtClose` in `src/billing/worker.ts`, `supply-checkout-8jc.30`; tested in `test/billing-worker.test.ts`), leaving the hourly purge as the backstop. `src/ops/seat-reconcile-handler.ts` is the nightly reconciliation that queues a `reconcile` sync per team (ended or not), for which the worker counts `SeatQuantityDrift`. For those it first runs the entitlement check (`supply-checkout-8jc.9`), `src/billing/entitlements.ts`: `createEntitlementCheck` compares the team's subscription, status, plan and seats with Stripe's (`entitlementDrift`), and fixes drift with `applySubscription(..., asRead)`, whose condition refuses to overwrite a team whose status, plan, seats or subscription changed since it was read (a value comparison, not a version: a change and back slips through, and the next event or night corrects it), then counts `EntitlementDrift`. `src/billing/subscription.ts` holds `SubscriptionLike` and `subscriptionState`, shared by the event path and the check. Tests: `test/billing-seats.test.ts` (the sync and the entitlement check behind the billing-worker role's mirror, the messages and the queue), `test/billing-ddb.test.ts` (`asRead` on DynamoDB Local), `test/members-api.test.ts`, `test/invites-api.test.ts` and `test/account-deletion-api.test.ts` (what the account handler queues), `test/ops-api.test.ts` (the sync after an operator's reopen), `test/ops-checks.test.ts` (the reconciliation) and `test/ops-ddb.test.ts` (the listing and the count on DynamoDB Local).
- **Deletion records.** `src/deletions/records.ts` (supply-checkout-0ic7). Deleted data lives on in the table's backups, so each deleted account and each purged team gets one small S3 object, `users/<userId>.json` or `teams/<teamId>.json`, holding the ID, the time and, for an account, the teams its deletion closed, or for a team, its Stripe customer and subscription IDs (`purgeTeam` hands them to `beforeDelete`, `supply-checkout-8jc.37`): never an email, name or item. The bucket keeps each under Object Lock (compliance mode) for `DELETION_RECORD_RETENTION_DAYS` (400), longer than any backup can be kept. The account handler writes the user's once nothing can refuse the deletion and before their rows and Cognito user go; the purge writes the team's before it deletes anything. Each is written once (`If-None-Match`), so a retry keeps the first. `src/data/restore.ts` and `npm run restore` (`scripts/restore.ts`) read every version of them (`ListObjectVersions`, so a record overwritten with junk still counts; `--records-before` leaves out versions written after a suspected compromise) to delete the same data again from a restored table, and copy a restored table back into the live one ([Put a restored table back into service](backups.md#put-a-restored-table-back-into-service)). Like the backfills, `index.ts` doesn't export `restore.ts`: no Lambda runs it.
- **Watching the operator audit.** `src/ops/operator-audit-watch-handler.ts` reads the table's stream (filtered by its event source mapping to `MODIFY` and `REMOVE` records of `OPAUDIT#` partitions, `INSERT`s of `AUDIT#` items, and its heartbeat item) and counts every change to an operator audit item that isn't a TTL expiry, and every new entry set to expire early, in `OperatorAuditChanged`, for the P1 "Operator audit changed" alarm, and each heartbeat in `OperatorAuditWatchHeartbeat`, for the P2 "Operator audit watch silent" alarm ([Operators](infrastructure.md#operators)). It logs keys and event names only. The lint config bans `ReturnValuesOnConditionCheckFailure`, `ALL_OLD` and `ALL_NEW` in the operator code (`src/operator/`, `src/data/operator.ts`), since no IAM condition limits what a failed condition returns.
- **Watching the operators group.** `src/ops/operator-group-watch-handler.ts` (run every 5 minutes) lists the `operators` group with `ListUsersInGroup` (`operator-group-members.ts`, keeping only each member's `sub` and enabled flag) and compares it with the snapshot it saved last in an SSM parameter (`operator-group-snapshot.ts`), counting each operator added, removed, disabled or enabled in `OperatorGroupChanged`, and a snapshot it has to start again in `OperatorGroupBaselineReset`, for the P1 "Operator group changed" alarm, and the group's size in `OperatorGroupMembers` for the P2 "Operator group watch silent" alarm ([Operators](infrastructure.md#operators), `supply-checkout-3sv.5`). It logs `sub`s and counts only.
- **Watching the deletion records.** `src/deletions/watch-handler.ts` gets the deletion records bucket's S3 events from EventBridge and counts in `DeletionRecordRewrites` any deletion that isn't a lifecycle expiry, any write to a key that isn't a record's, and any write to a record's key that then has more than one version or a delete marker (it lists the key's versions to tell), for the P2 "Deletion record rewritten" alarm ([backups.md](backups.md#when-a-deletion-record-is-rewritten)). It logs the kind of record and the S3 version and request IDs, never the ID in the key.
- **Deleting an account.** `DELETE /me` (`src/api/account-handler.ts`, with `src/data/accounts.ts`), typing `DELETE` to confirm. It's refused, with nothing changed, while the caller is the only owner of an open team that has other members (409 `last_owner`, naming up to three of the teams). Otherwise: `startAccountDeletion` puts `USER#<userId>` / `DELETING` (TTL 30 days), and `createTeam` and `acceptInvite` carry a `ConditionCheck` on it in their transactions, so no membership can be added once the deletion has listed the user's teams (403 "This account is being deleted"). The caller leaves every team with `removeMember` (so the counts move and it's audited), closing first any open team they're the only member of; every invite to their verified email is deleted (`deleteInviteForEmail`, each on a session tagged with that invite's team, the same entitlement as accepting it); `deleteUserRows` deletes what's left in their partition (stale switcher rows) except the mark and the `LIMIT#…` rate-limit counters, which expire by TTL so deleting and recreating an account can't reset a daily limit; and last the Cognito user is deleted with Cognito's `DeleteUser` and the caller's own access token (`cognitoDeleteUser` in `src/api/cognito-user.ts`), which needs no IAM permission and can only delete the caller. Every step is idempotent, so a retry after a failure part-way (the teams are left in parallel, each on its own) carries on. If leaving any team fails (a last-owner refusal after the pre-check, a join that stopped a closure, a conflict), the mark is taken away before the error is returned, so the user isn't blocked from joining teams for its 30 days; a retry marks the account again before it lists the teams. What stays: audit events in teams the user was in keep their user ID (never their email) until the audit trail's TTL or the team's purge, and invites they sent keep their user ID as `invitedBy` until they expire. The log line has only IDs and counts.
- **Live-update audience.** `liveUpdateRecipients(db, teamId)` (`src/data/live-audience.ts`) is who gets a team's live-update notices ([ADR 0016](adr/0016-per-member-live-update-channels.md)): the user IDs of its current members, or none if the team doesn't exist, an owner closed it, or its status has ended (`ENDED_STATUSES` in `model.ts`) and it has no live comp (`liveComp`, ADR 0015). Closure wins over a comp. Like `authorizeTeam`, it reads by team ID without a `TeamContext` (the stream consumer has no caller), and it names only `LIVE_AUDIENCE_ATTRIBUTES` (`schema.ts`), the attributes the consumer's IAM policy allows. `audienceChangeFromStream` tells the consumer which team's `META` or `MEMBER#` item a stream record changed, so it rereads that team's members.
- **Keys.** As in ADR 0005, except sheets: `SHEET#<sheetId>` instead of `SHEET#<date>#<id>`, because the date is editable and a key can't change. Date order comes from `GSI1` (`TEAM#<teamId>#SHEETS`, `<date>#<sheetId>`), which one update can change. `GSI1` also finds invites by the SHA-256 hash of their token, and `GSI2` (`INVITEE#<SHA-256 of the email>`, `INVITE#<inviteId>`) finds them by the invitee's email. `USER#<userId>` / `LIMIT#TEAMS#<date>` counts the teams a user created that day (TTL two days); `USER#<userId>` / `EMAIL_CODE_SENT` holds the SHA-256 of the address the user's last code went to (`POST /me/email/code`, TTL two days), and `USER#<userId>` / `VERIFIED_EMAIL` the SHA-256 of the address they last proved with that code through `POST /me/email/verify` (`src/data/verified-email.ts`), which the pre token generation trigger reads before it records a linked user's address (see "Sign-in" in infrastructure.md); `USER#<userId>` / `DELETING` marks an account being deleted (TTL 30 days); GSI1's `TEAMS#CLOSED` partition lists closed teams by when they're due to be purged; `TEAM#<teamId>` / `LIMIT#INVITES#<date>` and `TEAM#<teamId>` / `LIMIT#INVITES#<date>#<key>` and `INVITELIMIT#<key>` / `LIMIT#INVITES#<date>` count invites (see Invites); `TEAM#<teamId>` / `USAGE#<month>` and `USAGE#TRIAL` count a team's receipt reads, and `RECEIPTRATE#<userId>` / `RECEIPTS#<window>#<stamp>` a user's (see Receipt reading).
