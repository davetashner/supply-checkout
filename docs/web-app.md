# The web app

## Web hosting and releases

The web app and the demo are static builds served by one CloudFront distribution from one S3 bucket (`supply-checkout-qk1`).

- **Bucket.** `supply-checkout-<env>-web-<region>-<account>`, in the primary region's `data` stack (stateful, retained, versioned, private, SSE-S3, access logs to `supply-checkout-<env>-logs-<region>-<account>`). Only CloudFront distributions in the account can read it, through origin access control. A release is a folder, `releases/<version>/`, uploaded once and never changed. The second region's bucket, replication and the origin group are phase 2 (`supply-checkout-d79`).
- **Distribution** (`web` stack, `lib/stacks/web-stack.ts`), for the apex, `www.` and `app.`, with the `web` certificate from the domain stack, TLS 1.2+, HTTP/2 and HTTP/3, and standard logs to the logs bucket.
- **Routing and live version.** A CloudFront Function (`lib/web/router.js`, viewer request) routes by host and path:

  | Request | Response |
  |---|---|
  | `app.<domain>/…` | the `app` channel |
  | `<domain>/` and `<domain>/assets/…` | the `site` channel, the marketing home page. With nothing live on it (no key, `none`, a bad version or a store error), `/` 302s to `https://app.<domain>/`, `Cache-Control: no-store`, as before: publishing the site turns it on, and it never answers 503 |
  | `<domain>/demo` | 301 to `/demo/` |
  | `<domain>/demo/…` | the `demo` channel, with `/demo` taken off the path |
  | any other `<domain>` path (the site has only `/` and its hashed `assets/`) | 302 to `https://app.<domain>/`, `no-store` |
  | `www.<domain>/demo…` | 301 to `https://<domain>/demo/` |
  | any other `www.<domain>` path | 301 to `https://<domain>/` |

  Any other host (the distribution's `cloudfront.net` name, or `app.<domain>` with a trailing dot or a port) is treated like the apex. Every `Location` is a fixed URL from the configured host names; nothing from the request (host, path or query string) is copied into one, so there's no open redirect, and query strings are dropped (the app's invite links point at `app.` directly). The 301s say `max-age=86400`. Responses the function makes (the redirects and the 503) never reach the CloudFront cache, and they set HSTS and `nosniff` themselves, because AWS documents the response headers policy for cached and origin responses only.

  To serve a channel, the function reads its live version from a CloudFront KeyValueStore and rewrites the path to `releases/<version>/…`, adding `index.html` to paths that end in `/`. The cache key is the rewritten path, so switching versions needs no invalidation, and the KeyValueStore write reaches every edge within seconds. Until something is published, a channel answers 503. The demo build's URLs are relative (`./assets/…`, including the favicons and the ZXing chunk), so the same release works under `/demo/`; `tests/content-security-policy.spec.js` serves it there.
- **Headers** on every response: `Content-Security-Policy` (`lib/web/content-security-policy.ts`), HSTS (two years, subdomains), `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy` and `Cross-Origin-Opener-Policy`. The CSP allows only the app's own scripts (ZXing is bundled, in its own chunk), Google Fonts, inline `style` attributes, and `data:`/`blob:` images, plus the environment's `api.`, `realtime.` and `auth.` for connections. Infra tests check it against `src/index.html`, and `tests/content-security-policy.spec.js` runs the web app and the demo under it in every browser, failing on any violation. If you add a script, font or image host to the app, add it there too.
- **WAF** (CloudFront scope): a rate limit of 2,000 requests per IP per 5 minutes, then the AWS managed IP reputation, common and known-bad-inputs rule groups.
- **Caching.** `scripts/publish-web.mjs` uploads `assets/` with `Cache-Control: public, max-age=31536000, immutable`, and everything else (`index.html`) with `max-age=0, must-revalidate` for browsers and `s-maxage` for the edge, which is safe because a release never changes. Source maps aren't uploaded.

**The home page** (`site/`, `supply-checkout-a1s.1`) is a small static page of its own, with none of `src/` in it: `npm run build:site` writes `dist/site/` (every file, the clips and posters included, hashed into `assets/`, so a release's clips are never cached under an old name; `site-release.json` marks the build). It runs under the app's CSP (`default-src 'self'` covers its video; its fonts are the app's Google Fonts), with one script of its own that plays each clip only while it's on screen and, for anyone who prefers reduced motion, leaves the poster with a play button. Its clips are `site/clips/` (committed, under 3 MB each, with `clips.json`), recorded from the journey tests by `npm run journeys:video -- --marketing` ([Journey videos](testing.md#marketing-clips)); The link preview (what iMessage and Slack show for a shared link) comes from the page's `<title>` and Open Graph tags and `site/share.png` (1200 × 630, made from the checkout clip's poster by `npm run site:share`; commit it when the clips or the wording change); the build writes the image's full URL into the tags. `tests/site.spec.js` runs the page under the CSP in every browser. Publish it with `npm run publish:site` (a `site-<time>-<commit>` release on the `site` channel). The router change that serves it is a web stack deploy (`npm run deploy -- web`), done once, before the first publish; after that, publishing is all it takes, with no stack deploy. Roll back with `activate --channel site --version <older>`. To turn the page off, set the `site` key back to `none` (`aws cloudfront-keyvaluestore put-key`) and `/` redirects to the app again. A site release can't go live on another channel, nor another's on `site` (the marker file, as with `config.json`). It isn't in the deploy workflow yet, so it's published by hand after each change to the page or its clips.

**Publishing.** A release publishes the app and the demo through the deploy workflow, as `app-<tag>` and `demo-<tag>`, with the web stack's publisher role, then checks the router and the live site and rolls back if they fail ([Deploying a release](releases.md#deploying-a-release)). By hand, `npm run deploy -- app` builds the app, publishes it to `app.`, makes it live and runs `check-router`, from an up-to-date, clean `main` ([Deploying](infrastructure.md#deploying)). The commands below are the steps it runs, and the rest (the demo, rollbacks, status). `scripts/publish-web.mjs` reads the bucket and the KeyValueStore from the SSM parameters under `/supply-checkout/<env>/web/`, so it needs the web stack deployed and an AWS CLI v2 login:

```bash
npm run publish:demo                                            # build:demo, upload as demo-<time>-<commit>, make it live at /demo/
npm run publish:web -- publish --channel app --dir dist/web     # after npm run build:web: the same for app.
npm run publish:web -- publish --channel app --dir dist/web --version 1.3.0 --no-activate   # upload only
npm run publish:web -- activate --channel app --version 1.3.0  # switch, or roll back to any uploaded version
npm run publish:web -- status                                   # live versions and every uploaded release
npm run publish:web -- live --channel app                       # just the channel's live version (none if nothing)
npm run publish:web -- check-router                             # run the live router on a request to each host
```

**After every deploy of the web stack**, run `npm run publish:web -- check-router`. It runs the router function's LIVE stage with `aws cloudfront test-function` on `app.`, the apex's `/demo/` and `/`, and `www.`, and fails if CloudFront can't run it or it answers wrong (a channel with nothing live may answer 503). A router CloudFront can't run fails every request; the Site down and Web router failing alarms page for it, and [When the web app is down](observability.md#when-the-web-app-is-down) says how to roll back.

Options: `--env` (default `prod`), `--profile` (default `$AWS_PROFILE`, else `supply-prod`), `--dry-run` (print the writes instead of running them). Publishing a version that already exists fails, unless `--reuse` is given: then it isn't uploaded again but made live again (on its own channel only), which is how the deploy workflow deploys a release twice or an older one. Publishing to the `app` channel first writes `config.json` into the folder from the api, identity, realtime and web stacks' SSM outputs, so those must be deployed (the web stack from `supply-checkout-al0` on, which publishes the RUM app monitor's parameters; an older web stack makes the publish fail with the missing `/supply-checkout/<env>/web/rum-*` names, so redeploy it first); `npm run publish:web -- config` prints it. That `config.json` also marks a release's channel: publishing the demo refuses a folder that has one, and `activate` refuses a release from the other channel, so the app build is never served at `/demo/` or the demo at `app.`.

**First deploy, and the demo live at supplycheckout.com/demo/:**

```bash
aws sso login --profile supply-prod
# Once: the SSM parameters from "Domain and email" (hosted zone ID, DMARC report address)
ZONE_ID=$(aws ssm get-parameter --profile supply-prod --region us-east-1 \
  --name /supply-checkout/prod/dns/hosted-zone-id --query Parameter.Value --output text)
# The domain stack adds an SPF TXT record at the apex. This must print nothing: an existing
# apex TXT record (a site verification, say) must be removed, or its values merged into
# the ApexSpf record in lib/stacks/domain-stack.ts, before deploying.
aws route53 list-resource-record-sets --profile supply-prod --hosted-zone-id "$ZONE_ID" \
  --query "ResourceRecordSets[?Name=='supplycheckout.com.' && Type=='TXT']" --output text
# The web stack adds A/AAAA aliases at the apex, www. and app.: none may exist yet either.
aws route53 list-resource-record-sets --profile supply-prod --hosted-zone-id "$ZONE_ID" \
  --query "ResourceRecordSets[?(Type=='A' || Type=='AAAA' || Type=='CNAME') && contains(['supplycheckout.com.','www.supplycheckout.com.','app.supplycheckout.com.'], Name)].[Name,Type]" --output text
cd infra && npm ci
npx cdk deploy supply-checkout-prod-us-east-1-web --profile supply-prod -c backupCopy=false   # also deploys the domain and data stacks it needs
cd .. && npm ci
npm run publish:web -- check-router                                        # the router runs (503s until something is live)
npm run publish:demo
curl -sI https://supplycheckout.com/demo/ | head -20                       # 200, with the security headers
curl -sI https://supplycheckout.com/ | grep -i '^location\|^cache-control'  # 302 to https://app.supplycheckout.com/, no-store
```

The web stack deploys the data stack too, so keep `-c backupCopy=false` until [step 4 of the backup setup](backups.md#setting-it-up) ([why](infrastructure.md#the-cloudtrail-trail)).

Then check https://securityheaders.com/?q=supplycheckout.com/demo/ (it should grade A; `'unsafe-inline'` for style attributes stops it at A rather than A+) and that `https://www.supplycheckout.com/` redirects to the apex and `/demo` to `/demo/`. `https://app.supplycheckout.com/` answers 503 until the real app is published to the `app` channel.

## The operator page

The operator page (`ops/`, `npm run build:ops`, [ADR 0015](adr/0015-platform-operator-role.md) §9, `supply-checkout-gxlt`) is a separate small site at `ops.<env domain>`, with none of the customer app's code. What it does, and setting it up, are in [Operators](infrastructure.md#the-operator-page).

- **Distribution.** A second CloudFront distribution in the `web` stack, for `ops.<env domain>` alone, with its own certificate (the `domain` stack's `OpsWebCertificate`), TLS 1.2+, HTTP/2 and HTTP/3. It reads the same releases bucket through its own origin access control, and uses the same WAF web ACL and logs bucket (`cloudfront/ops/`). `A` and `AAAA` aliases for `ops.` point at it. Its ID and router's name are published as `web/ops-distribution-id` and `web/ops-router-function-name`.
- **Routing** (`lib/web/ops-router.js`, viewer request): only the host `ops.<env domain>` and only these paths are served, from the live release of the `ops` channel in the same KeyValueStore:

  | Request | Response |
  |---|---|
  | `ops.<domain>/` | the release's `index.html` |
  | `ops.<domain>/ops-config.json` | its config |
  | `ops.<domain>/assets/<name>.js`, `.css`, `.svg` | its hashed files |
  | anything else, or any other host | 404, made at the edge |

  The live version must be named `ops-*`, or the router answers 503, so an app or demo release can never be served there; a missing `ops` key (before the first publish) is a 503 too. The key isn't in the store's import source (adding it there would replace the store and reset every channel).
- **Headers** (`OpsSecurityHeaders`): the CSP in `lib/web/ops-content-security-policy.ts` (`default-src 'none'`; scripts, styles and images from the page's own origin only; `connect-src` only `'self'`, `api.` and `ops-auth.`; no frames, `<base>`, form targets, plugins, workers or manifest; Trusted Types required), `Cache-Control: no-store`, HSTS (two years, subdomains), `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `nosniff`, a Permissions-Policy with everything off, `Cross-Origin-Opener-Policy` and `Cross-Origin-Resource-Policy` `same-origin`, and `X-Robots-Tag: noindex, nofollow`. The router's own 404s and 503s carry HSTS, `nosniff`, `no-store` and a CSP that allows nothing. `tests/ops.spec.js` runs the page under this CSP and fails on any violation; `infra/test/web.test.ts` checks the policy.
- **Caching.** None: the managed CachingDisabled policy at the edge, and `no-store` in the browser. It's a few small files for a handful of operators.
- **Publishing.** `npm run publish:ops` builds the page and publishes it as `ops-<time>-<commit>` on the `ops` channel. Before the upload, `publish-web.mjs` writes `ops-config.json` into the folder: `apiUrl`, `authUrl` (the operator pool's `https://ops-auth.<env domain>`) and `clientId` (the `ops` client), from `api/url`, `identity/ops-auth-url` and `identity/ops-client-id`, and refuses unless the hosts are exactly this environment's. `ops-config.json` marks an ops release, as `config.json` marks an app release: an ops release can't go live on `app` or `demo`, nor an app or demo release on `ops`, a folder with the other's config file is refused, and only the `ops` channel takes `ops-*` versions. `npm run publish:web -- config --channel ops` prints the config, and `activate --channel ops --version ops-…` rolls back. `check-router` also runs the operator page's router (`ops.<domain>/` must be served or 503, and `/config.json` a 404). The web publisher role may test both routers and read the two `identity/ops-*` parameters, so the deploy workflow can publish the page when it's added there (a follow-up).
- **Tests.** `npm run test:ops` runs the page's logic (`ops/lib/`) in Node with a 100% coverage gate (in the lint job in CI). `tests/ops.spec.js` runs the built page in the browsers with the web build (`BUILD=web`), as CloudFront serves it, against stand-ins for Managed Login and the `/ops` routes: sign-in with PKCE and state, the token in memory only, a customer token refused, search, a team's detail, comps by months and by date, ending a comp, a 409, a retried write keeping its Idempotency-Key, the audit, expiry and sign-out, and API data shown as text. It's on its own origin, so `src/`'s coverage doesn't count it.

## The web app on AWS

The web build (`npm run build:web`, served at `app.<env domain>`) is the only build of the app that runs on AWS (the claude.ai artifact build is retired). `src/aws/main.js` runs first and provides `window.claude.use()` on the backend ([ADR 0004](adr/0004-runtime-adapter.md), `supply-checkout-a2b`); the tests and the demo bring their own runtime, which it leaves alone.

- **Config.** `config.json`, next to `index.html`: `apiUrl`, `authUrl`, `clientId`, `realtimeUrl` and `realtimeHost`, and for CloudWatch RUM `rumAppMonitorId`, `rumIdentityPoolId` and `rumRegion`. The publish step writes it from SSM (above), so one build works in every environment and no IDs are committed. The hosts aren't trusted from SSM, though (`supply-checkout-6uw.23`): the browser signs in at `authUrl` and sends its tokens to `apiUrl` and `realtimeUrl`, so the publish step refuses unless they are exactly `https://api.<env domain>`, `https://auth.<env domain>`, `wss://realtime.<env domain>/event/realtime` and `realtime.<env domain>`, with the domain taken from the deployment config (`DOMAIN` and `envDomain` in `scripts/publish-web.mjs`, which its tests keep in step with `infra/lib/config.ts`). It also refuses a `rumRegion` other than the web stack's region (`--region`, an approved region), an app monitor ID that isn't a lowercase UUID, and an identity pool ID that isn't `<rumRegion>:<UUID>`. Without it the app says shared storage isn't available. Without the `rum*` fields (or with a pool from another region) the app runs unmonitored.
- **Error and performance reporting** (`src/aws/rum.js`, `supply-checkout-al0`). With the `rum*` fields, the app loads the CloudWatch RUM client (bundled from `@aws-rum/web-slim` and `@aws-rum/web-core`, its own chunk, never in the demo) and sends the app monitor ([Observability](observability.md#front-end-errors-cloudwatch-rum)) JavaScript errors (uncaught errors and unhandled rejections, with a stack trace), page views (the path, always `/`), navigation and resource timing (scripts, stylesheets, fonts and images, not the API's requests) and web vitals, each tagged with the release version from `package.json`. It sets no cookies (the user ID is all zeros), adds no attributes, and every event's details go through `scrub()` first, which takes query strings and fragments off URLs and paths, absolute or relative (an invite's token, a sign-in code), and masks JWT-shaped strings and email addresses. It fails closed: a plugin's event is recorded as a scrubbed copy or not at all, and if an event the client builds itself (a page view) can't be cleaned, the client stops sending. It signs with guest credentials from the identity pool's enhanced flow, which it keeps in `localStorage` (`cwr_i`, `cwr_c`); they name no one. If the client can't load or start, the app carries on without it. The CSP allows `cognito-identity.<region>` and `dataplane.rum.<region>` for it.
- **Sign-in.** Managed Login with the code flow and PKCE ([Sign-in](infrastructure.md#sign-in)). The API's `/auth/session` redeems the code and keeps the refresh token in an HttpOnly cookie; the access token is only in memory. It's refreshed five minutes before it expires (a scheduled refresh the API doesn't answer is tried again a minute later), and after any 401 (then the request is tried once more). If refreshing fails, the sign-in screen comes back. API requests give up after 15 seconds. Sign out revokes the refresh token (no refresh runs while it does), forgets the chosen team and every team's receipt draft, then signs out of Managed Login; if the API can't be reached, the user stays signed in and is told.
- **Saved on the device.** `localStorage` keeps the last team used and a receipt draft per team (`supplyCheckout.receiptDraft.<teamId>`), marked with the user ID from `GET /me` (`supplyCheckout.owner`). A session can end without Sign out (it expires, or a sign-out times out here but goes through), so at every sign-in, a different user (or data from before the mark) makes the app forget the saved team and drafts before reading them; the same user keeps them. The last user's mark is removed first, and the new one is set only once nothing of theirs is left, so if something can't be removed the next sign-in tries again. Another tab still open as the last user sees the mark change (someone else signed in, or the user signed out or deleted their account there), when another tab writes storage or when it's shown again (it may have been asleep or in the back-forward cache). It then stops at once (no refresh with the refresh cookie, which may be the other user's now; no live updates; API calls refused without being sent; receipt drafts no longer kept; the app and any open form hidden, so an unsaved form or receipt edit is dropped, and a receipt save in flight at the switch isn't kept as a draft) and reloads as whoever is signed in now. Signing out or deleting the account in this tab stops watching the mark first, so hiding the tab before Managed Login's sign-out page loads doesn't reload over it. Drafts are also not kept once the mark isn't this user's, even before the tab has heard. As a backstop for a tab that never sees the mark change (the other tab couldn't write it), a refresh answered with another user's tokens (a different `sub` from the one signed in) is never taken up: the tab stops and reloads the same way. An invite link saved in a tab (`sessionStorage`) is marked with the first user it's offered to, and isn't offered to a different user who signs in there later unless `/me` lists it as theirs. Storage that can't be read or written is skipped (`src/aws/session.js`, `src/aws/account.js`).
- **Teams.** After sign-in, `GET /me` decides ([docs/api/onboarding.md](api/onboarding.md)): "Name your team" for a new user (`POST /teams`, one `Idempotency-Key` per name), the invite from an `?invite=<id>&token=<token>` link (kept across sign-in), or the last team used (in `localStorage`). A bar under the header shows the team, a switcher when there are several (switching reloads the page; when the team's data is re-listed, at most once a minute, it loads `/me` again and drops teams the user was removed from meanwhile, since nothing else tells the page), Members and Import CSV for owners, and Sign out. Viewers get the app's view-only notice: the API refuses a viewer's write with 403 `permission_denied`, `reason: "view_only"`, which `src/aws/db.js` hands to the app as `invalid_argument` (the artifact runtime's view-only code); any other `permission_denied` on a write means the user was removed from the team.
- **Verifying the email address** (`src/aws/verify-email.js`, `supply-checkout-ocjk`). Only a verified address lists and accepts invites. While `GET /me` says `emailVerified: false`, "Name your team" and the invite screen say so with **Verify email**, as does the team bar (a join refused with 403 `permission_denied` shows the prompt too). It opens a dialog: **Send code** (`POST /me/email/code`, Cognito emails a 6-digit code; another can be asked for once a minute), then the code (`POST /me/email/verify`). A wrong or expired code, too many tries (Cognito's limits, 429) and an address another account has each get their own message. Once the code is accepted the app refreshes its tokens, so the pre token generation trigger records a linked user's new address, and loads `/me` again; only when that says verified does the dialog say so, and the screens behind it start again with the new `/me` (its invites). Otherwise it offers Try again, or signing in again (a user whose downgrade is pending is cleared only by a Managed Login sign-in, after which they verify again). The API makes the Cognito calls with the user's access token rather than the browser, so the app still talks only to the API ([Sign-in](infrastructure.md#sign-in)).
- **Two-step sign-in** (`src/aws/mfa.js`, `supply-checkout-8jc.12`). Owners need it for Billing and Subscribe. **Account** says whether it's on (`GET /me`'s `user.mfa`: `off`, `totp`, or `provider` for a Google or Apple user, who has nothing to set up) and offers **Set up two-step sign-in**, or **Move to a new phone** once it's on. A billing button the server refuses with 403 `mfa_required` opens the same setup, saying why. The setup sets a password first (`POST /me/password`; the current one if they have one), or skips that with **Keep my current password**, because with an authenticator on Cognito only lets them sign in with a password and its code. Then it shows the secret as a QR code (ZXing's encoder, `src/aws/qr.js`, loaded only then), as a key in groups of four, and as an `otpauth://` link, and checks a 6-digit code (`POST /me/mfa/totp/verify`). That turns it on and signs the user out everywhere, so the app shows **Two-step sign-in is on** with **Sign in again**, through Managed Login's sign-out. The team and receipt drafts are kept for the same person.
- **Members** (`src/aws/members.js`, owners only). Members opens a dialog listing the team's members with their roles (`GET /teams/{teamId}/members`). An owner changes a role from its menu (`PATCH`) or removes someone with Remove, tapped twice (`DELETE`). While there's only one owner, their role and Leave are off, and the dialog says a team needs an owner; the server enforces the same thing atomically. An owner who changes their own role or leaves sees "Your access changed" and starts again. Above the list it says how many seats are used ("7 of 10 members", the members listed and `/me`'s `memberCap`, which the dialog asks `/me` for again as it opens, so a plan change shows without a reload), and **Send invite** turns off once members and invites that haven't expired fill them, as the server counts them (429 `team_full`). Below, the team's invites, then **Support activity**: what Supply Checkout support did to the team (`GET /teams/{teamId}/support-actions`, ADR 0015), 20 at a time with Show more, and Try again if the first 20 don't load.
- **Leaving, closing and deleting** (`src/aws/account.js`, `members.js`, `delete-account.js`). Contributors and viewers have **Leave team** in the team bar (two taps, then "Your access changed"); owners leave from Members. Owners close the team at the bottom of Members by typing its name (the button stays off until it matches). A closed team (`closedAt` in `/me`) shows when it will be deleted, opens read-only (`can("data.write")` is false; owners keep Export data; no Import CSV), and its Members screen only removes people and lets anyone leave, the last owner too. The app's notice says the team is closed rather than suggesting asking for Contributor access (`user.viewOnlyNotice()`, which the artifact runtime doesn't have). Its owners see "Reopen by <date and time>" (`/me`'s `reopenBy`, an hour before `deletesAt`) and get **Reopen team** under the notice until then, when the button goes: a modal that says what doesn't come back (cancelled invites, people who left or were removed) and takes the team's name typed the same way, then "Your access changed" and a reload with the team open (`POST /teams/{teamId}/reopen`; a refusal within an hour of the purge says the team is about to be deleted). **Account** in the team bar, and **Delete account** on the screens before a team, open a typed-DELETE confirmation for `DELETE /me`; the server's last-owner message is shown as is. Once deleted, live updates stop, the device forgets the user (as Sign out does, without revoking: Cognito already ended the sessions) and a refused refresh clears the cookie; **Done** signs out of Managed Login. A write refused with `team_closed` (closed by another owner meanwhile) switches the app to view-only and loads `/me` again: the team bar is then drawn as a closed team's (when it will be deleted, no Import CSV, Reopen team for owners) without a page reload, and the notice says the team is closed. If `/me` doesn't load or doesn't list the team as closed yet, the notice says an owner closed it and to reload to see when it will be deleted.
- **Change password** (`src/aws/password.js`, `supply-checkout-6uw.28`). **Account** has a **Password** section with **Change password**, which opens a dialog that sets the signed-in user's password (`POST /me/password`) without signing out and using Forgot password. The two-step setup's password step uses the same fields, checks and error messages from `password.js`. Decisions:
  - **Field order for password managers.** The form has a hidden `username` field holding the email, then **Current password** (`autocomplete="current-password"`), then **New password** and **Confirm new password** (both `autocomplete="new-password"`, with the pool's rules in `passwordrules`). Current first and a username make it read as a password change rather than a sign-up, so a manager fills the current password and offers to update it, instead of saving the new one in its place before the change is sent (which locked the owner out of the two-step setup once). The rules (12+ characters, upper and lower case, a number, a symbol) are shown under the new password.
  - **Current password.** Required when two-step sign-in is on (the user has a password for sure). Otherwise it's optional, with a hint to leave it empty if they've only signed in with an email code or a passkey: Cognito says nothing about whether a user has a password, so the same dialog changes one or sets the first, and Cognito refuses a missing current password for a user who has one (`password_mismatch`). **Forgot your current password?** explains the way back: sign out, reset the password from the sign-in page, and sign in with the new one.
  - **Signing out everywhere.** A **Sign out everywhere** checkbox, on by default, follows the change with `POST /me/sign-out-everywhere`. Cognito's GlobalSignOut has no "every session but this one", so it ends this tab's session too, and the app shows **Your password is changed** with **Sign in again** (through Managed Login's sign-out, keeping the team and drafts, as after two-step setup). Signing in again right away also checks the new password and lets the password manager save it. If the sign-out fails, the dialog says the password changed and offers **Sign out everywhere** again, or **Close** to stay signed in. With the box unchecked, the dialog closes with a toast and the user stays signed in.
  - **Security notice.** No backend change: the API already emails the account's verified address after `POST /me/password` ("A password was set on your Supply Checkout account", `passwordSet`), and a direct Cognito ChangePassword is emailed from CloudTrail (`backend/src/identity/security-notices-handler.ts`).
  - **Google and Apple.** A Google- or Apple-only account (`/me`'s `user.mfa` is `provider`) sees a note instead of the button: there's no Supply Checkout password to change, and the API refuses them (`federated_sign_in`).
- **Billing** (`src/aws/account.js`, owners only, `supply-checkout-121`). When `/me` says the team has a Stripe customer (`billingAccount`) and it isn't closed, owners get **Billing** in the team bar. It asks the API for a Customer Portal session (`POST /teams/{teamId}/billing/portal`) and puts a **Continue to billing** link in its place. The link goes to Stripe, where the owner adds or changes a card, switches between monthly and annual, downloads invoices or cancels. Stripe's sessions are short-lived, so after 4 minutes the button comes back to make a new one. When a subscription is canceled but still running (`cancelsAt`), the team bar tells everyone when it ends. A team whose subscription ended also shows **Subscribe** (Stripe Checkout). Next to Billing, **Invoices** (`src/aws/invoices.js`, `supply-checkout-eja`) lists the team's latest invoices (`GET /teams/{teamId}/billing/invoices`): the date, number, amount and whether it's paid (or what's due), with **View** (Stripe's hosted invoice page) and **PDF**, each opening in a new tab. It says older ones are in Billing when there are more, and that Stripe emails each invoice and receipt. A load that fails offers Try again; `mfa_required` opens the two-step setup, as for Billing.
- **Importing inventory** (`src/aws/import.js`, owners only, for assisted onboarding). Import CSV opens a dialog with a downloadable template (`src/aws/import-template.csv`: the ten columns and three made-up example rows, which pass the preview as they are) and a short guide to each column (brand, eaches, cost vs price, pack size, per [ADR 0014](adr/0014-units-cost-and-rounding.md), and the optional `reorder_at` and `reorder_qty`, supply-checkout-005.13, which the preview shows as Reorder at and the server checks as the product routes do; blank keeps an item's). The chosen file goes to `POST /teams/{teamId}/imports` as a dry run, and the dialog shows the server's preview (what each row creates or changes) or every problem in the file. Import sends it again with one `importId` per file; if the import doesn't finish, Try again sends the same request, which finishes it without adding anything twice ([backend.md](backend.md)). The imported items arrive through live updates like any other change. The artifact build has no import (it has no server to make it all or nothing).
- **Data.** The `db` calls map onto the data routes as [openapi.yaml](api/openapi.yaml) describes, with the API's error codes passed through. Projects are listed by ID and sorted in the browser, because the date-ordered route reads an index that can lag a write.
- **Low-stock alerts** (`src/reorder.js`, `supply-checkout-005.8`, journey J15). The item editor has **Reorder at** and **Usual order** (`reorderAt`, `reorderQty`, whole single items). An item that's counted and at or below its level shows **Low** in Inventory; the **Inventory** tab shows how many low items nobody has acknowledged, and **Running low (N)** lists them with **Copy list** (text, through the clipboard) and **Download CSV** (name, brand when an item has one, barcode, count, level, usual order, acknowledged). **Acknowledge** is a `PATCH` of `{ ackedAtStock: <stock> }`, shared by the team and made against the version the page holds, so a stale one gets "someone else changed this" and the latest shows. The alert stays quiet while stock is at or above the acknowledged count; the server ends the acknowledgment when a return, receipt, count or import takes stock above the level ([commands.md](api/commands.md#rules-the-server-enforces)), and saving a new level in the editor drops it too. **Mark ordered** (`supply-checkout-005.14`) asks how many (the usual order to start) and when (today to start) and saves the item with `orderedQty` and `orderedOn` and without its acknowledgment, as one `PUT` against the version the page holds; the row then says "On order: N since <date>" with **Cancel order** (a `PUT` without them), the Inventory row shows **On order**, and the item isn't counted however far stock falls (an order quiets the alert even at 0 in storage), until a restock above the level (the server removes the order as it removes an acknowledgment) or a cancel. Contributors and owners set levels, acknowledge and mark or cancel orders; viewers see the badges and the list. In the app only for now; an email digest is a later bead.
- **Export.** `user.isOwner()` is true for the team's owners, which shows the app's **Export data**; downloads are saved as `.csv` or `.json` files. The inventory CSV ends with **Reorder at** and **Usual order** (blank for an item without them), the same values the import's `reorder_at` and `reorder_qty` take, so an export can be edited and imported again.
- **Item brand** (supply-checkout-005.9). An item can have an optional brand (Add item and Edit item, at most 100 characters; blank removes it). The Inventory list and the pick list (Add item without a barcode) show it on its own line under the name; where the name has one line, it follows the name: "Paper towels · Brightleaf" in Check out and Quick take, and in a receipt line's inventory match list. The pick list's search matches it, the inventory CSV has a Brand column after Item (headers the CSV import reads), the JSON export has it as stored, and the receipt prompt lists it next to each name. A project's line copies only the name, as before.
- **Live updates.** One subscription to the user's own channel, `/users/<sub>` ([docs/api/realtime.md](api/realtime.md)). Events for other teams are ignored; each of the team's events is fetched through the API; both collections are re-listed after every subscribe, when the tab is shown again and every 10 minutes; the socket reconnects with backoff and with each new token; after three failed connects it polls every 15 seconds (60 while hidden) and retries the socket every 2 minutes. A 403 shows that the user was removed from the team.
- **Receipt reading** (`src/aws/receipts.js`, `supply-checkout-kx8`, ADR 0008). `use("sample")` sends the photo `src/photo.js` made (a JPEG or PNG of at most 1,500,000 bytes, else `image_rejected` without a request) as base64 to `POST /teams/{teamId}/receipts/read`, with a 40-second timeout instead of the usual 15 (the server gives the model 25) and the review's Stop as its abort signal: a Stop before the request goes out (while the photo is read, or during a token refresh) sends nothing, but one after only stops waiting, and the server's read still counts against the month. The server builds the prompt from the team's inventory, so the app's prompt isn't sent, and it answers `match` with product keys, which the result's `byKey` tells `src/main.js` (the artifact's model answers with the prompt's ids). Its reasons become the app's codes for `sampleErr`: `receipt_limit` (`trial_receipt_limit` when the last usage the server sent was a trial's), `rate_limited` (the person's own rate limit, `supply-checkout-wxx`: `receipt_rate`, shown in the server's words, which say how long to wait from the same value as its `Retry-After`, or that today's free trial scans are used up; the browser can't read `Retry-After` across origins), `model_busy` (`rate_limited`), `model_timeout` (`timeout`), `invalid_output` (`invalid_json`), `image_rejected`; a lost session is `session_expired`, anything else the general message. The capability's `usage()` reads `GET /teams/{teamId}/receipts/usage`, and `src/main.js` shows its label under the bar to those who can scan ("188 of 200 receipt scans left this month", "13 of 25 free trial receipt scans left"), updated from each read's own `usage` and read again after a limit refusal; when it can't be read there's no line and scanning still works. Owners also see the scans used in **Team settings** (`src/aws/settings.js`). The artifact build has no limits and shows neither. `RECEIPT_READING` in `src/aws/main.js` switches it off (sample is null and "Scan receipt" is hidden). The store, line names and printed text come from the model, so they're untrusted: the review and everywhere a saved name shows escape them (`esc`), and `tests/aws-receipts.spec.js` checks a name that looks like HTML stays text.
- **Not yet.** Checkout and return are the app's document writes (`src/moves.js`) until the atomic commands exist (`supply-checkout-1dg.1`). Other members' names aren't in the API yet, so their projects say "Someone".

**Trying it** once the identity, api and realtime stacks are deployed: `npm run build:web && npm run publish:web -- publish --channel app --dir dist/web --env <env>`, open `https://app.<env domain>/`, sign up, name a team, and check a project in two browsers at once. Outside prod, `http://localhost:5173` is also an allowed origin: `node scripts/publish-web.mjs config --env <env> > dist/web/config.json`, then `npx vite preview --mode web --port 5173`. There the refresh cookie (`SameSite=Strict`, on the API's site) isn't sent, so each reload signs in again.
