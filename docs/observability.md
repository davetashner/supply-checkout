# Observability

**Observability** (`lib/observability/`). Each region's `observability` stack has two SNS topics, `supply-checkout-<env>-alarms-p1` (email and SMS) and `-p2` (email), encrypted with a rotating KMS key, and the alarms from [docs/journeys.md](journeys.md) whose metrics exist ("Which alarms exist"). The primary region's stack also has the `supply-checkout-<env>` CloudWatch dashboard: traffic, errors, latency and every business metric, one line per region. An aspect (`lib/observability/defaults.ts`) gives every Lambda function X-Ray active tracing, JSON logs and the metrics namespace, and every log group a **one-year retention** unless it sets its own. One year is a placeholder until the information security policy (`supply-checkout-4p1`) sets it. Metric names come from `backend/src/observability/names.ts`, so the dashboard, the alarms and the code that sends the metrics can't drift apart.

**Scheduled checks** (`lib/observability/ops-checks.ts`, `backend/src/ops/`). Some alarms watch state no AWS metric shows, so the primary region's `observability` stack also has two small functions that an EventBridge rule runs every 10 minutes, each sending a gauge (a business metric read at its maximum): `supply-checkout-<env>-stuck-imports` counts CSV imports still committing an hour after they started (`StuckImports`, "Imports stuck"), and `supply-checkout-<env>-email-quota` sends SES's 24-hour sends as a share of its quota (`EmailQuotaUsedPercent`, "Near the sending limit"). The stuck-import check's role may only `Query` GSI1's `IMPORTS#COMMITTING` partition, naming only the keys and each job's progress (`dynamodb:LeadingKeys`, `dynamodb:Attributes`); the quota check's may only call `ses:GetAccount`. A failed run shows in the Functions failing alarm. The alarms on these gauges (and "Deletion overdue", below) are only in the primary region, where the checks run: their specs in `journey-alarms.ts` are `primaryOnly`, and every other journey alarm is in each region.

**Closed-team purge** (same construct, `backend/src/ops/team-purge-handler.ts`). Every hour, `supply-checkout-<env>-team-purge` deletes the teams whose 30 days after closing have passed ([backend.md](backend.md), "Purging closed teams"), starting no new team after 4 minutes (its timeout is 5), and counts them in `TeamsPurged`. A run where any team fails throws, so the Functions failing alarm sees it, and the team is tried again the next hour. Its role may `Query` only GSI1's `TEAMS#CLOSED` partition, and `GetItem`, `Query` (with `Select: SPECIFIC_ATTRIBUTES`, required by its own statement) and `DeleteItem` on `TEAM#*`, `USER#*` and `STRIPE#*` partitions, naming only `TEAM_PURGE_ATTRIBUTES` (keys, the closure fields, the Stripe customer and subscription, `stripeCancelledFor`, `stripeSetAsideFor`, `stripeSetAsideReason` and the link's team) and never returning old values, and `UpdateItem` on `TEAM#*` partitions naming only `TEAM_PURGE_MARK_ATTRIBUTES` (the META item's key, `purgeAfter`, `purging`, `stripeCancelledFor`, `stripeSetAsideFor` and `stripeSetAsideReason`, never `closedAt`, so it can't close or reopen a team), to mark a team before it deletes anything so it can't be reopened part-deleted, and to record that a closed team's Stripe subscription was set to end (or set aside for a person), with only `kms:Decrypt` and `kms:DescribeKey` on the table's key: it deletes whole items without reading documents, emails or names. The partitions are wildcards because it acts on whichever teams are due, which only the table's own index names. It may also read the one Stripe secret key for the environment and mode (`secretsmanager:GetSecretValue` on that secret's ARN, `STRIPE_SECRET_ID` and `STRIPE_MODE` in its environment): each run first sets closed teams' subscriptions to cancel at the period's end, and it deletes a team's Stripe customer before its items ([infrastructure](infrastructure.md#billing), "Closing a subscribed team"). A closed team whose subscription couldn't be ended also makes the run throw. A Stripe customer Stripe can't delete doesn't: the team is purged on schedule and the customer's deletion queued (`supply-checkout-8jc.42`), for which the role may also `PutItem`, `DeleteItem` and `Query` (`SPECIFIC_ATTRIBUTES`) the one `PURGE#STRIPE_DELETIONS` partition, naming only `STRIPE_DELETION_ATTRIBUTES` (the keys, `teamId`, `stripeCustomerId` and `queuedAt`; `dynamodb:LeadingKeys` exactly that partition, nothing returned). Every run retries the queue after purging and sends two gauges, `StripeCustomerDeletionsPending` and `StripeCustomerDeletionOldestHours` (the oldest entry's age, zero when it's empty), and a queue it can't read or clear makes the run throw. Every run that can read the index, even one where teams fail, also sends the `ClosedTeamsOverdue` gauge: the closed teams still there more than 24 hours after their deletion date (`PURGE_OVERDUE_AFTER_HOURS` in `backend/src/ops/names.ts`), counted with a `Select: COUNT` query on the closed-teams partition so it isn't capped at the 100 a run lists, zero included, so the privacy deadline has its own alarm ("Deletion overdue", above 0 at its maximum over two hours, so every period holds a run). When the gauge's samples stop for 3 hours (`PURGE_SILENT_ALARM_HOURS`), "Deletion job not running" alarms, missing data breaching: the schedule was disabled or deleted, or every run fails before it reads the index. It's in the primary region only, with the purge, and on the dashboard's alarm list. The dashboard's last row shows `TeamsClosed`, `AccountsDeleted` and `TeamsPurged`, and next to them `TeamClosedNotices` and `TeamClosedNoticeFailures`: owners emailed that their team closed, and owners who weren't (SES refused the message, no address on file, or the owners couldn't be listed). The team stays closed either way, and any failure over 15 minutes alarms ("Team closure emails failing"). The same row graphs `ClosedTeamsOverdue`, `ClosedTeamsSetAside` (the purge's gauge of closed teams set aside for a person, for "Closed-team subscription set aside"), `StripeCustomerDeletionsPending` and `StripeCustomerDeletionOldestHours`, and `EmailCodeSendFailures` and `EmailCodeVerifyFailures`. The dashboard's last row also graphs `ClosedTeamSubscriptionsEnded`, `ReopenedTeamSubscriptionsEnded`, `ReopenedTeamSubscriptionsResumed` (reopened teams' subscriptions resumed, by the worker's resync, the purge or the worker), `ReopenResyncsLate`, `ReopenedTeamSubscriptionsUndecided`, `ClosedTeamRenewalsCharged`, `ClosedTeamSubscriptionsNotFound`, `ClosedTeamSubscriptionsSetAside`, `StripeCustomersDeleted`, `StripeCustomersAlreadyDeleted`, `StripeCustomerDeletionsQueued` (purged teams whose Stripe customer deletion was queued) and `HeldTeamsPurged` (held teams the purge deleted 14 days after their deletion date with their subscription unresolved, for "Held team purged with its subscription unresolved"). It also shows `TeamsReopened` (closed teams an owner reopened before the purge) with `TeamReopenedNotices` and `TeamReopenedNoticeFailures`, the same emails for a reopening, which alarm the same way ("Team reopened emails failing").

**Nightly seat reconciliation** (same construct, `backend/src/ops/seat-reconcile-handler.ts`, `supply-checkout-l50`). At 07:00 UTC, `supply-checkout-<env>-seat-reconcile` lists the open teams with a Stripe customer from the operators' index and queues a seat check for each on the seat sync queue ([infrastructure](infrastructure.md#billing), Seats). The billing worker compares each subscription's seat quantity with the team's billed members; a mismatch counts `SeatQuantityDrift` and is fixed, and any drift in an hour alarms ("Seat counts drifting", P2, primary region only). The run sends the `SeatReconcileTeams` gauge (teams queued, zero included); when its samples stop for two days (`SEAT_RECONCILE_SILENT_ALARM_DAYS`), "Seat reconciliation not running" alarms (P2), missing data breaching, like "Deletion job not running". Invoke it once by hand after its first deploy, or that alarm fires before the first night. Its role may `Query` only GSI3's `OPS#TEAMS` partition, naming only the keys, `stripeCustomerId`, `closedAt` and `status` (`SEAT_RECONCILE_ATTRIBUTES`, with `Select: SPECIFIC_ATTRIBUTES`), decrypt the table key through DynamoDB, and `sqs:SendMessage` to the seat sync queue: no team partition and no Stripe key. A run where some messages weren't taken throws after queueing the rest, so the Functions failing alarm sees it. A seat sync the worker couldn't apply after 5 tries goes to the seat syncs dead-letter queue ("Seat syncs stuck", P2, every region). The same nightly messages carry the **entitlement check** (`supply-checkout-8jc.9`, `backend/src/billing/entitlements.ts`): the billing worker compares each team's subscription, status, plan and seats with Stripe's, applies Stripe's state where they differ, and counts `EntitlementDrift`; any in an hour alarms ("Entitlements drifting", P2, primary region only; what to do is in [journeys](journeys.md) and the [billing DLQ replay runbook](runbooks/billing-dlq-replay.md)). So the reconciliation also lists teams whose subscription has ended. The dashboard's J7 row graphs `SeatQuantityUpdates`, `SeatQuantityDrift`, `EntitlementDrift` and `SeatSyncQueueFailures` (membership changes whose sync couldn't be queued; the reconciliation fixes those), and `SeatReconcileTeams`.

**Receipt reading** (`supply-checkout-kx8`, [backend.md](backend.md)). The `receipts` function answers a failed model call (502 `invalid_output`, 503, 504 `model_timeout`, 429 `model_busy`, 400 `image_rejected` from Bedrock) rather than throwing, and counts it in `ReceiptReadFailures` next to `ReceiptReads`, which the **Receipt reading failing** alarm compares (above 10% over 15 minutes, at least 5 reads, P2). Its 5xx answers also count toward the API errors alarm. The dashboard's J5 row shows reads, failures and lines, the tokens (`ReceiptTokens`, the team ID in each log line's metadata, for cost per team in Logs Insights) and the model call's p95 in milliseconds (`ReceiptReadLatency`). The Bedrock alarms in journeys.md (throttled, errors, slow, cost spike) aren't built yet.

**Alarms on failures nothing throws for.** Some failures are answered or logged without failing a function, so the Functions failing and API errors alarms don't see them, and each has a business metric and an alarm of its own ([journeys.md](journeys.md) has each one's threshold and what to do): sign-outs not revoked, email verification not saved, **Email codes failing** (`EmailCodeSendFailures` + `EmailCodeVerifyFailures`, the 5xx answers of `POST /me/email/code` and `POST /me/email/verify`, too few for the API's 2% to notice; 3 or more in 15 minutes), **Live updates deferred** (`LiveUpdatesDeferred`, events the stream consumer's publish budget left for its next invocation; any in each of 3 consecutive 5-minute periods, so a single burst doesn't alarm), Security notices failing, Team closure emails failing, Team reopened emails failing, **Reopened team's subscription ended** (`ReopenedTeamSubscriptionsEnded`, a team reopened while the billing worker or the purge was ending its subscription, which couldn't be resumed at once, or one set to end whose team couldn't be read again afterwards, so a reopen can't be ruled out (`supply-checkout-8jc.30`); the worker's event is retried and then applies, so no dead-letter queue sees it), **Reopened team's billing not resynced** (`ReopenResyncsLate`, a reopened team the nightly reconciliation found still waiting for its Stripe subscription to be resynced, `supply-checkout-85qp`; primary region only), **Reopened team's subscription left to cancel** (`ReopenedTeamSubscriptionsUndecided`, a reopened team's subscription set to cancel that the resync couldn't attribute to the closure or the owner, left for a person), **Closed team charged** (`ClosedTeamRenewalsCharged`, a closed team's subscription charged for a period after it closed, which the purge only logs as a warning; primary region only), **Closed-team subscription not found in Stripe** (`ClosedTeamSubscriptionsNotFound`, a closed team's subscription Stripe says doesn't exist, which the purge sets aside rather than retry; a Stripe key or mode mismatch would look like that for every team; primary region only), **Closed-team subscription set aside** (the `ClosedTeamsSetAside` gauge, the closed teams the purge stopped retrying so they can't crowd newer closures out of its listing: another customer's subscription, one Stripe doesn't have, or one Stripe refused with an error retrying won't change; sent every run, so the alarm stays on until each is dealt with, and those teams aren't purged meanwhile; primary region only), **Many closed-team subscriptions set aside** (P1, the same gauge at 5 or more, most likely a Stripe key or mode mismatch, or set-asides left uncleared; primary region only), **Stripe customer already deleted** (`StripeCustomersAlreadyDeleted`, a purged team's customer Stripe said was already gone, which the purge takes as deleted but a key or mode mismatch looks the same; primary region only), **Stripe customer deletion retrying** (P2) and **Stripe customer deletion stuck** (P1) (the `StripeCustomerDeletionOldestHours` gauge above 24 hours and above 7 days at its maximum over two hours: a purged team's Stripe customer that couldn't be deleted with its data and still hasn't been on the hourly retries, `supply-checkout-8jc.42`; missing data doesn't breach, since a run that can't read the queue fails and Functions failing sees it; primary region only) and Deletion overdue. A spec in `journey-alarms.ts` sets `periods` for a rule that must hold for several periods in a row (evaluation periods and datapoints to alarm both).

**The web app down** (`lib/observability/web-alarms.ts`, `supply-checkout-3sv.2`). CloudFront publishes its metrics only in us-east-1 (with `Region=Global`), so the `observability` stack there (`GLOBAL_SERVICES_REGION`, the primary region in the MVP) has two P1 alarms on the web distribution, reading its ID and the router function's name from the web stack's SSM outputs (`/supply-checkout/<env>/web/distribution-id` and `/web/router-function-name`); that stack deploys after the web stack. **Site down** (`supply-checkout-<env>-p1-site-down`) fires when the distribution's `5xxErrorRate` is above 1% over 5 minutes, but only once it has 50 requests in those 5 minutes (metric math, `IF(r >= 50, e, 0)`), so one error on a quiet night doesn't page. **Web router failing** (`-p1-web-router-failing`) fires on 5 or more of the router's `FunctionExecutionErrors`, `FunctionValidationErrors` and `FunctionThrottles` in 5 minutes: a broken router fails every request, so this catches it when traffic is too light for Site down, and says where to look. Both are on the dashboard's alarm panel, with a row of CloudFront graphs (requests, the 5xx rate, the router's errors and throttles). Runbook: [When the web app is down](#when-the-web-app-is-down). The same construct has the RUM cost guard (`supply-checkout-3sv.7`): **RUM events surge** (`-p2-rum-events-surge`) and **RUM events flood** (`-p1-rum-events-flood`), on the events the RUM app monitor ingests in an hour (`AWS/RUM` `RumEventPayloadSize`, `SampleCount`, dimension `application_name`), above 100,000 (`RUM_EVENTS_SURGE_PER_HOUR`, $1 an hour) and 1,000,000 ($10 an hour). Honest traffic is far below the first: at most 200 events a session, and a few hundred sessions a day. Both are on the alarm panel too. Runbook: [When RUM events surge](#when-rum-events-surge).

**Operator pool changes** ([ADR 0015](adr/0015-platform-operator-role.md)). The primary region's `observability` stack also has EventBridge rules on CloudTrail's management events that send the P1 topic a message naming the CloudTrail event (not the person): user, membership, password and MFA changes and deleted operators on the operator pool, whoever makes them (CloudFormation included), and pool, client and group settings changes and operators disabled or signed out everywhere that CloudFormation didn't make (`supply-checkout-6uw.16`); what an operator's own token can change (TOTP, MFA preference, attributes, deleting the user); changes that would silence the operator audit watch, its alarms or the alarm topics (those on the topics, their key or CloudTrail also go to P2); changes to who the alarms reach, which go to P2 only, deploys included ([Alarm recipients](#alarm-recipients), `supply-checkout-6uw.23`); changes to the trail's bucket or key that would destroy or cut off the log archive (`supply-checkout-3sv.4`); and deleting, disabling or retargeting any of those rules, all named `supply-checkout-<env>-operator-*`. Only those rules may publish to the topic. Every rule on CloudTrail's events, these and the backup and deletion records ones, needs the account's trail logging: the primary region's `audit` stack has it ([The CloudTrail trail](infrastructure.md#the-cloudtrail-trail)). Without a trail, EventBridge receives no `AWS API Call via CloudTrail` events and the rules never fire. The first copy of management events is free; the trail's bucket and key cost about a dollar a month. Each event pattern stays well inside EventBridge's 2,048-character limit, which a test checks for every rule in every stack (`supply-checkout-pbp.17`). The full list is under [Operators](infrastructure.md#operators).

**Operator audit watch.** `supply-checkout-<env>-operator-audit-watch` (primary region) reads the table's stream, filtered to changes and deletions of `OPAUDIT#` items, new `AUDIT#` entries and its heartbeat item, and counts each change that isn't a TTL expiry, and each new entry set to expire more than a week short of its 2 years, in `OperatorAuditChanged`. **Operator audit changed** (P1) fires on any, **Operator audit watch failing** (P2) on any error of the function, **Operator audit watch dropped records** (P2) on any batch in its dead-letter queue, and **Operator audit watch silent** (P2) when it hasn't counted its heartbeat (an item a schedule rewrites every 10 minutes) in `OperatorAuditWatchHeartbeat` for 30 minutes, so anything that stops it reading the stream shows. All four are on the dashboard's alarm panel, and both metrics have graphs in the last row. See [Operators](infrastructure.md#operators).

**Operator group watch** (`supply-checkout-3sv.5`). `supply-checkout-<env>-operator-group-watch` (primary region) lists the operator pool's `operators` group every 5 minutes and compares it with what it saw last (an SSM parameter): each operator added, removed, disabled or enabled counts in `OperatorGroupChanged`, a snapshot it has to start again (the deploy's initial value, or one it can't read) in `OperatorGroupBaselineReset`, and **Operator group changed** (P1) fires on either, so the first deploy, and any deploy that changes its parameter, pages once. It exists because `AdminAddUserToGroup` and `AdminRemoveUserFromGroup` never reached EventBridge in the drill, though the trail had them. **Operator group watch silent** (P2) fires when no run has finished (`OperatorGroupMembers`) in 15 minutes. Both are on the alarm panel, and its metrics share a graph in the last row. See "Why group changes have their own watch" under [Operators](infrastructure.md#operators).

**Deletion records watch** ([backups.md](backups.md#when-a-deletion-record-is-rewritten)). `supply-checkout-<env>-deletion-records-watch` (primary region, `lib/observability/deletion-records-watch.ts`, `backend/src/deletions/watch-handler.ts`) gets the deletion records bucket's S3 events from EventBridge (writes, and deletions other than lifecycle expirations) and counts in `DeletionRecordRewrites` a record written over, deleted or hidden behind a delete marker, or an object that isn't a record. **Deletion record rewritten** (P2) fires on any in 5 minutes, and **Deletion records watch failing** (P2) on any error of the function, any event Lambda dropped after its retries (`AsyncEventsDropped`), or any invocation EventBridge couldn't make (`FailedInvocations`). A third rule, `DeletionRecordsWatchBucketChanges`, tells P1 when the bucket's lifecycle, notifications, policy, replication, ownership, public access, Object Lock or versioning changes (any of which could silence the watch), and `supply-checkout-<env>-deletions-rule-tampering` watches both of the watch's rules the way the operator rule-tampering rules watch theirs (and they watch it); the P1 topic lets the bucket rule publish by its ARN. Both are on the dashboard's alarm panel, and the metric has its own graph in the last row. Runbook: [When a deletion record is rewritten](backups.md#when-a-deletion-record-is-rewritten).

**Support SMTP user** ([Support email](infrastructure.md#support-email), `supply-checkout-6qd`, `lib/observability/support-smtp-watch.ts`). Prod with `supportMail` only. The IAM user whose SES SMTP key Gmail uses to send support replies can send any mail the domain identity can, so both its changes and its use alert P2:
- `supply-checkout-<env>-operator-support-smtp-user` (GLOBAL_SERVICES_REGION, where CloudTrail delivers IAM's events) tells P2 on calls naming the user, matched without regard to case (IAM names aren't case-sensitive): `CreateAccessKey`, `UpdateAccessKey`, `DeleteAccessKey`, `PutUserPolicy`, `AttachUserPolicy`, `AddUserToGroup`, `CreateLoginProfile`, `UpdateLoginProfile`, `PutUserPermissionsBoundary`, `DeleteUserPermissionsBoundary`, `UpdateUser` (a rename would take the user out of both alerts; the event carries the old name), `CreateServiceSpecificCredential`, `UploadSigningCertificate` and `UploadSSHPublicKey`; and on `CreatePolicyVersion` and `SetDefaultPolicyVersion` on its boundary policy, which would widen the boundary in place. Whoever makes them, CloudFormation included. Expect it when the owner rotates the key, and on a domain deploy that changes the user's policy or boundary (not on the first deploy, when the observability stack's rule doesn't exist yet). The P2 topic lets only this rule, by ARN, publish. It's named under the operator prefix, so the operator rule-tampering rules watch it: they're in the primary region and it's in GLOBAL_SERVICES_REGION, the same region for prod (a test checks).
- **Support SMTP sends** (`supply-checkout-<env>-p2-support-smtp-sends` and `-p2-support-smtp-daily-sends`, primary region) fire when the user sends more than 50 messages in an hour, or more than 150 in a day (a slower leak): SES's `Send` metric in `AWS/SES` with the dimension `ses:caller-identity` = the user's name, which the transactional configuration set's `SendsByCaller` CloudWatch event destination publishes (every send through the set is counted by its IAM identity; mail without one counts as `none`). One person answering support sends far fewer.

Runbook for both: [When the support SMTP key may be leaked](infrastructure.md#when-the-support-smtp-key-may-be-leaked).

**Backup alerts** ([backups.md](backups.md#alerts-on-the-backups)). The backup stack's P2 alarms (Backup failed, No recent backup, and with the copy Deletion records not replicated and Deletion records replication stuck, a record pending or an hour behind for an hour: [When deletion records stop replicating](backups.md#when-deletion-records-stop-replicating)) go to the P2 topic. Its two EventBridge rules, `supply-checkout-<env>-backup-changes` and `-backup-key-changes`, tell the P1 topic when a vault's access policy or lock, the plan, a selection or the vault key is changed or deleted; the P1 topic lets those two rule names publish, and no other rule but the operator-pool ones. The backup account's vault stack has its own encrypted topic, `supply-checkout-<env>-backup-alerts`, emailed to that account's `/supply-checkout/<env>/alarms/email-<n>` parameters (see below), with the same two rules there, a third, `supply-checkout-<env>-backup-vault-deletions-copy-changes`, on changes to the deletion records copy's bucket policy, ownership controls, Object Lock configuration or versioning ([When backups are tampered with](backups.md#when-backups-are-tampered-with)), and a `supply-checkout-<env>-backup-copies-missing` alarm.

**Cost alerts** (`lib/observability/cost-alerts.ts`, `supply-checkout-jxq`). The `observability` stack in `GLOBAL_SERVICES_REGION` (us-east-1) has the account's monthly cost budget, `supply-checkout-<env>-monthly`, and a Cost Anomaly Detection monitor, `supply-checkout-<env>-services` (every AWS service's cost, `DIMENSIONAL`/`SERVICE`), with its subscription `supply-checkout-<env>-anomalies`. Both email the P2 recipients through the P2 topic: a cost surprise isn't worth waking anyone for. The budget alerts at 50%, 80% and 100% of the month's actual spend and when the forecast passes 100%; it counts gross cost (credits and refunds excluded), so promotional credits can't hide a runaway cost until they run out. The anomaly subscription is `IMMEDIATE` (SNS subscribers must be) and alerts on an anomaly with a total impact of at least the threshold. Budgets and Cost Explorer are account-wide, not regional, and Cost Explorer's API is only in us-east-1, so they're in that one stack, not one per region; if us-east-1 ever stopped being a deployed region, they'd go with it, like the web alarms. Both services publish as AWS service principals, so the P2 topic's policy lets `budgets.amazonaws.com` (`AllowBudgetsToPublish`) and `costalerts.amazonaws.com` (`AllowCostAnomaliesToPublish`) publish, and the topics' KMS key lets them `kms:Decrypt` and `kms:GenerateDataKey*`, each only with `aws:SourceAccount` this account and `aws:SourceArn` this account's budgets (`arn:aws:budgets::<account>:*`) or anomaly subscriptions (`arn:aws:ce::<account>:anomalysubscription/*`); the P1 topic doesn't allow them. The budget and subscription depend on the topic's policy, since both services check they may publish when they're saved.

**The amounts are placeholders for the owner to set.** The defaults are `DEFAULT_MONTHLY_BUDGET_USD` (**$100** a month) and `DEFAULT_COST_ANOMALY_USD` (**$20** of impact) in `cost-alerts.ts`, a guess for a pre-launch account. Change them there, or per deploy with `-c monthlyBudgetUsd=150 -c costAnomalyUsd=25` (or the same keys in `cdk.json`'s context). Each must be above 0 and at most $10,000. Deploying, and testing an alert: [When a cost alert arrives](#when-a-cost-alert-arrives).

Logging and business metrics in the Lambda code are in [Backend](backend.md).

## Front-end errors (CloudWatch RUM)

`supply-checkout-al0`. The `web` stack (`lib/web/rum.ts`, in `GLOBAL_SERVICES_REGION` with the distribution) has the CloudWatch RUM app monitor `supply-checkout-<env>-app` for `app.<env domain>`, which the web build reports to ([The web app on AWS](web-app.md#the-web-app-on-aws)): JavaScript errors and page performance from real users, each event tagged with the release version. Telemetries are `errors` and `performance` only (no `http`, whose URLs carry team and document IDs, no clicks, no session replay), with cookies, X-Ray and custom events off, and every session sampled (`RUM_SESSION_SAMPLE_RATE`, lower it when traffic grows: RUM costs $1 per 100,000 events and the app's client sends at most 200 a session, in batches of at most 100). Events stay in RUM for 30 days; nothing goes to CloudWatch Logs. Source maps aren't uploaded, so stack traces point into the minified assets of that release.

- **Identity pool** `supply-checkout-<env>-rum`: guest (unauthenticated) identities only, no identity providers, the classic flow off. In the enhanced flow Cognito adds its own session policies on top of the role.
- **Guest role** `supply-checkout-<env>-rum-guest`: trusts only `cognito-identity.amazonaws.com` with `aud` this pool and `amr` `unauthenticated`, and has one statement, `rum:PutRumEvents` on this app monitor's ARN. cdk-nag's AwsSolutions-COG7 (guest identities) is acknowledged on the pool for that reason.
- **Abuse and cost.** The sample rate, the 200-events-a-session limit and the batch limit are the RUM client's settings, so they only bound honest clients. The pool's ID is in `config.json` by design, so anyone can get guest credentials and send events to the app monitor directly, as many as RUM's and Cognito's own throttling allow, and each is billed. They can't read anything or reach any other resource. RUM events surge (P2) and RUM events flood (P1) alarm on the events ingested in an hour ([When RUM events surge](#when-rum-events-surge)).
- **Outputs** under `/supply-checkout/<env>/web/`: `rum-app-monitor-id`, `rum-identity-pool-id` and `rum-region`, which `scripts/publish-web.mjs` copies into the app's `config.json`.

To see a release's errors, open the app monitor in the CloudWatch console (**Application Signals → RUM**) and filter **Errors** by version. To check it after a deploy, publish the app, open it, and run `setTimeout(() => { throw new Error("rum-verify") })` in the browser console; the error shows within a minute or two.

## Alarm recipients

**Alarm recipients.** The addresses and phone numbers aren't in this repository. Each one is an SSM parameter in the account, in every region with an `observability` stack (today, us-east-1), which CloudFormation reads at deploy time: `/supply-checkout/<env>/alarms/email-<n>` and `/supply-checkout/<env>/alarms/sms-<n>`, numbered from 1. Email recipients get P1 and P2 alarms; SMS recipients get P1 only. By default there is one of each; for more, pass `-c alarmContacts='{"email":2,"sms":2}'` (or set `alarmContacts` in `cdk.json`: it holds counts, nothing personal). Create the parameters before the first deploy of the stack, or the deploy fails:

```bash
aws ssm put-parameter --profile supply-prod --region us-east-1 --type String \
  --name /supply-checkout/prod/alarms/email-1 --value 'you@example.com'
aws ssm put-parameter --profile supply-prod --region us-east-1 --type String \
  --name /supply-checkout/prod/alarms/sms-1 --value '+15555550100'   # E.164
```

The backup account's vault stack reads the same `email-<n>` parameters from the backup account, so create them there too (see [backups.md](backups.md#setting-it-up)).

They must be `String`, not `SecureString`: CloudFormation can't resolve a `SecureString` into a subscription. To change a recipient, overwrite the parameter (`--overwrite`) and redeploy the observability stack. If the CDK reports no changes (the template is the same; only the parameter's value moved), deploy with `--force`.

**Editing a recipient sends P2 email, by design** (`supply-checkout-6uw.23`). Any change to a parameter under `/supply-checkout/<env>/alarms/` (put, delete, label), by anyone, emails the P2 recipients through the `supply-checkout-<env>-operator-alarm-recipients` rule, and the deploy that follows emails them again, once for each subscription it makes and once for each it removes (`-operator-alarm-subscriptions`). Expect those messages when you change a recipient; one nobody expected means someone may be rerouting the alarms (see [Operators](infrastructure.md#operators) for what to do). Neither exempts CloudFormation, and neither pages P1. The order matters: the subscriptions change only when the stack deploys, so the first email, sent when the parameter is written, goes to the recipients from **before** the change, the one being replaced included. At the deploy, CloudFormation subscribes the new address before it unsubscribes the old one, so the old recipient usually gets the email about the new subscription too; the email about removing the old subscription reaches only those still subscribed. SMS recipients get no P2 email, so a change to an `sms-<n>` parameter is announced to the email recipients. The messages name the call and the CloudTrail event, never the address or number.

After deploying, confirm each email subscription from the message AWS sends. Confirmed by its link, a subscription can be cancelled by anyone who has one of its emails, through the unsubscribe link at the bottom, without signing in. To require an AWS sign-in for that, confirm with the CLI instead of the link, using the token in the confirmation link's URL: `aws sns confirm-subscription --topic-arn <topic ARN> --token <token> --authenticate-on-unsubscribe true`. CloudFormation and CDK can't set it. SMS needs a new account out of the way first: in the SNS console, **Text messaging (SMS)**, add and verify each number under **Sandbox destination phone numbers**, and check the monthly SMS spending limit. Sending to US numbers can also need an origination identity (a toll-free number registered in AWS End User Messaging SMS, which takes days to approve); if the test text doesn't arrive, that's the likely cause. Then page yourself with any P1 alarm; it goes back to OK (and says so) on its next evaluation:

```bash
aws cloudwatch set-alarm-state --profile supply-prod --region us-east-1 \
  --alarm-name supply-checkout-prod-p1-checkout-broken \
  --state-value ALARM --state-reason "Testing the P1 page"
```

## When the web app is down

**Site down** or **Web router failing** fired: `app.` or `/demo/` is answering 5xx. On 2026-09-27 a web stack deploy shipped a router function CloudFront couldn't run, and every request got a 503 for 90 minutes.

1. **See it.** `curl -sI https://app.supplycheckout.com/` and `curl -sI https://supplycheckout.com/demo/` (use the environment's domain). A 503 with `retry-after: 60` is the router's own answer: nothing is live on that channel (step 4). Any other 5xx, or a 503 without it, is the router or the origin.
2. **Run the router.** `npm run publish:web -- check-router --env <env>` runs the router's LIVE stage (`aws cloudfront test-function`) on a request to each host and prints CloudFront's error message if it fails (a `SyntaxError`, say). Web router failing without a failing check-router is usually throttling: see the router's graph on the dashboard.
3. **Roll back a bad web deploy.** CloudFront Functions keep no old versions, so redeploy the web stack from the last commit that worked, then deploy it again from main once the fix is merged:

   ```bash
   git log --oneline -- infra/lib/web infra/lib/stacks/web-stack.ts   # the change before the bad one
   git worktree add ../web-rollback <good commit>
   cd ../web-rollback/infra && npm ci
   npx cdk deploy supply-checkout-<env>-us-east-1-web --exclusively --profile supply-prod
   cd - && npm run publish:web -- check-router --env <env>
   git worktree remove ../web-rollback
   ```

   `--exclusively` deploys only the web stack, not the older commit's copy of the stacks it depends on. Don't fix the function by hand in the console: the next deploy puts the template's code back.
4. **Nothing live, or a bad release.** `npm run publish:web -- status` shows each channel's live version. `none` (or a missing key) is a 503 by design: activate a release. If a new release is the problem, roll back to the previous one with `npm run publish:web -- activate --channel <app|demo> --version <previous>`; it reaches every edge in seconds.
5. **The origin.** If the router works and a release is live, CloudFront can't read the bucket: check the AWS Health Dashboard for CloudFront and S3 in us-east-1, and that the release's files are in `s3://<bucket>/releases/<version>/`.

The alarm recovers on its first 5-minute period below the threshold. After a web stack deploy, run `check-router` every time, so a bad router is caught before customers see it. To test the page without breaking anything, `aws cloudwatch set-alarm-state --alarm-name supply-checkout-<env>-p1-site-down --state-value ALARM --state-reason "Drill"` (see [Alarm recipients](#alarm-recipients)).

## When RUM events surge

**RUM events surge** (P2, more than 100,000 events in an hour) or **RUM events flood** (P1, more than 1,000,000) fired: the RUM app monitor `supply-checkout-<env>-app` is ingesting far more events than real users send, and each is billed ($1 per 100,000). The identity pool's ID is public, so anyone can get guest credentials and call `rum:PutRumEvents` directly.

1. **See it.** Open the app monitor in the CloudWatch console (**Application Signals → RUM**): a sudden jump in sessions or errors from one browser, a version that isn't a release, or pages that aren't the app's point to someone sending events by hand. A release whose error loops on every page is the honest cause: its events carry its version, and each session stops at 200, so it rises with traffic rather than all at once. For that one, roll back the release (`npm run publish:web -- activate --channel app --version <previous>`) and stop here.
2. **Stop new credentials.** Turn off guest identities on the pool, so no one can get new credentials. The app keeps working; it just stops reporting its errors.

   ```bash
   POOL=$(aws ssm get-parameter --profile supply-prod --region us-east-1 --name /supply-checkout/<env>/web/rum-identity-pool-id --query Parameter.Value --output text)
   aws cognito-identity update-identity-pool --profile supply-prod --region us-east-1 --identity-pool-id "$POOL" \
     --identity-pool-name supply-checkout-<env>-rum --no-allow-unauthenticated-identities --no-allow-classic-flow
   ```

3. **End the credentials already out.** Guest credentials last an hour. To end them now, revoke the guest role's sessions: in the IAM console, open the role `supply-checkout-<env>-rum-guest`, **Revoke sessions**. It adds an inline policy (`AWSRevokeOlderSessions`) that denies every call made with credentials issued before now.
4. **Watch it stop.** The alarm recovers on the first hour below the threshold. Check the app monitor's billed events in Cost Explorer (service CloudWatch) the next day.
5. **Rotate the identity pool, if it starts again.** Turning guest identities back on hands out credentials to whoever asks, including the same sender. A new pool gets a new ID, which only slows down a sender that has the old one written in; it's public again in the next `config.json`. Rename the pool in `lib/web/rum.ts` (`identityPoolName`) so CloudFormation replaces it, deploy the web stack, then republish the app (`npm run publish:web`) so `config.json` carries the new ID. While the abuse goes on, leave guest identities off and live without front-end errors.
6. **Turn it back on.** When it has stopped, run step 2's command with `--allow-unauthenticated-identities`, and delete the revoke policy (`aws iam delete-role-policy --role-name supply-checkout-<env>-rum-guest --policy-name AWSRevokeOlderSessions`). A web stack deploy doesn't undo either change by itself: CloudFormation only sets what its template changes.

There's no switch that turns an app monitor off. Deleting it (`aws rum delete-app-monitor`) stops ingestion at once but loses its 30 days of data, and CloudFormation still thinks it's there until the web stack is deployed with a change to it; prefer the steps above.

## When a cost alert arrives

A P2 email from AWS Budgets (`supply-checkout-<env>-monthly`: actual spend past 50%, 80% or 100% of the month's budget, or the forecast past 100%) or from Cost Anomaly Detection (`supply-checkout-<env>-anomalies`: one service's spend well above its usual pattern, by at least the threshold). Each budget threshold alerts once a month.

1. **See it.** Open **Billing and Cost Management → Cost Explorer**, this month, grouped by **Service**, then by **Usage type** for the service that jumped. An anomaly email links to the anomaly, with its root causes (service, region, usage type).
2. **Find the cause.** Usual suspects here: RUM events ([When RUM events surge](#when-rum-events-surge)), SES sends (Near the sending limit), Lambda or DynamoDB from a loop or a flood of requests (the dashboard's traffic row, and the WAF's blocked requests), CloudWatch Logs ingestion from a noisy function, and SMS (the account's SMS spending limit caps it).
3. **Stop it**, at its source: roll back the release, block the traffic, or turn the feature off. Then raise the budget only if the new spend is expected (below).
4. **Record it** on a bead, with the cause and the cost.

**Deploying the cost alerts.** They're in the us-east-1 `observability` stack, so `npm run deploy -- api` deploys them (with `--all` on a first deploy). Before the first deploy, check whether the account already has an AWS services monitor: an account may have only one, and AWS makes one (`Default-Services-Monitor`) for some accounts on its own, in which case the deploy fails creating `supply-checkout-<env>-services`:

```bash
aws ce get-anomaly-monitors --profile supply-prod --region us-east-1 \
  --query 'AnomalyMonitors[].[MonitorName,MonitorType,MonitorDimension,MonitorArn]' --output table
```

If one with type `DIMENSIONAL` and dimension `SERVICE` is there, either delete it (and its subscriptions, `aws ce get-anomaly-subscriptions`, then `aws ce delete-anomaly-subscription` and `aws ce delete-anomaly-monitor --monitor-arn <arn>`), which loses only its learned history (a new monitor needs about 10 days of history before it finds anomalies), or keep it and subscribe to it instead: put `"costAnomalyMonitorArn": "<its ARN>"` in `infra/cdk.context.json` in the main checkout (gitignored, so it applies to every deploy and the ARN, which has the account ID, never reaches the repo). Every deploy needs it from then on: a deploy without it would try to create the monitor and fail.

**Testing an alert.** Neither service has a "send a test" button, and only the service itself can publish as its principal, so test the whole path with a tiny budget. With some spend this month, deploy the observability stack once with a budget it has already passed:

```bash
cd infra && npx cdk deploy supply-checkout-prod-us-east-1-observability --exclusively \
  --profile supply-prod -c backupCopy=false -c monthlyBudgetUsd=1
```

Budgets checks spend a few times a day, so within about 12 hours the P2 recipients get the 50%, 80% and 100% emails. If they don't, look at the P2 topic's `NumberOfNotificationsFailed` metric in CloudWatch (a key policy problem shows there) and the budget's alert status in the Budgets console. Then deploy again without `-c monthlyBudgetUsd` (or with `npm run deploy -- api`) to put the real amount back. The anomaly subscription uses the same topic, key and kind of policy, so a working budget alert shows that path works too; its first real alert can only come once the monitor has history.
