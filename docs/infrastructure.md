# Infrastructure

`infra/` is the AWS CDK v2 app for the subscription product ([ADR 0002](adr/0002-serverless-aws-with-cdk.md)). It is a separate npm package with its own lockfile, so run its commands from `infra/` (or with `npm --prefix infra run …`).

```bash
cd infra
npm ci
npm run lint        # tsc type-check and ESLint
npm test            # vitest: config, stack layout, template snapshots, cdk-nag (every stack in each region)
npm run synth       # cdk synth; cdk-nag AwsSolutions fails it on any finding
npm run synth:all-regions  # the same for every approved region (-c regions=all)
npm run test:update # accept template snapshot changes after reviewing them
```

**Stacks.** Every stack is named `supply-checkout-<env>-<region>-<component>`. Each region in the environment gets `domain` (certificates, DNS records and the SES domain; see [Domain and email](#domain-and-email)), `data` (stateful: table, keys, buckets), `api` and `realtime` (stateless), and `observability`. The primary region also gets `identity` (stateful: Cognito), `backup` (stateful: AWS Backup for the table, copied to a separate backup account; see [Backups and restores](backups.md)), `audit` (stateful: the account's CloudTrail trail; see [The CloudTrail trail](#the-cloudtrail-trail)) and `email` (bounce and complaint handling; see [Transactional email](#transactional-email)). `GLOBAL_SERVICES_REGION` gets `web` (CloudFront and WAF, which AWS requires there; see [Web hosting and releases](web-app.md#web-hosting-and-releases)), and its `observability` stack has the account's cost budget and cost anomaly alerts, which are account-wide ([When a cost alert arrives](observability.md#when-a-cost-alert-arrives)), and always has a `domain` stack, because CloudFront, Cognito and AppSync only accept certificates from there. Stateful stacks have termination protection. Every stack writes `/supply-checkout/<env>/<component>/stack` to SSM Parameter Store, and later stacks publish their outputs beside it. All resources are tagged `app=supply-checkout`.

**Regions.** The MVP runs in **us-east-1 only**. Every stack takes its region as a parameter, and the tests and CI also synthesize us-west-2 (`synth:all-regions`), so turning on the second region from [ADR 0010](adr/0010-multi-region-active-active.md) is a config change: add it to `DEFAULT_REGIONS` in `lib/config.ts`. CDK is already bootstrapped in us-west-2. `lib/config.ts` is the only file in `infra/`, `backend/` or `src/` that may name a region: it holds `APPROVED_REGIONS`, `DEFAULT_REGIONS` and `GLOBAL_SERVICES_REGION` (where AWS requires CloudFront's certificate and WAF, and where Cognito lives). Stacks get their region as a parameter, Lambdas read `AWS_REGION`, and tests import the constants. `npm run check:regions` (in CI and the pre-commit hook) enforces this.

**Parameters.** The environment and regions are CDK context (`cdk.json` sets `envName=prod`; `regions` defaults to `DEFAULT_REGIONS` and `primaryRegion` to the first of them); override them with `-c envName=staging -c regions=all` (or a comma-separated list, with `-c primaryRegion=...`). Only the regions in `APPROVED_REGIONS` (`lib/config.ts`) are allowed. The account ID is never committed: it comes from the AWS profile at synth time, and a synth without credentials (CI, tests) is account-agnostic.

**The `app` table.** The primary region's `data` stack holds the single DynamoDB table from [ADR 0005](adr/0005-multi-tenant-dynamodb.md), `supply-checkout-<env>-app`. It's a `TableV2` (`AWS::DynamoDB::GlobalTable`) with one replica, in its own region: on-demand, encrypted with a customer-managed KMS key that rotates yearly, point-in-time recovery, deletion protection, a stream with new and old images, TTL on `expiresAt`, and one index, `GSI1`. Adding the us-west-2 replica in phase 2 is another entry in `replicas` with that region's key, not a new table. The data stack publishes `table-name`, `table-arn`, `table-stream-arn` and `table-key-arn` to SSM under `/supply-checkout/<env>/data/`. The key and index names come from `backend/src/data/schema.ts`, so the table and the code that reads it can't drift apart.

**cdk-nag.** `AwsSolutionsChecks` is registered as a CDK validation plugin, so every synth and deploy fails on an unacknowledged finding. When a finding is intended, acknowledge it on the narrowest construct with a written reason:

```ts
Validations.of(bucket).acknowledge({ id: "AwsSolutions-S1", reason: "…why this is safe…" });
```

## Deploying

A release deploys the stateless and stateful stacks to prod through the deploy workflow, after the owner approves its plan and then each change ([Deploying a release](releases.md#deploying-a-release)). The script below is the manual and break-glass path, and the way to deploy what the workflow doesn't yet (the web stack, the web app). For those, from the main checkout on an up-to-date, clean `main`:

```bash
npm run deploy -- api      # the api, realtime and observability stacks (new routes, Lambda code, alarms)
npm run deploy -- web      # the web stack, then check-router
npm run deploy -- app      # build the web app, publish it to app., make it live, check-router
npm run deploy -- all      # web, then api, then app
```

`scripts/deploy.sh` refuses any branch but `main`, uncommitted changes, and a `main` that isn't `origin/main`, so what goes out is what's merged. It runs `aws sso login` if the session has expired, installs the backend's and infra's dependencies (the synth bundles the Lambda code), shows `cdk diff` for each group of stacks and asks before deploying it, and deploys only those stacks (`--exclusively`, chosen by kind, `supply-checkout-<env>-*-api`, from `scripts/deploy-stacks.mjs`, which the deploy workflow uses too, so the two can't drift); CDK still asks about IAM and security group changes. It passes `-c backupCopy=false` until the backup copy vault's parameter exists (below). Options: `--env`, `--profile` (default `supply-prod`), and `--yes` to skip its own questions. Other stacks (domain, identity, data, email, audit, backup) and a first deploy use the commands below.

Until the pipeline in [ADR 0012](adr/0012-cicd-releases-rollbacks.md) takes over: before the first deploy, create the SSM parameters the stacks read: the hosted zone and DMARC report address ([Domain and email](#domain-and-email)), the alarm recipients ([Observability](observability.md#alarm-recipients)) and, only when the backup account exists, its vault ARN ([Setting it up](backups.md#setting-it-up)). The MVP has none and deploys with `-c backupCopy=false` ([ADR 0003](adr/0003-aws-account-structure.md)).

```bash
aws sso login --profile supply-prod
cd infra
npx cdk bootstrap --profile supply-prod        # once per account and region; bootstraps every region in the app
npx cdk diff --profile supply-prod -c backupCopy=false
npx cdk deploy --all --profile supply-prod -c backupCopy=false
```

`--all` includes the data and backup stacks, so keep `-c backupCopy=false` on both commands until [step 4 of the backup setup](backups.md#setting-it-up) is done (why: [The CloudTrail trail](#the-cloudtrail-trail)).

**Cost alerts** (`supply-checkout-jxq`). The us-east-1 `observability` stack holds the account's monthly AWS Budget and its Cost Anomaly Detection monitor and subscription, emailing the P2 recipients ([Observability](observability.md), "Cost alerts"). The budget ($100 a month) and the anomaly threshold ($20) are placeholders for the owner: change them in `infra/lib/observability/cost-alerts.ts`, or with `-c monthlyBudgetUsd=… -c costAnomalyUsd=…`. Before its first deploy, check for an existing AWS services anomaly monitor, which would make the deploy fail, and after it, test an alert: both are in [When a cost alert arrives](observability.md#when-a-cost-alert-arrives).

## GitHub Actions deploy role

`infra/lib/stacks/github-deploy-stack.ts`, bead `supply-checkout-5ik` ([ADR 0003](adr/0003-aws-account-structure.md), [ADR 0012](adr/0012-cicd-releases-rollbacks.md)). It lets a GitHub Actions job deploy to the prod account with short-lived credentials and no stored AWS keys. The MVP has one account, so there is one provider and one role, in `supply-checkout-prod`. The stack, `supply-checkout-<env>-<primary region>-github-deploy`, holds:

- An IAM OIDC provider for `https://token.actions.githubusercontent.com`, audience `sts.amazonaws.com` only. IAM fetches GitHub's certificate thumbprint itself.
- The role `supply-checkout-<env>-github-deploy`. Its trust policy has one statement: `sts:AssumeRoleWithWebIdentity` from that provider, with `StringEquals` on `aud` = `sts.amazonaws.com` and `sub` = `repo:<owner>@<owner ID>/<name>@<repository ID>:environment:production` or the same with `:environment:production-stateful` (a `StringEquals` list: either one, exactly). Only a job in this repository that runs in the `production` or `production-stateful` GitHub environment gets one of those subjects. The deploy workflow's stateful stacks job runs in `production-stateful`, so changing them takes an approval of its own (bead `supply-checkout-pbp.27`); it was added to the trust then, and the stack must be deployed again (step 2) before that job can sign in. A pull request, a push without the environment, a fork or another repository gets a different one and is refused. There are no wildcards.
- That subject is GitHub's immutable subject (bead `supply-checkout-pbp.23`): it carries GitHub's numeric owner and repository IDs next to the names. The older default, `repo:<owner>/<name>:environment:production`, would match whoever holds the name: if the account were renamed or deleted and the name registered again, a new repository with a `production` environment would get the trusted subject. An owner or repository ID is never reused, so it doesn't. GitHub turns immutable subjects on by default for repositories created after 2026-07-15, this one included, so no repository setting is needed (check it in step 1 below). A rename changes the subject: deploys from GitHub fail closed until the stack is deployed again with the new name (the IDs stay). A transfer to another owner changes the owner ID too.
- Its permissions: `sts:AssumeRole` and `sts:TagSession` on this account's CDK bootstrap roles (`cdk-<qualifier>-{deploy,file-publishing,image-publishing,lookup}-role-<account>-<region>`), in each deployed region and `GLOBAL_SERVICES_REGION`, and `sts:AssumeRole` on the web stack's publisher role, `supply-checkout-<env>-web-publisher` (bead `supply-checkout-pbp.28`). `cdk deploy` and `cdk diff` do everything else through the bootstrap roles, exactly as a deploy from a laptop does. The publisher role is for what they can't do: the file-publishing role writes only to CDK's staging bucket, the deploy role only drives CloudFormation, and the lookup role only reads, so none can upload a web release, switch the live version or test the router. It's in the web stack (`infra/lib/web/publisher.ts`): read publish-web's SSM parameters; list, read and write the releases bucket under `releases/` only (no delete); describe, list, get and put keys in the live-version KeyValueStore; get the distribution's config; describe and test the router function. Its trust is this account with `aws:PrincipalArn` = the deploy role, so only the deploy role can assume it. cdk-nag's AwsSolutions-IAM5 is acknowledged twice on its policy, each with a reason: the `/supply-checkout/<env>/web/*` parameters (the web stack's own outputs, read by name) and `releases/*` in the bucket (a release's folder is named when it's published; no delete). Its parameter ARNs are in the web stack's region, where publish-web reads them; in phase 2, if the primary region isn't `GLOBAL_SERVICES_REGION`, the api, identity and realtime parameters it reads must be published there too, or the ARNs pointed at the primary region. No managed policy, one-hour sessions, and cdk-nag passes with no suppressions.
- The output `DeployRoleArn`, the role `scripts/assume-aws-role.sh` assumes in the deploy workflow (the secret `AWS_DEPLOY_ROLE_ARN`).

The repository comes from `DEFAULT_GITHUB_REPOSITORY` in `lib/config.ts`: its `owner/name` (for the role's description) and its owner and repository IDs (for the trust). They are public identifiers, read with `gh api repos/davetashner/supply-checkout --jq '{owner_id: .owner.id, repo_id: .id}'`. Override all three together with `-c githubRepository=<owner>/<name> -c githubOwnerId=<n> -c githubRepositoryId=<n>`; the synth refuses some without the others, names outside GitHub's rules (so no `:`, `@` or wildcard), and IDs that aren't plain positive integers. The environment name comes from `GITHUB_DEPLOY_ENVIRONMENT`. No account ID is written down: the ARNs are built from CloudFormation's `AWS::AccountId`.

It is a separate CDK app, `bin/github-deploy.ts`, like the backup account's vault. `cdk deploy --all` never includes it, so a pipeline deploying the main app never changes the role it deploys with by accident. That is not a security boundary: a job with this role can assume the bootstrap deploy role and, through CloudFormation's execution role, update this stack or the role's trust too. The real boundary is the `production` environment's rules on GitHub, plus a narrower CloudFormation execution policy (bead `supply-checkout-3x3.2`; see [What it doesn't limit](#what-it-doesnt-limit)). The stack is prod only (the trust always names the `production` GitHub environment, so the synth refuses any other `envName`), and a bootstrap qualifier from context (`@aws-cdk/core:bootstrapQualifier`) must match CDK's own rule, 1 to 10 letters, digits, `_` or `-`, so it can't widen the role ARNs. The stack has termination protection, and the provider and role are retained if it's deleted.

**Revoking access.** Because the provider and role are retained, deleting the stack does not revoke GitHub's access. To cut it off, delete the role by hand (`aws iam delete-role-policy` for its policy, then `aws iam delete-role --role-name supply-checkout-prod-github-deploy`), or replace its trust policy with one that allows nothing (`aws iam update-assume-role-policy`). Deleting the OIDC provider also stops every role that trusts it.

**Deploying it (the owner, once).** CDK must already be bootstrapped in the account and regions (see [Deploying](#deploying)), and the `production` environment set up on GitHub (below). Then, in this order:

1. **Confirm the repository uses immutable subjects.** A read-only check:

   ```bash
   gh api repos/davetashner/supply-checkout/actions/oidc/customization/sub \
     --jq '[.use_default, .use_immutable_subject, .sub_claim_prefix]'
   ```

   It must print `[true,true,"repo:davetashner@5702882/supply-checkout@1388338851"]`: the default template, with immutable subjects on, and the prefix the trust expects (the role's `sub` is that prefix plus `:environment:production`). If it doesn't, stop: the trust won't match, and the subject setting is to be looked at before deploying.

2. **Deploy the stack.**

   ```bash
   aws sso login --profile supply-prod
   cd infra
   npm run synth:github-deploy                               # cdk-nag runs here too
   npx cdk diff --app "npx tsx bin/github-deploy.ts" -o cdk.out/github-deploy --profile supply-prod
   npm run deploy:github-deploy -- --profile supply-prod     # checks the environments first; CDK asks to confirm the IAM changes
   ```

   `deploy:github-deploy` (`scripts/deploy-github-deploy.mjs`) runs `scripts/check-environments.mjs` first and refuses to deploy unless `production` and `production-stateful` both exist with no admin bypass, `main` as their only deployment branch policy, and a required reviewer (it reads them with your `gh` login). It checks the repository the trust is for: the `-c githubRepository=<owner>/<name>` given to it (with the owner and repository IDs, after a rename or for a fork), else this one, and passes every argument on to `cdk deploy`. GitHub creates an environment with no protection the first time a job names one that doesn't exist, so a trust naming an environment that isn't set up yet would let any branch's job in. The deploy workflow runs the same check before every deploy.

3. **Check it with a dry run.** Set the `DeployRoleArn` output as the `production` environment's secret `AWS_DEPLOY_ROLE_ARN`, and as a repository secret of the same name (for the negative check, whose job has no environment, and for the `synth` job, which takes the account ID from it). Secrets, so the account ID in the ARN is masked in the public run logs. Also make the repository secret `DEPLOY_ASSEMBLY_KEY`, which seals the synth job's public `cloud-assembly` artifact: `openssl rand -base64 32 | gh secret set DEPLOY_ASSEMBLY_KEY` (it never shows the key). Then run the deploy workflow with **dry run** checked (Actions, Deploy, Run workflow, from `main`, with the latest release tag) and approve it. Its `trust` job, outside the environment, must be refused with `Not authorized to perform sts:AssumeRoleWithWebIdentity`, its `synth` job must synthesize with no credentials, and its `plan` job, in the environment, must sign in as the deploy role (`Prove who this job is`), drop to the lookup role, open and unpack the synth job's sealed assembly to the same hash and show the diffs, and deploy nothing. Every deploy repeats both checks ([Deploying a release](releases.md#deploying-a-release)).

**If the subject doesn't match, it fails closed.** If the repository's subject setting is changed (a custom template, or immutable subjects turned off) or the repository is renamed or transferred, tokens carry a different `sub` and the role refuses them until the stack is deployed again to match. Nothing is opened up in between, and nothing deploys from GitHub yet anyway.

An account can have only one OIDC provider for GitHub's URL. If one already exists (made by hand or another tool), the deploy fails: delete it first if nothing else uses it, or bring it into the stack with `cdk import`. Deploy the stack again when a region is added to `DEFAULT_REGIONS` (phase 2), so the role may assume that region's bootstrap roles, and after the repository is renamed (the name in the subject changes; the IDs stay) or transferred to another owner (the owner name and ID change). Until then, deploys from GitHub fail closed.

**Setting up the `production` and `production-stateful` environments on GitHub (the owner, once, before the first deploy of this stack).** The environment's rules decide which jobs get the trusted subject, so set them before the role exists. In the repository's Settings, Environments, create `production`, and `production-stateful` with the same rules, with:

- Deployment branches and tags: selected only, `main` only. Without this, a workflow on any branch could declare `environment: production`. Not the release tags: a run on a tag uses that tag's own copy of the deploy workflow, so a tag pointing at other code could leave out its checks. The deploy workflow runs from `main` and is given the tag as an input.
- Required reviewers: the owner, so every prod deploy waits for an approval.
- Optionally, prevent self-review and a wait timer.

Check it before deploying the stack:

```bash
for env in production production-stateful; do
  gh api "repos/davetashner/supply-checkout/environments/$env" \
    --jq '{name, can_admins_bypass, branch_policy: .deployment_branch_policy, rules: [.protection_rules[].type]}'
  gh api "repos/davetashner/supply-checkout/environments/$env/deployment-branch-policies" \
    --jq '[.branch_policies[] | {name, type}]'
done
```

For each environment, `deployment_branch_policy` must not be `null` (null means any branch may deploy), with `custom_branch_policies: true`; `can_admins_bypass` must be `false`; the second command must list only `main` (type `branch`); and `rules` must include `required_reviewers`. Don't deploy the stack until it does.

**What it enables.** `.github/workflows/deploy.yml` ([Deploying a release](releases.md#deploying-a-release)). Its `plan` and `apply` jobs run with `environment: production`, its `apply-stateful` job with `environment: production-stateful`, all with `permissions: id-token: write`, and they sign in with `scripts/assume-aws-role.sh web-identity` and `ROLE_ARN: ${{ secrets.AWS_DEPLOY_ROLE_ARN }}` (the environment's secret, or the repository's). That script exchanges the job's OIDC token (audience `sts.amazonaws.com`) with `sts:AssumeRoleWithWebIdentity` and prints nothing that names the account or the role: it masks the account ID, the keys, the session token and the assumed role's unique ID (`AROA…`) and ARN before anything else, and reports a failure by STS's error code alone. It replaced `aws-actions/configure-aws-credentials`, which always logs the role's unique ID, and this repository's logs are public (`supply-checkout-o60.13`). Any change to it must keep these:

- **No release code where the token can be requested before an apply approval** (`supply-checkout-pbp.39`). The release commit's code runs only in jobs without `id-token: write` (`build`, `synth`) or in the apply jobs, which deploy it. `plan` checks out only `main`'s commit and treats what those jobs hand on as data. `scripts/check-deploy-workflow.mjs` fails CI otherwise ([What approving runs](releases.md#deploying-a-release)).

- **Run only from `main`.** Every job in the deploy workflow has `if: github.ref == 'refs/heads/main'`, and the `production` environment allows `main` only. A run dispatched on a tag would use the tag's own copy of the workflow.
- **Protect the release tags.** The deploy deploys the commit a `v*` tag points at (it must be a published release on `main` that passed CI), so whoever can move a `v*` tag could pick which of those commits goes out (still behind the required reviewers). Add a tag ruleset for `refs/tags/v*` that restricts creation, update and deletion to release-please and the owner.
- **Never give `environment: production` or `production-stateful` to a `pull_request_target` or `workflow_run` job.** Both run with the base repository's context and secrets, yet can be triggered from a fork's pull request and may check out or act on its code. A job of either kind in the `production` environment would hand a fork's code the deploy role. The deploy workflow runs only on `workflow_dispatch` (the release workflow dispatches it, because a release made with `GITHUB_TOKEN` triggers no workflows).

To check the trust after deploying: `aws iam get-role --role-name supply-checkout-prod-github-deploy --profile supply-prod` shows the one statement above, with the two immutable subjects, and a job that runs without either environment fails in its sign-in step with `couldn't assume the role (AccessDenied)`.

### What it doesn't limit

The CDK bootstrap roles decide what a deploy can change. By default, `cdk bootstrap` gives the CloudFormation execution role `AdministratorAccess`, so anyone who can run a job in the `production` environment can change anything in the account through CloudFormation, this stack and the role's own trust included. The environment's branch rules and required reviewers are the guard. Bootstrapping with a narrower `--cloudformation-execution-policies` is bead `supply-checkout-3x3.2`.

## The CloudTrail trail

`lib/stacks/audit-stack.ts`, bead `supply-checkout-3sv.3`. Every EventBridge rule here on `AWS API Call via CloudTrail` (the operator alerts below, the backup and deletion records change alerts) needs a trail logging in the account: without one EventBridge receives none of those events, and the rules never fire. The primary region's `audit` stack (stateful, termination-protected, everything `RETAIN`) has it:

- `supply-checkout-<env>-trail`: multi-region, every management event (read and write), global services' events (IAM, STS) included, log file validation on. No data events and no CloudWatch Logs delivery.
- Its bucket, `supply-checkout-<env>-trail-<region>-<account>`: SSE-KMS with the stack's own rotating key (`alias/supply-checkout-<env>-trail`), public access blocked, ACLs off, TLS only, versioned (old versions kept 30 days), server access logs to the data stack's logs bucket under `s3/trail/` (the logs bucket's policy grants that bucket only), and log files expired after 400 days (`TRAIL_LOG_RETENTION_DAYS`; there's no information security policy yet, `supply-checkout-4p1`, so it's the deletion records' 400 days).
- Only this trail may use the key or write to the bucket: CloudTrail's statements in both policies have `aws:SourceArn` (the trail's ARN) and `aws:SourceAccount`, and it may write only under `AWSLogs/<account>/`. Reading the logs takes IAM permissions in the account, as for every key here.
- It publishes `trail-name`, `trail-bucket-name` and `trail-key-arn` under `/supply-checkout/<env>/audit/`. It deploys after the data stack (the logs bucket) and before the primary region's observability stack, whose `OperatorAlertKeyAndTrailChanges` rule also watches the trail's key, and `OperatorTrailBucketChanges` the trail's bucket and grants on its key.
- Cost: the first copy of management events is free. The rest is the key ($1 a month), its requests (CloudTrail asks for a data key for each log file, a few thousand a day across regions: well under $1 a month) and S3 storage of compressed logs (cents).

To deploy it on its own (`cdk deploy` without `--exclusively` also deploys the stacks a named stack depends on, so deploying the observability stack deploys the data and audit stacks first):

```bash
npx cdk diff supply-checkout-prod-us-east-1-data supply-checkout-prod-us-east-1-audit supply-checkout-prod-us-east-1-observability --profile supply-prod -c backupCopy=false
npx cdk deploy supply-checkout-prod-us-east-1-data supply-checkout-prod-us-east-1-audit supply-checkout-prod-us-east-1-observability --profile supply-prod -c backupCopy=false
```

Keep `-c backupCopy=false` on every such command, `diff` included, until [step 4 of the backup setup](backups.md#setting-it-up) has created `/supply-checkout/<env>/backup/copy-vault-arn` and `organization-id`: the data stack reads them at deploy time otherwise, and the deploy fails while they don't exist. Drop the flag once step 4 is done (then deploying the data stack adds the deletion records' replication).

Then check it:

1. `aws cloudtrail get-trail-status --name supply-checkout-prod-trail --profile supply-prod --region us-east-1` shows `"IsLogging": true`, and after about 15 minutes a `LatestDeliveryTime` with no `LatestDeliveryError`. After about an hour it should also show a `LatestDigestDeliveryTime` with no `LatestDigestDeliveryError`: the hourly digest files (for log file validation) are delivered separately, and a problem with them, such as the key or bucket encryption, shows only there. `aws cloudtrail describe-trails --profile supply-prod --region us-east-1` shows it multi-region with a `KmsKeyId` and `LogFileValidationEnabled`.
2. The alerts now arrive: add a test operator (`npm run operators -- add <username>`, as the `operators` skill hands it over) and a P1 message from `supply-checkout-prod-operator-pool-changes` should arrive within about 5 to 15 minutes (CloudTrail's usual delay). Remove the test operator afterwards (that alerts too). If nothing comes, look the `AdminCreateUser` event up in CloudTrail's event history and compare it with the rule's pattern (`aws events test-event-pattern`).
3. Record it in the [Drill log](backups.md#drill-log) with the other alert checks.

**Recreating it.** The trail and bucket have fixed names and, like the key, are retained if the stack is deleted, so a deleted `audit` stack can't simply be deployed again: the trail and bucket names are still taken, the old key is left behind without its alias (aliases aren't retained), and the new stack would fail to create them. Bring the retained trail, bucket and key back into a new stack with `cdk import`, or delete or rename the old trail and give the bucket a new name. Termination protection makes deleting the stack a deliberate step.

An **organization trail** from the management account (`supply-mgmt`), delivering to a log archive account ([ADR 0003](adr/0003-aws-account-structure.md)), is a stronger later step: nobody in this account could stop it. That's the owner's decision; this trail stays useful beside it (the rules here watch it).

## Domain and email

`lib/domain.ts` names every host, and each region's `domain` stack (`lib/stacks/domain-stack.ts`) holds the certificates and records for them (`supply-checkout-m64`). Prod serves `supplycheckout.com` itself; any other environment serves `<env>.supplycheckout.com` from a zone in its own account.

| Name | What serves it | Certificate |
| --- | --- | --- |
| apex, `www.` | the demo at `/demo/`; other paths redirect to `app.` until the landing page (CloudFront) | `web`, in `GLOBAL_SERVICES_REGION` |
| `app.` | the web app (CloudFront) | `web`, in `GLOBAL_SERVICES_REGION` |
| `auth.` | Cognito Managed Login | `auth`, in `GLOBAL_SERVICES_REGION` |
| `realtime.` | AppSync Events | `realtime`, in `GLOBAL_SERVICES_REGION` |
| `api.` | the HTTP API, in every region | `api`, in each region |
| `mail.` | SES custom MAIL FROM (MX and SPF) | none |
| apex MX (prod) | ImprovMX, forwarding `support@` to the owner's inbox ([Support email](#support-email)) | none |

The certificates are validated by DNS in the zone; CloudFormation adds the validation records and waits a few minutes for issuance. Each ARN is published to SSM as `/supply-checkout/<env>/domain/<name>-certificate-arn`, in the stack's region. The names start to resolve when the stacks that use them add their alias records: `web` (`supply-checkout-qk1`), `identity` (`supply-checkout-zsm`), `api` and `realtime`. Those stacks import the zone with `importZone()` from `lib/domain.ts`.

In the primary region, the stack also creates the SES domain identity with Easy DKIM (three CNAMEs), the `mail.` MAIL FROM domain, SPF on the apex (`v=spf1 include:amazonses.com -all`) and DMARC at `p=none`. In prod it also adds the apex MX records, an IAM user and a CloudWatch event destination for support mail ([Support email](#support-email)). SES in the second region is phase 2 (`supply-checkout-3x3.1`).

**The hosted zone is imported, never created.** Prod's zone was created by hand when the domain was delegated from Namecheap. The stack reads its ID from the SSM parameter `/supply-checkout/<env>/dns/hosted-zone-id` at deploy time (a CloudFormation SSM parameter), rather than `HostedZone.fromLookup`, so synth stays account-agnostic in CI and the zone ID never lands in `cdk.context.json`. Use a DMARC report service's `mailto:` address, not a personal mailbox at another domain: receivers drop reports to another domain unless that domain publishes an authorization record, which personal mail providers don't. ### Transactional email

The app sends invites and account notices itself (`supply-checkout-5hx`); Cognito sends its own sign-up and sign-in codes. Both go out from `noreply@<env domain>` through one SES configuration set, `supply-checkout-<env>-transactional`, which the primary region's `domain` stack creates and makes the domain identity's default.

- **Suppression.** The configuration set adds any address that hard-bounces or complains to SES's account-level suppression list, and SES won't send to it again. A later send to it comes back as a bounce (subtype `OnAccountSuppressionList`). Because the configuration set is the identity's default, this covers Cognito's mail too: someone who marks an invite as spam also stops getting sign-up and password-reset codes. See [Removing an address from the suppression list](#removing-an-address-from-the-suppression-list).
- **Bounce and complaint events.** The configuration set publishes them to the SNS topic `supply-checkout-<env>-email-events`, encrypted with its own KMS key, which only SES may publish to, and only for this configuration set. The `email` stack's function (`backend/src/email/events.ts`) subscribes to it. When the message was an invite (its SES tags name the team and invite), a permanent bounce (including a send to a suppressed address) or a complaint marks that invite `inviteStatus: "failed"` with `failureReason` (`bounced` or `complained`), as long as the invite is still there and is for the address that bounced, so the owner can see it and correct the address. Transient bounces (a full mailbox, an out-of-office auto-reply) are counted in `EmailBounces` but don't fail the invite. Nothing is re-sent automatically. The function may read only `homeRegion` from team items and update only an invite's failure fields (`dynamodb:Attributes` in its policy), whose names no other item in a team's partition uses: the policy pins the partition, not the item, so the invite field is `inviteStatus`, not `status` (a team's subscription status). Events it can't record after retries go to `supply-checkout-<env>-email-events-dlq`, which alarms (Email events dropped, [docs/journeys.md](journeys.md)).
- **The dead-letter queue holds email addresses.** Its messages are whole SES events, recipients included, so it's encrypted with its own KMS key and keeps messages for 7 days. Read it only to replay or diagnose an event, and don't copy messages into tickets, chat, commits or logs; quote the invite and team IDs from the message's `mail.tags` instead.
- **Sending.** A function gets permission with `grantSendEmail(fn, config)` (`lib/email.ts`): `ses:SendEmail` on the domain identity and the configuration set only, with the condition `ses:FromAddress = noreply@<env domain>`, and the environment `mailerFromEnv()` reads (`backend/src/email/mailer.ts`). The `account` function has it, in every region's `api` stack, for invites, team closure and reopening notices, and the security notices (a password set, two-step sign-in turned on) to the caller's own verified address (it sends through SES in the primary region); billing notices (`supply-checkout-x0l`) add it where they send. The `email` stack's security notices function has it too, for the same notices when the change was made directly against Cognito, the `emailChanged` notice to an account's previous address ([Sign-in](#sign-in), "What it protects"), and the `passwordReset` notice after a reset, which the post confirmation trigger hands it (Sign-in, "After a reset"; so it has a fixed name, `supply-checkout-<env>-security-notices`). Its role may also call `ListUsers` and `AdminGetUser` on the app pool only, and `GetItem` (projected: `Select` `SPECIFIC_ATTRIBUTES` required, not `IfExists`, `supply-checkout-3sv.24`), `UpdateItem` (returning nothing) and `ConditionCheckItem` (the `DELETING` mark) in `USER#` partitions naming only `SECURITY_NOTICE_ATTRIBUTES` (the keys, `noticeSentAt`, `noticeFor`, `noticeAddress`, `noticeAddressAt`, `noticeSeenHash`, and `totpOnAt` for when two-step sign-in was turned on, [Sign-in](#sign-in); no other item has them, and no TTL attribute). **After deploying the `email` stack** (it now deploys after `identity`), this check is a gate: if it fails, direct changes aren't noticed at all. While SES was in the sandbox, the statement also covered `identity/*`, because SES then authorizes `ses:SendEmail` on each recipient's identity as well (`supply-checkout-3sv.20`); production access was granted on 2026-10-07 (`supply-checkout-3sv.18`) and that allowance is gone (`supply-checkout-3sv.21`). If an account is ever back in the sandbox (a new environment, or SES pausing this one), sends to verified addresses fail with `AccessDeniedException` (`Invite email not sent` in the account function's logs) until it's out again.
  1. With a test account signed in, change its password with the AWS CLI and its own access token (`aws cognito-idp change-password`). Within a few minutes one `passwordSet` email must arrive, and the function must log `Security notice sent` with `via: cloudtrail`. **If no event reaches the function** (no invocation; CloudTrail management events don't always reach EventBridge, as the operator group's `AdminAddUserToGroup` events didn't in `supply-checkout-3sv.5`), **or it logs `Security notice not sent` with `NoSub`**, the feature doesn't work: Cognito's events can't be matched to a user, and direct changes go unnoticed.
  2. Look at that event in CloudTrail and confirm where `sub` and `userPoolId` are, and that `requestParameters.userAttributes` of an `UpdateUserAttributes` event is `HIDDEN_DUE_TO_SECURITY_REASONS`. If the attributes (the new address) are in clear, the dead-letter queue holds addresses: it needs its own KMS key and a row in the privacy policy's data inventory.
  3. Set a password through the app, and confirm only one email arrives.
  4. Load the app once, change the account's email with `update-user-attributes` and `verify-user-attribute`, and confirm the old address gets the `emailChanged` email.
  5. Confirm the function logs no `AccessDeniedException` (`reason: error`): DynamoDB Local doesn't enforce the `dynamodb:Attributes` conditions.
- **The welcome email** (`supply-checkout-6uw.25`, `backend/src/email/welcome-handler.ts`). Every new account gets one welcome email, whichever way it signed up, from the `email` stack's `supply-checkout-<env>-welcome-email` function. The user pool's triggers hand it over with an asynchronous invoke, so nothing is sent inside Cognito's 5 seconds and a slow SES can't touch sign-up ([Sign-in](#sign-in), "The welcome email"). The request carries only the account's sub and how it signed up (`email`, `Google`, `SignInWithApple`); the function looks the user up in the app pool and sends only to the address the account API trusts, greeting them by their `given_name` if they have one. What it says: the account is ready and signs in with this address; the next step, which is creating a team and its 14-day trial with no card needed, or, when the account is already in a team or a live invite is waiting for its address, opening Supply Checkout to accept the invite (with a line that they can still create a team of their own); and `support@<env domain>` for questions. It links only to the app, has no images or tracking, and is transactional (the usual footer, nothing to unsubscribe from). **Once**: before sending, the function claims `USER#<sub>` / `WELCOME` (`welcomeSentAt`, `data/welcome.ts`) with a conditional write that also fails for an account being deleted (the `DELETING` mark, in the same transaction), so a retried trigger, both triggers, Lambda's retries or a replay can't send a second one. If SES refuses the message, the claim is given up (only while it's still the one made) and the request isn't retried; if the function dies between claiming and sending, the claim stays and that account gets none (its retry logs `Welcome email already claimed`, and **Welcome email function failing**, on the function's Lambda `Errors`, shows the death): at most one, never two. **Failures** are logged with the sub, the method, a reason and the error's name only, never the address or the name, and counted in `WelcomeEmailFailures` (reasons `no_address`, `lookup_failed`, `error`, `invalid`; and from the triggers, `invoke` and `deferred`), which raises **Welcome emails failing** (P2, any in an hour); sent ones count in `WelcomeEmails`, by method. **SES refusing** a message (sending paused, a suppressed address) is counted apart, in `WelcomeEmailsRefused`, and raises **Welcome emails refused** (P2) on any one in an hour (`WELCOME_REFUSALS_ALARM_PER_HOUR`, 1 since SES production access, `supply-checkout-3sv.21`). A failed Cognito or DynamoDB call is thrown, so Lambda tries twice more, then the request waits 14 days on `supply-checkout-<env>-welcome-email-dlq` (SQS-encrypted; a sub and a method, no address) to be replayed, which raises **Welcome emails dropped** (P2, [journeys.md](journeys.md)). **IAM**: `grantSendEmail`; `ListUsers` and `AdminGetUser` on the app pool only; `UpdateItem` (returning nothing) and `ConditionCheckItem` in `USER#` partitions naming only `WELCOME_RECORD_ATTRIBUTES` (`PK`, `SK`, `welcomeSentAt`, which no other item has, and no TTL attribute); `Query` of `USER#` partitions naming only the keys (is the user in a team), and of GSI2's `INVITEE#` partitions naming only `WELCOME_INVITE_ATTRIBUTES` (the keys, `type`, `email` and `expiresAt`: never the team's name, the role or the inviter), both with `Select` `SPECIFIC_ATTRIBUTES`; the table's key through DynamoDB only. No `GetItem`, `PutItem`, `DeleteItem` or `Scan`. The same residuals as the notice address grant apply: changed code on this role could set `welcomeSentAt` on any `USER#` item, or read one from a conditional write made to fail (no IAM key for `ReturnValuesOnConditionCheckFailure`).
- **Deploying.** Deploy the primary region's `domain` stack first (it adds the configuration set, and changes the identity's default to it), then `data`, then `email`. Deploying `email` deploys `data` too, so keep `-c backupCopy=false` until [step 4 of the backup setup](backups.md#setting-it-up) ([why](#the-cloudtrail-trail)):

  The function's IAM conditions (`dynamodb:Attributes`, `dynamodb:Select`, `dynamodb:ReturnValues`) aren't enforced by DynamoDB Local, so check them once in the deployed stack: create a test invite for `bounce@simulator.amazonses.com` in a test team, send the same message with `--email-tags Name=kind,Value=invite Name=teamId,Value=<team ID> Name=inviteId,Value=<invite ID>`, and confirm the invite item gets `status: failed` and the function logs no `AccessDeniedException`. ### Removing an address from the suppression list

Do this only when the address's owner asks, for example after they fixed a full or misconfigured mailbox, or marked an invite as spam by mistake and now can't get sign-in codes. An address on the list gets no invites, notices or Cognito codes. Check it, then remove it (use the address they gave you; don't paste it anywhere else):

```bash
aws sesv2 get-suppressed-destination --profile supply-prod --region us-east-1 --email-address "$ADDRESS" \
  --query 'SuppressedDestination.{reason:Reason,since:LastUpdateTime}'
aws sesv2 delete-suppressed-destination --profile supply-prod --region us-east-1 --email-address "$ADDRESS"
```

A complaint means the person asked not to get our mail, so remove a `COMPLAINT` entry only on their own request. If an invite to the address had failed, the owner sends a new invite; the failed one isn't retried.

**Staging and dev.** Only the prod account exists today, so nothing is delegated yet. When one of those accounts exists (`staging` here):

1. In the staging account, create the zone `staging.supplycheckout.com` (`aws route53 create-hosted-zone --name staging.supplycheckout.com --caller-reference staging-$(date +%s)`) and put its ID in that account's `/supply-checkout/staging/dns/hosted-zone-id`.
2. In the prod account, put the new zone's four name servers in a `StringList` parameter: `aws ssm put-parameter --type StringList --name /supply-checkout/prod/dns/delegation/staging --value 'ns-1.awsdns-01.org,ns-2.awsdns-02.co.uk,…'`.
3. Add `"delegatedEnvs": ["staging"]` to `cdk.json` (it holds names only) and redeploy prod's `domain` stack, which adds the NS record. Keep it in `cdk.json` rather than passing `-c`: a prod deploy without it removes the delegation.
4. Deploy staging with `-c envName=staging` and that account's profile.

### Support email

`support@supplycheckout.com` forwards to the owner's Gmail through [ImprovMX](https://improvmx.com)'s free plan, and the owner replies from Gmail as `support@` (`supply-checkout-6qd`). Revisit a shared inbox (Google Workspace or a help desk) when two people answer support.

**The security notices name it** (`supply-checkout-3sv.12`). Every security notice (`passwordSet`, `twoStepOn`, `passwordReset`, `emailChanged`) ends with the same recovery path for a reader who didn't make the change: secure the mailbox, reset the password with a code sent to it (not after an email change, when codes go to the new address), tell the other owners, and write to `support@<env domain>` from that address, where support confirms the account is theirs before changing anything, then signs it out everywhere and helps reset its password, email address and two-step sign-in (`recoveryPath` in `backend/src/email/templates.ts`). The address reaches every sending function as `EMAIL_SUPPORT_ADDRESS`, which `grantSendEmail` sets, and a security notice won't render without a plain address. The operator's steps for a hijacked account are kept outside this public repo.

**What the prod `domain` stack adds** (primary region, only when `supportMail` is set; `cdk.json` sets `"supportMail": "improvmx"`, and other environments ignore it). Keep it in `cdk.json`: a prod deploy without it removes the MX records and support@ stops receiving mail.

- Apex MX: `10 mx1.improvmx.com` and `20 mx2.improvmx.com`, from ImprovMX's DNS setup guides, checked 2026-10-01 (`MAIL_FORWARDERS` in `lib/email.ts`).
- **No SPF change.** The apex SPF record stays `v=spf1 include:amazonses.com -all`. ImprovMX forwards with SRS (its own envelope sender), so it never needs to pass SPF as supplycheckout.com, and including `spf.improvmx.com` would let its servers pass SPF for the domain. ImprovMX's dashboard warns that SPF isn't set up; ignore that warning. SES's own SPF on `mail.` is unchanged too.
- The IAM user `/smtp/supply-checkout-prod-support-smtp`, with no access key. Its one permission, which is also its permissions boundary (`supply-checkout-prod-support-smtp-boundary`, so a policy attached later can't give it more): `ses:SendRawEmail` (what an SES SMTP send is authorized as) on the domain identity and the `transactional` configuration set, with `ses:FromAddress` = `support@supplycheckout.com` and `ses:FromDisplayName` = `Supply Checkout Support`. It can't call any other AWS API. Its SMTP password is made by hand (below) and kept only in Gmail's settings, never in the repo, SSM or a shared note.
- A CloudWatch event destination on the transactional configuration set, `SendsByCaller`, counting sends by `ses:caller-identity`, for the Support SMTP sends alarm.

**What the key can do.** Treat it like the domain's signing key. `ses:FromAddress` is most likely matched against the envelope sender of an SMTP send, not the message's From header, so whoever holds the key can probably send any mail the domain identity can: a header From of `noreply@supplycheckout.com` or any other address at the domain, DKIM-signed and passing DMARC, which makes convincing phishing. The display name condition only adds friction (an attacker can copy it). What limits the damage is detection and rotation: P2 alerts on any change to the user or its boundary policy and on more than 50 sends in an hour or 150 in a day ([Observability](observability.md), "Support SMTP user"), the key rotation below, and step 8's check of what the policy really refuses.

**Why replies go through SES.** Gmail's "send as" through Gmail's own SMTP sends from Google's servers, signed by `gmail.com`: SPF fails for supplycheckout.com (`-all`), the DKIM signature isn't the domain's, and DMARC fails, which gets replies junked now and rejected once DMARC moves to `p=quarantine`. Through SES SMTP (`email-smtp.us-east-1.amazonaws.com`, port 587, TLS), replies are DKIM-signed by `supplycheckout.com` (Easy DKIM) and their envelope sender is `mail.supplycheckout.com`, so both DKIM and SPF align and DMARC passes. **Until SES production access is granted (`supply-checkout-3sv.18`), replies and auto-replies reach only addresses verified in SES**; anything else bounces back to the Gmail inbox.

**Which configuration set.** Support replies go through the identity's default, the transactional set, so a recipient who marks a reply as spam is added to the account-level suppression list, which also stops their sign-up codes and invites ([Transactional email](#transactional-email)); a hard bounce does the same. A separate support set with suppression off would avoid that, but SMTP mail picks a configuration set only with the `X-SES-CONFIGURATION-SET` header, and Gmail's "send as" can't add headers. So replies stay on the transactional set, and the risk stands: if a customer says they no longer get codes after writing to support, check the suppression list ([Removing an address from the suppression list](#removing-an-address-from-the-suppression-list)).

Check in step 8 that the auto-reply comes from support@ through SES: if Gmail sends it from your Gmail address instead, it still arrives (it passes DMARC for gmail.com) but shows your personal address, so turn the filter off and use a plain manual reply until there's a help desk.

#### When the support SMTP key may be leaked

The P2 alerts: a change to the support SMTP user nobody made (a new key or other credential, a policy, a group, a password, its boundary, a rename, or a new version of its boundary policy), or **Support SMTP sends** (over 50 in an hour or 150 in a day).

1. Deactivate every key at once: `aws iam list-access-keys --profile supply-prod --user-name supply-checkout-prod-support-smtp`, then `aws iam update-access-key --profile supply-prod --user-name supply-checkout-prod-support-smtp --access-key-id <id> --status Inactive` for each. Support replies stop until step 4.
2. Undo whatever the CloudTrail event shows was changed (the alert names its event ID): delete an extra key, credential, certificate, SSH key, attached or inline policy, group membership or login profile, and rename the user back (`aws iam update-user --user-name <new name> --new-user-name supply-checkout-prod-support-smtp`). A redeploy **doesn't** restore a removed or changed boundary or policy (CloudFormation doesn't notice the drift), so put them back by hand and then check for drift:
   ```bash
   U=supply-checkout-prod-support-smtp
   ACCOUNT=$(aws sts get-caller-identity --profile supply-prod --query Account --output text)
   BOUNDARY="arn:aws:iam::$ACCOUNT:policy/smtp/$U-boundary"
   # The boundary: back on the user, and its CloudFormation version the default again
   aws iam put-user-permissions-boundary --profile supply-prod --user-name $U --permissions-boundary "$BOUNDARY"
   aws iam list-policy-versions --profile supply-prod --policy-arn "$BOUNDARY"   # find the version CloudFormation wrote (created before the alert)
   aws iam set-default-policy-version --profile supply-prod --policy-arn "$BOUNDARY" --version-id '<that version>'
   aws iam delete-policy-version --profile supply-prod --policy-arn "$BOUNDARY" --version-id '<the version the attacker made>'
   # The inline policy: its name and document are in the domain stack's template (SupportSmtpUserDefaultPolicy)
   aws iam list-user-policies --profile supply-prod --user-name $U
   aws cloudformation detect-stack-drift --profile supply-prod --region us-east-1 --stack-name supply-checkout-prod-us-east-1-domain
   aws cloudformation describe-stack-resource-drifts --profile supply-prod --region us-east-1 --stack-name supply-checkout-prod-us-east-1-domain \
     --stack-resource-drift-status-filters MODIFIED DELETED --query 'StackResourceDrifts[].[LogicalResourceId,StackResourceDriftStatus]' --output text
   ```
   If the inline policy is missing or modified, `aws iam put-user-policy --user-name $U --policy-name <its name> --policy-document file://policy.json` with the document from `npx cdk synth supply-checkout-prod-us-east-1-domain`. Drift detection should then report nothing for the user, its policy or the boundary.
3. Look at what was sent: SES's sending statistics and the `SendsByCaller` metric for the user, and bounces and complaints on the email events topic. If mail went out as the domain that you didn't send, treat it as a security incident: tell the people it reached that it wasn't from us.
4. Make a new key and SMTP password (steps 4 and 5) once the cause is understood.

## Sign-in

The `identity` stack (`lib/stacks/identity-stack.ts`, [ADR 0007](adr/0007-identity-cognito.md), `supply-checkout-zsm`) holds the Cognito user pool, in the primary region. It's stateful: termination protection, deletion protection on the pool, and a `RETAIN` removal policy.

- **Essentials tier** with **Managed Login** at `auth.<env domain>`, branded with the app's colors (`managedLoginBranding` in `lib/identity.ts`; light or dark follows the browser).
- Sign-in by email with a **one-time code**, a **password** (12+ characters, mixed), or a **passkey**. Passkeys use `auth.<env domain>` as their relying party ID, which Cognito requires with a custom domain. They are bound to that host, so changing it orphans every passkey.
- **Optional TOTP MFA**, no SMS. Owners must turn it on before changing billing (`supply-checkout-8jc.12`). The billing routes enforce that, not the pool: after the membership and role checks they call `GetUser` with the caller's own access token and answer 403 `mfa_required` unless `UserMFASettingList` has `SOFTWARE_TOKEN_MFA` and it's the preferred factor. A Google or Apple user (one who signs in only through the provider, `isFederatedOnly`) passes without it: Cognito never asks them for a second factor, and the provider's sign-in counts for it. A native user with a provider linked must turn TOTP on to pass, but after that a sign-in through Google or Apple isn't asked for the code either (Cognito never asks for MFA on a provider sign-in, and no token says how a session signed in): the provider's sign-in counts, as for a Google or Apple user.
  - **Setting it up** (Account in the app, `src/aws/mfa.js`): with optional MFA, Cognito lets a user with TOTP on sign in only with a password and the code, never an email code or a passkey. So the app first sets a password (`POST /me/password`, Cognito's `ChangePassword`; the current password confirms it, and a passwordless user sends none), then gets a secret (`POST /me/mfa/totp`, `AssociateSoftwareToken`) to show as a QR code, then checks a code from the app (`POST /me/mfa/totp/verify`: `VerifySoftwareToken`, then `SetUserMFAPreference`). All with the user's own token, like the email code routes: no IAM grant.
  - **Why "on the session" holds**: turning it on ends every session the user has (`GlobalSignOut`, tried three times; if it still fails the route answers 503 `signout_failed` and the app finishes it with `POST /me/sign-out-everywhere`), and `GetUser` refuses a revoked access token, so any native session the billing check accepts afterwards began with the password and code. The app then sends the user through Managed Login's `/logout` and back to sign in. That alone leaves two gaps: TOTP turned on with direct Cognito calls (the admin scope allows them) signs no one out, and another browser signed in to Managed Login in the hour before (its session cookie) can get new tokens without the code. So the billing check also needs the session to have begun after TOTP was turned on (below). What remains is a linked user's provider sign-in (above).
  - **The session must begin after TOTP was turned on** (`supply-checkout-8jc.14`). The user's own partition holds when TOTP was last turned on (`USER#<sub>` / `TOTP_ON`, `totpOnAt`, `backend/src/data/two-step.ts`), and for a native user with TOTP on, the billing routes refuse an access token whose `auth_time` (when that session signed in, in whole seconds) isn't a later second: 403 `mfa_sign_in_again`, and the app asks the owner to sign in again (it revokes the refresh token and goes through Managed Login's `/logout`, so the cookie can't sign straight back in, and keeps the team and drafts). A token without `auth_time` is refused too. Three writers keep the record, each with a time no earlier than the change, and it only ever moves later (a conditional update), so a late or replayed event can't move it back:
    - the `account` function, once `POST /me/mfa/totp/verify` has turned TOTP on and before it signs the user out everywhere (best effort: a failed write is logged, `Two-step sign-in time not recorded`, and the two writers below cover it);
    - the security notices function, from CloudTrail's `VerifySoftwareToken`, `SetUserMFAPreference` and `AdminSetUserMFAPreference` (an administrator's call on the app pool) records, however the call was made: when `AdminGetUser` shows an authenticator among the user's MFA methods, the event's time (CloudTrail's whole second, never later than the call); when it doesn't (TOTP turned off), it removes a record older than the event, so turning TOTP on again directly can't be passed by a session from in between before that event arrives. A failed write is logged (`Two-step sign-in time not recorded`) and counted (`SecurityNoticeFailures`, reason `totp_record`), the notices for the event are still sent (they're the main defence), and then the event is thrown so Lambda retries it (then the dead-letter queue);
    - the `billing` function, when a user with TOTP on has no record (on since before this shipped, or turned on directly and its event not processed yet): the time it found none, which is after TOTP was on. It then refuses, so that owner signs in again once.
    - Each write is defence in depth against IAM not limiting the sort key: the code checks the key is `TOTP_ON` in the caller's partition before any call, and each update's condition names it, so none creates or changes any other item.
  - **Accepted residual risk: turning TOTP off and on again within CloudTrail's delivery time.** Someone with the owner's password and a session from before `totpOnAt` (a stolen token, say) can turn TOTP off directly (`SetUserMFAPreference`), sign in with the password alone (no code is asked while it's off), turn TOTP on again with the owner's existing authenticator still listed, and call billing with the new session before the turn-off event is processed (CloudTrail usually takes a few minutes). The record still holds the owner's older time, and the new session's `auth_time` is later, so it passes. Code can't close this: Cognito doesn't say when TOTP was enabled, and only CloudTrail reports the turn-off. Both changes send the account's verified address a `twoStepOn` notice ("What it protects", below) when TOTP is on at lookup, and it needs the owner's password as well as a session.
  - The billing function reads and writes the record on a billing-access role session tagged with the caller's own `sub` (`userId`, from the verified token), which may name only the keys and `totpOnAt` in `USER#<userId>` (IAM, below), its reads projected (`Select` `SPECIFIC_ATTRIBUTES` required, not `IfExists`, `supply-checkout-3sv.23`). **After deploying** (`api` and `email`): (1) as an owner with TOTP on, open Billing: the first time it asks you to sign in again if you turned TOTP on before this deploy; after signing in with the password and code it opens. If it keeps asking right after a fresh sign-in, the access token has no `auth_time` in API Gateway's claims, or a different one: look at the token's claims. (2) The Managed Login cookie, with a test owner: sign in in browser A (no TOTP yet); in browser B turn TOTP on through the app (which signs A out everywhere); within the hour, reload the app in browser A. If Managed Login asks A for the password and code, its cookie didn't outlive the sign-out and there's nothing more to check. If it signs A in without the code (the cookie), open Billing in A: it should answer `mfa_sign_in_again`, which shows that `auth_time` keeps the cookie's original sign-in time. If Billing opens instead, the cookie-based sign-in got a fresh `auth_time` and that gap is still open for up to an hour after TOTP is turned on: record it on the bead, and the fix is to require `auth_time` to be at least the Managed Login session's lifetime (an hour) after `totpOnAt` (`sessionAfterTotp` in `billing-handler.ts`), at the cost of owners waiting an hour after turning TOTP on before billing opens. (3) Turn TOTP on directly against Cognito for a test user (`associate-software-token`, `verify-software-token`, `set-user-mfa-preference` with its access token) and confirm the `TOTP_ON` item appears in the table within a few minutes with CloudTrail's event time. (4) As an administrator, `aws cognito-idp admin-set-user-mfa-preference` on that test user of the app pool, turning TOTP off then on: the item should be removed, then written again. If the function counts `SecurityNoticeFailures` with reason `no_user` instead, CloudTrail doesn't give the user's `sub` for administrator calls: look at the event's fields and adjust the handler (the username is in `requestParameters` if CloudTrail doesn't hide it).
  - **What it protects**: an owner who has turned it on, against someone with their password or their inbox signing in. It's trust on first use: until they turn it on, whoever gets into the account (an email code from a stolen inbox, say) can set a password and their own authenticator, reach billing, and lock the owner out. A stolen access token can do the same for a passwordless user. So the account's verified address hears of it (`supply-checkout-8jc.15`): after `POST /me/password` succeeds, and after `POST /me/mfa/totp/verify` turns TOTP on (once the sign-out everywhere has run, whether or not it finished), the `account` function emails it what changed and when (UTC), and what to do if it wasn't them (the `passwordSet` and `twoStepOn` templates). The address is the verified one `GetUser` returned for the caller's own token before the change, never one from the request, and the message links only to the app. It's best effort: the change stands if SES refuses the message, takes longer than 3 seconds, or there's no verified address, which is logged (`Security notice not sent`) with the user ID, the kind and the error's name only, and counted in `SecurityNoticeFailures` (sent ones in `SecurityNotices`; both on the dashboard, and any failure in 15 minutes alarms, "Security notices failing", P2). A refused change sends nothing. **Changes made directly against Cognito** (`supply-checkout-8jc.28`, `8jc.29`): the admin scope lets anyone with a session make the same changes with the access token alone, and change the account's email (`UpdateUserAttributes`, then `VerifyUserAttribute` with a code sent to the new address). The email can't be made read-only for the client, because Google and Apple map it and Cognito requires mapped attributes to be client-writable. So the `email` stack's `supply-checkout-<env>-security-notices` rule sends CloudTrail's records of the app pool's `ChangePassword`, `VerifySoftwareToken`, `SetUserMFAPreference`, `AdminSetUserMFAPreference` (an administrator's, which only records or clears when TOTP was turned on, and sends `twoStepOn` when it's on), `UpdateUserAttributes` and `VerifyUserAttribute` calls, whoever made them, to the security notices function (`backend/src/identity/security-notices-handler.ts`). CloudTrail records the user's `sub` for these calls (`additionalEventData.sub`), not the username or the token; the function finds the user by it in the app pool (`ListUsers`, then `AdminGetUser`) and sends the same `passwordSet` notice, or `twoStepOn` when an authenticator is among the user's MFA methods, to the verified address (the same rule as the API's). A change made through the API isn't emailed twice: the `account` function marks the kind sent once SES has taken its notice (`NOTICE#<kind>` in the user's partition; one it couldn't send is left to the function), and the function sends only if no notice of that kind went out in the last 15 minutes, which also keeps the two calls of one TOTP setup to one email. **An email change** is told to the address the account had before (`emailChanged`), and it's checked on every one of these events, so a later event catches a change whose own events were missed. `/me` records the account's first verified address (`NOTICE_ADDRESS`), never for an account being deleted (it checks the `DELETING` mark in the same transaction), with a hash of Cognito's own address as it was. Whether the email changed is decided on that hash: Cognito's verified address only trimmed and lowered, not the app's rules, so a linked user's new address the API doesn't count, one over 254 characters the app can't normalize, or one NFKC would fold into the recorded one all still count, since Cognito sends codes and resets to each. The address told is always the recorded one, which starts only as an address the API trusts. The notice is claimed for the new address and sent, and only then does the record move on (to the new address if it normalizes, otherwise it stays at the old one, marked as told). The claim holds for 45 seconds, just over the function's timeout, and SES calls are bounded (5 seconds per try with `throwOnRequestTimeout`, 2 tries; 10 seconds in all for this notice). If SES refuses it or takes too long, the claim is given up and the event retried. An attempt that finds the claim held but the record not moved throws, and counts it (`pending`) once the claim is 15 seconds old (younger, it's likely another attempt still sending), so an attempt that died holding the claim ends in a retry that sends it (or the dead-letter queue), never in a silent success. The address is recorded where a verified address first appears, so an account has one before anyone can change its email ("Recording the notice address", below, `supply-checkout-8jc.31`); an account that still has none (every writer failed) has it recorded at the event, and nobody is told. Failures are logged with the user ID, the kind and the error's name only, and counted in `SecurityNoticeFailures` with a `via: cloudtrail` property and a reason (`not_sent`, `no_address`, `no_user` for an event without a sub, `lookup_failed`, `pending`, `totp_record` for when two-step sign-in was turned on not recorded, `error` for anything else thrown), so they raise "Security notices failing" too. A failed lookup, write or email change notice is retried by Lambda, and an event Lambda or EventBridge gives up on waits 14 days on `supply-checkout-<env>-security-notices-dlq` (SQS-encrypted) to be replayed, which alarms ("Security notices dropped", [journeys.md](journeys.md)). The rule matches this account's events only. See [Transactional email](#transactional-email) for the function's permissions and what to check after deploying.
  - Nothing is logged but the user ID (`Password set`, `Two-step sign-in turned on`): never the password, the secret or a code. There's no way to turn it off in the app, and a lost phone is an administrator's reset for now.
- Email codes come from `noreply@<env domain>` through SES, using the domain identity from the `domain` stack.
- **Forgotten passwords** (`supply-checkout-6uw.26`). `preventUserExistenceErrors` stays on, so Managed Login's own reset says nothing when an address has no account (or no password: a Google or Apple account, or one never confirmed) and sends nothing. Managed Login's pages can't be reworded (its branding has colors and layout, no text), so the app's sign-in screen has its own **Forgot your password?** (`src/aws/reset-password.js`). It shows everyone the same guidance after a request: "If there's an account for this address, we've sent a code. Nothing in a few minutes? You may have signed up with a different email or with Google, or you may not have an account yet", with **Create an account** (Managed Login's `/signup`). **The owner's decision (2026-10-08):** help stays on screen, and no email goes to an address with no account, nor to an unconfirmed or unverified one. The bead first asked for an email to those addresses too; the security review found that anyone could then make the app mail made-up addresses, whose bounces and complaints could get SES sending paused for the whole account (sign-up codes, resets, invites and notices with it). Only a Google or Apple account's address, which the pool knows and the provider verified, gets a short hint email.
  - `POST /auth/password-reset` (the api stack's `PasswordResetFunction`, no authorizer, an Origin check, throttled at 2 requests a second, burst 5) checks the address's form and counts the request's limits, keyed by SHA-256 hashes in `RESETLIMIT#ADDRESS#` and `RESETLIMIT#IP#` partitions with a TTL (`backend/src/data/password-resets.ts`): 3 an hour and 6 a day per address (its invite-limit key, so `+tags` and Gmail's dots are one mailbox), 10 an hour and 30 a day per IP address (an IPv6 address by its /64). They count requests, not accounts, so they're the same for every address. Past any, it answers 429 `rate_limited` and queues nothing; the app then links to Managed Login's `/forgotPassword`, which has Cognito's limits instead. Otherwise it hands `{email}` to the email stack's password reset function with an asynchronous invoke and answers 204. It never looks the address up, so its answer and its timing are the same for every address. Its role may `UpdateItem` only `PK`, `SK`, `count` and `expiresAt` in those two kinds of partition, returning nothing, and invoke only `supply-checkout-<env>-password-reset` in the primary region.
  - The password reset function (`backend/src/email/password-reset-handler.ts`): a native user who signs in with the address, enabled, confirmed and with its email verified, gets Cognito's own code (`ForgotPassword`, the public call Managed Login makes). Any other native user (disabled, unconfirmed, an unverified address) gets nothing. With no native user, an enabled Google or Apple user whose verified `email` is the address gets a hint (`passwordResetProvider`): there's no password to reset, sign in with Google (or Apple). Any other address gets nothing. The hint is fixed text with nothing from the request in it but the recipient, at most one an address a UTC day, and `PASSWORD_RESET_HINTS_PER_DAY` (500) a day in all (`backend/src/data/schema.ts`: the one number to lower, or set to 0 to send none). Reaching that cap counts `PasswordResetHintsCapped`, which the **Password reset hints capped** alarm (P2) watches. Its role may call `AdminGetUser` and `ListUsers` on the app pool, send the app's email, and `UpdateItem` only `PK`, `SK`, `count` and `expiresAt` in `RESETLIMIT#HINT` partitions. Looking up a Google or Apple user by `email` (`ListUsers`) asks for the address as typed and in lower case: Cognito doesn't say the filter ignores case, and a provider user whose stored address is cased some third way gets no hint (the screen's guidance mentions Google). No retries and no dead-letter queue: a request holds an address, and the person can ask again. It logs only the outcome, and counts `PasswordResetProviderHints` and `PasswordResetsLimited` (which limit, in metadata).
  - `POST /auth/password-reset/confirm` sets the new password with Cognito's `ConfirmForgotPassword` (the web client's ID, as Managed Login does), after checking the pool's password policy. Every way a code fails (wrong, expired, never sent) is one answer, `code_mismatch`.
  - A reset through Managed Login works as before, and still says nothing for an address with no account.
  - **After a reset: sign-out and a notice** (`supply-checkout-6uw.32`). Cognito's `ConfirmForgotPassword` doesn't revoke the account's refresh tokens, so without this, sessions from before a reset (an attacker's, say) kept working and nobody was told. Both resets, the app's and Managed Login's, end in that call, and Cognito then runs the **post confirmation trigger** (`PostConfirmation_ConfirmForgotPassword`), whose event names the pool, the username and the sub. So the trigger:
    0. records the reset's time in the user's own partition (`USER#<sub>` / `PASSWORD_RESET`, `passwordResetAt`, `backend/src/data/password-reset-time.ts`, 1-second timeout, alongside the sign-out): see the next bullet;
    1. signs the account out everywhere (`AdminUserGlobalSignOut`, 1-second timeout) before Cognito answers the reset, so the new password's first sign-in isn't signed out with the old sessions. That revokes refresh tokens only: an access token already issued stays valid at the API for up to 60 minutes, and a Managed Login session cookie from the last hour can get new tokens, so an old session could keep working for up to an hour: the API refuses those, from the time recorded alongside (next bullet). If the timeout aborts a sign-out that Cognito still completes, the only effects are a false alarm (`sign_out`) and a notice without the sign-out sentence;
    2. hands the security notices function `{type: "passwordReset", userId, at, signedOut}` with an asynchronous invoke (by its fixed name, `supply-checkout-<env>-security-notices`), while it fits the trigger's 4-second budget. The function looks the user up and emails the verified address **"Your Supply Checkout password was reset"** (`passwordReset`): when, that it took a code sent to this address, that devices that were signed in were signed out though a session may keep working for up to an hour (only if the sign-out worked), and what to do if it wasn't them (secure the mailbox first, then reset again). Once per 15 minutes (`NOTICE#passwordReset`), with the email change check every event gets. Logs and metrics say `via: reset`.

    Neither ever fails the reset. A failed sign-out (`Not signed out after a password reset`, with the user's sub; the notices function also logs `Reset without sign-out` with `signedOut: false`), a missing sub, or a hand-over that failed or didn't fit (`Password reset notice not queued`) is logged with the error's name only and counted in `SecurityNoticeFailures` (kind `passwordReset`, reasons `record_reset`, `sign_out`, `no_user`, `invoke`, `deferred`), which raises **Security notices failing**. The function's own failures are counted as its CloudTrail ones are, and a failed lookup is retried, then dead-lettered. **Why not CloudTrail**: `ConfirmForgotPassword` is an unauthenticated call, AWS doesn't document that its record names the user, and Managed Login's reset is recorded as its own page events (`forgotPassword_POST`), not as `ConfirmForgotPassword`; the trigger covers both with Cognito's own word for who it was. **IAM**: the post confirmation trigger's role may also call `AdminUserGlobalSignOut` on the app pool only, and invoke only the security notices function (`PostConfirmationResetSignOut`, a policy attached after the pool exists). **After deploying `identity` and `email`**: reset a test account's password in the app while it's signed in on another browser; that browser's next refresh must fail (signed out), the reset address must get one `passwordReset` email saying it was signed out, and the post confirmation function must log `Notice address` with `resetRecorded: "recorded"`, `signOut: "done"` and `resetNotice: "queued"`. Then do the same through Managed Login's **Forgot your password?**.
  - **Sessions from before a reset are refused** (`supply-checkout-6uw.33`). The sign-out above revokes refresh tokens only, so an access token from before the reset still passes API Gateway's JWT authorizer for up to 60 minutes, and a Managed Login session cookie from the last hour can get new tokens, a new 30-day refresh token among them, without the password. Every token of a session keeps that session's `auth_time` (when it signed in, whole seconds), however it's refreshed. So the post confirmation trigger records the reset's time (the trigger's clock when it started, after Cognito changed the password; it only ever moves later), and **every route the app's access token reaches** (the data, account, billing and receipts functions) refuses a token whose `auth_time` is more than 5 seconds (`RESET_SKEW_MS`) before it: 401 `unauthenticated` with the reason `password_reset` (`backend/src/api/session-reset.ts`). With no record (most users) nothing more is checked; with one, a token without a whole-number `auth_time` is refused. The 5 seconds cover the rounding down of `auth_time` and a small difference between Lambda's and Cognito's clocks, so a sign-in with the new password right after the reset is never refused; a session begun with the old password in those few seconds before the reset passes, and is signed out everywhere with the rest.
    - **Why every route, not only billing, account, members and export**: a session from the cookie can hold a new refresh token for 30 days, and the data routes are the team's data (an export is the app's lists of them). A check on a few routes would leave that session the team's data for a month. Live updates (AppSync) aren't checked: an event names a document and carries none of its data, which the app then fetches through the data API.
    - **Cost**: one strongly consistent `GetItem` of one small attribute (1 read unit), cached per container for 10 seconds (`RESET_CACHE_MS`, at most 1,000 users, least recently used dropped), so a busy user costs about one read per container every 10 seconds, not one per request: a fraction of a cent per user per month. Concurrent requests for a user who isn't cached share one read. The data and receipts functions run it alongside the membership check, its refusal winning, so it adds no wait there; the account and billing functions run it first. Every container sees a reset within those 10 seconds. A read that fails, or takes more than 2 seconds (`RESET_READ_TIMEOUT_MS`), refuses the request (500, logged), never lets it through.
    - **Signing out everywhere records it too**: `POST /me/sign-out-everywhere` (what the app sends after **Change password**, unless the person unticks **Sign out everywhere**, and when turning on two-step sign-in couldn't sign out) records the time after Cognito's `GlobalSignOut`, so the API refuses the sessions that sign-out doesn't end, as after a reset. Not `POST /me/password` itself: the person may choose to stay signed in, and the app's next call is the sign-out, with a token from before. A failed record is logged (`Sign-out time not recorded`) and counted in `SecurityNoticeFailures` (kind `signOutEverywhere`, `via: api`, reason `record_reset`), which raises **Security notices failing**, and doesn't fail the sign-out, which has happened. After the write, even a failed one (it may have landed though its answer timed out), the account function drops its own cached reset time for the caller (`SessionCheck.forget`, `supply-checkout-6uw.34`), so a session from before is refused there at once; the other functions' containers see it within their 10-second cache. Turning two-step sign-in on doesn't record it (billing's `TOTP_ON` check covers that).
    - **What the person sees** (`src/aws/session.js`, `account.js`): the app doesn't refresh (refreshed tokens keep the old `auth_time`), stops, closes any open dialog and shows **Signed out everywhere** with **Sign in again** (neutral, `supply-checkout-6uw.34`: the same refusal follows a password change or two-step sign-in turned on in another session, through `POST /me/sign-out-everywhere`, not only a reset; the API's message is neutral too, and the reason stays `password_reset`). Once refused, it sends no refresh at all (`refresh()` returns at once). **Sign in again** which revokes the refresh token and goes through Managed Login's `/logout`, so its session cookie from before can't sign straight back in, then the sign-in page asks for the password. The team, drafts and owner mark are kept for the same person, as when billing asks to sign in again. Calls still on their way are left unanswered, so nothing shows an error over that screen. **Why not `prompt=login`** on the next sign-in instead: it would only help the browser that was refused, which already goes through `/logout`; an attacker's browser never sends it, and the API check is what refuses their tokens.
    - **IAM**: the post confirmation trigger may `UpdateItem` naming only `PK`, `SK` and `passwordResetAt` (`PASSWORD_RESET_RECORD_ATTRIBUTES`) in `USER#` partitions, returning nothing, and read nothing of it (`RecordPasswordReset` in `PostConfirmationResetSignOut`). The data, account, billing and receipts functions' own roles may `GetItem` naming only those attributes in `USER#` partitions (`ReadPasswordResetTime`), with the table's key through DynamoDB, and nothing else of the table: their other reads and writes stay on their scoped role sessions. The readers' `dynamodb:Select` must be `SPECIFIC_ATTRIBUTES` (`StringEquals`, not `IfExists`): a `GetItem` without a projection may carry neither condition key, and would otherwise read a whole `USER#` item. The account function's sign-out record is written on its account-access session, in the caller's own partition. Neither role has a per-user session, so IAM can't name the user or the sort key; the code reads and writes only `USER#<sub>` / `PASSWORD_RESET` for the verified token's or Cognito's event's `sub`, and checks the key before any call. All any other read could see is when another user last reset their password. Deleting an account removes the record with the user's other rows. Residual, as for the notice address's write: DynamoDB has no condition key for `ReturnValuesOnConditionCheckFailure`, so changed code on the trigger's role could read a whole `USER#` item (a membership row's email, say) from a conditional `UpdateItem` made to fail; the code never sets it.
    - **After deploying `api` and `identity`** (check (2) gates closing `supply-checkout-6uw.33`: the bead stays open until it's done and its result is recorded on the bead): (1) sign a test account in on browser A; on browser B reset its password (the app's **Forgot your password?**). The `PASSWORD_RESET` item must appear in the table. Within 10 seconds, anything browser A does (open Members, say) must show **Your password was reset**; **Sign in again** must ask for the password. (2) The Managed Login cookie: sign in on browser A, reset the password on browser B, then within the hour open the app in a new tab of browser A. If Managed Login signs A straight in (the cookie), A must see **Your password was reset**, which shows the cookie's tokens keep the original `auth_time`. If A gets in and the app works, the cookie's sign-in got a fresh `auth_time`, so this check doesn't cover the cookie: record it on the bead (the token can't show whether a sign-in used the password, so closing it would need another signal). (3) A sign-in with the new password right after the reset must work everywhere.

- **Recording the notice address** (`supply-checkout-8jc.31`, `backend/src/identity/notice-address.ts`). An email change is told to the address in `USER#<sub>` / `NOTICE_ADDRESS` ("What it protects", above), so an account must have one before anyone can change its email. It's recorded, with GET /me's rule (only an address the account API trusts, `emailVerifiedFrom`, that normalizes; never over one already recorded; never for an account being deleted, checked in the same transaction), by:
  - the **post confirmation trigger** (`post-confirmation-handler.ts`, on every app pool, providers or not), when a native user confirms their sign-up with Cognito's email code (or a forgotten password): before they have any token to change the email with. Cognito reports a failed post confirmation trigger to the client after the user is confirmed, so it never throws;
  - the **pre token generation trigger** (with Google or Apple on), at every token, once it has settled whether the email is verified: a Google or Apple user's is first verified there, and a linked user's once it's the address they proved. Never an address the trigger has just unverified or tried to. Only with time left for its two calls within Cognito's 5 seconds (otherwise `deferred`, and a later token does it);
  - GET /me, and the security notices function when it finds none;
  - for accounts made before this, the one-time `notice-address` backfill ([Backfills](#backfills)), which the owner runs after the deploy.

  Both triggers read only whether an address is recorded (`noticeAddressAt`), never the address, and log the outcome only (`recorded`, `present`, `not-recorded`, `untrusted`, `deferred`, `failed`; the pre token generation trigger's in its `Federated email` line as `noticeAddress`), never the email, username or sub. A failure is logged (`Notice address not recorded`) with the error's name only and counted in `SecurityNoticeFailures` with reason `record_address` (`via` `sign-up` or `sign-in`), so it raises "Security notices failing"; the account's next token or GET /me records it. Each DynamoDB call has a timeout (1 second in post confirmation; `NOTICE_CALL_TIMEOUT_MS`, 500 ms, in pre token generation, whose two calls start only while they fit its 4-second write budget), so the worst case stays well inside Cognito's 5 seconds with a cold start. A post confirmation function that errors, times out or is throttled fails the person's sign-up confirmation (Cognito reports it after confirming them), which **Sign-up trigger failing** (P1, [journeys.md](journeys.md)) watches. A pre token generation function that errors, times out or is throttled fails that sign-in or token refresh, which **Sign-in trigger failing** (P1, `supply-checkout-3sv.16`) watches, by its fixed name `supply-checkout-<env>-email-verified`. **Don't change that name once the trigger is live**: a new function name replaces the function, so CloudFormation creates the new one, points the pool's trigger and its invoke permission at it, then deletes the old one, and tokens can fail for the few seconds in between. The name was added while prod had no such trigger (neither `googleSignIn` nor `appleSignIn` was in `cdk.json`), so prod's first deploy with Google or Apple on creates it under that name and nothing is replaced. An environment that already ran the trigger under its old generated name takes the swap once, at its next identity deploy: deploy it when few people are signing in. **IAM** (`grantNoticeAddress` in `identity-stack.ts`, a policy of its own per trigger, attached after the pool exists): `GetItem` in `USER#*` partitions naming only `NOTICE_ADDRESS_CHECK_ATTRIBUTES` (`PK`, `SK`, `noticeAddressAt`), projected (`Select` `SPECIFIC_ATTRIBUTES` required, not `IfExists`, so a `GetItem` without a projection is denied, `supply-checkout-3sv.23`); `UpdateItem` and `ConditionCheckItem` in `USER#*` partitions naming only `NOTICE_ADDRESS_RECORD_ATTRIBUTES` (`PK`, `SK`, `noticeAddress`, `noticeAddressAt`, `noticeSeenHash`; the DELETING check names only the keys) and returning nothing; and the table's key through DynamoDB only (`kms:Decrypt`, `DescribeKey`, `Encrypt`, `GenerateDataKey`, as every table writer here). No other item has those attributes, so neither trigger can change a user's teams, proofs, notices or two-step record. Residual read: DynamoDB has no IAM condition key for `ReturnValuesOnConditionCheckFailure`, so a trigger's role running changed code could read a whole item in any `USER#` partition (a membership row with an email, say) from a conditional `UpdateItem` or `ConditionCheckItem` it makes fail on purpose; the code never sets that parameter. IAM can't name the user (a trigger has no per-user session) or the sort key, or require the write's condition: the code only ever writes `NOTICE_ADDRESS`, on the condition that no address is there, so a trigger's role could, at worst, set those three attributes on another item in a `USER#` partition or replace a recorded address, which needs the trigger's code changed (and the pre token generation trigger's role can already rewrite any user's attributes in the pool). **After deploying the `identity` stack**: sign up a new test account with an email code, and before loading the app, check its `USER#<sub>` / `NOTICE_ADDRESS` item exists (`aws dynamodb get-item ... --projection-expression noticeAddressAt`), and that the post confirmation function logged `Notice address` with `outcome` `recorded`. If it logged `untrusted`, Cognito's post confirmation event doesn't carry `email_verified` `"true"` at that point: record it on the bead (GET /me still records it at the first load). Then run the backfill below.
- **The welcome email** (`supply-checkout-6uw.25`). Each new account is handed to the welcome email function once its address is one the account API trusts ([Transactional email](#transactional-email) for what it sends and how it's sent once):
  - a native user, by the **post confirmation trigger**, at `PostConfirmation_ConfirmSignUp` only: a forgotten password's `PostConfirmation_ConfirmForgotPassword` hands nothing over (it signs out and sends the reset notice instead, "After a reset", above), nor does a Google or Apple user (their email isn't verified yet). It hands over the sub whether or not the event says the email is verified: the function checks the address with Cognito before sending, and counts `no_address` if the API wouldn't trust it. Admin-created users don't confirm a sign-up, so they're never welcomed;
  - a Google or Apple user, by the **pre token generation trigger**, at the Managed Login sign-in where it marks their email verified (outcome `verified`): their account's first sign-in. Later sign-ins are `unchanged` and hand nothing over, refreshes never do, and an account whose email was already verified before this was deployed is never welcomed. A first Google or Apple sign-in linked to an existing account (`AccountLink`) makes no new account and gets none. A provider that stops vouching for an address and later vouches again gets `verified` again, but the function's once-only record means no second email.

  Each trigger calls `lambda:Invoke` with `InvocationType` `Event` (`backend/src/identity/welcome-invoke.ts`, signed with the trigger's role): Lambda queues it and answers 202, so it's one short call, started only while it fits the trigger's budget, so a slow DynamoDB or a cold start can't push the trigger past Cognito's 5 seconds: in post confirmation, `WELCOME_INVOKE_TIMEOUT_MS` (500 ms) within `WELCOME_BUDGET_MS` (4 seconds) after the notice address's two calls; in pre token generation, `WELCOME_CALL_TIMEOUT_MS` (800 ms) within the 4-second write budget after the promotion and the notice address (3 seconds at worst). A failed invoke, or no time left, never fails the confirmation or the token: it's logged (`Welcome email not queued`, with the error's name, `NoTimeLeft` for no time) and counted in `WelcomeEmailFailures` (reason `invoke` or `deferred`). **Nothing tries it again**: a native user confirms once, and a Google or Apple user's later sign-ins are `unchanged`, so that account gets no welcome unless an operator invokes the function for it ([journeys.md](journeys.md), Welcome emails failing). The triggers log only the outcome (`welcome`: `queued`, `failed`, `not-new`, `no-sub`) in their `Notice address` and `Federated email` lines. **IAM** (`grantWelcome` in `identity-stack.ts`, a policy of its own per trigger): `lambda:InvokeFunction` on `supply-checkout-<env>-welcome-email` only, named by its ARN rather than referenced, since the `email` stack that makes it deploys after `identity`. The function's name is fixed for that reason (`emailResourceNames().welcomeFunction`) and reaches the triggers as `WELCOME_FUNCTION`. **After deploying** `identity` and then `email` (until `email` is deployed, the triggers' invokes fail with `ResourceNotFoundException` and are counted, so deploy both together): sign up a new test account with an email code and confirm one welcome email arrives, that the post confirmation function logged `welcome` `queued`, and that the welcome function logged `Welcome email sent` with no `AccessDeniedException` (DynamoDB Local doesn't enforce the `dynamodb:Attributes` or `dynamodb:Select` conditions; `Welcome email's team check failed` means the `Query` grants refuse it, and the email then says both next steps). Then reset that account's password and sign in again: no second email. With Google or Apple on, do the same with a new Google account: one email, `via` `Google`, at the first sign-in only.
- **Verified emails from Google and Apple.** With either provider on, three triggers in `backend/src/identity` (`supply-checkout-6v9`, `supply-checkout-0b1`) handle federated users:
  - **One way in** (pre authentication, `sign-in-guard-handler.ts`). The invariant is that a federated-only user signs in only through Google or Apple. A federated-only user is one whose username is `<provider>_<provider user ID>` for a Google or Apple entry in `identities`, or whom Cognito marks `EXTERNAL_PROVIDER`. Cognito runs this trigger for native sign-ins (password, email code, passkey) and not for federated ones, and it refuses every native sign-in by such a user, even one who somehow got a password or a passkey. Native users, including ones with a linked provider (below), are let through: a linked user keeps its native username and `CONFIRMED` status. If who counts as federated ever changes, change `isFederatedOnly()`, the `email_verified` trigger and the linking trigger together. The guard has no AWS permissions.
  - **`email_verified` from the provider** (pre token generation, `email-verified-handler.ts`). For a federated-only user it sets `email_verified` to match the provider's claim with `AdminUpdateUserAttributes`. The value is `"true"` only when the provider says the email is verified (Google sends a boolean, Apple a boolean or `"true"`/`"false"`), and `"false"` otherwise. Users can write `custom:idp_email_verified` themselves, so the trigger reads it only when Cognito has just rewritten it from the provider. That is at a Managed Login token (`TokenGeneration_HostedAuth`, not a refresh) for a federated-only user with status `EXTERNAL_PROVIDER`, and the guard makes every such token a provider sign-in. A failed update is logged and the sign-in goes ahead, and the next sign-in tries again. A failed promotion leaves the user unverified. A failed downgrade leaves them verified until a later sign-in succeeds, and is logged at error level as its own outcome, `downgrade-failed`. Its role can write its own log group and call `cognito-idp:AdminUpdateUserAttributes` on this pool only. The grant is a separate IAM policy attached after the pool exists, because the pool names the function and the function can't name the pool.
  - **Linking to an existing account** (pre sign-up, `account-link-handler.ts`). Cognito runs it the first time a Google or Apple identity signs in (`PreSignUp_ExternalProvider`), before it creates a user. Other sign-ups pass through unchanged, and it never confirms or verifies anyone. It links the identity to an existing native user with `AdminLinkProviderForUser`, so the sign-in lands in the same user (same `sub`) and so the same teams. It links only when all of these hold:
    - The provider says the email is verified. `custom:idp_email_verified` is fresh from the provider here, since the user doesn't exist yet.
    - **The provider is authoritative for the address**, not just someone who once checked it. For Google that's `@gmail.com` or `@googlemail.com`, or a Workspace account whose `hd` claim (mapped to `custom:idp_hd`, read only here) equals the email's domain. For Apple it's a private relay address (`@privaterelay.appleid.com`), `@icloud.com`, `@me.com` or `@mac.com`. A personal Google or Apple account can still carry a work address its owner verified years ago and no longer controls, and linking on that would hand the address's current owner's account to them. Other addresses get a separate account. Linking those is the settings-based flow for a signed-in user (`supply-checkout-b4g`).
    - The email is plain ASCII with no `"` or `\`. Addresses and domains are compared after lowering ASCII letters only, so Unicode case folding can't make two match.
    - ListUsers finds exactly one native (not federated-only) user with that email, on one page. Several matches are refused rather than guessed at.
    - That user is `CONFIRMED`, enabled and has `email_verified` `"true"` (proven with Cognito's own code).
    - It has no identity from the same provider yet.
    - If it already has a Google or Apple identity linked, its `email` still equals `custom:linked_email`, the address recorded when that identity was linked. That attribute is set only by this trigger: no IdP maps it and no client can write it.

    Linking records the email in `custom:linked_email`, then links. Otherwise the sign-up goes ahead and makes a separate federated-only user, as before. After linking, the trigger fails that sign-in on purpose with `ACCOUNT_LINKED:<provider>` (Cognito would otherwise fail it with "Already found an entry for username"). Cognito sends the person back with it in `error_description`, and the web app (`src/aws/session.js`) signs in again once, straight to that provider (`identity_provider`), which lands in the linked user. If a Cognito call fails, the sign-in fails and can be tried again, since going ahead would make a separate account for good. Each call has a 1.5-second timeout, so all three fit in the 5 seconds Cognito gives a trigger.

    Its role can write its own log group and call `cognito-idp:ListUsers`, `cognito-idp:AdminUpdateUserAttributes` and `cognito-idp:AdminLinkProviderForUser` on this pool only. IAM can't limit ListUsers' filter; the code only searches by exact email. Like the `email_verified` trigger's grant, it's a separate policy. A linked user signs in with the provider or natively.
  - **Linked users' `email_verified`** (`supply-checkout-kgw`, the same pre token generation trigger). Cognito applies the provider's attribute mapping to a linked user at every provider sign-in, so a changed provider email overwrites `email` while `email_verified` stays `"true"`. The rule: a linked user's `email_verified` is `"true"` only for the address in `custom:linked_email`, which is always one the person proved with a Cognito code. For a native user with a Google or Apple identity linked, whose email differs from the recorded one while `email_verified` is `"true"`:
    - At a Managed Login token (`TokenGeneration_HostedAuth`), the only kind that follows a provider sign-in, the trigger sets `email_verified` to `"false"` (outcome `linked-unverified`), whatever the provider claims. The person proves the new address with a Cognito code, as for any change of email. We chose this over restoring the recorded address: the trigger only ever takes trust away, never writes an address the provider no longer asserts (and which may be taken or no longer the person's), and Cognito would rewrite a restored address again at every sign-in anyway. Before the downgrade it sets `custom:downgrade_pending` to `"1"`, and the downgrade clears it in the same `AdminUpdateUserAttributes` call, so only a successful downgrade clears the flag (`supply-checkout-0qr8`). If the flag's write fails, the downgrade is still tried. A failed downgrade is tried once more after a 250 ms pause, when there's time left: each call has a 1.2-second timeout, so the flag, two tries and the pause fit in 4 of the 5 seconds Cognito gives a trigger. If both tries fail, that sign-in fails too (`linked-downgrade-failed`, counted in `EmailUnverifyFailures`) and can be tried again. Its log says whether the flag is set (`flagged`) and carries the user's correlation handle (`user`): the first 16 hex digits of an HMAC-SHA256 of the user's `sub`, keyed with a secret the identity stack generates in Secrets Manager. The key reaches the function as an environment variable through a dynamic reference resolved at deploy time, so the role gets no Secrets Manager access. The handle names no one to someone reading the logs; an operator with the key finds the user (runbook in [journeys.md](journeys.md), "Email verification not saved"). A native Managed Login sign-in looks the same to the trigger, so a native change of email that's first followed by a Managed Login sign-in is unverified too and needs its code again.
    - While `custom:downgrade_pending` is set, a downgrade is owed: a Managed Login token with `email_verified` `"true"` downgrades again, even when the email is the recorded one (the address may have been recorded in the moment before the flag). If `email_verified` is already `"false"` (an operator unverified the user), any token clears the flag (`linked-cleared`), since a later `"true"` can only come from a Cognito code; a failed clear (`linked-clear-failed`, counted in `EmailVerifyFailures`) leaves the user untrusted until a later token.
    - At any other token (a refresh, an API sign-in, which never follow a provider sign-in), the trigger records the email in `custom:linked_email` (`linked-recorded`), so the API trusts it and a second provider can still be linked for it, only when it's the address the person last proved with a code in the app (`supply-checkout-ytr2`). A code proves only the address it was sent to (`supply-checkout-cjw7`): once Cognito has sent a code, `POST /me/email/code` reads GetUser again and, if the address is unchanged, writes an `EMAIL_CODE_SENT` item in the caller's own `USER#` partition (the SHA-256 of the address, trimmed and ASCII-lowercased, and the time; otherwise 409 `email_changed`). `POST /me/email/verify` asks Cognito to check the code only if the caller's email is that address and the code is less than a day old; then, if GetUser shows the same address verified, it writes a `VERIFIED_EMAIL` item (the hash and the time) and deletes `EMAIL_CODE_SENT` in one transaction, on the condition that it's still for that address (`backend/src/data/verified-email.ts`). Otherwise it records nothing, deletes the used code's record, and answers 409 `email_changed`. So a provider's rewrite between sending and checking a code gets nothing recorded, even if Cognito accepted the old code for the new address, which it doesn't document either way. Both writes use the function's usual session. The trigger reads the proof (`GetItem`, strongly consistent, 1.2-second timeout) and records the email only when it matches and is less than an hour old (the app refreshes right after the code, and an old proof can't be replayed for an address that comes back later); the same write clears `custom:downgrade_pending`, so a proven address also ends a pending downgrade without a Managed Login sign-in. Any other verified-looking address is left unrecorded (`linked-not-proven`, or `linked-downgrade-pending` while the flag is set), and the API keeps treating it as unverified until the person verifies it in the app. This is a positive signal: nothing has to be written to Cognito for a rewritten address to stay unrecorded, so throttling the pool's shared user-update quota can't get one recorded. A failed read (`linked-lookup-failed`) or recording (`linked-record-failed`), both counted in `EmailVerifyFailures`, lets the refresh go ahead, and the next token tries again. The trigger's role may read only that hash: `dynamodb:GetItem` on the app table where the partition key is `USER#…` (`dynamodb:LeadingKeys`), naming no attributes but `PK`, `SK`, `verifiedEmailHash` and `verifiedAt` (`dynamodb:Attributes`, `VERIFIED_EMAIL_ATTRIBUTES` in `backend/src/data/schema.ts`, with `dynamodb:Select` `SPECIFIC_ATTRIBUTES` required, not `IfExists`, so a `GetItem` without a projection is denied, `supply-checkout-3sv.23`), and `kms:Decrypt` on the table's key only through DynamoDB. IAM can't name the user (the trigger has no per-user session) or the sort key, so it could read those two attributes of any user; no other item has them, and it's a hash, not an address. The account function needs no new permission (its session already reaches the caller's own partition) and no `AdminUpdateUserAttributes`. Deleting an account removes both items with the user's other rows (neither sort key is a `LIMIT#` one). The identity stack now deploys after the primary region's data stack, whose SSM output names the table's key.

    The account API applies the same rule to what GetUser returns (`backend/src/api/cognito-user.ts`): a linked user's email counts as verified only while it's the recorded one, and no user's counts while `custom:downgrade_pending` is set, so a rewritten address never lists another person's invites in `/me` or accepts them, even if the trigger's write failed. That relies on the web client reading every attribute (no `ReadAttributes`), which a test checks: GetUser must return `custom:linked_email` and `custom:downgrade_pending`. Reading the flag tells a user only that their own downgrade is pending. The linking trigger also refuses a user whose downgrade is pending. A native change of email counts once the person has verified it in the app and the app's next refresh has recorded it. The linking trigger refuses such a user both ways: its `email_verified` is `"false"`, and its email isn't the recorded one, so a victim's first Google or Apple sign-in with the rewritten address makes its own account. The trigger's role can call `AdminUpdateUserAttributes` on this pool, and read the proven address's hash as above.
  - **Accepted risks.**
    - If a provider sign-in left the claim out, Cognito would keep the attribute's last value, which the user may have written. Google and Apple always send `email_verified` with the `email` scope. A forged verified email would show that address's pending invites (team name and role) in `/me`. Joining still needs the token from the emailed link.
    - Linking trusts Google's `hd` claim for a Workspace address, and so Google's own check that the Workspace tenant owns the domain (DNS verification when the domain is added). A tenant's admin controls every mailbox at the domain anyway. If Google ever let a tenant keep or claim a domain it doesn't own (say, one that lapsed and was re-registered by someone else), that tenant's accounts could be linked to our accounts at that domain. We rely on Google here as every "Sign in with Google" relying party does.
    - If a linked user's downgrade fails after Cognito rewrote the email (even with the flag's write failing too, say because someone flooded the pool's shared user-update quota), the rewritten address keeps `email_verified` `"true"` in Cognito until a later Managed Login sign-in downgrades it. No refresh records it, since no code proved it, and the API doesn't trust it (`supply-checkout-ytr2`); the "Email verification not saved" alarm still reports the failed downgrade. What's left: an address Cognito verified outside the app (a client calling `VerifyUserAttribute` itself, or an operator setting `email_verified`) isn't recorded until the person verifies it in the app again, or the operator also sets `custom:linked_email`.
    - With `keepOriginal` on, a native change of email keeps the old, verified address in `email` until the new one's code is entered, so `/me` shows the old address as verified while the new one waits. The app has no change-of-email flow yet, so there's no pending-address signal; a client that changes its email through Cognito directly verifies it there, and then verifies it in the app before it counts for a linked user.
    - The `email_verified` trigger's log correlation key reaches the function as an environment variable, so anyone allowed `lambda:GetFunctionConfiguration` on it, or who can read CloudFormation drift detection's results for the identity stack, can read the key, and with it turn a handle back into a user by hashing candidate `sub`s. Those are operators who can already read the logs and the user pool; the handle protects only against someone who has the logs alone.

**Verifying an email address in the app** (`supply-checkout-ocjk`). A user whose email isn't verified (a native change of email, or a linked user's address the trigger unverified) verifies it from the web app: `POST /me/email/code` and `POST /me/email/verify` on the account function call Cognito's `GetUserAttributeVerificationCode` and `VerifyUserAttribute` with the caller's own access token (`cognitoEmailCodes()` in `backend/src/api/cognito-user.ts`), which the web client's `aws.cognito.signin.user.admin` scope allows. Like GetUser, they need no IAM permission. They go through the API rather than straight from the browser so that the app keeps talking only to the API: the content security policy's `connect-src` has no Cognito regional endpoint and `config.json` names no region (ADR 0010), the handler checks the token's `sub` against the authorizer's as for every account route, and API Gateway throttles both routes in front of Cognito's own per-user limits on codes and tries. A user can also ask for only 10 codes a UTC day (a counter in their own `USER#` partition, `backend/src/data/email-codes.ts`, like the daily team limit), so one user can't use up the route's shared throttle. A user whose downgrade is pending (`custom:downgrade_pending`) doesn't count as verified, so they can ask for a code; since `supply-checkout-ytr2`, a correct code records the address as proven and the next refresh records it and clears the flag. The app's dialog suggests signing in again when `/me` hasn't caught up. Cognito's refusals come back as `bad_request` with `code_mismatch` or `code_expired`, 429 `quota_exceeded`, or 409 `email_in_use`; only an error's name is ever logged, never the token, the code or Cognito's message. After a code is accepted the account function records the address as proven (a `VERIFIED_EMAIL` item, above) and the app refreshes its tokens, and that refresh is when the pre token generation trigger records a linked user's new address, so `GET /me` then shows `emailVerified: true`. A code counts only for the address it was sent to (above): if the email changed after the code was sent, or while it's checked, or Cognito doesn't show it verified, the route records nothing and answers 409 `email_changed`, and the person sends a new code.

The stack publishes `user-pool-id`, `user-pool-arn`, `web-client-id`, `issuer-url` and `auth-url` under `/supply-checkout/<env>/identity/`. `cognitoJwtAuthorizer()` in `lib/identity.ts` builds the HTTP API's JWT authorizer from them. A change to `issuer-url`, `web-client-id` or `user-pool-id` (the realtime authorizer's pool), the operator pool's `ops-issuer-url` or `ops-client-id`, or `auth-url`, made outside a deploy pages P1 through an `OperatorAuthorizer*` rule (`supply-checkout-6uw.23`, under [Operators](#operators)): rewritten, the next `api` or `realtime` deploy would accept another pool's or client's tokens, or the next web publish would send people to sign in elsewhere. The auth function doesn't read `auth-url`: its `AUTH_URL`, where it sends the sign-in code, PKCE verifier and refresh token, is `https://auth.<env domain>` fixed in the template, and the function refuses to start unless it's `auth.` on the domain of its first `https://app.` origin in `ALLOWED_ORIGINS` (`expectedAuthUrl` in `backend/src/api/auth-handler.ts`). `scripts/publish-web.mjs` likewise refuses to write a `config.json` whose `authUrl`, `apiUrl` or realtime host isn't the one built from the deployment config's domain ([web-app.md](web-app.md)).

**Team isolation**, two layers:

1. **Membership, in the handler.** API Gateway's JWT authorizer checks the token; the handler also requires an unexpired access token and takes the user from `sub`. The team comes only from the path: `authorizeTeam` reads the caller's `MEMBER` item on every request (so a role change applies at once) and issues the `TeamContext` every data function needs. A body that names a team, or any server-owned field, is refused. Then the role (ADR 0007): each route in `routes.ts` names the least role that may call it (`minRole`), checked before anything runs (`roles.ts`). Viewers read; contributors also write sheets and inventory and run the commands; owners also import and manage members. A role below the route's gets 403 `permission_denied` with `reason` `view_only` (the web runtime hands it to the app as view-only access) or `owners_only`, and `backend/test/roles.test.ts` calls every team route as every role.
2. **IAM, `dynamodb:LeadingKeys`.** The data function's own role has no DynamoDB access. For each team it assumes the `DataAccessRole` with the session tag `teamId=<path team>` (cached for up to an hour per team), and that role allows `GetItem`, `PutItem`, `DeleteItem`, `UpdateItem`, `ConditionCheckItem` and `Query` (the last three for the inventory commands' transactions; no `Scan`, no batch writes) only on items whose partition key is `TEAM#${aws:PrincipalTag/teamId}`, or the team's date index partition `TEAM#…#PROJECTS` (its name before the projects rename, `TEAM#…#SHEETS`, was dropped with the sheets aliases, `supply-checkout-005.6.5`). Every item a team route touches is in one of those partitions, so a bug that built another team's key would be refused by IAM too. The same role denies (`NoTeamBillingWrites`, `supply-checkout-3sv.25`) any `PutItem`, `UpdateItem` or `DeleteItem` that names one of a team's billing, Stripe, comp, membership-count, closure or purge attributes anywhere in the request (`dynamodb:Attributes` with `ForAnyValue:StringEquals`, the list `DATA_ROLE_DENIED_ATTRIBUTES` in `backend/src/data/schema.ts`): `plan`, `seats`, `owners`, `members`, `homeRegion`, `trialEndsAt`, `test`, the `stripe*` fields, `closedBy`, `purgeAfter`, `purging`, the `comp*` fields and a member's `photoId` (only the account function sets it). IAM can't condition on the sort key, so the deny covers every item in the team's partitions, and documents refuse fields with those names (`isReservedField`). The only `META` write the data routes make is the first-run checklist (`PATCH /teams/{teamId}/checklist`: `checklistStartedAt`, `checklistReceipt`, `checklistDone`, conditioned on `closedAt`); team settings are their own item. `ConditionCheckItem` isn't denied, so transactions still check the team is open. Residual risk: `name`, `status`, `closedAt`, `createdAt`, `version` and the GSI1 keys can't be in the list, because projects use the same top-level names (and the checklist conditions on `closedAt`), so on `META` they stay protected by the data layer alone, and IAM can't stop a `DeleteItem` of `META` that names no attribute. `backend/test/data-policy.ts` mirrors the deny in the handler tests. DynamoDB Local doesn't enforce `dynamodb:Attributes`, so after deploying the `api` stack, as an owner of a test team, mark a first-run checklist step, change the team's settings, create, edit and delete a project and a product, check out and return an item, and confirm the data function's log group has no `AccessDeniedException`. Then create products whose keys are exactly `test` and `seats`, check each out onto a project and return it, and confirm the same: a project's lines are a nested map (`#items.#line`), and only top-level names count in `dynamodb:Attributes`, so a product key that's on the list must still work.

**First sign-in and teams** (`supply-checkout-l5y`; the app's side is in [docs/api/onboarding.md](api/onboarding.md)). `GET /me` lists the caller's teams (role, plan, trial status) and the live invites for their **verified** email. `POST /teams` creates a team with the caller as owner, `homeRegion` from the serving region and a 14-day trial; it's idempotent per `Idempotency-Key` (the team's ID is derived from the user and the key, and its creation is conditional) and limited to 5 teams per user per UTC day by a counter in the user's partition. `POST /invites/{inviteId}/accept` joins the team that invited the caller's verified email, with `{"token"}` from the emailed link; the transaction checks the token's hash, the address, the expiry and that the invite is unused. Each user can be in at most 20 teams, which also bounds the role sessions one `/me` needs, and the account routes have their own API Gateway throttles (`throttle` in `routes.ts`), as does the CSV import (5 requests a second, burst 10), which can write up to 1,000 items. The email comes from Cognito's `GetUser`, called with the caller's own access token.

These routes write outside any team the caller is in (a new team, or the team they're joining, plus their own `USER#` rows), so the `account` function can't use the `DataAccessRole`. It assumes the **`AccountAccessRole`** with five session tags: `userId` (the token's `sub`), `teamId`, `invitee` (the SHA-256 of the verified email), `member` and `inviteLimit` (the invite limit key of an address being invited: its SHA-256 without a `+tag`, `inviteLimitKey`), unused ones set to `.`, which no key matches. That role allows `GetItem`, `PutItem`, `DeleteItem`, `UpdateItem`, `ConditionCheckItem` and `Query` (no `Scan`, no batch writes) only where the partition key is `USER#<userId>`, `TEAM#<teamId>` or, on `GSI2`, `INVITEE#<invitee>`, and only `UpdateItem` and `DeleteItem` where it's `USER#<member>`, naming no attributes but `PK`, `SK` and `role` (`dynamodb:Attributes`, `MEMBER_ROW_ATTRIBUTES` in `backend/src/data/schema.ts`) and returning nothing (`dynamodb:ReturnValues` `NONE`). The update is conditioned on `attribute_exists(PK)`, so it can't create a row. Where it's `INVITELIMIT#<inviteLimit>`, it allows only `UpdateItem`, naming only `PK`, `SK`, `count`, `type` and `expiresAt` (`INVITE_LIMIT_ATTRIBUTES`) and returning nothing: the address's daily invite counter, and nothing else about it. Where it's `FEEDBACK#<teamId>` (the tagged team), it allows only `PutItem`, naming only `FEEDBACK_ATTRIBUTES` (the report's own fields, no email) and returning nothing (`WriteFeedbackReport`): a member's report, and no way to read, list, change or delete one. The handler tags a team only when the request is entitled to it: the ID derived from the caller's own idempotency key, the team of an invite found under their verified email, a team in their own `USER#` rows after the membership check, or the path's team on the members routes (which then check membership and role). It tags a `member` only on a role change or removal, after the caller's owner check and only for a user whose `MEMBER` item is in that team, so the member's team-switcher row changes in the same transaction as their membership. It tags an `inviteLimit` only when an owner creates or re-sends an invite, after the owner check, with the limit key of the invite's address (from the request for a new invite, from the stored invite for a re-send). Residual risk: IAM can't limit the sort key, so a session tagged with a member could still delete any of that member's rows, or change `role` on one that exists (their switcher rows for other teams, or their daily team-creation counter). It can't read them, write any other attribute or create items, and only the members routes set the tag, after the checks above; `backend/test/members-api.test.ts` checks that their writes stay inside that list. The `DataAccessRole` is unchanged.

**Invites** (`supply-checkout-5tp`; the data layer is in [backend.md](backend.md)). Owners invite an address with a role; the `account` function writes the invite and emails the link, and owners list, revoke and re-send invites. Creating and re-sending have the tightest API Gateway throttles (5 requests a second, burst 10), and each team (50), each team for one address (3) and each address (15, from every team together) has a daily limit. Invite addresses must be bare addr-specs, which the mailer checks again. Removing a member revokes their other invites to the team.

**Reports, Report an issue** (`supply-checkout-bmsh.1`; the storage is in [backend.md](backend.md)). `POST /teams/{teamId}/feedback` is served by the `account` function: it needs the caller's membership of the path's team (any role) and the team in the path, so isolation and the purge follow the team, and the user's daily counter in `USER#<userId>` the account role already reaches. (A user-scoped route would have needed a user-only session and a way for the purge to find a user's reports across teams.) The report is written to its own partition, `FEEDBACK#<teamId>`, never the team's: IAM can't condition on a sort key, so an item in `TEAM#<teamId>` could be read back by the `DataAccessRole`, which holds every item there. The `DataAccessRole` has no statement for `FEEDBACK#`, so no data route can list, fetch or change a report even through a bug; the `AccountAccessRole` may only `PutItem` there (`WriteFeedbackReport`, above); the team purge's role may `Query` (keys only) and `DeleteItem` in `FEEDBACK#*`, so a team's reports go with it; and everything else (the triage CLI) uses the owner's own AWS credentials. Reports expire (TTL) 2 years after they're sent. The route has its own throttle (2 requests a second, burst 5, across all callers), a 4 KB body cap checked in the function, and 5 reports per user per UTC day. New reports are found across teams on GSI1 (`FEEDBACK#STATUS#new`, sorted by time), an existing index with a new key pattern, not a new index or table: the data role's GSI1 access is its own `TEAM#` partitions only, and the report volume is tiny. Deploy: the `api` stack (the account role's policy, the route and its throttle) and the `observability` stack (the purge role's partitions).

**Members and roles** (`supply-checkout-dj6`). Owners list members, change roles and remove members; anyone can leave. The team item's `owners` count moves in the same transaction as every owner membership change, conditioned on `owners > 1` for a decrease, so the last owner can't be removed, demoted or leave (409 `aborted` with `reason: "last_owner"`), even when two owners act at once. Owner actions on someone else also re-check the caller's own `MEMBER` item at write time.

**Sign-in sessions.** The web app keeps access and ID tokens in memory. `/auth/session` redeems the Managed Login code (with its PKCE verifier) at Cognito's `/oauth2/token` and sets the refresh token as `__Secure-sc_refresh` (`HttpOnly; Secure; SameSite=Strict; Path=/auth`, 30 days). `/auth/refresh` redeems it, and because rotation is on, stores the new refresh token each time. `/auth/sign-out` revokes it and clears the cookie. Each checks that `Origin` is the app's (`https://app.<env domain>`, plus `http://localhost:5173` outside prod), and CORS allows only those origins, with credentials.

**Latency.** Functions run Node.js 24 on arm64, bundled by esbuild (ESM, minified, the AWS SDK v3 clients tree-shaken into the bundle) with their clients created once per container. The data function has 1 GB of memory, for CPU. A warm read is a membership check (one `TransactGetItems`) and one `GetItem` or `Query`; a write adds a `PutItem`.

**Deploying.** The api stack reads, from SSM in its region: the `api.` certificate (the domain stack), the table's KMS key ARN (the data stack) and the issuer, web client ID and auth URL (the identity stack). So deploy those first. The synth bundles the handlers, so install the backend's dependencies too. Deploying `api` and `observability` deploys the stacks they depend on (data and audit among them), so keep `-c backupCopy=false` until [step 4 of the backup setup](backups.md#setting-it-up) ([why](#the-cloudtrail-trail)):

```bash
aws sso login --profile supply-prod
(cd backend && npm ci)
cd infra && npm ci
npx cdk diff supply-checkout-prod-us-east-1-api --profile supply-prod -c backupCopy=false
npx cdk deploy supply-checkout-prod-us-east-1-api supply-checkout-prod-us-east-1-observability --profile supply-prod -c backupCopy=false
# No token: API Gateway answers 401 {"message":"Unauthorized"}
curl -si https://api.supplycheckout.com/teams/t/products | head -1
```

The observability stack adds the API errors and API slow alarms, reading the API's ID from `/supply-checkout/<env>/api/api-id`.

In the primary region it also adds the scheduled checks and the closed-team purge ([Observability](observability.md)). The stuck-import check's IAM conditions (`dynamodb:LeadingKeys`, `dynamodb:Attributes`, `dynamodb:Select`) aren't enforced by DynamoDB Local, so after the first deploy of the observability stack, and after any change to that policy or to `listStuckImports`, run both checks once and confirm each answers without an error and logs no `AccessDeniedException`:

```bash
aws lambda invoke --profile supply-prod --region us-east-1 \
  --function-name supply-checkout-prod-stuck-imports /dev/stdout   # {"stuck":0}
aws lambda invoke --profile supply-prod --region us-east-1 \
  --function-name supply-checkout-prod-email-quota /dev/stdout     # {"usedPercent":…}
```

A `FunctionError` in the response, or `AccessDeniedException` in the log group of `supply-checkout-prod-stuck-imports` ([Finding a function's log group](journeys.md#finding-a-functions-log-group)), means the role and the query disagree: the query must send `Select: SPECIFIC_ATTRIBUTES` and name only `STUCK_IMPORT_ATTRIBUTES`. The same goes for the team purge (`TEAM_PURGE_ATTRIBUTES`): invoke `supply-checkout-prod-team-purge` once (`{"purged":0,"failed":0,"due":0}` with no closed teams due) and check its log group for `AccessDeniedException`. To test it end to end in staging, close a test team and set its META item's `purgeAfter` and `GSI1SK` to a past time.

**Account deletion and Cognito.** `DELETE /me` deletes the caller's Cognito user with `DeleteUser` and their own access token (the `aws.cognito.signin.user.admin` scope the web app already asks for), like `GetUser`: the account function has no IAM permission to delete users, so a bug can't delete anyone but the caller. After it, the user's refresh token stops working at once; an access token they still hold passes API Gateway's JWT check until it expires (at most 60 minutes), but the account routes that matter call `GetUser`, which refuses it (401), and they're in no team, so the data routes refuse it too.

### Receipt reading

`POST /teams/{teamId}/receipts/read` ([ADR 0008](adr/0008-receipt-reading-bedrock.md), `supply-checkout-kx8`) is served by the `receipts` function (`backend/src/api/receipts-handler.ts`, [backend.md](backend.md)): the app sends a receipt photo and gets back the lines Claude read, for its review screen. Nothing is saved, and the photo is never stored or logged.

- **Model.** `RECEIPT_MODEL_ID` in `infra/lib/config.ts` (Claude Haiku 4.5 through its `us.` cross-region inference profile), passed to the function as `RECEIPT_MODEL_ID`, so changing the model is a deploy, not a code change. The client is the Anthropic SDK's Bedrock client (`AnthropicBedrock` from `@anthropic-ai/bedrock-sdk`) on Bedrock's InvokeModel API, which takes the `us.` inference profiles and structured outputs. (ADR 0008 names `AnthropicBedrockMantle`; the Messages-API Mantle endpoint takes `anthropic.` model IDs, needs `bedrock-mantle:CreateInference`, and doesn't support structured outputs, so it isn't used.) The client is built in `backend/src/receipts/client.ts` with the endpoint (`https://bedrock-runtime.<region>.amazonaws.com`) and the SDK's log level (`off`) set in code, so `ANTHROPIC_BEDROCK_BASE_URL` or `ANTHROPIC_LOG` in the function's environment can't send the photo elsewhere or log it, and the function won't start with `AWS_BEARER_TOKEN_BEDROCK` set (calls are always signed with its role) or with `ANTHROPIC_CUSTOM_HEADERS` set (no extra headers on its requests).
- **IAM.** The function's role may call `bedrock:InvokeModel` on the receipt model's inference profile in its own region, and on the foundation model in each region the US profile routes to (`RECEIPT_MODEL_REGIONS`), only when the call comes through that profile (`bedrock:InferenceProfileArn`). No other model, no `*`. For DynamoDB it assumes the **`ReceiptAccessRole`** with two session tags, the path's team (`teamId`) and the caller (`userId`, always the token's `sub`; the trust policy requires both and allows no others), which may `GetItem` and `Query` only in `TEAM#<teamId>` (the membership check, the team's allowance from its `META` item, and the inventory to match lines against), `UpdateItem` there only the attributes of the receipt counters (`RECEIPT_USAGE_ATTRIBUTES`: `PK`, `SK` and `receipts`, so it can't rewrite `type` or any other field of the partition's other items, or set a TTL), `UpdateItem` in `RECEIPTRATE#<userId>` only the per-user rate counters' attributes (`RECEIPT_RATE_ATTRIBUTES`: `PK`, `SK`, `count` and `expiresAt`), returning nothing, and `UpdateItem` in the one shared `RECEIPTTRIALS` partition only the account-wide trial count's attributes (`RECEIPT_TRIAL_CAP_ATTRIBUTES`: the same four), returning nothing (`TrialReceiptCapOnly`, `supply-checkout-i1d.3`). No puts, deletes, index or scan. Residual risks, accepted: IAM can't limit the sort key, so the session could add a `receipts` attribute to another item of its own team's partition (the code only names `USAGE#` keys), or create rate counter items with any sort key in its own user's partition. Any session can move the shared trial count (every trial read does), so a caller could only use up the day's trial reads, which the per-user and per-team limits already bound, and can read nothing from it.
- **Limits** (`supply-checkout-wxx`, [backend.md](backend.md)). Each caller's rate, from all their teams together: 10 reads a UTC minute, 60 an hour and 200 a day (`RECEIPT_RATE_LIMITS`), and at most 30 reads for trial teams a UTC day (`RECEIPT_TRIAL_READS_PER_USER_PER_DAY`, provisional; a mitigation for one account farming trial teams), then 429 `rate_limited` with `Retry-After`. Every trial team's reads together: at most `RECEIPT_TRIAL_READS_PER_DAY` (500, provisional) a UTC day, set per deploy with `-c receiptTrialReadsPerDay=<0..100000>` (0 stops every trial read), then 429 `rate_limited` with `Retry-After` to the next UTC day (`supply-checkout-i1d.3`); paying teams aren't counted or stopped. Bedrock spend is watched by the **Bedrock spend high** alarm and the `supply-checkout-<env>-bedrock` budget ([observability.md](observability.md)). Each team's allowance, provisional until pricing is decided (`supply-checkout-akz`): 200 a UTC month while it pays or has a live comp (`RECEIPTS_PER_TEAM_PER_MONTH`), 25 in all for a trial (`RECEIPTS_PER_TRIAL`), then 429 `receipt_limit`. Both are counted atomically before the model is called; a read the model service refused with a throttle (429) or a 503 is given back to the team. A team that subscribes mid-month has that month's trial reads counted against its 200. The photo is at most 1,500,000 bytes, a JPEG or PNG whose bytes match its type. API Gateway throttles the read route at 5 requests a second (burst 10) and the usage route (`GET /teams/{teamId}/receipts/usage`) at 10 (burst 20), across all callers: the per-user limits stop one caller using up the route's share. **Reserved concurrency** is off by default; `-c receiptsReservedConcurrency=<1..100>` caps the receipts function's concurrent reads, but Lambda takes it from the account's unreserved concurrency, which must stay at least 100, so check the account's quota first (`aws lambda get-account-settings`): with the default quota of 1,000 a value of 20 is safe, and with a new account's lower quota any value can fail the deploy.
- **Time.** The function has 29 seconds (API Gateway stops waiting at 30). The model call has a 25-second deadline, or less if the function has less time left, after which it's aborted and the app gets 504 `model_timeout`.
- **After the first deploy**, and after changing the model or its regions, read one real receipt through the app (or `curl` with a contributor's token and a small JPEG as base64) and check the function's log line `Request` has `status: 200` and token counts. An `AccessDeniedException` (status 503, `failureDetail: "APIError:403"`) means the policy and the profile disagree: Bedrock routed the call to a region missing from `RECEIPT_MODEL_REGIONS`, or the account hasn't enabled the model there.

### Profile photos

A user's profile photo (`supply-checkout-6uw.30`, [backend.md](backend.md)) is served by the `account` function: `PUT /me/photo` (5 a second, burst 10, across all callers; 20 uploads per user a UTC day is the real cost bound), `DELETE /me/photo` (2, burst 5) and `GET /teams/{teamId}/photos` (50, burst 100, like `GET /me`; any member), with `photoUrl` on `GET /me` and the owners' members list.

- **Bucket.** `supply-checkout-<env>-photos-<region>-<account>` (`photosBucketName`, `backend/src/photos/names.ts`), the data stack's `PhotosBucket`, in the primary region only, published as `/supply-checkout/<env>/data/photos-bucket-name`. Block Public Access, SSL only, SSE-S3, bucket-owner-enforced ownership, server access logs to the logs bucket under `s3/photos/`, incomplete multipart uploads aborted after a day, and `RETAIN`. One object per photo, `photos/<photoId>.jpg`, the ID random: no user ID, name or email in any key.
- **No versions, no backup copy.** The bucket isn't versioned (the S3 versioning test exempts it by name), so a photo its owner removed or replaced, or deleted with their account, is gone at once rather than kept as an old version, and it isn't in AWS Backup (the backup plan selects only the table). A photo lost to an accident is re-uploaded. Restoring the table from a backup can bring back a photo record or MEMBER copy that names an object since deleted: the URL then fails to load and the app shows initials until the person uploads again.
- **IAM.** Only the account function's own role reaches the bucket: `s3:PutObject`, `s3:GetObject` and `s3:DeleteObject` on `photos/*` (`grantPhotos` in `api-stack.ts`, cdk-nag's IAM5 acknowledged for the prefix): no `ListBucket`, no other prefix, no ACL, tagging or version actions. The account-access role (the per-user DynamoDB session) has no S3 at all. `PHOTOS_BUCKET` and `PHOTOS_REGION` reach the function by environment; in a second region (phase 2) it still writes to the primary region's bucket.
- **Serving.** The function presigns a GET for an hour (or less: never past its own role's credentials) that makes S3 answer `Content-Type: image/jpeg`, `Content-Disposition: inline` and `Cache-Control: private, max-age=3600`. The web app's `img-src` allows `https://<bucket>.s3.<region>.amazonaws.com`, that one bucket's regional host, and nothing else of S3 (`infra/lib/web/content-security-policy.ts`). The bucket has no CORS: the app shows the URLs with `<img>`, never `fetch`. The URLs are bearer links, so they're never logged.
- **Access logs.** The bucket's S3 server access logs record each presigned URL's query string, signature included; it expires within the hour and can't sign anything else.
- **What's served.** The table and a scan's entropy-coded data can carry arbitrary bytes, but a photo is only ever served as `image/jpeg` (`inline`) from the bucket's own S3 origin, never the app's.
- **Removed members.** A member removed from a team drops out of its `/photos` at once, but a URL a teammate already fetched keeps working until it expires, so their photo can stay visible there for up to an hour.
- **Downloads.** S3 request metrics under `photos/` and the P2 alarm **Profile photo downloads high** (over 5 GiB in an hour) guard the bill against a leaked URL fetched in a loop ([Observability](observability.md#profile-photo-downloads-high)).
- **Deploy order.** The data stack (the bucket) before the api stack (the grant and the routes) and the web stack (the CSP), then the web app that uses them. A release does this by itself (`apply-stateful`, then `apply`, [releases.md](releases.md)). By hand: `npx cdk deploy supply-checkout-<env>-<region>-data` first, then `npm run deploy -- api` and `npm run deploy -- web`. Deployed the other way round, `PUT /me/photo` answers 500 until the bucket exists, and photos don't load until the CSP allows them.
- **After deploying**, check the bucket's Block Public Access is all on and it has no bucket policy beyond SSL-only; upload a photo from Account and check the function's log has `Photo set` with a photo ID and no URL, that an object `photos/<id>.jpg` exists and its metadata says `image/jpeg`, that a teammate in another browser sees it, and that `DELETE /me/photo` leaves no object. An `AccessDenied` in the log means the api stack deployed before the data stack.

## Operators

Platform operators ([ADR 0015](adr/0015-platform-operator-role.md), `supply-checkout-6uw.1`) list and search teams, read one team's account record, comp a team (a free plan for a pilot, say) and read the operator audit. They never read a team's sheets, inventory, invites or receipts (they see how many receipts it read, and nothing of them): support access with an owner's approval is a later bead.

**The operator pool.** The `identity` stack has a second user pool, `supply-checkout-<env>-ops`, next to the customers' one:

- No self sign-up. Operators are created by an administrator with `npm run operators` or the AWS CLI under an SSO role (below). No Lambda role and no app client can create users or change groups; an `infra` test checks that no policy in any stack grants `AdminCreateUser`, `AdminAddUserToGroup`, `AdminRemoveUserFromGroup` or `CreateGroup`.
- Username and password (16+ characters, mixed), then TOTP, which the pool requires: the first sign-in sets it up, and the pool can't issue a token without it, so every token it issues comes from a session that used MFA. No email codes, passkeys, SMS, Google or Apple, and no email unless an administrator asks for one (`npm run operators -- add --send-email`, which uses Cognito's default sender): a forgotten password is reset by an administrator (`npm run operators -- reset`).
- An `operators` group. Being in the pool isn't enough: the API checks the group.
- Managed Login at `ops-auth.<env domain>` (its certificate is in the `domain` stack in `GLOBAL_SERVICES_REGION`).
- One public client, `ops`: authorization code with PKCE, calling back only to `npm run ops` on `http://localhost:8765/` (`OPS_CLI_CALLBACK` in `lib/identity.ts`) and to the operator page at `https://ops.<env domain>/` (its sign-out URLs are the same two; [The operator page](#the-operator-page)). Access and ID tokens last 15 minutes; refresh tokens last 8 hours, with rotation and revocation. It has the `aws.cognito.signin.user.admin` scope so the ops function can call `GetUser` with the operator's token.
- It publishes `ops-user-pool-id`, `ops-user-pool-arn`, `ops-client-id`, `ops-issuer-url`, `ops-auth-url` and `ops-branding-id` (the ops client's managed login branding, which `OperatorBrandingChanges` matches) under `/supply-checkout/<env>/identity/`.
- **After an `identity` deploy that replaces the ops pool, the ops client or the ops branding, deploy `observability` straight after.** The operator rules read the pool's and the branding's IDs from those parameters only when `observability` deploys, so until it does they match the old IDs and miss every call on the new ones. The same goes for an `audit` deploy that replaces the trail key and a `data` deploy that replaces the table, its key or its stream. A deploy that only updates them in place keeps the IDs and needs nothing. The `OperatorInput*` rules alert when one of these parameters is changed other than by a deploy.

**The ops routes.** The `/ops/*` routes (`OPS_ROUTES` in `backend/src/api/routes.ts`) are on the same HTTP API, in the primary region only, behind their own JWT authorizer for the operator pool (its issuer and the `ops` client). A customer's token fails it, and an operator's token fails the customer authorizer; the team routes never read `cognito:groups`. The `ops` function (`backend/src/operator/`) then checks, on every request: an unexpired access token from the operator pool for the `ops` client whose `cognito:groups` names `operators`; `GetUser` with the token, which Cognito refuses once the token is revoked or the user disabled; and `AdminListGroupsForUser`, which must still list `operators`. So removing someone from the group, disabling them or signing them out globally takes effect on their next request, not when their token expires. Each route has its own throttle (1 to 5 requests a second; the receipt ranking, which reads up to 1,000 teams' counters, 1).

**The operator-access role.** The ops function's own role can reach no table: it may assume `OperatorAccessRole` (tagged with the team a comp changes, or `.`) and call `AdminListGroupsForUser` on the operator pool. The role may:

- `Query` GSI3's `OPS#TEAMS`, `OPS#OWNERS#*` and `OPS#AUDIT#*` partitions, with `dynamodb:Select` limited to `ALL_PROJECTED_ATTRIBUTES` or `SPECIFIC_ATTRIBUTES`. GSI3 is sparse and projects only `OPS_INDEX_ATTRIBUTES` (`backend/src/data/schema.ts`): a team's account record (name, plan, seats, status, trial end, owner count, when it was closed, creation time, Stripe customer, version and comp), an owner's email and join date, and an audit event's action and operator. Team `META` items and owners' `MEMBER#` items carry `GSI3PK`; sheets, products, movements, invites and imports never do.
- `UpdateItem` in the tagged team's partition, naming only `COMP_ATTRIBUTES` (`PK`, `SK`, `type`, `version` and the `comp*` fields; `dynamodb:Attributes`), returning at most those. So it can't change a team's `plan` or `status` (ADR 0009), and it has no `GetItem`, `Query`, `PutItem` or `DeleteItem` on any `TEAM#` partition.
- `PutItem` and `Query` in `OPAUDIT#*` partitions, never `UpdateItem` or `DeleteItem`.
- For receipt usage (`supply-checkout-wxx`): `BatchGetItem` in any `TEAM#*` partition naming only `RECEIPT_USAGE_ATTRIBUTES` (`PK`, `SK`, `receipts`), with a projection (`dynamodb:Select` must be `SPECIFIC_ATTRIBUTES`). Only `BatchGetItem`: no `GetItem` or `Query` there, so it reads exact keys the code names and can't list a team's sort keys (which would show product keys, member IDs and sheet IDs). Only the receipt counters (`USAGE#<month>`, `USAGE#TRIAL`) have a `receipts` attribute, so it reads nothing else of any team. A team's record (`GET /ops/teams/{teamId}`, audited as `ops.team.read`) has its reads for this month and the five before, and in its trial; `GET /ops/receipts?month=` (`npm run ops -- receipts`, audited as `ops.receipts.usage` in the platform audit with the teams it returned) ranks the month's teams by reads, reading at most 1,000 teams from the index (`complete: false` when there are more). Both show an **estimated cost**: reads times `ESTIMATED_COST_PER_RECEIPT_USD` ($0.007, the top of ADR 0008's Haiku estimate, provisional). That's the bead's "cost per team": an estimate from read counts, not billing; real spend is in Cost Explorer, and tokens per team in the receipts function's logs (`ReceiptTokens`, team ID in metadata). Residual risks, accepted: the statement reaches every team's partition (an operator ranks them all), limited to the `receipts` attribute by key; and IAM can't limit sort keys, so the role could confirm that a guessed key exists in any `TEAM#` partition (it gets back `PK` and `SK` only, no other attributes). If a team's counters can't be read, its record comes back with `receipts: null`.
- For the Test badge (`supply-checkout-o60.2`): `BatchGetItem` in any `TEAM#*` partition naming only `TEST_MARK_ATTRIBUTES` (`PK`, `SK`, `test`), with a projection (`dynamodb:Select` `SPECIFIC_ATTRIBUTES`), read only. GSI3 already projects 20 attributes, DynamoDB's most, so the mark is read from teams' `META` items by key (`opsTestTeams`). Residual risk, accepted: as with the receipt counters, it could confirm that a guessed key exists in any `TEAM#` partition, and read a `test` attribute only `META` items have. If the marks can't be read, the list and record come back with `test: null`.
- For stuck imports (`supply-checkout-6uw.2`): `Query` GSI1's `IMPORTS#COMMITTING` partition naming only `STUCK_IMPORT_ATTRIBUTES` (what the scheduled check may read), and `UpdateItem` in the tagged team's partition naming only `IMPORT_INDEX_ATTRIBUTES` (`PK`, `SK`, `GSI1PK`, `GSI1SK`). `POST /ops/teams/{teamId}/imports/{importId}/clear` removes a job's GSI1 keys, on the condition that it's still in that partition and started over an hour ago, with its audit item in the same transaction ("Imports stuck" in [journeys.md](journeys.md)).

Residual risks, accepted: IAM can't require a condition expression, so a `PutItem` in `OPAUDIT#` could overwrite an item with the same key (the code conditions every put on `attribute_not_exists(PK)`, and keys hold a random ID; the operator audit watch below alarms P1 on any overwrite, change or deletion); an `UpdateItem` could create an item in the tagged team's partition holding only comp attributes (the code's `#type = :team` condition prevents it); IAM can't tell `REMOVE` from `SET`, or limit the sort key, so the stuck-import statement would let code set or remove the GSI1 keys of any item in the tagged team's partition (the code's `GSI1PK = IMPORTS#COMMITTING` condition keeps it to a stuck import job, and the route only ever names an `IMPORT#<id>` sort key). The worst case is a closed team's `META` item: removing its GSI1 keys (`TEAMS#CLOSED`) would take it out of the purge queue, so the hourly purge would never find it and the team would never be deleted, silently breaking the promise to delete a closed team's data, with no alarm ("Deletion overdue" counts only teams still in that queue). A test (`backend/test/ops-api.test.ts`, "can't take a closed team out of the purge queue") checks the route can't; a code change could; and `dynamodb:ReturnValues` doesn't cover `ReturnValuesOnConditionCheckFailure`, so code that asked for `ALL_OLD` on a failed condition could read the item it tried to update (the ops code never sets it, and the backend lint config bans `ReturnValuesOnConditionCheckFailure`, `ALL_OLD` and `ALL_NEW` in `src/operator/` and `src/data/operator.ts`). Each would take a change to the ops function's code, which only a deploy can make.

**Reopening a closed team** (`supply-checkout-6uw.6`). The operator-access role has no closure field on purpose: IAM can't tell removing an attribute from setting it, so a role that could reopen a team (remove `closedAt`, `purgeAfter` and the `TEAMS#CLOSED` index keys) could also close one and set a `purgeAfter` in the past, and the hourly purge would delete it. So `POST /ops/teams/{teamId}/reopen` goes through a second function, `OpsReopenFunction` (`backend/src/operator/reopen-handler.ts`), which has no route and which only the ops function may invoke (`lambda:InvokeFunction` on it, unqualified). The ops function verifies the operator as for every route, then invokes it synchronously with plain values (operator `sub`, team ID, reason, `expectedVersion`, `Idempotency-Key`), never expressions. Its own role reaches no table either: per request it assumes `OperatorReopenRole`, tagged with the team, which may `GetItem` (projected: `Select` `SPECIFIC_ATTRIBUTES` required, `supply-checkout-3sv.24`) and `UpdateItem` only in that team's partition naming only `REOPEN_ATTRIBUTES` (keys, `type`, `version`, `owners`, `closedAt`, `closedBy`, `purgeAfter`, the purge's `purging` mark, `GSI1PK`, `GSI1SK`, and `stripeResyncFor`, which the reopen sets so the billing worker resyncs the team's Stripe subscription, [Billing](#billing)) and returning nothing, and `PutItem` and `Query` only in that team's `OPAUDIT#` partition. `reopenOpsTeam` (`backend/src/data/operator.ts`) reads the closure, then in one transaction removes it, moves the version (conditioned on the version and closure read, on `purgeAfter` being more than `OPS_REOPEN_CUTOFF_MINUTES` (5) away, on no `purging` mark, and on `owners > 0`), writes the `ops.team.reopen` audit item (before: `closedAt` and `purgeAfter`) and the idempotency record. An operator can restore a disputed closure within its last hour, when an owner no longer can (60 minutes): the purge marks a team `purging` (conditioned on it still being closed and due) before deleting anything, and the reopen's condition refuses that mark, so whichever write lands first wins and a team is never reopened part-deleted. Owners see it in their support actions. Unlike an owner's reopen there's no daily limit and no email to owners. The role's `GetItem` statement (`ReopenClosureFieldsRead`, separate from its `UpdateItem` one) also requires `dynamodb:Select` to be `SPECIFIC_ATTRIBUTES` (`StringEquals`, not `IfExists`, `supply-checkout-3sv.24`), so a `GetItem` without a projection (which names no attributes and would return the whole item) is refused; `reopenOpsTeam` always projects. Residual risks, accepted: the reopen function's code could, with its role, close the one team it's tagged with; `ReturnValuesOnConditionCheckFailure: ALL_OLD` has no IAM control, so code that set it could read the META item it failed to update (the backend lint config bans it in the operator code); the role could `UpdateItem` other items in `TEAM#<tag>` naming only allowed attributes, for example removing a sheet's GSI1 keys; and an administrator with a wildcard `lambda:InvokeFunction` can invoke the reopen function directly with any operator `sub`, which would be attributed to that sub in the audit (CloudTrail still records the real caller). The first three would take a compromised or changed reopen function, which only a deploy makes.

**Comps and the audit.** `PUT /ops/teams/{teamId}/comp` writes `compPlan`, `compSeats`, `compUntil` (at most 12 months ahead), `compReason`, `compBy` (the operator's `sub`) and `compAt` on the team's `META` item, conditioned on the item being a team at the version the operator read, with an operator audit item (`OPAUDIT#<teamId>`, `AUDIT#<ts>#<eventId>`, also in GSI3's `OPS#AUDIT#<yyyy-mm>`) and a record of the `Idempotency-Key` in the same transaction; a retry replays. `DELETE` ends the comp the same way. Reading one team's record is audited too (`ops.team.read`), and so is listing or searching teams (`ops.teams.list`, in `OPAUDIT#PLATFORM`, with the search and the teams returned), since the list shows owners' emails. The list is paged in team ID order (the index's order), and each request reads at most 1,000 teams from the index (`MAX_OPS_TEAMS_READ`) and looks up the owners of the teams it returns 10 at a time, however many teams there are (`supply-checkout-6uw.8`). So a search can return fewer teams than its page size, even none, with a cursor: follow it until there's none. A search for a team ID finds that team directly, on the first page. A closed team can't be comped (409); the check reads the index, which lags a close by a moment, and a comp in that window only sets comp attributes on a team that stays closed. When the purge deletes a team, its `META` and `MEMBER#` items leave GSI3 with it; its operator audit stays for its 2 years. While a comp is live, the team counts as paying for the member cap, keeps getting live updates even if its Stripe status has ended, and `/me` shows it (`liveComp` in `backend/src/data/model.ts`). Audit items expire after 2 years. Owners read their team's operator audit at `GET /teams/{teamId}/support-actions`, attributed to "Supply Checkout support": the data-access role may `Query` its team's `OPAUDIT#` partition only for `OWNER_OPERATOR_AUDIT_ATTRIBUTES`, which don't include the operator's `sub`. The ops function logs one line per request with the route, team ID, operator `sub` and status, never emails or tokens.

**Comping for months, and Stripe** (`supply-checkout-6e4b`, ADR 0015 §8). A comp alone changes only access in the app, so a team paying through Stripe would still be charged. `npm run ops -- comp <teamId> --months N --reason <text>` (N from 1 to 12, `months` in the `PUT` body instead of `until`; the plan is the team's own unless `--plan` names one) comps the team until N calendar months from now (the same day of the month, or the last day of a shorter one) and records `compMonths` on `META`. For a team with a live (not ended, not incomplete) Stripe subscription billed monthly, the billing worker then puts a 100%-off coupon on the subscription, duration `repeating`, `duration_in_months` N, so its invoices in those N months are $0 and billing resumes by itself afterwards, on the same subscription and card. A team with no subscription just gets the comp. A comp with `until`, or `uncomp`, removes the discount. How:

- **The ops function never writes to Stripe.** Its key stays a restricted Subscriptions: Read + Invoices: Read key, and its role gains only `compMonths` in `COMP_ATTRIBUTES`. After every comp change (set, extend, end; a replay too) it queues a message with reason `comp` on the seat sync queue, to which it could already send, for the team's Stripe customer from the team's index entry, never the request, and answers `stripeDiscount`: `queued`, `no_stripe_customer`, or `not_queued` (logged as `Comp discount sync not queued` and counted in `SeatSyncQueueFailures`).
- **The billing worker applies it** (`backend/src/billing/comp-discount.ts`), with the Stripe secret key it already holds and already uses to update subscriptions. It finds the team from our own `STRIPE#` link for the message's customer, skips a closed, purging or gone team or one whose own customer isn't the message's, and reads the comp from the team's `META` item (`compPlan`, `compUntil`, `compMonths`; `compMonths` joins `BILLING_READ_ATTRIBUTES`). So the message can only make the worker bring that customer's subscription in line with its own team's comp: neither an operator nor a forged message chooses a discount. It wants exactly one discount from our coupons, `supply-checkout-comp-<N>m`, with the comp's end stamped in the subscription's metadata (`supply_checkout_comp_until`) and ending no later than a day after the comp does (`COMP_DISCOUNT_SLACK_MS`, the same as the comped portal's grace), while the team has a live comp with `compMonths` and a monthly subscription, and none of ours otherwise; other discounts (a promotion code, later) are always kept. The coupon is sized to the comp's time left, not its length (`discountMonthsLeft`: the most whole months from now that end within that day of the comp's end), so right after the comp it's the comp's N months, and later (a new subscription, a discount put back after a hand removal) fewer. With under a month left nothing new is put on (`under_a_month`): that last part-month is billed as usual rather than risk a free invoice past the comp; one of ours already there that ends in time is kept. One of ours that would end later than that, or has no end, is out of step and replaced (or removed, with under a month left). A comp changed or extended later has a new end, so its discount is replaced too. A yearly subscription (or a price billed every few months) never gets one, and loses ours if it was switched: a coupon applies to every invoice in its months, so a renewal in that window would be a whole year free (outcome `not_monthly`).
- **No switching price while comped.** Switching from monthly to annual in the Customer Portal invoices the annual price at once, inside the coupon's months, so it would be $0, a whole year free. So while a team has a comp, and for a day after it ends (`compUntil` stays, as when it stopped; `COMPED_PORTAL_GRACE_MS`), its owners get a second portal configuration, `owners-comped` (`portalVariantFor` in `backend/src/billing/portal.ts`), the same as the usual one but with `subscription_update` off: they can still change their card and details, see invoices and cancel. The catalog script makes both. Without the comped one the portal fails for a comped team (500, `BillingPortalErrors`) rather than falling back to the usual one. Residual risks, accepted: a portal session opened just before the comp keeps the usual configuration for its short life (Stripe can't revoke one), so before a `comp --months` on an owner's request, ask them to close any open billing tab. **The owner runs `npm run stripe-catalog -- ... --apply` once per mode (test now, live when it's set up) after this deploys and before the first `comp --months`.**
- **The coupons** are 12 fixed IDs, created by the worker the first time each is needed (idempotency key `comp-coupon-<id>`) and checked before every use (100% off, no amount off, `repeating` for the right months, valid, for every product): one changed by hand is refused (`CompCouponMismatch`) and never applied. Being shared, nothing is left behind per team when a discount is removed, when Stripe ends it after its months, or when the purge deletes a closed team's customer. A closed team's discount is left as it is: its subscription is ending, and the purge deletes the customer.
- **Idempotent.** Each subscription update has an idempotency key hashed from the team, the subscription, the action, the comp's end, the discounts found and the coupon applied, and once Stripe has applied it the worker finds the subscription in step (`in_sync`) and sends nothing, so a retried request, message or delivery applies one coupon.
- **Audited.** The operator's change is `ops.comp.set` (with `months`) or `ops.comp.end` as before. What the worker did is a second audit item in the team's `OPAUDIT#` partition, `ops.comp.discount`, attributed to `system-billing-worker` (`before`: our coupon before; `after`: the outcome, coupon, comp end and subscription), written for every outcome of a `comp` message on a found team, after Stripe was asked (so if that write fails, the retry finds the subscription in step and records `in_sync` instead; the log line has the `applied`). It's in the team's audit (`audit --team`), not the audit by month: the billing-worker role gains `PutItem` in `OPAUDIT#<its team tag>` naming only `COMP_DISCOUNT_AUDIT_ATTRIBUTES` (no `reason`, and no GSI3 keys, so the worker can't put anything into the operators' index), returning nothing; no read, update or delete there, and the operator audit watch alarms on any overwrite. Owners see it among their support actions ("Made the team's bills free for its free plan's months", "Took the free plan's discount off the team's bills", or "Checked the team's bills for its free plan").
- **Failures** throw: the message is retried, then lands in the seat sync dead-letter queue ("Seat syncs stuck"). The nightly reconciliation also runs the reconcile, after the seat sync and whether or not the seat sync failed (the message then still fails for the seat sync, and a second failure is logged as `Comp discount failed`), for every open team with a Stripe customer that has ever been comped (`compUntil` set), auditing only what it changes, so a message that was never queued or failed for good is put right within a day. So does the seat sync right after a reopen: a comp that ended while the team was closed (the worker leaves a closed team's discount alone) has its discount taken off within seconds of the reopen (if that step fails after the reopen's resync succeeded, the retry no longer sees a resync pending, so the next nightly run puts it right).
- **Webhooks and entitlements.** A discount change sends `customer.subscription.updated`, which the worker applies like any other: status, plan, seats and interval don't change, and a $0 invoice is `invoice.paid`. `customer.discount.*` isn't subscribed: nothing in the team's record depends on a discount. The nightly entitlement check compares status, plan, seats and cancellation only, so a discounted subscription is never drift. A subscription started during the comp (a resubscribe) gets its discount from the next nightly reconciliation, or at once from another `comp --months`. A trialing subscription gets the discount too, so the comp's months count from the comp, trial or not. If our discount is taken off by hand during the comp, the nightly reconciliation puts a fresh one on for the months left, which never runs more than a day past the comp's end.
- **Seeing it.** `npm run ops -- team <id>` shows the comp's months left and, from the subscription on the ops key (no new permission: its metadata and discount IDs are part of a subscription), `comp discount: invoices $0 until about <date>` while the stamp is in the future and the subscription has a discount (`compDiscountUntil`, `discountCount`). `npm run ops -- audit --team <id>` shows both audit items.
- **Test-mode check (the owner, once per environment).** In the Stripe sandbox, on a team with a monthly subscription, attach a test clock to its customer before subscribing, run `comp <id> --months 2`, check `team <id>` shows the discount and `audit --team <id>` shows `applied`, then advance the clock: the next two invoices are $0 and the third full price. Run the same `comp` again and check the subscription still has one discount. `uncomp` then removes it (`removed` in the audit).

**A team's Stripe billing** (`supply-checkout-6uw.4`). `GET /ops/teams/{teamId}` also returns `stripe`: the team's current subscription (ID, status, the price's lookup key and the catalog's plan and interval for it, seats, period end, `cancelAtPeriodEnd`, when it cancels, trial end, created) and its latest 12 invoices without drafts (ID, number, status, date, currency, total, amount due and paid), for the Stripe customer on the team's index entry, never one from the request (`backend/src/operator/stripe-detail.ts`). It never returns the customer's email, name or address, payment methods or card details, or links to Stripe's hosted invoice page or PDF: those are bearer links that show the billing details and let anyone pay, and owners already have them in the app. A team with no Stripe customer gets `stripe: null`, and Stripe isn't called. The ops function calls Stripe with **its own restricted key**, never the billing functions' secret key: `supply-checkout/<env>/stripe/<mode>-ops-restricted-key` (`stripeOpsKeySecretName` in `backend/src/billing/names.ts`), in the primary region, which only the ops function's role may read (`ReadOpsStripeKey`: `secretsmanager:GetSecretValue` on that one secret's ARN, `stripeOpsKeySecretArn` in `infra/lib/config.ts`; `infra/test/api.test.ts` checks that no other role reads it and the ops function reads no other secret). It's read on first use and kept for an hour, like the billing key; a key of the other mode is refused, and so is anything but a restricted key (`rk_`, `requireRestricted`), so a full secret key stored there by mistake never works. Secrets Manager reads time out after 3 seconds (`secretsManagerReader`), so a hung read can't hold the shared pending read for the container. It fails soft: until the owner stores the key, or when Stripe errors or takes more than 4 seconds (`OPS_STRIPE_DEADLINE_MS`), the answer is the team's record with `stripe: { "error": "unavailable" }`, and the function logs `Stripe detail unavailable` with the team ID and Stripe's error type, code, status and request ID only (or the error's name, such as `ResourceNotFoundException`): never the key, Stripe's message or an email. The `ops.team.read` audit is written before Stripe is called, as before.

**The ops Stripe key, once per environment and mode (the owner).** Restricted keys can only be made in the Stripe Dashboard. In the sandbox (and later in live mode), **Developers → API keys → Create restricted key**, named `supply-checkout-<env>-ops`, with exactly two permissions, **Subscriptions: Read** and **Invoices: Read**, and every other one **None**: only what this code calls (`subscriptions.list` and `invoices.list` by customer). Comping for months (`supply-checkout-6e4b`) doesn't change it: the billing worker applies those discounts with its own key. Promo campaigns (`supply-checkout-8jc.8`) add **Coupons: Write** and **Promotion Codes: Write** when they ship: edit this key's permissions in place, or roll a new key into the same secret (ADR 0015 §2). If the check below gets a permission error that names customers, add **Customers: Read** and write down here why it's needed. The function refuses any value that isn't a restricted key (`rk_…`): a full secret key (`sk_…`) pasted here by mistake makes the detail `unavailable` rather than quietly working with every right. Then store it, with Secrets Manager's default AWS managed key (a customer managed key would also need a `kms:Decrypt` grant for the ops function), from a terminal (the prompt keeps the key out of your shell history):

```bash
read -r -s -p 'Ops restricted key (rk_test_...): ' KEY; echo
aws secretsmanager create-secret --profile supply-prod --region us-east-1 \
  --name supply-checkout/prod/stripe/test-ops-restricted-key \
  --description "Stripe restricted key for the ops function (ADR 0015)" \
  --secret-string "$KEY"
unset KEY
```

For live mode, the same with a live key and `live-ops-restricted-key`. To rotate it, roll the key in Stripe and `aws secretsmanager put-secret-value` the new one under the same name; the function picks it up within an hour. No deploy is needed after either: until the secret exists, the team's detail just has no Stripe part. Check it with `npm run ops -- team <teamId>` for a team with a subscription: it shows `subscription sub_… active` and its invoices, not `Stripe: unavailable`.

**The CLI.** `npm run ops` (`scripts/ops.mjs`) is the operators' terminal client; the [operator page](#the-operator-page) does the team and comp commands in a browser:

```bash

npm run ops -- audit --team '<teamId>'           # or --month 2026-09 for everyone's

npm run ops -- receipts --month 2026-09        # the teams that read the most receipts, with estimated cost (audited)
npm run ops -- clear-import '<teamId>' '<importId>' --reason "Owner re-imported it"

```

The first command opens `ops-auth.<env domain>` in the browser (username, password, TOTP) and takes the redirect on `http://localhost:8765/`, listening on the loopback addresses only. It keeps only the access token, for its 15 minutes, in `~/.config/supply-checkout/ops-<env>.json` (mode 600); no refresh token is stored. The ops client ID comes from `--client-id`, `SUPPLY_OPS_CLIENT_ID`, or SSM with the AWS CLI (`--profile`, default `supply-prod`). `--env staging` points it at another environment, `--json` prints the API's answers. `comp` reads the team first and sends its `version` with a new `Idempotency-Key`, so a comp never overwrites a change it didn't see.

**The alerts.** The primary region's `observability` stack has thirty EventBridge rules on CloudTrail's management events, the ones listed below (`test/observability.test.ts` counts them), that send a message naming the CloudTrail event, not the person: twenty-eight to the P1 topic (two of those to P2 as well), and the two alarm recipient rules to the P2 topic only. Each topic's policy lets only its own rules publish. Each operator rule has a fixed name, `supply-checkout-<env>-operator-<suffix>` (`OPERATOR_RULE_SUFFIXES` in `lib/stacks/observability-stack.ts`). EventBridge allows an event pattern 2,048 characters (the "Event pattern size" quota; the `PutRule` API's own 4,096 isn't the limit that applies), so the calls are spread over rules small enough to stay well inside it, and `test/observability.test.ts` checks every pattern in every stack with each name or ARN as long as a real one (`supply-checkout-pbp.17`):

- `OperatorPoolChanges`: calls on the operator pool, in two lists in `lib/stacks/observability-stack.ts`. `OPERATOR_USER_EVENTS` change who is an operator or how they sign in (`AdminCreateUser`, `AdminDeleteUser`, `AdminAddUserToGroup`, `AdminRemoveUserFromGroup`, `AdminSetUserPassword`, `AdminResetUserPassword`, `AdminEnableUser`, `AdminSetUserMFAPreference`, `AdminUpdateUserAttributes`, `AdminLinkProviderForUser`) and always alert, even when CloudFormation makes them, so a deploy can't add an operator silently. `OPERATOR_POOL_CONFIG_EVENTS` configure the pool, its client, domain, groups and identity providers (`CreateGroup`, `UpdateGroup`, `DeleteGroup`, `UpdateUserPool`, `SetUserPoolMfaConfig`, `CreateUserPoolClient`, `UpdateUserPoolClient`, `DeleteUserPoolClient`, `UpdateUserPoolDomain`, `DeleteUserPoolDomain`, `CreateUserPoolDomain`, `DeleteManagedLoginBranding`, `UpdateManagedLoginBranding`, `CreateIdentityProvider`, `UpdateIdentityProvider`, `DeleteIdentityProvider`) and alert unless CloudFormation made them for a deploy. Deleting or changing the ops client or domain locks every operator out; identity provider changes are watched so one can't be added and repointed unseen (the ops client supports only `COGNITO`, so they aren't themselves a lockout) (`supply-checkout-6uw.19`). `CreateUserPoolDomain` catches a second, custom domain on the pool, and the two branding calls catch the ops client's managed login branding (its only style) being deleted or rewritten, which likely breaks operator sign-in (`supply-checkout-6uw.20`). It matches by `requestParameters.userPoolId`, which `UpdateManagedLoginBranding` doesn't require, so a branding call that names only the branding ID alerts through `OperatorBrandingChanges` instead (below). Unlike the other rules, its state is `ENABLED_WITH_ALL_CLOUDTRAIL_MANAGEMENT_EVENTS` (`OPERATOR_POOL_RULE_STATE`), in case EventBridge counts some of these calls as read-only (see "Why group changes have their own watch" below). `OPERATOR_LOCKOUT_EVENTS` (`AdminDisableUser`, `AdminUserGlobalSignOut`) lock an operator out without deleting them, and alert unless CloudFormation made them (no template does). Deleting, disabling or signing out every operator would lock responders out, so each alerts (`supply-checkout-6uw.16`); the operator group watch also sees a deletion or a disable within 5 minutes.
- `OperatorBrandingChanges` (`supply-checkout-6uw.21`): `DeleteManagedLoginBranding` and `UpdateManagedLoginBranding` (`OPERATOR_BRANDING_EVENTS`) whose `requestParameters.managedLoginBrandingId` is the ops branding's ID (published as `ops-branding-id`), unless CloudFormation made them for a deploy, the same exemption as `OperatorPoolChanges`. `UpdateManagedLoginBranding` takes `UserPoolId` as optional, so a call that leaves it out logs no `requestParameters.userPoolId` and `OperatorPoolChanges` can't see it. This rule matches only calls that don't name the ops pool (`userPoolId` missing, or another pool's ID): a call that names it already alerts through `OperatorPoolChanges`, so it pages once either way. It's a rule of its own, under the operator prefix (so the tampering rules watch it) and on the P1 topic policy's `aws:SourceArn` list, so `OperatorPoolChanges`' pattern stays as it was. A branding update with very large assets could still exceed EventBridge's 256 KB event size and never reach either rule; CloudTrail keeps the record.
- `OperatorPoolProtection` (`supply-checkout-6uw.20`): the operator pool itself. `DeleteUserPool` on the ops pool, and an `UpdateUserPool` on it whose `requestParameters.deletionProtection` is missing or anything but `ACTIVE` (`OPERATOR_POOL_PROTECTION_EVENTS`), whoever makes them, CloudFormation included: no deploy should turn the ops pool's protection off, and that's the first step of deleting it. `UpdateUserPool` resets any setting it isn't given to its default, and `DeletionProtection` defaults to `INACTIVE`, so a call that leaves it out turns protection off too; the `exists: false` match covers that. Verified from real CloudTrail records (the 2026-09-27 deploy): `UpdateUserPool`'s `requestParameters` carry camelCase `userPoolId` and `deletionProtection` (`"ACTIVE"` from a deploy), so a call that keeps `ACTIVE` doesn't match. `DeleteUserPool` has no `deletionProtection` field, so it always matches, even when protection makes it fail. An `UpdateUserPool` that turns protection off outside a deploy also alerts through `OperatorPoolChanges`. The CDK sets the ops pool's `DeletionProtection` to `ACTIVE` (`test/identity.test.ts` asserts it). It's a rule of its own because its extra `requestParameters` condition can't share the pool ID's place in `OperatorPoolChanges`' pattern.
- `OperatorSelfServiceChanges`: what an operator's own token can change: `AssociateSoftwareToken`, `VerifySoftwareToken`, `SetUserMFAPreference`, `UpdateUserAttributes`, `DeleteUser`. CloudTrail records these with the pool ID in `requestParameters` or `additionalEventData`, so the rule matches either.
- `OperatorAuditWatchChanges` (`supply-checkout-6uw.11`): deleting the operator audit watch's event source mapping, or its function or the operator group watch's (`supply-checkout-3sv.5`), or removing a permission from either function (`RemovePermission`, such as EventBridge's permission to invoke the group watch, which would otherwise stop every run with only the P2 silent alarm 15 minutes later: `supply-checkout-3sv.9`), whoever does it; and, outside a deploy, updating the mapping (disabling it or changing its filter), the function's code or configuration, or its concurrency (zero stops it). Lambda's event names carry an API version (`UpdateEventSourceMapping20150331`), so the rule matches them by prefix; the mapping by its UUID (`uUID`), the function by its name or ARN.
- `OperatorAuditWatchRoleChanges`: deleting the watch's role, or its role policies, whoever does it (`DeleteRole`, `DeleteRolePolicy`, `DetachRolePolicy`); and, outside a deploy, changing its policies, trust policy or permissions boundary. The same for the operator group watch's role (`supply-checkout-3sv.5`), and, outside a deploy, `CreateFunction` or `UpdateFunctionConfiguration` giving any function that role (matched by prefix for Lambda's versioned event names). `requestParameters.role` matches the role's ARN exactly, or any ARN ending in `:role/` and then anything ending in the role's name (`supply-checkout-3sv.9`), in case CloudTrail records the ARN spelled differently from the template's. That wildcard also matches another role whose name ends in this one, which only over-alerts. EventBridge can't match a wildcard and ignore case at once, so an ARN with the name in another case wouldn't match. The drill below confirms what CloudTrail records in `requestParameters.role`.
- `OperatorAuditWatchLogChanges`: the watch's log group. `DeleteLogGroup` on it whoever calls it (its role can't recreate the group, and its metrics are embedded in its log lines, so nothing would arrive); `PutTransformer`, `DeleteTransformer` or `PutDataProtectionPolicy` on that group outside a deploy (a transformer could strip the metric from its lines); and `PutAccountPolicy` for a `TRANSFORMER_POLICY` or `DATA_PROTECTION_POLICY`, which reach every log group, whoever calls it (this app never makes one).
- `OperatorAuditWatchTableChanges`: the rest of the watch's data path. `PutResourcePolicy` or `DeleteResourcePolicy` on the table or its stream outside a deploy (a Deny on `GetRecords` cuts the watch off without an error); `UpdateTable` on the table outside a deploy, and `UpdateTable` turning its stream off whoever calls it; and `DisableKey` or `ScheduleKeyDeletion` on the table key whoever calls them, and `PutKeyPolicy` on it outside a deploy.
- `OperatorAlarmChanges`: `DisableAlarmActions` or `DeleteAlarms` on the four operator audit alarms whoever calls them, and `PutMetricAlarm` on them outside a deploy.
- `OperatorGroupWatchAlarmChanges` (`supply-checkout-3sv.5`): the same calls on the operator group watch's two alarms, **Operator group changed** and **Operator group watch silent**, in a rule of its own because `OperatorAlarmChanges` has no room left inside the pattern limit.
- `OperatorGroupSnapshotChanges` (`supply-checkout-3sv.5`): `PutParameter`, `DeleteParameter`, `DeleteParameters`, `LabelParameterVersion` or `UnlabelParameterVersion` on the operator group watch's snapshot parameter, its name matched with any padding (`*<name>*`, as for `OperatorInput*` below; these calls take only a name, never an ARN, though the wildcard would match one), unless the watch's own role (`userIdentity.sessionContext.sessionIssuer.arn`) or CloudFormation made the call. A deploy that changes the parameter doesn't alert here, but the watch's next run pages (below).
- `OperatorInputOpsPoolId`, `OperatorInputOpsBrandingId`, `OperatorInputTrailKeyArn`, `OperatorInputTableKeyArn` and `OperatorInputTableStreamArn` (`supply-checkout-<env>-operator-input-ops-pool-id`, `-input-ops-branding-id`, `-input-trail-key-arn`, `-input-table-key-arn`, `-input-table-stream-arn`; bead `supply-checkout-6uw.22`), one rule per SSM parameter the operator rules and watches read at deploy time (`operatorRuleInputParameters`): `/supply-checkout/<env>/identity/ops-user-pool-id` (the pool rules, the self-service rule and the operator group watch), `identity/ops-branding-id` (`OperatorBrandingChanges`), `audit/trail-key-arn` (`OperatorAlertKeyAndTrailChanges`, `OperatorTrailBucketChanges`), `data/table-key-arn` (`OperatorAuditWatchTableChanges` and the audit watch's role) and `data/table-stream-arn` (the audit watch's event source mapping). Each alerts on `PutParameter`, `DeleteParameter`, `DeleteParameters`, `LabelParameterVersion` or `UnlabelParameterVersion` (`RULE_INPUT_PARAMETER_EVENTS`) on its parameter unless CloudFormation made the call (the stacks that own them write them when they deploy), the same exemption as `OperatorGroupSnapshotChanges`. Anyone with `ssm:PutParameter` could otherwise rewrite one, and the next ordinary `observability` deploy would point the rules at nothing through CloudFormation's own `PutRule`, which the tampering rules exempt. CloudTrail records the parameter in `requestParameters.name`, and for `DeleteParameters` in the list `requestParameters.names`. SSM removes spaces from the beginning and end of a name before it acts, so `--name " /supply-checkout/prod/identity/ops-user-pool-id "` rewrites the real parameter while CloudTrail may record the padded name: each rule matches its name with one wildcard on each side, `*<name>*` (`ssmParameterNameMatch`), which also matches an ARN (these calls don't take one) and over-alerts on a longer name that contains it. EventBridge refuses a rule whose wildcards are too complex when it's saved, and repeated sequences after a wildcard add to that (the tests can't see it), so each rule names one parameter and has two wildcards, the shape `OperatorAuditWatchLogChanges` deploys with. `test/observability.test.ts` fails if an operator rule's pattern, or either watch, reads an SSM parameter that isn't in the list (by `Ref` or inside an `Fn::Sub`), or if the template uses a `{{resolve:ssm:...}}` reference. If one fires and nobody expected it, put the value back (the drill's check below gives each right value; putting it back alerts too), then deploy `observability`, which points the rules back at the right value if a deploy since the change pointed them elsewhere.
- `OperatorAuthorizerIssuerUrl`, `OperatorAuthorizerWebClientId`, `OperatorAuthorizerUserPoolId`, `OperatorAuthorizerOpsIssuerUrl`, `OperatorAuthorizerOpsClientId` and `OperatorAuthorizerAuthUrl` (`supply-checkout-<env>-operator-authz-issuer-url`, `-authz-web-client-id`, `-authz-user-pool-id`, `-authz-ops-issuer-url`, `-authz-ops-client-id`, `-authz-auth-url`; bead `supply-checkout-6uw.23`), the same rules for the SSM parameters sign-in and the API's and realtime authorizers read at deploy or publish time (`authorizerInputParameters`): `/supply-checkout/<env>/identity/issuer-url` and `identity/web-client-id` (the customer JWT authorizer's issuer and audience), `identity/user-pool-id` (the realtime authorizer function's pool), and `identity/ops-issuer-url` and `identity/ops-client-id` (the ops JWT authorizer's issuer and audience, and the ops function's own token check; the ops function's pool ID is `OperatorInputOpsPoolId`'s), and `identity/auth-url`, which `scripts/publish-web.mjs` writes into the web app's `config.json` as where the browser signs in. Rewritten, the next `api` or `realtime` deploy would accept another pool's or client's tokens, through CloudFormation, or the next web publish would send people to sign in elsewhere (the publish script refuses an `auth-url` that isn't `https://auth.<env domain>` from the deployment config, and the auth function takes its own sign-in URL from the template, not from SSM). They're named under the operator prefix, so the tampering rules watch them. `test/observability.test.ts` fails if anything in the `api` or `realtime` template (the JWT authorizers, any function's environment, any policy) reads an `identity/` parameter that none of these rules or `OperatorInputOpsPoolId` watches, other than `ops-user-pool-arn` (see "What the rules don't list" below).   **Who hears about it.** The subscriptions take their endpoints from these parameters only when the `observability` stack deploys (CloudFormation resolves them then; see `AlarmTopics`), so at the moment of the SSM write nothing has changed yet: the P2 message goes to the email recipients subscribed *before* the change, including the one being replaced. Residual risks, accepted (`supply-checkout-6uw.11`). Each needs the `supply-prod` administrator's rights (or the management account's), and each call is still in CloudTrail:

- **The key.** One KMS key (`AlarmTopics` in `lib/observability/alarm-topics.ts`) encrypts **both** alarm topics, P1 and P2. So `DisableKey`, or a `PutKeyPolicy` that takes away EventBridge's, CloudWatch's or SNS's use of it, breaks P1 and P2 at once: every alarm and alert goes undelivered, including the alert on that very call, which travels through the same key. The alarms still change state in CloudWatch, and the call is in CloudTrail, but nobody is told. `ScheduleKeyDeletion` leaves the key working for its 7 to 30 days, so that alert arrives. A separately keyed path for these alerts (a second key for one topic, or a CloudWatch Logs target with its own alarm) would close this; it isn't built.
- **Both topics at once.** Deleting or unsubscribing everyone from one topic reaches the other; doing both, the first call's alert should go out through the topic still there, but a second call made before EventBridge delivers the first can beat it.
- **CloudTrail itself.** These rules only see calls CloudTrail records, and only while a trail is logging in the account: the audit stack's ([The CloudTrail trail](#the-cloudtrail-trail)). Stopping or deleting it alerts through the rule above (that call itself is recorded), but every rule is blind after that until it's turned back on. Changes to the trail bucket's policy, lifecycle, versioning, encryption or logging, and grants on its key, alert P1 through `OperatorTrailBucketChanges` (above); a policy change that cuts CloudTrail off also shows as a delivery error in `get-trail-status`. An organization trail is managed from the management account (`supply-mgmt`), where nothing here watches; the rule above catches trails in this account only.
- **Deleting the whole stack.** A `DeleteStack` on the observability stack deletes every rule, topic and alarm in one go; the first `DeleteRule` alerts only if the other tampering rule and a topic are still there when EventBridge delivers it.
- **Deploys, including other stacks'.** The `outsideDeploys` calls are exempt when CloudFormation makes them (`userIdentity.invokedBy` is `cloudformation.amazonaws.com`). That's true of a call made through **any** CloudFormation stack, not just this app's: someone who can create a stack could, for example, put a key policy or a table resource policy in a stack of their own and it wouldn't alert. The heartbeat below still catches one that cuts the watch off; one that only breaks alerting (a topic policy) it doesn't. The alarm recipient rules exempt no deploy: a stack that subscribes to an alarm topic, or a deploy that unsubscribes from one, alerts P2.
- **Alarm recipients elsewhere** (`supply-checkout-6uw.23`). The alarm recipient rules are in the primary region, like every operator rule, and watch that region's parameters and topics. A second region's `observability` stack (phase 2) reads its own `/supply-checkout/<env>/alarms/` parameters there, and the backup account's vault stack reads that account's `email-<n>` parameters; nothing watches either yet.
- **Email unsubscribe links.** Every SNS email has an unsubscribe link, and an email subscription confirmed by clicking the link in AWS's confirmation message can be unsubscribed by anyone holding one of those emails, without signing in. `Unsubscribe` from the link may not be recorded as a normal CloudTrail call, so the rule above may not see it. CDK and CloudFormation can't set `AuthenticateOnUnsubscribe`; to require it, confirm each email subscription with the CLI instead of the link (see "Alarm recipients" in [observability.md](observability.md#alarm-recipients)).
- **What the rules don't list.** `SetAlarmState` (sets an alarm to OK until its next evaluation); purging or deleting the watch's dead-letter queue (it only holds positions of batches already given up on; the dropped-records alarm fires first); the heartbeat schedule (`UpdateSchedule`, `DeleteSchedule`), grants on the table key (`RevokeGrant`, `RetireGrant`), and a log transformer or table change made in a deploy of any stack: each of these stops the heartbeat, so **Operator audit watch silent** (P2) fires within 30 minutes instead of a P1 message at once; and anything a new EventBridge, Lambda, IAM, CloudWatch Logs, DynamoDB, KMS or SNS API adds later. Three identity parameters are deliberately unwatched (`supply-checkout-6uw.23`): `identity/ops-user-pool-arn` and `identity/user-pool-arn` are only IAM resources (the ops function's `AdminListGroupsForUser`, the security notices function's Cognito calls), so a rewritten one narrows a permission and fails closed; and `identity/ops-auth-url` is read by nothing, since `scripts/ops.mjs` and `scripts/operators.mjs` build `https://ops-auth.<env domain>` from the domain. Anything that starts reading `ops-auth-url` needs it watched first.
- **A stronger control, for the owner.** A service control policy in the organization could deny `events:DeleteRule`, `DisableRule`, `RemoveTargets` and `PutRule` on the operator rules, and the watch, topic and key calls above, to everyone but the CloudFormation execution role. SCPs are set in the management account, so that's the owner's decision, outside this repository.

**The operator audit watch.** Operator audit items (`OPAUDIT#`, both the `AUDIT#` entries and the `REQUEST#` idempotency records) are append-only, and nothing in the app changes or deletes one. The primary region's `observability` stack runs `supply-checkout-<env>-operator-audit-watch` (`backend/src/ops/operator-audit-watch-handler.ts`, `lib/observability/operator-audit-watch.ts`) on the table's stream. Its event source mapping passes only `MODIFY` and `REMOVE` records whose partition key starts with `OPAUDIT#`, the `INSERT`s below and its own heartbeat item, so it never sees team data, and its role can read the stream and nothing in the table. Each change counts in `OperatorAuditChanged` unless it's a TTL expiry: a `REMOVE` by DynamoDB's TTL process, or of an item whose `expiresAt` had already passed (another replica's TTL deletion can arrive without the TTL identity; making a live item look expired takes a `MODIFY`, which counts). It also reads `INSERT`s of `AUDIT#` entries (never the `REQUEST#` records, which live 24 hours by design) and counts one whose `expiresAt` is more than 7 days short of 2 years after the write (`SHORT_RETENTION_SLACK_DAYS`): the TTL would delete it early as an "expiry", which a `REMOVE` alone can't tell apart. **Operator audit changed** (P1) fires on any in 5 minutes. A batch the function fails on is retried, so its errors alone don't alarm (there was an **Operator audit watch failing** alarm until `supply-checkout-7pe.1`); after five retries the mapping gives the batch up and records its shard and sequence numbers (never the items) in the watch's dead-letter queue, and **Operator audit watch dropped records** (P2) fires: read the message, then the records from the stream while they're still there (24 hours) or compare the audit with point-in-time recovery for that time. The log line has the item's keys, the event name and the stream event ID, never its attributes. It's the stream's second consumer, after the live-update publisher; DynamoDB advises no more than two per shard, so a third needs a fan-out.

**The heartbeat** (`supply-checkout-6uw.11`). Every alarm above needs the watch to read the stream and its metrics to reach CloudWatch, and many things stop that without an error: a disabled mapping, zero concurrency, a stream or key policy, the stream turned off, a deleted or transformed log group. So an EventBridge Scheduler schedule rewrites one item, `OPWATCH#HEARTBEAT` / `HEARTBEAT` (`OPERATOR_AUDIT_HEARTBEAT` in `backend/src/data/schema.ts`), every 10 minutes with DynamoDB's `PutItem` directly, no function; the item holds only its keys and `at`, the scheduled time. Its role may `PutItem` only that partition, naming only those three attributes, and use the table key through DynamoDB. The watch counts each write of it in `OperatorAuditWatchHeartbeat`, and **Operator audit watch silent** (P2) fires when none arrives in 30 minutes (missing data breaches). An alarm on the mapping's `IteratorAge` was the other choice, but Lambda sends it only when it invokes the function, and the filter means it's rarely invoked, so a stalled read would look like a quiet night. If it fires: check the mapping is enabled (`aws lambda get-event-source-mapping`), the function's concurrency, its log group exists (if it was deleted, recreate it with the same name and retention: the role can only write to it, and a redeploy doesn't recreate it) and has no transformer (`aws logs get-transformer`), the table's stream is on and has no resource policy (`aws dynamodb get-resource-policy`), the table key is enabled with its policy as deployed, and the schedule is enabled; then look for the CloudTrail event that changed it.

Delivery from CloudTrail is best effort, and that's all AWS says.

### The operator page

`https://ops.<env domain>/` (`supply-checkout-gxlt`, [ADR 0015](adr/0015-platform-operator-role.md) §9) does in a browser what `npm run ops` does for teams and comps: list and search teams (following a search's empty pages, as the CLI does), open one (its record, owners, comp with months left, Stripe subscription with the comp discount's state, invoices and receipt reads), comp it for 1 to 12 months or until a date (plan, optional seats), end a comp, and read the operator audit by month or by team. Reopening a team, stuck imports and the receipt ranking stay in the CLI. It calls only `GET /ops/teams`, `GET /ops/teams/{teamId}`, `PUT` and `DELETE /ops/teams/{teamId}/comp` and `GET /ops/audit`, with the same requests as the CLI: each write reads the team first (the page shows it) and sends its `version` as `expectedVersion` and a new `Idempotency-Key`, and needs a reason. A 409 (the team changed since it was read, it's closed, or it has no comp to end) says so and offers **Read the team again**, keeping what was typed. A write that got no answer is sent again with the same key, so it's applied once.

- **Code**: `ops/` (`index.html`, `main.js`, `ops.css`, and `lib/` for sign-in, the API client, the config check and formatting), built by `npm run build:ops` into `dist/ops/`, with nothing from `src/` and no dependencies. API data is only put in the page with `textContent`.
- **Hosting**: its own CloudFront distribution in the `web` stack, for `ops.<env domain>` only, with its own certificate (`OpsWebCertificate` in the `domain` stack in `GLOBAL_SERVICES_REGION`, published as `domain/ops-web-certificate-arn`), router (`lib/web/ops-router.js`) and response headers (CSP in `lib/web/ops-content-security-policy.ts`, `Cache-Control: no-store`, HSTS, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`), and the managed CachingDisabled policy. It shares the releases bucket, WAF and logs bucket with the web app. Details in [the web app's hosting](web-app.md#the-operator-page).
- **Sign-in**: the code flow with PKCE against `ops-auth.<env domain>` and the `ops` client, which calls back to the page's root. Only the PKCE verifier and state are kept (in `sessionStorage`, while the browser is at the sign-in host); the access token lives in the page's memory only, with no refresh token, so after 15 minutes (or a 401) the page asks the operator to sign in again, usually without a new password and code within Managed Login's hour. **Sign out** forgets the token and goes to the ops pool's `/logout`. It doesn't revoke the token (it expires within 15 minutes); `npm run ops -- sign-out` or `admin-user-global-sign-out` revokes every token.
- **A customer's token can't be used**: the page only takes a token whose claims name the `ops` client, and the ops authorizer refuses any other pool's or client's token (tests: `ops/test/auth.test.mjs`, `tests/ops.spec.js`, and the ops handler's tests in `backend/`).
- **The API's CORS** allows `https://ops.<env domain>` as well as `app.`. CORS is per API, so API Gateway answers its preflights and adds `Access-Control-Allow-Origin` and `Access-Control-Allow-Credentials` for it to every route's real responses, the auth routes' included. That's safe: only the auth routes read a cookie (`backend/test/cookie-readers.test.ts`), the refresh cookie is host-only on `api.` with `Path=/auth`, `Secure`, `HttpOnly` and `SameSite=Strict`, and the auth handler checks `Origin` against `ALLOWED_ORIGINS`, still `app.` only (`infra/test/api.test.ts` checks), before reading it; every other route takes a bearer token only. So the page can't use a customer's refresh cookie.
- **Who can publish it**: the same people and roles as the web app (the web publisher role, assumed by the GitHub deploy role; `PutKey` on the live-version store and `PutObject` under `releases/`).
- **Alerts on the ops client**: the identity deploy that adds the page's callback and sign-out URL is an `UpdateUserPoolClient` on the ops pool made by CloudFormation, which `OperatorPoolChanges` exempts, so it doesn't page. The same change made outside a deploy pages P1, as it should. Nothing else the rules watch changes (the client's ID and the pool's are the same).

**Setting it up (the owner, once per environment).** In this order, from an up-to-date `main` after the PR merges:

1. Deploy the `domain` stack in `GLOBAL_SERVICES_REGION` (it adds the `ops.` certificate; CloudFormation adds the DNS validation record and waits for the certificate): `cd infra && npx cdk deploy supply-checkout-prod-us-east-1-domain --exclusively --profile supply-prod -c backupCopy=false`.
2. Deploy the `identity` stack the same way (the ops client gains `https://ops.<env domain>/` as a callback and sign-out URL). Expect no operator alert ([above](#the-operator-page)); if `OperatorPoolChanges` does page, check in CloudTrail that the `UpdateUserPoolClient` was CloudFormation's.
3. Deploy the `api` stacks (`npm run deploy -- api`, or the next release): CORS for `ops.`.
4. Deploy the `web` stack (`npm run deploy -- web`): the new distribution, its router, its `A` and `AAAA` records for `ops.`, and two parameters. Before it, check that no record exists for `ops.<env domain>` in the zone (`aws route53 list-resource-record-sets --hosted-zone-id "$ZONE_ID" --query "ResourceRecordSets[?Name=='ops.supplycheckout.com.']"` must print `[]`). `check-router` now also runs the operator page's router (the page answers 503 until it's published).
5. Publish the page: `npm run publish:ops` (builds it, writes `ops-config.json` from SSM, uploads `ops-<time>-<commit>` and makes it live). Roll back with `npm run publish:web -- activate --channel ops --version <an earlier ops-*>`.
6. Check it: `curl -sI https://ops.supplycheckout.com/` shows `cache-control: no-store` and the strict `content-security-policy`; `curl -sI https://ops.supplycheckout.com/x` is a 404; then sign in as an operator, open a team and read the audit.

Using it, and what its messages mean: [the operator page runbook](runbooks/operator-page.md). After the first time, each release's deploy publishes the page ([Deploying a release](releases.md#deploying-a-release)). **Operator page down** (P2) watches its distribution, and so its router, which fails a request with a 5xx when it breaks ([observability.md](observability.md#when-the-web-app-is-down)).

**PKCE isn't enforced for the `ops` client (an accepted risk, `supply-checkout-8jc.47`).** The page and the CLI always send a `code_challenge` (S256), and once one is sent Cognito won't redeem the code without the matching verifier. But Cognito has no setting that *requires* PKCE for an app client (`CreateUserPoolClient` and `UpdateUserPoolClient` have no such field), and Managed Login accepts an authorize request without a `code_challenge`. Someone could craft an authorize link to `ops-auth.<env domain>/oauth2/authorize` with no `code_challenge` and get a signed-in operator to follow it. Cognito would then send a code that needs no verifier to whichever of the client's two callbacks the link names:
- **The page, `https://ops.<env domain>/?code=…`.** The page refuses the code (it has no state the page made). But for the code's ~5 minutes it sits in the browser's history and in the ops distribution's CloudFront access log (`cloudfront/ops/` in the logs bucket, which logs the query string).
- **The CLI's callback, `OPS_CLI_CALLBACK` (`http://localhost:8765/`).** The code goes to whatever is listening on that port on the operator's machine, which may not be `npm run ops`.

Whoever gets such a code can redeem it at the token endpoint for a 15-minute access token and an 8-hour refresh token. The token has the `aws.cognito.signin.user.admin` scope, so it can also replace the operator's TOTP (`AssociateSoftwareToken`, `VerifySoftwareToken`). Signing in again still needs the operator's password, and each of those calls pages P1 (`OPERATOR_SELF_SERVICE_EVENTS`, under [Operators](#operators)).

We accept this. The attacker has to get an operator to follow the link, then within minutes read that operator's browser history or local port, or the logs bucket. Those are already behind the operator's own machine or AWS access to this account. The token still needs the `operators` group on every request, and every use is audited.

Hardening, if it's ever wanted, is the owner's call: it costs money and risks locking operators out.
- A regional AWS WAF web ACL on the operator pool that blocks `/oauth2/authorize` without `code_challenge_method=S256`, tried in Count mode first. WAF inspects Managed Login's headers and query strings, but Cognito doesn't forward it the request body for Managed Login ([Associate an AWS WAF web ACL with a user pool](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-waf.html)). The parameters are in the authorize request's query string. This would close both callbacks.
- Stop CloudFront logging query strings on the ops distribution. That covers only the logs bucket, not browser history or the localhost callback.

### Backfills

One-off migrations for items written before a change, in `backend/src/data/backfill.ts`, run with `npm run backfill` from `backend/` (`backend/scripts/backfill.ts`). They run with your SSO credentials, not a Lambda role: no Lambda may `Scan` the table, and `index.ts` doesn't export them. Each mode scans the whole table (strongly consistent; `notice-address` lists the app pool instead), is a dry run unless given `--apply`, prints counts only (never emails, names or user IDs), and conditions every write so it never overwrites a newer value and never re-creates an item the purge deleted in the meantime. Each is idempotent: run it again and it finds nothing. Two guards against pointing it at the wrong place: `--table` must be an app table's name (`supply-checkout-<env>-app`), and `--profile` is required (and `notice-address` takes its pool only from the table's environment, as below). Before it reads or writes anything, it asks STS which account the profile signs in to and prints it in its first line (`members on supply-checkout-prod-app in us-east-1 in account <account ID> (profile supply-prod)`): check it's the account you mean before you run it with `--apply`. With `--endpoint` (DynamoDB Local), it needs no profile and takes any table name. If one stops partway (a throttle, an expired session), run it again.

| Mode | What it changes | Why |
| --- | --- | --- |
| `stray-ops-keys` | Removes `GSI3PK` and `GSI3SK` from items that shouldn't have them, or have other values than they should, on the condition that they're still the values it read (and, for a member, that they haven't been made an owner since). | Nothing customer-written may reach the operators' index (above). |
| `ops-index` | Sets GSI3 keys on every team `META` item and owner `MEMBER#` item without them, on the condition that they're still absent (and that the member is still an owner). #### Projects rename

`projects-rename` (`backend/src/data/projects-rename.ts`, `supply-checkout-005.6.2`) is section 2 of [the rename plan](projects-rename-plan.md). Run it only on a server release that reads both `SHEET#` and `PROJECT#` (the plan's section 3, release 1), so the app works the whole time. The release that removes the sheets aliases (`supply-checkout-005.6.5`, the plan's PR 6) no longer reads `SHEET#`: deploy it only after a run without `--team` finds no sheet items and no movement with `sheetId`. The mode stays in the code, with `--reverse`, for one more release, as a tool for a restored table. Unlike the other modes it doesn't scan the whole table for one team:

- `--team <teamId>` reads that team's partition with a `Query`. Without it, every team: a `Scan` that reads only keys, for teams with a `SHEET#` item or a movement with `sheetId` or `fromSheetId`.
- For each sheet: a strongly consistent read, then one transaction that puts the copy (on the condition that the new key is free) and deletes the old item (on the condition that its `version` is still the one read). If someone edits the sheet in between, it reads it again and retries, up to 5 times, then reports it and moves on. A `PROJECT#` copy that's already there is never overwritten: if it's equal apart from the renamed attributes, only the old item is deleted; if not, both are left and it's counted as a conflict.
- Movements get `sheetId` and `fromSheetId` renamed, on the condition that the old names are still there and the new ones aren't.
- One write at a time, about 25 a second. `--limit <n>` stops after n sheets and leaves the movements for a full run.
- `--reverse` does the same from `PROJECT#` back to `SHEET#`: the rollback. It's the same code, and it's tested both ways.
- `--export-to <path>` writes the team's `SHEET#`, `PROJECT#` and `MOVE#` items to a new JSON file (owner-only, never over an existing file) before anything is written. It refuses a path inside the repo, or inside any folder with a `.git` entry (so a worktree's main checkout too), compared as the disk spells it: the file holds client names and prices.
- `--team` on a team with no `META` item (a typo) says so, and the run is never `Done.`
- A team with no `META` item, or one that's closed (`purgeAfter`) or being purged (`purging`), is left alone and counted, and the run isn't `Done.` while there is one: its data goes with the purge, and a copy must not outlive it. Every move's transaction checks the `META` item again. A closed team that's reopened can be run then.
- `--expect-account <id>` (any backfill mode) stops before reading anything unless the profile signs in to that account.

The output is counts and check names only: no team, sheet or user IDs, names or emails. A dry run (the default) counts the sheets it would move, the conflicts, the movements, and about how many bytes the sheets hold (the largest must stay well under DynamoDB's 400 KB). After `--apply` it checks, and prints `Done.` only when all of them hold (otherwise `Not done`, and it exits 1):

- no `SHEET#` items are left, and GSI1's `TEAM#<t>#SHEETS` partition is empty;
- the `PROJECT#` count is the count before plus the sheets moved, and GSI1's `TEAM#<t>#PROJECTS` count equals it (it waits up to 60 seconds for the index);
- every moved item's attributes hash the same as before, the renamed ones left out, and its totals (counts and charge in cents, added as `src/project-math.js` adds them) are the same;
- every product's `stock` is what it was;
- no movement still has `sheetId` or `fromSheetId`.

A user taking or returning stock during the run changes a stock count and fails that check, and a user editing a project after it moved and before the checks fails the hash and totals checks the same way; run it again (it finds nothing left to move and checks again) once things are quiet. Run it outside 8am to 8pm Eastern if you can, for the canary and the pilot's day.

The runbook. `<profile>`, `<teamId>`, `<recovery point ARN>` and `<path>` are placeholders: keep the real values out of the repo, and put the recovery point in the bead.

```bash
aws sso login --profile '<profile>'
cd backend && npm ci
P=(--profile '<profile>' --region us-east-1)
B=(--table supply-checkout-prod-app "${P[@]}")

# 1. Backup: an on-demand AWS Backup recovery point (as in docs/backups.md, "Prove the copy path now"), and the PITR time
TABLE_ARN=$(aws dynamodb describe-table --table-name supply-checkout-prod-app --query Table.TableArn --output text "${P[@]}")
ROLE_ARN=$(aws iam get-role --role-name supply-checkout-prod-backup --query Role.Arn --output text --profile '<profile>')
aws backup start-backup-job "${P[@]}" --backup-vault-name supply-checkout-prod-backups \
  --resource-arn "$TABLE_ARN" --iam-role-arn "$ROLE_ARN" --lifecycle DeleteAfterDays=35
aws backup describe-backup-job "${P[@]}" --backup-job-id '<id>'    # until COMPLETED; note the recovery point ARN in the bead
date -u +%Y-%m-%dT%H:%M:%SZ                              # the PITR time to restore to, if it ever comes to that
aws dynamodb describe-continuous-backups --table-name supply-checkout-prod-app "${P[@]}"   # PITR is ENABLED

# 2. Export and dry run: read the counts (and the account on the first line)
B=("${B[@]}" --expect-account '<account ID>')                     # stops unless the profile signs in to prod's account
npm run backfill -- projects-rename "${B[@]}" --team '<teamId>' --export-to '<path outside the repo>/rename-<teamId>.json'

# 3. Apply, then the final check: a second run finds nothing to move and prints Done.
npm run backfill -- projects-rename "${B[@]}" --team '<teamId>' --apply
npm run backfill -- projects-rename "${B[@]}" --team '<teamId>' --apply
```

Then sign in as one of the team's users: the list is there, one finished and one open project open, a checkout and a return work, and the production alarms stay clear ([journeys](journeys.md)). Later, once every team is done, a run without `--team` (dry run, then `--apply`) is the cleanup and should find nothing.

**Rollback**, in order:

1. Before `--apply` there's nothing to roll back.
2. During or after: `npm run backfill -- projects-rename "${B[@]}" --team <teamId> --reverse` (dry run), then with `--apply`. It carries back anything written to a project since, which is why it comes before a restore. If the application is rolled back to a release that reads only `SHEET#`, run it first. The release that removed the aliases (`supply-checkout-005.6.5`) reads `PROJECT#` only, so while it is deployed a part-moved team has to be finished forward, not reversed; `--reverse` is for a rollback to the dual-reading release or earlier.
3. Last resort: restore to the PITR time into a new table (`supply-checkout-<env>-app-restore-*`) and copy the team's partition back, as in [the restore drill](backups.md#restore-drill) and [Put a restored table back into service](backups.md#put-a-restored-table-back-into-service). This loses every write since that time. The export file is a smaller option for a few items: put them back with `aws dynamodb put-item` from it.

The tests (`backend/test/backfill-projects-rename.test.ts`) run it against DynamoDB Local: an empty team, many sheets, a conflicting copy, a re-run, an edit mid-move and one that keeps changing, a round trip with `--reverse`, movements, `--limit`, the export and where it may go, every team by scan, and that the output holds no IDs or names.

The role's IAM conditions (`dynamodb:Attributes`, `dynamodb:Select`, `dynamodb:LeadingKeys` patterns) aren't enforced by DynamoDB Local, so after the first deploy, and after any change to the role or to `backend/src/data/operator.ts`, list teams, read a test team, comp it and end the comp, and confirm the ops function's log group (the api stack's `OpsFunctionLogs`; [Finding a function's log group](journeys.md#finding-a-functions-log-group)) has no `AccessDeniedException`.

**Managing operators** (`supply-checkout-6uw.15`). `npm run operators` (`scripts/operators.mjs`) adds, lists, disables, removes and resets operators with the AWS CLI v2, under an SSO administrator role (`--profile`, default `$AWS_PROFILE`, else `supply-prod`; `--env`, default `prod`; the pool ID from SSM, `/supply-checkout/<env>/identity/ops-user-pool-id`, or `--pool-id`). Before it reads or changes any user, it checks the pool is named `supply-checkout-<env>-ops` and has the `operators` group (`describe-user-pool`, `get-group`), and stops otherwise, so a wrong `--pool-id`, the customers' pool say, can't be touched. In Claude Code, the `operators` skill (`.claude/skills/operators/SKILL.md`) hands the owner the command to run; Claude doesn't run these itself.

```bash
npm run operators -- add alex                                   # prints a temporary password once
npm run operators -- add alex --email alex@example.com --send-email   # Cognito emails it instead
npm run operators -- list                                       # status, enabled, TOTP, group, created (--emails to show addresses: not under Claude Code's !)
npm run operators -- disable alex                               # and enable alex
npm run operators -- remove alex                                # out of the group, signed out, disabled; --yes also deletes
npm run operators -- reset alex                                 # a stolen password or token (below); stays disabled unless --enable
npm run operators -- remove alex --yes --dry-run                # any command: print the AWS CLI calls, run nothing
```

Usernames are 1 to 64 lowercase letters, digits, `.`, `_` or `-` (stricter than the pool, so they're easy to read out). Each command says which of its calls alert P1 (`OperatorPoolChanges`, below): those alerts are expected. A command that fails part-way says what's done, what isn't, and how to finish or undo it; `remove` and `reset` can simply be run again.

The temporary password (`add`, `reset`) is 24 characters from `node:crypto` with every class the pool requires, and never on a command line or in the environment, so it isn't in `ps`. The script writes the request to a file of its own, `--cli-input-json file://<path>`: created owner-only (mode 600, exclusively, not through a symlink) in a fresh owner-only folder under the temporary directory, and removed as soon as the AWS CLI returns, whether the call worked or not, and on Ctrl-C, `SIGTERM` or any other exit. (Standard input, `file:///dev/stdin`, was the first choice, but the AWS CLI can't open it on macOS when Node hands it a socket: `supply-checkout-6uw.17`.) With `--send-email`, `add` makes no password at all: Cognito generates it and emails it, so it never passes through the script. It's printed once, and only when stdout is a terminal, so it can't land in a pipe, a file or Claude Code's `!` transcript (`--print-password` overrides that when you know where stdout goes). The script refuses to run when the profile has the AWS CLI's `cli_history` on, which would store the request in `~/.aws/cli/history`. A dry run shows it as `<redacted>`. Clear the terminal's scrollback once it's handed over.

**Adding an operator.** Only with an SSO administrator role: `npm run operators -- add alex`. The temporary password goes to the person out of band, in person or read out on a call, and expires in a day. They choose a new one and set up TOTP at their first sign-in. Keep the TOTP secret on a phone, not in the same password manager as the password. `--send-email` (with `--email`) has Cognito generate the password and email it with its default sender instead, which works while SES is in the sandbox but puts the password in an inbox: prefer in person. The P1 alert fires for both calls (`AdminCreateUser`, `AdminAddUserToGroup`).

By hand, if the script can't be used:

```bash
P=(--profile supply-prod --region us-east-1)
POOL=$(aws ssm get-parameter "${P[@]}" --name /supply-checkout/prod/identity/ops-user-pool-id --query Parameter.Value --output text)
aws cognito-idp admin-create-user "${P[@]}" --user-pool-id "$POOL" --username alex --message-action SUPPRESS \
  --temporary-password "$(openssl rand -base64 18)Aa1!"   # note it, then hand it over in person
aws cognito-idp admin-add-user-to-group "${P[@]}" --user-pool-id "$POOL" --username alex --group-name operators
```

(That puts the password on the command line, where `ps` shows it for a moment; the script doesn't.)

**Removing one:** `npm run operators -- remove alex` takes them out of the group, signs them out everywhere and disables them; `--yes` then deletes them. Their operator audit entries stay. By hand: `admin-remove-user-from-group`, `admin-user-global-sign-out` and `admin-disable-user`, then `admin-delete-user` when you're sure. Every one of those calls alerts P1 (`disable` and `reset` alert too): say where the alerts go that it's you.

**A stolen operator token or password.** A stolen access token lasts at most 15 minutes, but with the `aws.cognito.signin.user.admin` scope (which the ops function's `GetUser` check needs) it can also replace the operator's TOTP, change their MFA preference or attributes, or delete the user: each of those alerts P1 (below). So:

1. `npm run operators -- reset alex` cuts them off and resets them in one go: global sign-out and disable (both take effect on the next request), TOTP off (the pool, which requires MFA, then asks for a new TOTP setup at the next sign-in), a new temporary password (printed once to hand over in person). They stay disabled until `npm run operators -- enable alex`, once they've a clean device and within the temporary password's day; `--enable` enables them at the end instead. `--send-email` (with `--enable`) sets a throwaway temporary password nobody sees (Cognito's `RESEND` refuses a confirmed user, and this puts them in `FORCE_CHANGE_PASSWORD`), then has Cognito resend the invitation with a new password it generates to the address on the account; that relies on `RESEND` working for a user just given a temporary password, so confirm the email arrives and works the first time it's used. It prints what the operator does next. Then run `npm run operators -- list` and check it shows them with `no TOTP`. By hand:
   ```bash
   aws cognito-idp admin-user-global-sign-out "${P[@]}" --user-pool-id "$POOL" --username alex
   aws cognito-idp admin-disable-user "${P[@]}" --user-pool-id "$POOL" --username alex
   aws cognito-idp admin-set-user-mfa-preference "${P[@]}" --user-pool-id "$POOL" --username alex --software-token-mfa-settings Enabled=false,PreferredMfa=false
   aws cognito-idp admin-set-user-password "${P[@]}" --user-pool-id "$POOL" --username alex --no-permanent \
     --password "$(openssl rand -base64 18)Aa1!"   # note it, then hand it over in person
   aws cognito-idp admin-enable-user "${P[@]}" --user-pool-id "$POOL" --username alex   # once they've a clean device
   ```
2. Read what the account did: `npm run ops -- audit` for the month (and `--team PLATFORM` for team lists and searches), CloudWatch Logs Insights on the ops function's log group (`filter operator = "<sub>"`), and CloudTrail for the pool's calls. Comps it made can be ended with `npm run ops -- uncomp`; its audit items can't be changed or removed by the ops role.
3. The operator deletes the old entry from their authenticator app, signs in with the new temporary password, and sets up TOTP again.

The ops client's write attributes are limited to `given_name` and `family_name`, which nothing trusts. Cognito can't grant `GetUser` without the rest of the admin scope, so the alerts are the control for the rest.

## Billing

Stripe Billing, in the Stripe sandbox (test mode) until the live account and prices are ready ([ADR 0009](adr/0009-billing-stripe.md), [ADR 0013](adr/0013-web-billing-only.md); beads `supply-checkout-8jc.10`, `supply-checkout-x0l`, `supply-checkout-dri`). Stripe is the source of truth for money; the team's `META` item is the source of truth for access.

**Keys.** The Stripe secret key lives only in Secrets Manager, in each region the api stack runs in: `supply-checkout/<env>/stripe/test-secret-key` for the sandbox and, later, `supply-checkout/<env>/stripe/live-secret-key` (`stripeSecretName` in `backend/src/billing/names.ts`), a plain string or a JSON object with one field holding the key. The owner stores them; nothing in the repo does. Which one an environment uses is `stripeMode` in CDK context (`test` unless `-c stripeMode=live`), and the functions refuse a key of the other mode (`STRIPE_MODE`). A function reads the key the first time it needs Stripe and keeps the client for an hour (`backend/src/billing/stripe.ts`), so a rotated key is picked up without a deploy. Neither the key nor Stripe's error messages are ever logged: only Stripe's error type, code, status and request ID. The ops function has its own restricted key, under its own name (`<mode>-ops-restricted-key`, [Operators](#operators), A team's Stripe billing), and can't read this one.

**Products and prices.** `backend/src/billing/catalog.ts` is the catalog, **provisional** until the pricing decision (`supply-checkout-akz`): ADR 0009's proposal, Starter at $9 a month including 3 seats then $3 a seat, and annual at 10 months' price. Each plan is one Stripe product with an ID we choose, and one graduated tiered price per interval (a flat amount for the included seats, then per seat; the subscription's quantity is the seat count), found by its **lookup key**. No price ID is written down anywhere: the billing function looks prices up by lookup key and keeps them for 10 minutes. `npm run stripe-catalog` (`backend/scripts/stripe-catalog.ts`) makes Stripe match the catalog. It's idempotent: a product or price that matches is left alone, a product's name or description is updated in place, and a price whose amounts changed (Stripe can't edit those) is replaced by a new one that takes over the lookup key, with the old one archived. So running it twice leaves one product per plan and one price per plan and interval. Without `--apply` it's a dry run. Without `--live` it reads the test secret and refuses anything but a test-mode key; with `--live` it reads the live secret and refuses anything but a live key.

```bash
aws sso login --profile supply-prod
cd backend && npm ci
npm run stripe-catalog -- --profile supply-prod --region us-east-1            # dry run: what would change in the sandbox
npm run stripe-catalog -- --profile supply-prod --region us-east-1 --apply    # make the sandbox match
# Live mode, once the live key is stored (supply-checkout-dri) and the prices are final (akz):
npm run stripe-catalog -- --profile supply-prod --region us-east-1 --live           # dry run against the live account
npm run stripe-catalog -- --profile supply-prod --region us-east-1 --live --apply
```

After changing the catalog, run it before deploying code that sells the new prices, or checkouts fail with a price the billing function can't find (the Checkout broken alarm).

The same script then makes the **Customer Portal configuration** match `backend/src/billing/portal.ts` (`supply-checkout-121`): one configuration of ours per Stripe mode, found by its metadata (`app: supply-checkout`, `portal: owners`), created if there's none, updated (and reactivated) if its features differ or it names other prices, otherwise left alone; its line in the output is `portal owners`. It lets owners update their card and billing details (name, email for receipts, address, tax ID), see and download invoices, switch the plan's price between the catalog's monthly and annual prices (not the seat count, which follows the team's members, `supply-checkout-l50`; a switch during the free trial keeps the trial, with prorations otherwise), and cancel at the end of the period, with a reason and no refund. The billing function finds the configuration by the same metadata (kept for 10 minutes) and passes it on every session, so the Dashboard's default portal configuration is never used. Without ours, the portal fails with `BillingPortalErrors` (the Billing portal broken alarm): run the script with `--apply` in that mode before deploying, and again whenever the catalog's prices change. A price replaced by a new one is swapped in the portal by the same run.

**Checkout.** `POST /teams/{teamId}/billing/checkout` ([openapi.yaml](api/openapi.yaml)) is served by the `billing` function (`backend/src/api/billing-handler.ts`), in every region. Owners only (checked before the body is read or Stripe is called). The body is only the plan and interval: the seat count is the server's, so a team with viewers isn't billed for them and its first invoice isn't prorated down by the seat sync right after Checkout. It makes the team's Stripe customer the first time (named after the team, `metadata.teamId`) and links it to the team (`linkStripeCustomer`: the `STRIPE#<customerId>` link and the team's `stripeCustomerId`, in one transaction, so a customer can never move to another team), then creates a Checkout Session in subscription mode for that customer, which requires a billing address and lets a business add its name and tax ID (`billing_address_collection: required`, `tax_id_collection`; Stripe saves them on the customer and prints them on every invoice): the plan's price, `quantity` = the team's billed members as they are now (`countBilledMembers`, at least 1; `supply-checkout-8jc.20`), `client_reference_id` and `metadata.teamId` the team. A team with at least two days of its free trial left keeps it: the subscription's `trial_end` is the team's `trialEndsAt`, Checkout asks for no card (`payment_method_collection: if_required`), and if no card is added by then Stripe cancels the subscription (`trial_settings.end_behavior.missing_payment_method: cancel`). Otherwise Checkout asks for a card. **Never a trial for a team that is or was unpaid** (`trialAllowed`, `supply-checkout-8jc.44`), each rule checked on its own rather than left to the trial's dates: not when the team is `unpaid`, not when any of its customer's subscriptions (the ones Checkout already lists) is `unpaid`, and not when Stripe has ever invoiced the customer for money (its latest 100 invoices, read only when no other rule has ruled a trial out: any but a draft with an amount due or paid, so paid, still owed, written off or uncollectible). Such a team pays at once, so a trial can't be used to have an unpaid subscription's debt written off (below). A closed team (403 `team_closed`) or one whose subscription hasn't ended (409 `already_subscribed`) can't start a checkout. Every Stripe create has an idempotency key (the customer's from the team and its name; the session's from the request's `Idempotency-Key`, the customer, the price, the seats and the trial end), so a retry answers the same page. Nothing about the team's plan, seats or status changes here: the webhook (`supply-checkout-2kl`) applies what Stripe records, and the billing worker then keeps the subscription's quantity at the team's billed members (Seats, below), which is where Checkout started it unless someone joined or left in between. A failure on our side or Stripe's counts `CheckoutSessionErrors` (the Checkout broken alarm).

**Customer Portal** (`supply-checkout-121`). `POST /teams/{teamId}/billing/portal` ([openapi.yaml](api/openapi.yaml)) is served by the same `billing` function, in every region. Owners only, checked first (`authorizeTeam` on the path's team, then `requireRole`), exactly as for Checkout: the team comes only from the path and the caller's membership in it, read on a billing-access role session tagged with that team, and the customer only from that team's `META` item (`stripeCustomerId`, which only `linkStripeCustomer` writes, together with the `STRIPE#` link, so a customer can never belong to two teams). The body must be empty or `{}`: nothing in the request reaches Stripe. The session is made for that customer with our portal configuration and `return_url` `https://app.<env domain>/?billing=portal&team=<teamId>` (`APP_URL`, set by the stack, never from a request header). A closed team is 403 `team_closed`; a team with no Stripe customer yet (no checkout started) is 409 `no_billing_account`; a team whose subscription ended can still open it, for its invoices and card. It reads the team and writes nothing: no new IAM, since the function's own role already reads the Stripe secret key, and the billing-access role's `GetItem` in `TEAM#<teamId>` covers the reads. Logged: `Billing portal opened` with the team ID; a failure logs `Billing portal failed` with Stripe's error fields only, and counts `BillingPortalErrors`. `GET /me` gives each team `billingAccount` (it has a Stripe customer, so the web app shows owners **Billing** in the team bar) and `cancelsAt` (the end of the period a canceled subscription still runs to; the team bar says so to everyone). What an owner changes in the portal comes back through the webhook: `customer.subscription.updated` records a switch of price (plan and interval), a new card, or a cancellation (`cancelAtPeriodEnd`, set from Stripe's `cancel_at_period_end`, or a `cancel_at` date), and `customer.subscription.deleted` ends it at the period's end, turning the team read-only and emailing its owners, all within a minute. The trial-ending and payment-failed emails send owners to the app, where Billing is how they add or fix a card. Both routes need two-step sign-in (Sign-in, above): an owner without it gets 403 `mfa_required`, and the app opens the setup; one whose session began before it was turned on gets 403 `mfa_sign_in_again`, and the app asks them to sign in again.

**Webhook, queue and worker** (`supply-checkout-2kl`). `POST /billing/webhook` is Stripe's endpoint, in every region, with no authorizer: the `billing-webhook` function (`backend/src/billing/webhook-handler.ts`) checks the `Stripe-Signature` header against the endpoint's signing secret (5-minute tolerance), puts the event on the billing queue, and only then answers 200. A bad or missing signature is 400 and counts `WebhookSignatureFailures` (the Webhook signature failures alarm); a queue that won't take the event is 500, so Stripe retries. Events we don't handle, and events from the other Stripe mode, are answered 200 and dropped. The message holds only IDs, the event's type and time, and the statuses and dates the owner emails need, never a name, email or address. The queue (`supply-checkout-<env>-billing-events.fifo`) is FIFO, grouped by Stripe customer (one team, one customer) and deduplicated by event ID; a message that fails 5 times goes to `supply-checkout-<env>-billing-events-dlq.fifo` (the Billing events stuck alarm, P1; Billing events late, P2, when the oldest message is over 5 minutes old). The `billing-worker` function (`backend/src/billing/worker.ts`) takes one event at a time: it skips an event already recorded, finds the team from our own `STRIPE#` link (never from the event), fetches the subscription's latest state from Stripe and applies it to the team's `META` item (`plan`, `seats`, `status`, `billingInterval`, `currentPeriodEnd`, `cancelAtPeriodEnd`, `stripeSubscriptionId`) with `applySubscription`, emails owners when that's called for, and only then records the event (`WEBHOOK#<eventId>`, kept 30 days). Replaying an event changes nothing. The write is conditioned on the item existing (a purged team is never recreated), on no `closedAt` and no `purging` (a closed team changes no more; see "Closing a subscribed team" below for its subscription), on the customer being the team's, and on the subscription being the team's, or the new one when the team's has ended. A second live subscription for a team that has one (two Checkout pages finished before the first webhook) isn't applied: the worker cancels it at once, and logs it (a second one that was already paid needs a refund by hand). Checkout also refuses a team whose customer has a live subscription the webhook hasn't recorded yet.

**Invoices** (`supply-checkout-eja`). Stripe makes, emails and keeps the invoices; the app only lists them. `GET /teams/{teamId}/billing/invoices` ([openapi.yaml](api/openapi.yaml)) is served by the same `billing` function, with the portal's checks (owners only, two-step sign-in, `no_billing_account`) and for the same customer, the one on the path's team's `META` item: it lists that customer's latest 24 invoices from Stripe (`invoices.list`, newest first), so the list is always Stripe's. Unlike the portal, a closed team (closed by an owner, or by the lapsed-team job) still lists its invoices (`supply-checkout-8jc.24`), owners only and with two-step sign-in as before, so they can save them before the purge deletes the team and its Stripe customer: until its `purgeAfter`, then 409 `team_deleting`, as soon as the purge is due or has marked the team `purging`. Drafts are left out (Stripe hasn't sent them); `hasMore` says older ones are in the Customer Portal. Each has its number, status, date, amounts and currency, and links to Stripe's hosted invoice page and PDF, passed on only if they're `https` pages on `stripe.com`. Nothing from the request reaches Stripe, it writes nothing, and it needs no new IAM (the same `GetItem`s as the portal, and the Stripe key the function already reads). Logged: `Invoices listed` with the team ID and the count; a failure logs `Invoices failed` with Stripe's error fields only and counts `InvoiceListErrors` (on the dashboard's billing errors graph, with no alarm: the portal lists invoices too). The billing details on an invoice (the billing name, address, and a business's tax ID) are the customer's: Checkout collects them, and owners change them in the portal (name, email for receipts, address, tax ID).

**Invoice and receipt emails.** Stripe sends them, not us: there's no second email path. They're account settings in the Stripe Dashboard, not something the API or the catalog script sets, so the owner turns them on once per mode (the sandbox emails only addresses on the Stripe account's own team, so test with one of those): in Settings, **Customer emails**, "Successful payments" (receipts); in Settings, **Billing, Subscriptions and emails**, "Send finalized invoices and credit notes to customers" (with links to the hosted page and PDF), and the renewal and failed-payment reminders as wanted. The address is the customer's email, which Checkout saves on the customer the first time (the customer is made without one) and the owner changes in the portal. The invoice's header and footer come from **Settings, Business, Public details** (the business name, address and support email) and **Billing, Invoice template**: fill those in before going live.

**Closing a subscribed team** (`supply-checkout-t0en`, `backend/src/billing/closing.ts`). Closing a team never calls Stripe: the closure is one DynamoDB transaction, so a Stripe outage can't refuse a closure or leave it half done, and the closed team itself is the pending cancellation. The hourly closed-team purge carries it out: at the start of each run it lists every closed team (GSI1's `TEAMS#CLOSED` partition) that has a `stripeSubscriptionId` and no `stripeCancelledFor` equal to its `closedAt`, re-reads each one (consistent), fetches the subscription from Stripe, ends it, and then records `stripeCancelledFor = closedAt` on the `META` item, conditioned on the same `purgeAfter` (still this closure). Ending it means `cancel_at_period_end` for a `trialing`, `active` or `past_due` subscription (nothing more is charged, and a trial ends at its trial end uncharged), with the closure stamped in the subscription's metadata (`supply_checkout_closed_at`, its `closedAt`) so a reopen can tell that cancellation from one the owner made in the Customer Portal, cancelling at once one that's `unpaid`, `paused` or `incomplete` (nothing is being paid for), and nothing for one that's ended or already set to cancel. Three kinds of team are set aside for a person instead (`stripeSetAsideFor = closedAt` and `stripeSetAsideReason`, the same condition, counted in `ClosedTeamSubscriptionsSetAside`): a subscription that belongs to another customer (`CustomerMismatch`, left untouched); one Stripe doesn't have (`NotFound`, also logged as a warning and counted in `ClosedTeamSubscriptionsNotFound`, the "Closed-team subscription not found in Stripe" alarm, since a Stripe key or mode mismatch would look like that for every team: it isn't recorded as done, so once the key is fixed, removing `stripeSetAsideFor` has the next run end it); and one Stripe refused to end with an invalid-request error about the subscription itself (`PermanentError`: a 400 or 404, never an error about the key, mode, permissions, a lock or a rate limit, `isPermanentStripeError`), only when the same run had Stripe take the same request (the fetch, the `cancel_at_period_end` update or the cancel) for another team, since a bad key or a bug in that request would refuse every team alike, and those stay listed and fail the run. None of them ends by retrying, and the listing (at most 100 teams a run, `CLOSED_TEAMS_TO_END_PER_RUN`, with a warning when it's full) leaves set-aside teams out, so they can't starve newer closures (`supply-checkout-8jc.17`). Every run then counts the teams set aside for their current closure and sends the `ClosedTeamsSetAside` gauge, which keeps the "Closed-team subscription set aside" alarm on until each is dealt with, and logs up to 25 of them by ID and reason (`supply-checkout-8jc.36`). Each Stripe call has an idempotency key hashed from the action, the team, `closedAt` and the subscription, so a retry sends the same request; a team reopened and closed again is a new closure with new keys. A team that fails (Stripe down, say) isn't recorded, is tried again the next hour, and makes the run throw, which the Functions failing alarm sees; the run still purges and still sends its gauge. The subscriptions part starts no new team after half the run's 4-minute budget. **Ending it at close** (`supply-checkout-8jc.30`): the purge is the backstop, not the usual path. Right after the closing transaction, the account function puts a message with reason `closed` on the seat sync queue for the team's Stripe customer (for an owner's close and for a team closed with its only member's account; operators can't close a team), and the billing worker (`endAtClose` in `backend/src/billing/worker.ts`), finding the team from our own `STRIPE#` link, sets its recorded subscription to cancel at the period's end with the closure's stamp, usually within seconds. Its idempotency key is the purge's plus the message's ID (`closingKey(..., messageId)`). It writes nothing to the team: the stamp on the subscription is the record that this closure set it to cancel, which is all a reopen needs to resume it (below), so the worker's role gains no write. The purge's next run then finds it already set to cancel for this closure (`closingAction` is `none` for a subscription stamped with the same `closedAt`), sends Stripe nothing and records `stripeCancelledFor` as usual. Only a cancellation at the period's end is made at close: a subscription to cancel at once (`unpaid`, `paused`, `incomplete`) is left to the purge (`left_to_purge`), since nothing is charging and a reopen can't resume a cancelled one. It's best effort and doesn't wait on Stripe: the close doesn't wait for it, a message that can't be queued is logged (`Closed team's subscription end not queued`) and counted in `SeatSyncQueueFailures`, and a Stripe or DynamoDB failure in the worker is logged (`Closed team's subscription not ended at close: the purge will`, the error's name) without failing the message, so it never holds up the customer's later syncs. Because the queue is FIFO per customer, a reopen's seat sync (which resumes the subscription) is handled after the close's. So a closed team's subscription is set to cancel within seconds of the closure, or within about an hour when Stripe or the queue is failing: a renewal or trial conversion charged in that gap is logged by the purge (`Closed team's subscription renewed after it closed`) and counted in `ClosedTeamRenewalsCharged`, and the "Closed team charged" alarm fires, so the invoice gets refunded by hand. The billing worker also ends a live subscription on a closed team when an event for it arrives (a checkout that finished just after the team closed, whose subscription the team never recorded), with the same keys; it never writes to a closed team. A team reopened while the purge or the worker was calling Stripe had its subscription set to end for a closure that's over, possibly after the reopen's resync already ran. The purge finds it when recording `stripeCancelledFor` fails its condition; the worker, after any change it asked Stripe for, re-reads the team (consistent, the same `GetItem` on `META` it already makes) and finds it open, or closed again with another `closedAt`. If the team is open and the change was `cancel_at_period_end`, either resumes it at once (`resumeSubscription`, an idempotency key of its own, `ReopenedTeamSubscriptionsResumed`) and warns (`Team reopened while its subscription was being ended: resumed`). Otherwise (cancelled at once, closed again, or the resume failed, `Reopened team's subscription not resumed`) it's logged as an error (`Team reopened while its subscription was being ended`) and counted in `ReopenedTeamSubscriptionsEnded` (the "Reopened team's subscription ended" alarm), and fails the run. The worker's event is retried either way, and then applies to the open team; a `closed` message isn't (the team is open, so a retry would do nothing), and reports `team_reopened`. If the worker's re-read, or the purge's recording of `stripeCancelledFor`, fails after Stripe took the change, nothing could see a reopen in that window (`supply-checkout-8jc.30`): it's logged as an error (`Closed team's subscription set to end, but the team wasn't read again`) and counted in `ReopenedTeamSubscriptionsEnded` too (metadata `checked: "no"`), so a person checks whether the team is open. The event is retried and the purge's run fails, as for any failure. A team the purge has started deleting isn't listed for ending: deleting its customer ends any subscription on it, as long as the purge's Stripe key is for the right account and mode. Under a key or mode mismatch it isn't: the delete gets "not found" too and ends nothing. So a team set aside for its current closure (for any reason) isn't purged until a person deals with it (`supply-checkout-8jc.37`): the purge leaves it out of its listing and `purgeTeam` holds it, even past its deletion date, while "Closed-team subscription set aside" stays on (and "Deletion overdue" fires for it too, once it's a day past its date). That hold ends 14 days after its deletion date (`HELD_PURGE_GRACE_DAYS`, the owner's decision, `supply-checkout-8jc.40`): the purge lists and purges it like any other team (the listing and the `purging` mark's condition take the cutoff, `purgeAfter` at or before the run's time less 14 days, as a value, so the purge's IAM attribute lists are unchanged), its deletion record keeping its Stripe customer and subscription IDs, and logs it as an error (`Held team purged with its subscription unresolved`, the team ID, the Stripe IDs and the set-aside reason only) and counts it in `HeldTeamsPurged` ("Held team purged with its subscription unresolved", P2), so a person ends the subscription by hand in Stripe. Five or more set aside at once is treated as a mismatch (or set-asides left uncleared), P1 ("Many closed-team subscriptions set aside"). When the purge deletes a team, it first writes the team's deletion record, which keeps the team's Stripe customer and subscription IDs, then deletes the team's Stripe customer (`customers.del`: its name, email, address and saved cards, and any subscription still on it ends at once; Stripe keeps the invoices and payments). A customer already deleted counts as done, since a run that stopped after deleting it gets that, but it's also what a mismatch looks like, so it's warned of and counted in `StripeCustomersAlreadyDeleted` ("Stripe customer already deleted", P2). **The deletion deadline never waits on Stripe** (`supply-checkout-8jc.42`, the owner's decision on `supply-checkout-8jc.19`): when Stripe can't delete the customer (an outage, a 5xx, a timeout, a rate limit, a key that can't be read; any error), the purge queues the customer's deletion in the table (`backend/src/data/stripe-deletions.ts`: one item in the fixed partition `PURGE#STRIPE_DELETIONS`, sort key the team ID, holding only the team ID, `stripeCustomerId` and `queuedAt`, written once), counts it (`StripeCustomerDeletionsQueued`), logs `Stripe customer deletion queued` (the IDs and Stripe's error type, status and request ID, never its message), and purges the team as usual. The queue entry is written before any of the team's items go, after its deletion record, which keeps the same Stripe IDs for 400 days; only a queue entry that can't be written leaves the team for the next run. After 3 failures in a row (`STRIPE_FAILURES_BEFORE_QUEUEING`) a run stops calling Stripe and queues the rest straight away, so an outage's timeouts can't slow the data deletions. After its purging, every run retries the queue, oldest first, within the same 4-minute budget. Before asking Stripe it reads the team's `META` item (consistent, `closedAt, purgeAfter, purging` only): an entry whose team is still there and not marked `purging` is refused, never sent to Stripe, and fails the run, as is one whose customer ID isn't `^cus_[A-Za-z0-9]+$` (checked on write too). A customer Stripe deletes (or says is already gone, counted for "Stripe customer already deleted" the same way) has its entry removed, and a failure is logged (`Queued Stripe customer deletion failed`) and left for the next run. Each run that can read the queue sends `StripeCustomerDeletionsPending` and `StripeCustomerDeletionOldestHours` (the oldest entry's age), and "Stripe customer deletion retrying" (P2, a day) and "Stripe customer deletion stuck" (P1, a week) alarm on the age ([journeys.md](journeys.md)). A queue that can't be read or cleared, or holds an entry the app didn't write (never sent to Stripe), fails the run. Both purge paths end the same way: a team purged on schedule and a held team purged 14 days late both have their data gone, their Stripe IDs in their deletion record, and their customer either deleted or queued; a held team's subscription is still left to a person ("Held team purged with its subscription unresolved"), since a key or mode mismatch wouldn't end it. A restore's re-applied deletions queue each re-purged team's customer the same way (`backend/src/data/restore.ts`), so an entry lost with the restore comes back, and one already deleted is just cleared. When the purge itself deletes a customer, it also removes any queue entry for that team (best effort, a warning if it can't), so an entry left by a stopped run isn't retried and reported as "already deleted". `ClosedTeamSubscriptionsEnded` and `StripeCustomersDeleted` count both. The purge's role may read the one Stripe secret key for the environment and mode (`secretsmanager:GetSecretValue` on its ARN only), its table grants gained only `stripeSubscriptionId`, `stripeCancelledFor`, `stripeSetAsideFor` and `stripeSetAsideReason`, and it may `PutItem`, `DeleteItem` and `Query` (`SPECIFIC_ATTRIBUTES`) only the `PURGE#STRIPE_DELETIONS` partition, naming only its keys, `teamId`, `stripeCustomerId` and `queuedAt` (`STRIPE_DELETION_ATTRIBUTES`) ([Observability](observability.md)).

**Reopening a subscribed team** (`supply-checkout-85qp`, `backend/src/billing/reopening.ts`). Reopening never calls Stripe either, so a Stripe outage can't refuse a reopen. The reopen's own update (`reopenTeam` for an owner, `reopenOpsTeam` for an operator) sets `stripeResyncFor` on the `META` item to the closure it ends (its `closedAt`), and the seat sync the account or ops function already queues after a reopen has the billing worker resync the subscription: before every seat sync, the worker checks the team (found from our `STRIPE#` link) for `stripeResyncFor`, from the same link, context and team reads the seat sync uses (`findSeatTeam`: read once per message, then only the team again after a resync or the nightly entitlement check, so the seat sync sees what they applied; `supply-checkout-8jc.39`), and for an open team with one it fetches the recorded subscription; resumes it if the closure it was reopened from set it to cancel at the period's end (`resumeAction`: `cancel_at_period_end`, the `supply_checkout_closed_at` stamp naming that closure, and Stripe's `canceled_at`, the time of the latest request that set it to cancel, no later than the reopen's `stripeReopenedAt`; it sets `cancel_at_period_end` back to false and removes the stamp, with an idempotency key from the team, the closure and the subscription, counted in `ReopenedTeamSubscriptionsResumed`); applies Stripe's latest state with `applySubscription`, as for an event (the team's events were skipped while it was closed); and removes `stripeResyncFor`, on the condition it's still that closure. A cancellation the owner made in the Customer Portal before closing is left alone, and recorded, so the app says when it ends. A subscription that has ended (cancelled at once at closing because it was `unpaid`, `paused` or `incomplete`, or set to cancel and its period ran out before the reopen) can't be resumed: its status is applied, the team is read-only as for any ended subscription, and its owners see Subscribe, which starts a new Checkout; the reopen dialog says so beforehand. The owners' reopen email is sent before the resync, so it covers every outcome without promising one: a subscription the closure set to end will be set to renew again, an owner can renew it from Billing if the app still says it will end (a resume that failed or was left for a person), and one that had already ended needs an owner to subscribe again. A Stripe or DynamoDB failure throws, so the seat sync is retried (5 tries, then the seat syncs dead-letter queue); `stripeResyncFor` stays, and the nightly reconciliation's message for the team does it instead, counting `ReopenResyncsLate` and logging `Reopened team's subscription not yet resynced` first (the "Reopened team's billing not resynced" alarm, P2, primary region, which fires again each night until it's done). A subscription Stripe doesn't have, or that isn't the customer's, is warned of and left pending for a person. The closure's `stripeCancelledFor` and `stripeSetAsideFor` stay on the item: both name that closure's `closedAt`, so nothing reads them once the team is open, and a new closure has a new one. `stripeCancelledFor` isn't what decides a resume, because the purge also records it for a subscription the owner had already set to cancel. The stamp only ever means "set to cancel by this closure", and only until the resync of the reopen after it: on an open team with no resync pending, the worker removes any stamp of ours from a live subscription, set to cancel or not (an owner who renewed and cancelled again in the Portal before the worker saw the renewal would otherwise carry it), the resync removes one it didn't resume, and while a resync is pending the worker removes it from a subscription no longer set to cancel (`staleStamp`, `removeStamp`, keyed by the message). An unstamped cancellation is the owner's, and closing never stamps it. Closing a team whose subscription is already set to cancel with an earlier closure's stamp stamps it again with the new `closedAt`, so reopen, close, reopen still resumes ours. A cancellation an owner makes in the Portal after the reopen is never resumed, stamp or not, since its `canceled_at` is after `stripeReopenedAt`. A subscription set to cancel before the stamp existed (no stamp) is taken as ours only when the purge recorded ending it for that closure (`stripeCancelledFor`) and its `canceled_at` falls between the closure and the reopen, while the billing API refused the team's owners the Customer Portal; set before the closure, it's the owner's, and stays. If Stripe gives no `canceled_at`, or the team has no `stripeReopenedAt` (reopened before this was recorded), it's left set to cancel, counted in `ReopenedTeamSubscriptionsUndecided` and warned of (`Reopened team's subscription left set to cancel`, the "Reopened team's subscription left to cancel" alarm, P2), so a person decides rather than the code charging an owner who cancelled. Resuming a `trialing` subscription means it converts to paid at its trial end, and a `past_due` one means Stripe goes on retrying its card: both charge the customer, as before the closure. The worker's role also reads `stripeReopenedAt` and `stripeCancelledFor`, and the operator reopen role may name `stripeReopenedAt`. The billing worker's role reads `stripeResyncFor` and `cancelAtPeriodEnd` and may name `stripeResyncFor` in its update (`BILLING_READ_ATTRIBUTES`, `BILLING_UPDATE_ATTRIBUTES`), and the operator reopen role may name `stripeResyncFor` and `stripeReopenedAt` (`REOPEN_ATTRIBUTES`); the purge's grants are unchanged. The worker's own requests to end a closed team's subscription carry the Stripe event's ID in their idempotency key, so a later event's request (after the subscription was renewed, say) is never answered from Stripe's cache of an earlier one. A reopen right after a close resumes the cancellation the worker made at close (`supply-checkout-8jc.30`) the same way: it carries the closure's stamp, and its `canceled_at` is before the reopen, since the reopen's seat sync is behind the close's message on the customer's FIFO group (a reopen while Stripe was being asked is the race above, which the worker resumes itself).

**Billing access rules** (ADR 0009, Terms 4, 5.6 and 6, `supply-checkout-qdx`). One function decides them, `billingAccess` in `backend/src/data/model.ts`, from the team's META item; `authorizeTeam`, `GET /me`, the billing worker and the nightly entitlement check all use it. A live comp gives full access whatever Stripe says, and no clock below starts before a comp that ran out did.

| Team | Access | Deletion date (`readOnlyDeletesAt`) |
| --- | --- | --- |
| `active`, a Stripe trial (`trialing` with a subscription), `incomplete`, `paused` | Full | No |
| The app's own trial (`trialing`, no subscription) before `trialEndsAt` (or 14 days after `createdAt`) | Full | No |
| The app's trial after it ended (`trial_ended`) | Read-only | 30 days after the trial ended, rounded up (below) |
| `past_due` within 7 days of `pastDueSince` | Full, with the grace's end on `/me` (`paymentGraceEndsAt`) | No |
| `past_due` after that (`payment_overdue`) | Read-only until it's paid | No: when Stripe's retries all fail it cancels the subscription (below), and the last row applies |
| `unpaid` (`payment_overdue`), a fallback: Stripe isn't set to use it | Read-only until it's paid | No |
| `canceled`, `incomplete_expired` (`subscription_ended`) | Read-only | 30 days after `subscriptionEndedAt`, rounded up (below) |

A deletion date is rounded up to the end of its UTC calendar date in the last time zone on Earth (UTC−12): 12:00 UTC the next day (`deletionTime` in `model.ts`). Owners are told that date (`deletionLastDay`: the emails say "after November 1", and `/me` has it as `readOnlyLastDay`), so nobody, in any US time zone or elsewhere, loses data while it's still the date they were told.

A read-only team's context has `subscriptionEnded` (and `readOnlyReason`), and `writable` refuses a write with `SubscriptionEndedError` (403 `permission_denied`, `reason: "subscription_ended"` for all three, with a message for each), except what a closed team allows (leaving, removing members, revoking invites, closing) and a member keeping their own email current and an owner linking the customer to subscribe again. Every read stays open, so members can still list everything and owners can export it; owners can still open Checkout (no subscription, or an ended one) and the Customer Portal (to pay an overdue invoice), but can't invite or change roles. `GET /me` says so (`subscriptionEnded`, `readOnlyReason`, `readOnlyDeletesAt` and `readOnlyLastDay`, `paymentGraceEndsAt`), and the web app shows a banner, keeps the app view-only, and gives owners a Subscribe button that starts Checkout (Starter, monthly, a seat per member) and then a link to it. The billing worker keeps the dates the rules count from on the META item (`applySubscription`): `pastDueSince`, the first time it applies `past_due`, and `subscriptionEndedAt`, Stripe's `ended_at` (or, without one, when it first applied it) for `canceled` and `incomplete_expired` only (`STOPPED_STATUSES`; never `unpaid`, a payment still owed), each removed with any other status; the nightly entitlement check records one a team is missing (drift field `accessDates`). **Stripe's failed-payment setting** (the owner's, in each Stripe account and mode): Settings → Billing → Subscriptions and emails → Manage failed payments → after all retries fail: **cancel the subscription**. So an overdue payment ends in `canceled`, and the Terms' 30-day read-only window (section 6) starts then; Terms 5.6 says so. If it's ever set to mark the subscription unpaid instead, `unpaid` teams stay read-only as overdue (`payment_overdue`) and are never deleted for it, and nothing changes in the code. Check it when setting up a Stripe account or mode, and after any change to the retry settings.

`incomplete` (a first payment still being confirmed, which Stripe expires to `incomplete_expired` within 23 hours) and `paused` (only if someone pauses the subscription in Stripe: Checkout's trials cancel, not pause, without a card) keep full access on purpose: neither is a lapse the Terms make read-only, and both end in a status the rules do cover. Ending a comp early (`DELETE /ops/teams/{teamId}/comp`) keeps `compUntil` as when it stopped, so the clocks start then. The billing worker ignores an event for another `canceled` or `incomplete_expired` subscription when the team's is `unpaid`, or ended later (`endedEarlier`), so a late or replayed event can't give an overdue team a deletion date or move one earlier; only a paid subscription (a resubscription) replaces an unpaid one. **Resubscribing an unpaid team** (`supply-checkout-8jc.44`, `backend/src/billing/replaced.ts`). The owner's decision: once the team pays for a new subscription, the unpaid one's debt is written off. Only a paid replacement does that (`isPaidReplacement`): one that's `active`, or `past_due` after at least one of its invoices took money (a trial's $0 invoice doesn't count). Never a `trialing` one, so a trial can't be used to have the debt voided without paying (and Checkout gives such a team no trial, above). Until then the team stays on its unpaid subscription, read-only as overdue, and the worker logs `Resubscription not live yet: the team keeps its unpaid subscription`; the new one's later event (`invoice.paid`, say) applies it once it's paid. An `incomplete` one (its first payment still being confirmed) waits the same way; if it expires instead, the team is still on the unpaid one, which has no deletion date while it stays `unpaid` in Stripe (once Stripe cancels it, the 30 days start as for any ended subscription). Before the team takes the paid one, the worker cancels the unpaid one at once and voids its open invoices (the customer's own only; drafts, and paid, void or uncollectible invoices, aren't touched), so the old debt isn't dunned or collected alongside the new subscription, and logs `Replaced unpaid subscription cleared` (the IDs, whether it cancelled, how many it voided and how many Stripe refused). It does this first, so a failure retries the event while the team still names the old one; a subscription Stripe no longer has as `unpaid` is never cancelled again (no double cancellation, even after Stripe's 24-hour idempotency window), Stripe's listing of open invoices leaves out those already voided, and each request has an idempotency key from the object it changes (`cancel-replaced-<subscription>`, `void-replaced-<invoice>`). An invoice Stripe refuses to void for good (an invalid-request error about it, `isPermanentStripeError`) is logged by ID as `Replaced unpaid subscription's invoice not voided: void it by hand` (with Stripe's error type, code, status and request ID) and skipped, so the event isn't retried forever; void it in the Stripe Dashboard. If the clearing keeps failing, the event goes to the billing dead-letter queue, and the old subscription's own end (`customer.subscription.deleted`) can arrive while the team still names it: for an event about the team's own subscription that has ended (or gone unpaid), the worker first looks among the customer's latest 10 subscriptions for a paid replacement, and if there is one applies it instead (clearing the old one as above), so no deletion date starts while a paid subscription exists. A later end of a subscription the team no longer names changes nothing (`ignored`). An unpaid one Stripe has that the team hasn't heard of yet (the team still says `active`) is cleared the same way, and one that was paid meanwhile is still live, so the resubscription is cancelled as a second subscription. The nightly entitlement check does the same when it finds a lost resubscription for an unpaid team, with the same paid-replacement rule. The worker's key is the secret key, so this needs no new Stripe permission; if it's ever a restricted key, it needs **Subscriptions: Write** and **Invoices: Write** (ADR 0015). An ended team without `subscriptionEndedAt` is read-only but never gets a deletion date. Missing or unreadable dates never make a team read-only sooner. The hourly lapsed-team job acts on it (`backend/src/ops/team-lapse-handler.ts`, [runbook](runbooks/lapsed-teams.md)): it emails owners as an app trial ends (3 days before, and at the end), when a payment's grace ends, and at least 7 days before the deletion date (recorded once delivered; a team with no owners to warn is counted, never closed), then, once the later of the date and 7 days after the warning (rounded up the same way) has passed and Stripe confirms nothing is live and no Checkout Session is open, and no owner started Checkout in the last 25 hours (`stripeCheckoutAt`, set by every Checkout), closes at most 10 teams a run (`LAPSE_MAX_CLOSURES_PER_RUN`, holding the rest and alarming), closing each with `purgeAfter` 24 hours later (`closedBy: system:lapsed`, conditioned on its version and that Checkout time; reopenable until then, as any closed team). One run goes at a time (a lease, `LAPSE#RUN`), and the function has no retries. The hourly closed-team purge then deletes the team with its deletion record and Stripe customer. Comped, closed, `unpaid` and overdue teams are never closed by it.

**Owner emails** (`sendTeamNotice`, the existing `trialEnding`, `paymentFailed` and `readOnly` templates): a trial ending with no card on the subscription (`customer.subscription.trial_will_end`), a failed payment (`invoice.payment_failed`, with the next try and the 7-day grace), and the subscription ending (`customer.subscription.deleted`, or `.updated` into `canceled`, `unpaid`, `incomplete_expired` or `paused` from another status), unless a comp keeps the team going; the read-only email says when the team is deleted unless an owner subscribes. Each owner is emailed at most once per event: the worker claims `WEBHOOK#<eventId>` / `NOTICE#<userId>` before sending, so a retried event never emails twice, and an email that fails after the claim is counted (`BillingNoticeFailures`) rather than retried. Closed teams get none.

**Seats** (`supply-checkout-l50`). A subscription's quantity is the team's **billed members**: owners and editors (`contributor`); viewers are free (owner decision, 2026-09-28). That rule is one list, `BILLED_ROLES` in `backend/src/data/seats.ts`. The quantity is just that count (at least 1): the price is graduated, so the plan's included seats are in its flat first tier and nothing here adds or subtracts them. The sync is **asynchronous, through a queue of its own**, so a membership change never waits on Stripe or fails because Stripe is down:

- After a membership change commits (an invite accepted, a role changed, a member removed or leaving, an account deleted, a team reopened, whose sync also resyncs its subscription, above), the account function puts a seat sync on the seat sync queue for the team's Stripe customer, taken from the team's own `META` item (`queueSeatSync` in `backend/src/api/account-handler.ts`, `sqsSeatSyncQueue` in `backend/src/billing/seat-queue.ts`). Only for an open team with a Stripe customer. The ops function does the same after an operator reopens a team (`POST /ops/teams/{teamId}/reopen`), reading the customer from the operators' index (`opsTeamStripeCustomer`), since members may have left while it was closed (`supply-checkout-8jc.21`). It's best effort: a sync that couldn't be queued is logged (`Seat sync not queued`, the error's name) and counted (`SeatSyncQueueFailures`), and the membership change or reopen stands.
- A message with reason `closed` isn't a seat sync: the account function sends it as a team closes, and the worker sets the closed team's subscription to end instead (see "Closing a subscribed team", above).
- The queue (`supply-checkout-<env>-seat-syncs.fifo`, in every region) is FIFO, grouped by the customer, so one team's syncs are handled one at a time, and deduplicated by the message's own ID within the customer's group (`deduplicationScope` `messageGroup`, with `fifoThroughputLimit` `perMessageGroupId`), so no sender can drop another customer's sync, the nightly reconciliation's included, by sending its ID first (`supply-checkout-8jc.26`). The worker refuses a seat sync whose customer isn't its group, whose ID isn't its deduplication ID, or that has the reconciliation's ID (`reconcile-<day>-<customer>`) without reason `reconcile` and that customer, or reason `reconcile` without that ID (`checkSeatSyncDelivery`, error `SeatSyncMismatch`). Only a sender that can already queue syncs for that customer (the account or ops function) can still send a customer's reconciliation ID first; SQS then drops that night's real reconciliation for that customer, but a mismatched message never becomes one: it's refused into the dead-letter queue, and Seat syncs stuck fires. A message that fails 5 times goes to `supply-checkout-<env>-seat-syncs-dlq.fifo` (the Seat syncs stuck alarm, P2). The message is `{kind: "seats", id, customer, reason, created}`. It names no team: the worker finds the team from our `STRIPE#` link, as for an event. It's a queue of its own, not the billing queue, so only the webhook ever sends Stripe events: the billing worker reads both, and takes only seat syncs from this one (it knows it by `SEAT_QUEUE_ARN`) and only Stripe events from the other. Ordering with the customer's Stripe events doesn't matter: the quantity is always recomputed, and Stripe's own update event records it.
- The worker (`createSeatSync`) skips a closed, purging or purged team, a team whose own `stripeCustomerId` isn't the message's customer (`not_ours`, logged as `Seat sync skipped: the team has another Stripe customer`), a team with no subscription (a trial that never went through Checkout), a team or subscription that has ended, an `incomplete` subscription, one that isn't the customer's (`not_ours`, logged too), and one that isn't exactly one item on a catalog price. More billed members than a team can have (`MEMBERS_PER_TEAM`, 100) means something is wrong elsewhere: it changes nothing, logs `Seat sync skipped: more billed members than a team can have` with both numbers, and counts `SeatQuantityDrift`, so the Seat counts drifting alarm brings a person (outcome `over_cap`). Otherwise it counts the billed members **as they are when it runs** (a strongly consistent query of the `MEMBER#` items' roles), and if the seat item's quantity differs it calls `subscriptionItems.update` with that quantity and `proration_behavior: create_prorations`. It never adds or subtracts, so two changes that race converge on the same number, and a late or repeated message does no harm. The Stripe idempotency key is `seats-<teamId>-<sha256 of the message ID, the SQS message ID that delivered it, the item, the current quantity and the target>`: a queue retry of the same message has the same SQS message ID and sends the same key, and a retry after Stripe applied the update finds the quantity right and sends nothing. Every new delivery gets a new key, so a message ID used again (the reconciliation's is fixed per customer per day, and a Stripe event can be redelivered) never replays an update Stripe cached earlier and logs `updated` for a change that wasn't made. The seat sync queue's event source mapping runs at most 5 workers at once (`SEAT_SYNC_MAX_CONCURRENCY`), so the nightly fan-out stays near 20 Stripe requests a second, under Stripe's rate limit (25 a second in test mode). A Stripe failure throws, so the message is retried (5 tries, then the seat syncs dead-letter queue). Stripe's `customer.subscription.updated` then records the new `seats` on the team.
- After applying (or re-seeing) any Stripe event about a subscription, the worker runs the same sync, so the quantity chosen at Checkout follows the billed members from the start. It runs after the event is recorded, so a failure there retries only the sync (the event is a duplicate then); but if Stripe stays unreachable for all 5 tries, the event itself lands in the billing dead-letter queue (Billing events stuck) although it was applied. Replaying it is safe.
- **Nightly reconciliation.** `supply-checkout-<env>-seat-reconcile` (`backend/src/ops/seat-reconcile-handler.ts`, primary region, 07:00 UTC) lists the open teams with a Stripe customer, whether or not their subscription has ended, from the operators' index and queues a seat sync with reason `reconcile` on the seat sync queue for each (one message per customer per day, batches of 10). When one finds the quantity wrong the worker counts `SeatQuantityDrift` (the Seat counts drifting alarm), logs `Seat quantity drift` with the team and subscription IDs, the Stripe quantity and the billed members, and fixes it. So a sync that was never queued, went to the dead-letter queue, or a change made outside the account and ops APIs (a restore removing a deleted user, see [backups](backups.md#8-writes-back-on)) is put right within a day, and noticed. It runs in the primary region only, and that's enough once `us-west-2` serves teams too (phase 2, ADR 0010): the table is a global table, so the operators' index lists every region's teams, and their syncs go on the primary region's seat sync queue, whose worker reads the same table and calls Stripe, which has no region. It converges because the quantity is always recomputed, never incremented: a primary-region sync that read a replica a moment behind a `us-west-2` membership change, and landed after that region's own sync, is put right by the team's next sync or the next night's run. The run sends `SeatReconcileTeams` (how many it queued); none for two days is the Seat reconciliation not running alarm. The same message carries the entitlement check, below.
- **Nightly entitlement check** (`supply-checkout-8jc.9`, `backend/src/billing/entitlements.ts`). For each seat sync with reason `reconcile`, the worker first checks the team's billing against Stripe, so a webhook that was lost (Stripe gave up, the endpoint or its secret was wrong) or is sitting in the billing dead-letter queue is put right within a day. No schedule, queue or IAM of its own: it rides on the seat reconciliation's message and the worker's existing Stripe key and `BillingWorkerRole` grants. It finds the team from our `STRIPE#` link (skipping a closed, purging or gone team), retrieves the team's recorded subscription, and when there's none or it has ended, lists the customer's subscriptions (`status: all`, the newest 10) for a live one (not `incomplete`) the team never recorded (a lost checkout or resubscription) that's over an hour old (`UNRECORDED_GRACE_SECONDS`, so one being made as the check runs has time for its own events). It compares Stripe's subscription ID, status, plan, seat quantity and whether it's set to cancel with the team's `stripeSubscriptionId`, `status`, `plan`, `seats` and `cancelAtPeriodEnd` (`entitlementDrift`; a price we don't sell leaves the plan alone), so a cancellation or renewal whose event was lost (or skipped while the team was closed) still reaches the app's "subscription was canceled" note. The first night after this comparison was added may count a one-time wave of `EntitlementDrift` (field `cancelAtPeriodEnd`) for teams whose cancellation was never recorded, which the check fixes; it's expected once. Any difference is fixed with `applySubscription`, conditioned (`asRead`) on the team's `META` item still being at the version the check read (`supply-checkout-8jc.27`). Every write to the team's billing, closure or comp moves the version, so an event the worker applied meanwhile, even one that changed a field and changed it back or changed only `currentPeriodEnd`, is never overwritten with older state: that conflict throws, and the retry reads the team again. Once the fix is written it counts `EntitlementDrift` (the Entitlements drifting alarm, P2, primary region) and logs `Entitlement drift` with the team and subscription IDs, the fields, and both sides' subscription ID, status, plan, seats and `cancelAtPeriodEnd`. A recorded subscription, or a customer, Stripe doesn't have (`resource_missing`) is counted and logged (`Entitlement drift: subscription missing in Stripe`, `... customer missing in Stripe`) but changes nothing, and that team's seat sync is skipped, so it doesn't reach the dead-letter queue every night. No owner email is sent for a fix; replaying the lost event does that ([runbook](runbooks/billing-dlq-replay.md)). A seat sync after a membership change never runs the check.

**Which customer a team's subscription belongs to** (`supply-checkout-8jc.35`). A team never records a subscription that isn't its own customer's. Only two writes set a team's Stripe IDs, and both check:

- `stripeCustomerId`: only `linkStripeCustomer` (`backend/src/data/billing.ts`), from Checkout (`customerFor` in `backend/src/api/billing-handler.ts`), with the customer Stripe just made for the team. Its transaction sets it only on an open team with no customer or the same one, and puts the `STRIPE#<customer>` link only if there's none or it already names the team, so a team's customer never changes and a customer never moves to another team. The billing-access role may write nothing else on the team.
- `stripeSubscriptionId`: only `applySubscription` (same file), whose condition requires the team's `stripeCustomerId` to equal the customer it's given (`state.customerId`); a failed condition on a team with another customer is `ignored`. Its three callers find the team from our own link for the customer (never from the event or message), and each checks that the subscription's own `customer`, as Stripe returns it, is that customer before applying it:
  - Stripe events, including `checkout.session.completed` (`process` in `backend/src/billing/worker.ts`): the subscription is fetched from Stripe, and one that isn't the event's customer's is recorded as `ignored`.
  - The nightly entitlement check (`backend/src/billing/entitlements.ts`): the recorded subscription that isn't the customer's is `not_ours` (`Entitlement check skipped: subscription isn't the customer's`), and the listing for an unrecorded one keeps only the customer's own.
  - The reopen resync (`backend/src/billing/reopening.ts`): one that isn't the customer's is `not_ours` (`Reopened team's subscription not resynced: another customer's subscription`) and left pending.

Nothing else writes either field: the seat sync, the close-time cancellation and the purge only read them (the first two skip a subscription that isn't the customer's, `not_ours`, and the purge sets it aside, `CustomerMismatch`), the ops function and `scripts/ops.mjs` only show them, the backfills don't touch them, and a restore's copy-back puts back the team's own earlier `META` item whole. Stripe never moves a subscription to another customer, and a Stripe key or mode mismatch makes the subscription "not found", not another customer's. So the purge's `CustomerMismatch` ([journeys.md](journeys.md), "Closed-team subscription set aside: what to do") means a hand edit of the team's `META` item or corrupted data, not a path in the app. The tests: `backend/test/billing-ddb.test.ts` ("refuses another customer's subscription"), `backend/test/billing-worker.test.ts` and `backend/test/billing-seats.test.ts`.

**The Stripe endpoint.** In the sandbox, the event destination `supply-checkout-prod-billing` sends to `https://api.supplycheckout.com/billing/webhook` on API version `2026-08-26.dahlia` (the `stripe` package's), subscribed to exactly: `checkout.session.completed`, `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `customer.subscription.trial_will_end`, `invoice.paid` and `invoice.payment_failed` (`BILLING_EVENTS` in `backend/src/billing/names.ts`). Its signing secret (`whsec_…`) is stored as a plain string at `supply-checkout/prod/stripe/test-webhook-secret` in us-east-1. If the secret is missing or wrong, every webhook fails (500 without it, 400 and the Webhook signature failures alarm with the wrong one), and Stripe retries for 3 days. Another environment, or live mode, needs its own destination and secret (`supply-checkout/<env>/stripe/<mode>-webhook-secret`), subscribed to the same events. Rotating: roll the secret in Stripe and update the stored value; functions pick it up within an hour, so keep Stripe's overlap window at least that long. Adding an event to `BILLING_EVENTS` means adding it to the destination too.

**IAM.** The billing function's own role can't reach the table, but to read when the caller's password was last reset (`ReadPasswordResetTime`, Sign-in above). It may `secretsmanager:GetSecretValue` on the one secret for its environment and mode (`arn:…:secret:supply-checkout/<env>/stripe/<mode>-secret-key-??????`, built by `stripeSecretArn` in `infra/lib/config.ts`: Secrets Manager's six random characters and nothing else; it's encrypted with Secrets Manager's AWS managed key, which needs no KMS grant), and assume the **`BillingAccessRole`** with three session tags: `teamId` (the path's team), `stripeCustomer` (`.` until Stripe has made the team's customer) and `userId` (the caller's own `sub` from the verified token, for the two-step sign-in check only; `.` otherwise). That role allows `GetItem` in `TEAM#<teamId>` (the membership check and the team), `Query` there on the table only, naming only `PK`, `SK` and `role` (`MEMBER_SEAT_ATTRIBUTES`) with `Select` `SPECIFIC_ATTRIBUTES` required (the billed member count for Checkout's quantity, so it reads no names or emails), `UpdateItem` there naming only `PK`, `SK`, `stripeCustomerId`, `closedAt` (its condition), `version` and `stripeCheckoutAt` (`CUSTOMER_LINK_TEAM_ATTRIBUTES`: every Checkout links the customer again before its session is made, moving the team's version and recording when, so the lapsed-team job's closure, conditioned on the version it read and on no Checkout in the last 25 hours, never closes a team under a Checkout Session, and a team already closed gets no session) and returning nothing, `PutItem` only in `STRIPE#<stripeCustomer>`, naming only the link's attributes (`STRIPE_LINK_ATTRIBUTES`) and returning nothing, and `GetItem` (projected: `Select` `SPECIFIC_ATTRIBUTES` required, not `IfExists`, `supply-checkout-3sv.23`) and `UpdateItem` (returning nothing) only in `USER#<userId>`, naming only `PK`, `SK` and `totpOnAt` (`TOTP_RECORD_ATTRIBUTES`, `supply-checkout-8jc.14`): when the caller turned two-step sign-in on, which no other item has, so it can't read or change a user's teams, proofs or notices. IAM can't limit the sort key, so the grant still lets a session create an item holding only the keys and `totpOnAt` anywhere in the caller's own `USER#<sub>` partition, or set or remove `totpOnAt` on one of their existing items (nothing else reads it). The code only ever uses `TOTP_ON`: `data/two-step.ts` checks the key before any call, and each update's condition names it. No other `Query`, and no `Scan` or `DeleteItem`. The handler tags a customer only with the ID Stripe returned for that team: a new one, or the one already linked to the team, which every Checkout links again. The update also names `closedAt` (its condition, so a team closed after the membership check isn't linked), and IAM can't limit the sort key, so the grant covers updating `stripeCustomerId`, `closedAt`, `version` and `stripeCheckoutAt` on any item in `TEAM#<teamId>`: the code only ever updates `META`, on the condition `attribute_exists(PK)`; a stray `closedAt` could make a team read-only but never put it in the purge's index (`purgeAfter` and the GSI1 keys aren't allowed), a stray `version` only makes a concurrent versioned write retry, and a stray `stripeCheckoutAt` only delays a lapsed team's closure. No other function may assume the role. `backend/test/billing-api.test.ts` runs the handler against a check that mirrors the role (`backend/test/billing-policy.ts`).

The webhook function may only read its signing secret (`supply-checkout/<env>/stripe/<mode>-webhook-secret-??????`) and `sqs:SendMessage` to the billing queue: no table and no Stripe API key. The worker's own role may read the Stripe secret key, send owner emails (`grantSendEmail`) and assume the **`BillingWorkerRole`**, tagged with the event, its customer and (once the link is read) the team, whose policy allows `GetItem` and `PutItem` in `WEBHOOK#<eventId>` naming only the event records' attributes (`WEBHOOK_RECORD_ATTRIBUTES`), `GetItem` in `STRIPE#<customer>` naming only `teamId`, `GetItem` and `Query` in `TEAM#<teamId>` naming only `BILLING_READ_ATTRIBUTES` (the `META` item's billing, closure and comp fields and its `version`, and an owner's role and email: never documents), every read projected (`Select` `SPECIFIC_ATTRIBUTES` required, not `IfExists`, so each `Query` sends `Select` itself, `supply-checkout-3sv.24`), and `UpdateItem` there naming only `BILLING_UPDATE_ATTRIBUTES`, returning nothing, and `PutItem` in `OPAUDIT#<teamId>` naming only `COMP_DISCOUNT_AUDIT_ATTRIBUTES`, returning nothing (a comp's Stripe discount outcome, [Operators](#operators), `supply-checkout-6e4b`). Like the billing function's, the update's attributes include `closedAt` and `purging` (its condition's) but never `purgeAfter` or the GSI1 keys. `backend/test/billing-worker.test.ts` runs the worker behind a mirror of that role, and `backend/test/billing-seats.test.ts` the seat sync, whose billed-member count is a `Query` of `MEMBER#` items naming only `SK` and `role`, inside the same grant.

Seats add the seat sync queue, which the worker reads (its event source mapping's grant), and three senders to it and nothing else: the account function's own role and, in the primary region, the ops function's may `sqs:SendMessage` to it (`QueueSeatSyncs`, with `SEAT_QUEUE_URL`; the ops function reads the team's customer through the operator-access role's GSI3 grant it already has), and the seat reconciliation's role may `sqs:SendMessage` to it (by its name, from the observability stack), `Query` GSI3's `OPS#TEAMS` partition naming only `SEAT_RECONCILE_ATTRIBUTES` (`PK`, `SK`, the GSI3 keys, `stripeCustomerId`, `closedAt`, `status`; `dynamodb:Select` `SPECIFIC_ATTRIBUTES`), and decrypt the table key through DynamoDB. None of them can read a team's partition or the Stripe key, or send to the billing queue. A seat sync can only make the worker recompute a quantity from the team's own members and, for the nightly reconciliation's, re-apply the state Stripe has for the team's own customer (the entitlement check), with the grants it already has.

## Live updates

The `realtime` stack (`lib/stacks/realtime-stack.ts`, [ADR 0006](adr/0006-api-and-realtime-sync.md), [ADR 0016](adr/0016-per-member-live-update-channels.md), `supply-checkout-dpc`, `supply-checkout-4zn`) is an AppSync Events API with one channel per user, `/users/<sub>`, at `realtime.<env domain>`. [docs/api/realtime.md](api/realtime.md) is the client contract: how to connect, the event shape, reconnecting and the polling fallback.

- **Subscribing.** Clients connect and subscribe with their Cognito access token. A Lambda authorizer (`backend/src/realtime/authorizer-handler.ts`) verifies the token (signature, issuer, expiry, the web client, `token_use=access`) and allows a subscription only to exactly `/users/<sub>` for the token's own user. It reads no data and has no table or KMS access. Nothing is cached. Publishing takes IAM, and only the stream consumer's role may, on the `users` namespace.
- **Publishing.** A consumer (`backend/src/realtime/publisher-handler.ts`) reads the table's stream, filtered to `PRODUCT#` and `PROJECT#` items (the changes) and to `META` and `MEMBER#` items (who gets them), and publishes `{teamId, collection, id, op, version}` for each document write to the channel of each current member of the team, with no document data: clients fetch through the data API, which checks membership on every request.
- **Cutting off removed members, and canceled and closed teams.** The consumer reads a team's members, billing status and closure with `liveUpdateRecipients` and caches them for 30 seconds, forgetting them as soon as the stream shows a `META` or `MEMBER#` write for that team. So a removed member, or every member of a team whose status is `canceled`, `unpaid` or `incomplete_expired`, stops getting notices at once in practice and within 30 seconds at worst. Its table permission is `GetItem` and `Query` on `TEAM#*` partitions for `LIVE_AUDIENCE_ATTRIBUTES` only (`PK`, `SK`, `userId`, `role`, `status`, `closedAt`, `compPlan`, `compUntil`; `dynamodb:Attributes`), with `dynamodb:Select` `SPECIFIC_ATTRIBUTES` required, not `IfExists` (`supply-checkout-3sv.24`: the `GetItem` projects and the `Query` sends `Select`), so it can't read documents or emails through the table. It does see whole items in the stream images it's handed (a `MEMBER#` item has the member's email), and it never logs a record, an image or an event: its logs have team IDs, counts and error messages only (`backend/test/realtime-publisher.test.ts` checks). It reads a team's members again before each chunk of 5 events (from its cache, normally), so the 30-second bound holds however long an invocation runs; a read that takes over 2 seconds fails and is retried with the batch (`AUDIENCE_READ_TIMEOUT_MS`), and each DynamoDB request has a 1-second timeout (`CONSUMER_DB_REQUEST_TIMEOUT_MS`). A batch with more than 10 changes to one team's collection (`COLLECTION_EVENT_AFTER`, an import) publishes one "re-list" event for them instead ([docs/api/realtime.md](api/realtime.md#collection-events)). Partial batch failures are retried from the first unsent record; a batch that keeps failing goes to `supply-checkout-<env>-live-updates-dlq`. Batches are 25 records (`STREAM_BATCH_SIZE`), and one invocation makes at most 2,500 publish requests and starts them for at most 5 seconds, each with a 3-second timeout, inside the function's 10 seconds (`PUBLISHES_PER_INVOCATION`, `PUBLISH_BUDGET_MS`, `PUBLISH_TIMEOUT_MS` in `backend/src/realtime/channels.ts`). Past the budget it stops and reports the earliest unfinished record, and Lambda carries on from there, so a big, busy team can't hold up the other teams on its shard for longer than that. Requests go out earliest record first, and the batch's first chunk (the earliest document record's team, up to 5 events) always goes to every member at once, outside the budget and the concurrency limit, so it finishes within one publish timeout and every invocation moves the shard forward by at least one record, however big the team or slow AppSync. A full batch of teams at the member cap (100) fits the budget; a budget stop is logged as a warning, in the `Batch` line's `deferred` and in the `LiveUpdatesDeferred` metric, not counted in `LiveUpdateFailures`. **Retries and budget stops.** A response that reports a record is, to the event source mapping, a failed invocation: AWS retries "up to the retry limit" and doesn't document the count resetting when the checkpoint moves forward (only bisecting a batch is said not to use it), so we assume every budget stop spends one of the mapping's `MaximumRetryAttempts`. That's why it is `STREAM_RETRY_ATTEMPTS` (25, at least `STREAM_BATCH_SIZE`): each stop moves at least one record, so stops alone always drain a batch before its retries run out. Real failures retry that many times too, inside the one-hour maximum record age, then go to the dead-letter queue. Alarms: Live updates failing, delayed, dropped and deferred ([docs/journeys.md](journeys.md)).
- **Regions.** The custom domain is added where its certificate is (`GLOBAL_SERVICES_REGION`). The consumer runs in the primary region, which has the table's stream; the second region's consumer is phase 2.

**Deploying.** The realtime stack reads, from SSM in its region: the table's stream and key ARNs (data stack), the user pool ID and web client ID (identity stack) and the `realtime.` certificate (the domain stack in `GLOBAL_SERVICES_REGION`). Deploy it after those, and before observability. Deploying it deploys the data stack too, so keep `-c backupCopy=false` until that environment has done [step 4 of the backup setup](backups.md#setting-it-up) ([why](#the-cloudtrail-trail)):

```bash
npx cdk diff supply-checkout-staging-us-east-1-realtime --profile '<staging profile>' -c backupCopy=false
npx cdk deploy supply-checkout-staging-us-east-1-realtime supply-checkout-staging-us-east-1-observability --profile '<staging profile>' -c backupCopy=false
```

Then measure the 2-second p95 and the reconnect behavior in staging as described in [docs/api/realtime.md](api/realtime.md#measuring-after-a-deploy).

## Journey tests

`infra/lib/stacks/journeys-stack.ts`, bead `supply-checkout-o60.3`: what the prod journey tests need in AWS ([the plan](journey-tests-plan.md), "The test mailbox" and "Credentials and secrets"). One stack, `supply-checkout-<env>-<primary region>-journeys` (stateful: termination protection, buckets `RETAIN`), prod only, holds:

- **The test mail subdomain**, `e2e.<domain>` (`JOURNEY_MAIL_LABEL` in `lib/journeys.ts`): an MX record to `inbound-smtp.<primary region>.amazonaws.com`, and an SES domain identity for it with Easy DKIM (three CNAMEs in the zone): SES receives mail only for a domain verified as an identity. It was also what let Cognito's codes and the app's invites reach it while SES was in the sandbox (`supply-checkout-3sv.18`, out since 2026-10-07). It sends nothing, and no role may send from it. Every test account's address is at this subdomain, and only we can read its mail.
- **An SES receipt rule set**, `supply-checkout-<env>-journeys`, with one rule, `test-mail`: recipient the subdomain exactly (not other domains, not its subdomains), TLS required, spam and virus scanning on (the verdicts, with SPF and DKIM, are in the stored message's headers, for the harness's reader), and one action: write the raw message to the mail bucket under `inbox/`. CloudFormation can't make a rule set active, and **only one receipt rule set can be active per account and region**, so it's activated by hand (below).
- **The mail bucket**, `supply-checkout-<env>-journey-mail-<region>-<account>`: SSE-S3, public access blocked, ACLs off, TLS only, server access logs to the data stack's logs bucket under `s3/journey-mail/`. `inbox/` expires after a day; everything else (`runs/<runId>/accounts`, the harness's records of each run's throwaway accounts, so the next run's cleanup can find a crashed run's) after 30. Only SES may write it, under `inbox/`, and only for this account's `test-mail` rule (`aws:SourceAccount` and `aws:SourceArn`; CDK's own S3 action checks only the account, so the stack writes the grant itself).
- **The results bucket**, `supply-checkout-<env>-journey-results-<region>-<account>`: the same protections, logs under `s3/journey-results/`, everything expires after 30 days. Playwright traces and videos go here under `runs/<runId>/`, never to Actions artifacts, which are public in this repository.
- **The journeys role**, `supply-checkout-<env>-journeys`. Its trust has one statement: `sts:AssumeRoleWithWebIdentity` from GitHub's OIDC provider (the [GitHub deploy stack](#github-actions-deploy-role)'s; its ARN is fixed by the URL), with `StringEquals` on `aud` = `sts.amazonaws.com` and `sub` = `repo:<owner>@<owner ID>/<name>@<repository ID>:environment:production-journeys` (`GITHUB_JOURNEYS_ENVIRONMENT`): GitHub's immutable subject, as for the deploy role. A session lasts an hour at most. The subject carries no branch: that the job runs on `main` comes from the environment's deployment branch rule, as for `production`. Its one inline policy, and nothing else:

  | Sid | Actions | Resource | Why |
  | --- | --- | --- | --- |
  | `ListTestMailAndRunRecords` | `s3:ListBucket` | the mail bucket, only with `s3:prefix` like `inbox/*` or `runs/*` | Find a run's message, and a crashed run's account records |
  | `ReadAndDeleteTestMail` | `s3:GetObject`, `s3:DeleteObject` | mail bucket `inbox/*` | Read a code or link, then delete the message |
  | `ReadAndWriteRunRecords` | `s3:GetObject`, `s3:PutObject` | mail bucket `runs/*` | Record and read each run's throwaway accounts |
  | `UploadTraces` | `s3:PutObject` | results bucket `runs/*` | Upload a run's traces |

  No KMS (both buckets use SSE-S3), Cognito, DynamoDB, Secrets Manager, SES, CloudWatch, `iam:PassRole` or `sts:AssumeRole`. The deploy role doesn't trust it, and it trusts neither the deploy role nor the publisher role. cdk-nag's `AwsSolutions-IAM5` is acknowledged for the three object-prefix resources only (object keys are run and message IDs).
- SSM parameters under `/supply-checkout/<env>/journeys/` (`mail-domain`, `mail-bucket-name`, `results-bucket-name`, `role-arn`), and the outputs `JourneysRoleArn`, `MailBucketName`, `ResultsBucketName` and `ReceiptRuleSetName`.

Neither bucket is versioned, unlike every other bucket that holds data here: they hold throwaway test mail and traces, and a deleted sign-in code should be gone, not kept as an old version.

**A separate CDK app**, `bin/journeys.ts`, like the GitHub deploy role: the release pipeline never deploys it. GitHub creates an environment with no protection the first time a job names one that doesn't exist, so a role trusting `production-journeys` must not exist before that environment is set up (`main` only, no admin bypass): `npm run deploy:journeys` (`scripts/deploy-journeys.mjs`) runs `scripts/check-environments.mjs --environment production-journeys` first and deploys nothing unless it passes, and CI refuses any workflow but `journeys.yml` that names the environment, and any that a pull request can start ([The production-journeys environment](releases.md#the-production-journeys-environment)). The data stack, which the pipeline does deploy, grants the two buckets' access logs in prod (`JourneyMailBucketAccessLogs`, `JourneyResultsBucketAccessLogs`). `npm run synth:journeys` synthesizes it with cdk-nag (CI runs it).

**Deploying it (the owner, once), in this order:**

1. **The data stack**, with the access-log grants: the next release's stateful stacks (approval 2) include it, or deploy it by hand as in [Deploying](#deploying).
2. **The `production-journeys` environment** on GitHub, set up and checked: [The production-journeys environment](releases.md#the-production-journeys-environment), steps 1 and 2. Don't deploy the stack before it is (`npm run deploy:journeys` refuses).
3. **Check no receipt rule set is active** in the primary region. Activating this one deactivates any other, and inbound mail to that set's domains would stop:

   ```bash
   aws ses describe-active-receipt-rule-set --region us-east-1 --profile supply-prod
   ```

   It must print nothing (or `{}`): no active rule set. Support mail doesn't use one (it arrives through the forwarder's MX at the apex, [Support email](#support-email)), and no stack here makes one but this. If one is active, stop: its rules would have to move into this stack first.
4. **Check nothing exists at `e2e.`** in the zone (an MX, CNAME or TXT there makes the deploy fail):

   ```bash
   aws route53 list-resource-record-sets --hosted-zone-id "$(aws ssm get-parameter --name /supply-checkout/prod/dns/hosted-zone-id --query Parameter.Value --output text --profile supply-prod)" \
     --query "ResourceRecordSets[?contains(Name, 'e2e.')]" --profile supply-prod
   ```

5. **Deploy the stack** with `npm run deploy:journeys`, never a bare `cdk deploy` of `bin/journeys.ts`: it checks `production-journeys` with your `gh` login (and the repository context and IDs, as `deploy:github-deploy` does), refuses unless it's locked down, then runs `cdk deploy` with your arguments. CDK asks to confirm the IAM changes.

   ```bash
   aws sso login --profile supply-prod
   cd infra
   npm run synth:journeys
   npx cdk diff --app "npx tsx bin/journeys.ts" -o cdk.out/journeys --profile supply-prod
   npm run deploy:journeys -- --profile supply-prod
   ```

6. **Activate the rule set** (the manual step CloudFormation can't do):

   ```bash
   aws ses set-active-receipt-rule-set --rule-set-name supply-checkout-prod-journeys --region us-east-1 --profile supply-prod
   aws ses describe-active-receipt-rule-set --region us-east-1 --profile supply-prod   # shows the test-mail rule
   ```

7. **Check it end to end.** `aws sesv2 get-email-identity --email-identity e2e.supplycheckout.com --region us-east-1 --profile supply-prod` shows `"VerifiedForSendingStatus": true` once DKIM verifies (usually minutes, up to 72 hours). Then send a message to any address at `e2e.supplycheckout.com` (from your own mail, or `aws sesv2 send-email` from `noreply@supplycheckout.com`), and within a minute it's in the bucket:

   ```bash
   aws s3 ls "s3://$(aws ssm get-parameter --name /supply-checkout/prod/journeys/mail-bucket-name --query Parameter.Value --output text --profile supply-prod)/inbox/" --profile supply-prod
   ```

   Besides `AMAZON_SES_SETUP_NOTIFICATION` (SES's test write when the rule was made), there's one object per message.
8. **Hand the role to the workflow**: the `JourneysRoleArn` output becomes the `production-journeys` environment's secret `JOURNEYS_AWS_ROLE_ARN` (a secret, so the account ID in it is masked in the public logs). The long-lived accounts, teams and other secrets follow: [The production-journeys environment](releases.md#the-production-journeys-environment), steps 6 to 8.

**Revoking access.** Like the deploy role, delete the role by hand or replace its trust with one that allows nothing (`aws iam update-assume-role-policy --role-name supply-checkout-prod-journeys`). To stop receiving test mail, deactivate the rule set (`aws ses set-active-receipt-rule-set` with no name). Deleting the stack leaves the buckets (`RETAIN`); empty and delete them by hand.

**Cost.** SES inbound is $0.10 per 1,000 messages plus a fraction of a cent per KB; a few messages a run. The buckets hold kilobytes of mail and a few MB of traces for 30 days. Under a dollar a month.

## Template snapshots

`test/stacks.test.ts` snapshots every stack's synthesized template, one file per stack in `test/__snapshots__/<stack name>.json` (for example `supply-checkout-prod-us-east-1-api.json`), so a change to one stack only touches that stack's file. Every test builds its App with `testApp()` from `test/cdk-app.ts`, which carries `cdk.json`'s context, feature flags included, just as `cdk synth` does for `bin/app.ts`, so the snapshots are the templates CloudFormation gets (apart from CDK's path metadata); `test/cdk-app.test.ts` fails if the flags drift apart. A test that needs other context passes it to `testApp()` rather than building an `App` of its own. Lambda asset hashes and the function version IDs made from them are masked, because they depend on the checkout's path. When a change to a stack is intended, review the test's diff, then accept it and commit the changed files:

```bash
cd infra
npm run test:update
git diff --stat test/__snapshots__
```
