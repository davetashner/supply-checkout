# Infrastructure

`infra/` is the AWS CDK v2 app for the subscription product ([ADR 0002](adr/0002-serverless-aws-with-cdk.md)). It is a separate npm package with its own lockfile, so run its commands from `infra/` (or with `npm --prefix infra run …`).

```bash
cd infra
npm ci
npm run lint        # tsc type-check and ESLint
npm test            # vitest: config, stack layout, template snapshots, cdk-nag (every stack in each region)
npm run synth       # cdk synth; cdk-nag AwsSolutions fails it on any finding
npm run synth:all-regions  # the same for every approved region (-c regions=all)
npm run test:update # accept template snapshot changes after reviewing them
```

**Stacks.** Every stack is named `supply-checkout-<env>-<region>-<component>`. Each region in the environment gets `domain` (certificates, DNS records and the SES domain; see [Domain and email](#domain-and-email)), `data` (stateful: table, keys, buckets), `api` and `realtime` (stateless), and `observability`. The primary region also gets `identity` (stateful: Cognito), `backup` (stateful: AWS Backup for the table, copied to a separate backup account; see [Backups and restores](backups.md)), `audit` (stateful: the account's CloudTrail trail; see [The CloudTrail trail](#the-cloudtrail-trail)) and `email` (bounce and complaint handling; see [Transactional email](#transactional-email)). `GLOBAL_SERVICES_REGION` gets `web` (CloudFront and WAF, which AWS requires there; see [Web hosting and releases](web-app.md#web-hosting-and-releases)), and always has a `domain` stack, because CloudFront, Cognito and AppSync only accept certificates from there. Stateful stacks have termination protection. Every stack writes `/supply-checkout/<env>/<component>/stack` to SSM Parameter Store, and later stacks publish their outputs beside it. All resources are tagged `app=supply-checkout`.

**Regions.** The MVP runs in **us-east-1 only**. Every stack takes its region as a parameter, and the tests and CI also synthesize us-west-2 (`synth:all-regions`), so turning on the second region from [ADR 0010](adr/0010-multi-region-active-active.md) is a config change: add it to `DEFAULT_REGIONS` in `lib/config.ts`. CDK is already bootstrapped in us-west-2. `lib/config.ts` is the only file in `infra/`, `backend/` or `src/` that may name a region: it holds `APPROVED_REGIONS`, `DEFAULT_REGIONS` and `GLOBAL_SERVICES_REGION` (where AWS requires CloudFront's certificate and WAF, and where Cognito lives). Stacks get their region as a parameter, Lambdas read `AWS_REGION`, and tests import the constants. `npm run check:regions` (in CI and the pre-commit hook) enforces this.

**Parameters.** The environment and regions are CDK context (`cdk.json` sets `envName=prod`; `regions` defaults to `DEFAULT_REGIONS` and `primaryRegion` to the first of them); override them with `-c envName=staging -c regions=all` (or a comma-separated list, with `-c primaryRegion=...`). Only the regions in `APPROVED_REGIONS` (`lib/config.ts`) are allowed. The account ID is never committed: it comes from the AWS profile at synth time, and a synth without credentials (CI, tests) is account-agnostic.

**The `app` table.** The primary region's `data` stack holds the single DynamoDB table from [ADR 0005](adr/0005-multi-tenant-dynamodb.md), `supply-checkout-<env>-app`. It's a `TableV2` (`AWS::DynamoDB::GlobalTable`) with one replica, in its own region: on-demand, encrypted with a customer-managed KMS key that rotates yearly, point-in-time recovery, deletion protection, a stream with new and old images, TTL on `expiresAt`, and one index, `GSI1`. Adding the us-west-2 replica in phase 2 is another entry in `replicas` with that region's key, not a new table. The data stack publishes `table-name`, `table-arn`, `table-stream-arn` and `table-key-arn` to SSM under `/supply-checkout/<env>/data/`. The key and index names come from `backend/src/data/schema.ts`, so the table and the code that reads it can't drift apart.

**cdk-nag.** `AwsSolutionsChecks` is registered as a CDK validation plugin, so every synth and deploy fails on an unacknowledged finding. When a finding is intended, acknowledge it on the narrowest construct with a written reason:

```ts
Validations.of(bucket).acknowledge({ id: "AwsSolutions-S1", reason: "…why this is safe…" });
```

## Deploying

For the everyday deploys, from the main checkout on an up-to-date, clean `main`:

```bash
npm run deploy -- api      # the api and observability stacks (new routes, Lambda code, alarms)
npm run deploy -- web      # the web stack, then check-router
npm run deploy -- app      # build the web app, publish it to app., make it live, check-router
npm run deploy -- all      # web, then api, then app
```

`scripts/deploy.sh` refuses any branch but `main`, uncommitted changes, and a `main` that isn't `origin/main`, so what goes out is what's merged. It runs `aws sso login` if the session has expired, installs the backend's and infra's dependencies (the synth bundles the Lambda code), shows `cdk diff` for each group of stacks and asks before deploying it, and deploys only those stacks (`--exclusively`, chosen by kind, `supply-checkout-<env>-*-api`); CDK still asks about IAM and security group changes. It passes `-c backupCopy=false` until the backup copy vault's parameter exists (below). Options: `--env`, `--profile` (default `supply-prod`), and `--yes` to skip its own questions. Other stacks (domain, identity, data, email, audit, backup) and a first deploy use the commands below.

Until the pipeline in [ADR 0012](adr/0012-cicd-releases-rollbacks.md) takes over: before the first deploy, create the SSM parameters the stacks read: the hosted zone and DMARC report address ([Domain and email](#domain-and-email)), the alarm recipients ([Observability](observability.md#alarm-recipients)) and, only when the backup account exists, its vault ARN ([Setting it up](backups.md#setting-it-up)). The MVP has none and deploys with `-c backupCopy=false` ([ADR 0003](adr/0003-aws-account-structure.md)).

```bash
aws sso login --profile supply-prod
cd infra
npx cdk bootstrap --profile supply-prod        # once per account and region; bootstraps every region in the app
npx cdk diff --profile supply-prod -c backupCopy=false
npx cdk deploy --all --profile supply-prod -c backupCopy=false
```

`--all` includes the data and backup stacks, so keep `-c backupCopy=false` on both commands until [step 4 of the backup setup](backups.md#setting-it-up) is done (why: [The CloudTrail trail](#the-cloudtrail-trail)).

## GitHub Actions deploy role

`infra/lib/stacks/github-deploy-stack.ts`, bead `supply-checkout-5ik` ([ADR 0003](adr/0003-aws-account-structure.md), [ADR 0012](adr/0012-cicd-releases-rollbacks.md)). It lets a GitHub Actions job deploy to the prod account with short-lived credentials and no stored AWS keys. The MVP has one account, so there is one provider and one role, in `supply-checkout-prod`. The stack, `supply-checkout-<env>-<primary region>-github-deploy`, holds:

- An IAM OIDC provider for `https://token.actions.githubusercontent.com`, audience `sts.amazonaws.com` only. IAM fetches GitHub's certificate thumbprint itself.
- The role `supply-checkout-<env>-github-deploy`. Its trust policy has one statement: `sts:AssumeRoleWithWebIdentity` from that provider, with `StringEquals` on `aud` = `sts.amazonaws.com` and `sub` = `repo:<owner>/<name>:environment:production`. Only a job in this repository that runs in the `production` GitHub environment gets that subject. A pull request, a push without the environment, a fork or another repository gets a different one and is refused. There are no wildcards.
- Its one permission: `sts:AssumeRole` and `sts:TagSession` on this account's CDK bootstrap roles (`cdk-<qualifier>-{deploy,file-publishing,image-publishing,lookup}-role-<account>-<region>`), in each deployed region and `GLOBAL_SERVICES_REGION`. `cdk deploy` and `cdk diff` do everything else through those roles, exactly as a deploy from a laptop does. No managed policy, one-hour sessions, and cdk-nag passes with no suppressions.
- The output `DeployRoleArn`, for `role-to-assume` in `aws-actions/configure-aws-credentials`.

The repository comes from `DEFAULT_GITHUB_REPOSITORY` in `lib/config.ts` (override it with `-c githubRepository=<owner>/<name>`), and the environment name from `GITHUB_DEPLOY_ENVIRONMENT`. No account ID is written down: the ARNs are built from CloudFormation's `AWS::AccountId`.

It is a separate CDK app, `bin/github-deploy.ts`, like the backup account's vault. `cdk deploy --all` never includes it, so a pipeline deploying the main app never changes the role it deploys with by accident. That is not a security boundary: a job with this role can assume the bootstrap deploy role and, through CloudFormation's execution role, update this stack or the role's trust too. The real boundary is the `production` environment's rules on GitHub, plus a narrower CloudFormation execution policy (bead `supply-checkout-3x3.2`; see [What it doesn't limit](#what-it-doesnt-limit)). The stack is prod only (the trust always names the `production` GitHub environment, so the synth refuses any other `envName`), and a bootstrap qualifier from context (`@aws-cdk/core:bootstrapQualifier`) must match CDK's own rule, 1 to 10 letters, digits, `_` or `-`, so it can't widen the role ARNs. The stack has termination protection, and the provider and role are retained if it's deleted.

**Revoking access.** Because the provider and role are retained, deleting the stack does not revoke GitHub's access. To cut it off, delete the role by hand (`aws iam delete-role-policy` for its policy, then `aws iam delete-role --role-name supply-checkout-prod-github-deploy`), or replace its trust policy with one that allows nothing (`aws iam update-assume-role-policy`). Deleting the OIDC provider also stops every role that trusts it.

**Deploying it (the owner, once).** CDK must already be bootstrapped in the account and regions (see [Deploying](#deploying)).

```bash
aws sso login --profile supply-prod
cd infra
npm run synth:github-deploy                               # cdk-nag runs here too
npx cdk diff --app "npx tsx bin/github-deploy.ts" -o cdk.out/github-deploy --profile supply-prod
npm run deploy:github-deploy -- --profile supply-prod     # CDK asks to confirm the IAM changes
```

An account can have only one OIDC provider for GitHub's URL. If one already exists (made by hand or another tool), the deploy fails: delete it first if nothing else uses it, or bring it into the stack with `cdk import`. Deploy the stack again when a region is added to `DEFAULT_REGIONS` (phase 2), so the role may assume that region's bootstrap roles, and after the repository is renamed or transferred (with the new `-c githubRepository`).

**Setting up the `production` environment on GitHub (the owner, once, before the first deploy of this stack).** The environment's rules decide which jobs get the trusted subject, so set them before the role exists. In the repository's Settings, Environments, create `production` with:

- Deployment branches and tags: selected only, `main` and the release tags (`v*`). Without this, a workflow on any branch could declare `environment: production`.
- Required reviewers: the owner, so every prod deploy waits for an approval.
- Optionally, prevent self-review and a wait timer.

Check it before deploying the stack:

```bash
gh api repos/davetashner/supply-checkout/environments/production \
  --jq '{branch_policy: .deployment_branch_policy, rules: [.protection_rules[].type]}'
gh api repos/davetashner/supply-checkout/environments/production/deployment-branch-policies \
  --jq '[.branch_policies[] | {name, type}]'
```

`deployment_branch_policy` must not be `null` (null means any branch may deploy), with `custom_branch_policies: true`; the second command must list only `main` (type `branch`) and `v*` (type `tag`); and `rules` must include `required_reviewers`. Don't deploy the stack until it does.

**What it enables.** The CI/CD bead (`supply-checkout-qq7`) adds the deploy workflow. Its deploy job runs with `environment: production` and `permissions: id-token: write`, and uses `aws-actions/configure-aws-credentials` with `role-to-assume` set to the `DeployRoleArn` output (keep it in a `production` environment variable, not in the repository). Nothing deploys from GitHub until then.

To check the trust after deploying: `aws iam get-role --role-name supply-checkout-prod-github-deploy --profile supply-prod` shows the one statement above, and a job that runs without the `production` environment fails in `configure-aws-credentials` with `Not authorized to perform sts:AssumeRoleWithWebIdentity`.

### What it doesn't limit

The CDK bootstrap roles decide what a deploy can change. By default, `cdk bootstrap` gives the CloudFormation execution role `AdministratorAccess`, so anyone who can run a job in the `production` environment can change anything in the account through CloudFormation, this stack and the role's own trust included. The environment's branch rules and required reviewers are the guard. Bootstrapping with a narrower `--cloudformation-execution-policies` is bead `supply-checkout-3x3.2`.

## The CloudTrail trail

`lib/stacks/audit-stack.ts`, bead `supply-checkout-3sv.3`. Every EventBridge rule here on `AWS API Call via CloudTrail` (the operator alerts below, the backup and deletion records change alerts) needs a trail logging in the account: without one EventBridge receives none of those events, and the rules never fire. The primary region's `audit` stack (stateful, termination-protected, everything `RETAIN`) has it:

- `supply-checkout-<env>-trail`: multi-region, every management event (read and write), global services' events (IAM, STS) included, log file validation on. No data events and no CloudWatch Logs delivery.
- Its bucket, `supply-checkout-<env>-trail-<region>-<account>`: SSE-KMS with the stack's own rotating key (`alias/supply-checkout-<env>-trail`), public access blocked, ACLs off, TLS only, versioned (old versions kept 30 days), server access logs to the data stack's logs bucket under `s3/trail/` (the logs bucket's policy grants that bucket only), and log files expired after 400 days (`TRAIL_LOG_RETENTION_DAYS`; there's no information security policy yet, `supply-checkout-4p1`, so it's the deletion records' 400 days).
- Only this trail may use the key or write to the bucket: CloudTrail's statements in both policies have `aws:SourceArn` (the trail's ARN) and `aws:SourceAccount`, and it may write only under `AWSLogs/<account>/`. Reading the logs takes IAM permissions in the account, as for every key here.
- It publishes `trail-name`, `trail-bucket-name` and `trail-key-arn` under `/supply-checkout/<env>/audit/`. It deploys after the data stack (the logs bucket) and before the primary region's observability stack, whose `OperatorAlertKeyAndTrailChanges` rule also watches the trail's key, and `OperatorTrailBucketChanges` the trail's bucket and grants on its key.
- Cost: the first copy of management events is free. The rest is the key ($1 a month), its requests (CloudTrail asks for a data key for each log file, a few thousand a day across regions: well under $1 a month) and S3 storage of compressed logs (cents).

To deploy it on its own (`cdk deploy` without `--exclusively` also deploys the stacks a named stack depends on, so deploying the observability stack deploys the data and audit stacks first):

```bash
npx cdk diff supply-checkout-prod-us-east-1-data supply-checkout-prod-us-east-1-audit supply-checkout-prod-us-east-1-observability --profile supply-prod -c backupCopy=false
npx cdk deploy supply-checkout-prod-us-east-1-data supply-checkout-prod-us-east-1-audit supply-checkout-prod-us-east-1-observability --profile supply-prod -c backupCopy=false
```

Keep `-c backupCopy=false` on every such command, `diff` included, until [step 4 of the backup setup](backups.md#setting-it-up) has created `/supply-checkout/<env>/backup/copy-vault-arn` and `organization-id`: the data stack reads them at deploy time otherwise, and the deploy fails while they don't exist. Drop the flag once step 4 is done (then deploying the data stack adds the deletion records' replication).

Then check it:

1. `aws cloudtrail get-trail-status --name supply-checkout-prod-trail --profile supply-prod --region us-east-1` shows `"IsLogging": true`, and after about 15 minutes a `LatestDeliveryTime` with no `LatestDeliveryError`. After about an hour it should also show a `LatestDigestDeliveryTime` with no `LatestDigestDeliveryError`: the hourly digest files (for log file validation) are delivered separately, and a problem with them, such as the key or bucket encryption, shows only there. `aws cloudtrail describe-trails --profile supply-prod --region us-east-1` shows it multi-region with a `KmsKeyId` and `LogFileValidationEnabled`.
2. The alerts now arrive: add a test operator (`npm run operators -- add <username>`, as the `operators` skill hands it over) and a P1 message from `supply-checkout-prod-operator-pool-changes` should arrive within about 5 to 15 minutes (CloudTrail's usual delay). Remove the test operator afterwards (that alerts too). If nothing comes, look the `AdminCreateUser` event up in CloudTrail's event history and compare it with the rule's pattern (`aws events test-event-pattern`).
3. Record it in the [Drill log](backups.md#drill-log) with the other alert checks.

**Recreating it.** The trail and bucket have fixed names and, like the key, are retained if the stack is deleted, so a deleted `audit` stack can't simply be deployed again: the trail and bucket names are still taken, the old key is left behind without its alias (aliases aren't retained), and the new stack would fail to create them. Bring the retained trail, bucket and key back into a new stack with `cdk import`, or delete or rename the old trail and give the bucket a new name. Termination protection makes deleting the stack a deliberate step.

An **organization trail** from the management account (`supply-mgmt`), delivering to a log archive account ([ADR 0003](adr/0003-aws-account-structure.md)), is a stronger later step: nobody in this account could stop it. That's the owner's decision; this trail stays useful beside it (the rules here watch it).

## Domain and email

`lib/domain.ts` names every host, and each region's `domain` stack (`lib/stacks/domain-stack.ts`) holds the certificates and records for them (`supply-checkout-m64`). Prod serves `supplycheckout.com` itself; any other environment serves `<env>.supplycheckout.com` from a zone in its own account.

| Name | What serves it | Certificate |
| --- | --- | --- |
| apex, `www.` | the demo at `/demo/`; other paths redirect to `app.` until the landing page (CloudFront) | `web`, in `GLOBAL_SERVICES_REGION` |
| `app.` | the web app (CloudFront) | `web`, in `GLOBAL_SERVICES_REGION` |
| `auth.` | Cognito Managed Login | `auth`, in `GLOBAL_SERVICES_REGION` |
| `realtime.` | AppSync Events | `realtime`, in `GLOBAL_SERVICES_REGION` |
| `api.` | the HTTP API, in every region | `api`, in each region |
| `mail.` | SES custom MAIL FROM (MX and SPF) | none |

The certificates are validated by DNS in the zone; CloudFormation adds the validation records and waits a few minutes for issuance. Each ARN is published to SSM as `/supply-checkout/<env>/domain/<name>-certificate-arn`, in the stack's region. The names start to resolve when the stacks that use them add their alias records: `web` (`supply-checkout-qk1`), `identity` (`supply-checkout-zsm`), `api` and `realtime`. Those stacks import the zone with `importZone()` from `lib/domain.ts`.

In the primary region, the stack also creates the SES domain identity with Easy DKIM (three CNAMEs), the `mail.` MAIL FROM domain, SPF on the apex (`v=spf1 include:amazonses.com -all`) and DMARC at `p=none`. SES in the second region is phase 2 (`supply-checkout-3x3.1`).

**The hosted zone is imported, never created.** Prod's zone was created by hand when the domain was delegated from Namecheap. The stack reads its ID from the SSM parameter `/supply-checkout/<env>/dns/hosted-zone-id` at deploy time (a CloudFormation SSM parameter), rather than `HostedZone.fromLookup`, so synth stays account-agnostic in CI and the zone ID never lands in `cdk.context.json`. DMARC aggregate reports go to the address in `/supply-checkout/<env>/dns/dmarc-rua`. Use a DMARC report service's `mailto:` address, not a personal mailbox at another domain: receivers drop reports to another domain unless that domain publishes an authorization record, which personal mail providers don't. Create both parameters before the first deploy, in each region with a `domain` stack (today, us-east-1):

```bash
aws sso login --profile supply-prod
ZONE_ID=$(aws route53 list-hosted-zones-by-name --profile supply-prod --dns-name supplycheckout.com \
  --query "HostedZones[?Name=='supplycheckout.com.'].Id | [0]" --output text | sed 's|/hostedzone/||')
aws ssm put-parameter --profile supply-prod --region us-east-1 --type String \
  --name /supply-checkout/prod/dns/hosted-zone-id --value "$ZONE_ID"
aws ssm put-parameter --profile supply-prod --region us-east-1 --type String \
  --name /supply-checkout/prod/dns/dmarc-rua --value 'mailto:dmarc-reports@example.com'   # your DMARC report service's address
# The stack adds TXT records at the apex and _dmarc, and MX and TXT at mail.
# If any of those already exist in the zone, the deploy fails: remove them, or
# merge their values into lib/stacks/domain-stack.ts first.
aws route53 list-resource-record-sets --profile supply-prod --hosted-zone-id "$ZONE_ID" \
  --query "ResourceRecordSets[?Type!='NS' && Type!='SOA'].[Name,Type]" --output text
cd infra
npx cdk deploy supply-checkout-prod-us-east-1-domain --profile supply-prod
```

**Then, by hand:**

1. Check the identity is verified (DKIM `SUCCESS`, MAIL FROM `SUCCESS`; DNS can take up to an hour):
   ```bash
   aws sesv2 get-email-identity --profile supply-prod --region us-east-1 --email-identity supplycheckout.com \
     --query '{sending:VerifiedForSendingStatus,dkim:DkimAttributes.Status,mailFrom:MailFromAttributes.MailFromDomainStatus}'
   ```
2. Request SES production access. New accounts are in the sandbox (200 messages a day, verified recipients only). AWS answers within about a day, and may ask follow-up questions by email:
   ```bash
   aws sesv2 put-account-details --profile supply-prod --region us-east-1 \
     --production-access-enabled --mail-type TRANSACTIONAL --contact-language EN \
     --website-url https://supplycheckout.com \
     --additional-contact-email-addresses you@example.com \
     --use-case-description "Transactional email for Supply Checkout, a subscription app for tracking supplies checked out to client jobs: team invitations, sign-in and account notices, and billing receipts, sent only to users of a team and people a team member invites. No marketing or purchased lists. Bounces and complaints go to an SNS topic; addresses that hard-bounce or complain are suppressed with the SES account-level suppression list, and we alarm on bounce and complaint rates."
   aws sesv2 get-account --profile supply-prod --region us-east-1 \
     --query '{production:ProductionAccessEnabled,review:Details.ReviewDetails}'
   ```
3. Check DMARC. While still in the sandbox, verify your own address (`aws sesv2 create-email-identity --email-identity you@example.com`, then click the link), and send yourself a message from the domain:
   ```bash
   DOMAIN=supplycheckout.com
   aws sesv2 send-email --profile supply-prod --region us-east-1 \
     --from-email-address "noreply@$DOMAIN" --destination ToAddresses=you@example.com \
     --content 'Simple={Subject={Data=DMARC test},Body={Text={Data=Test}}}'
   ```
   In the received message's headers ("Show original" in Gmail), SPF, DKIM and DMARC should all say `PASS`. Aggregate reports arrive at the `dmarc-rua` address daily. Once they show SES mail passing for a couple of weeks, change `p=none` to `p=quarantine` in `lib/stacks/domain-stack.ts`.

### Transactional email

The app sends invites and account notices itself (`supply-checkout-5hx`); Cognito sends its own sign-up and sign-in codes. Both go out from `noreply@<env domain>` through one SES configuration set, `supply-checkout-<env>-transactional`, which the primary region's `domain` stack creates and makes the domain identity's default.

- **Suppression.** The configuration set adds any address that hard-bounces or complains to SES's account-level suppression list, and SES won't send to it again. A later send to it comes back as a bounce (subtype `OnAccountSuppressionList`). Because the configuration set is the identity's default, this covers Cognito's mail too: someone who marks an invite as spam also stops getting sign-up and password-reset codes. See [Removing an address from the suppression list](#removing-an-address-from-the-suppression-list).
- **Bounce and complaint events.** The configuration set publishes them to the SNS topic `supply-checkout-<env>-email-events`, encrypted with its own KMS key, which only SES may publish to, and only for this configuration set. The `email` stack's function (`backend/src/email/events.ts`) subscribes to it. When the message was an invite (its SES tags name the team and invite), a permanent bounce (including a send to a suppressed address) or a complaint marks that invite `inviteStatus: "failed"` with `failureReason` (`bounced` or `complained`), as long as the invite is still there and is for the address that bounced, so the owner can see it and correct the address. Transient bounces (a full mailbox, an out-of-office auto-reply) are counted in `EmailBounces` but don't fail the invite. Nothing is re-sent automatically. The function may read only `homeRegion` from team items and update only an invite's failure fields (`dynamodb:Attributes` in its policy), whose names no other item in a team's partition uses: the policy pins the partition, not the item, so the invite field is `inviteStatus`, not `status` (a team's subscription status). Events it can't record after retries go to `supply-checkout-<env>-email-events-dlq`, which alarms (Email events dropped, [docs/journeys.md](journeys.md)).
- **The dead-letter queue holds email addresses.** Its messages are whole SES events, recipients included, so it's encrypted with its own KMS key and keeps messages for 7 days. Read it only to replay or diagnose an event, and don't copy messages into tickets, chat, commits or logs; quote the invite and team IDs from the message's `mail.tags` instead.
- **Sending.** A function gets permission with `grantSendEmail(fn, config)` (`lib/email.ts`): `ses:SendEmail` on the domain identity and the configuration set only, with the condition `ses:FromAddress = noreply@<env domain>`, and the environment `mailerFromEnv()` reads (`backend/src/email/mailer.ts`). The `account` function has it, in every region's `api` stack, for invites, team closure and reopening notices, and the security notices (a password set, two-step sign-in turned on) to the caller's own verified address (it sends through SES in the primary region); billing notices (`supply-checkout-x0l`) add it where they send. The `email` stack's security notices function has it too, for the same notices when the change was made directly against Cognito, and the `emailChanged` notice to an account's previous address ([Sign-in](#sign-in), "What it protects"). Its role may also call `ListUsers` and `AdminGetUser` on the app pool only, and `GetItem` (projected), `UpdateItem` (returning nothing) and `ConditionCheckItem` (the `DELETING` mark) in `USER#` partitions naming only `SECURITY_NOTICE_ATTRIBUTES` (the keys, `noticeSentAt`, `noticeFor`, `noticeAddress`, `noticeAddressAt`, `noticeSeenHash`, which no other item has, and no TTL attribute). **After deploying the `email` stack** (it now deploys after `identity`), this check is a gate: if it fails, direct changes aren't noticed at all.
  1. With a test account signed in, change its password with the AWS CLI and its own access token (`aws cognito-idp change-password`). Within a few minutes one `passwordSet` email must arrive, and the function must log `Security notice sent` with `via: cloudtrail`. **If no event reaches the function** (no invocation; CloudTrail management events don't always reach EventBridge, as the operator group's `AdminAddUserToGroup` events didn't in `supply-checkout-3sv.5`), **or it logs `Security notice not sent` with `NoSub`**, the feature doesn't work: Cognito's events can't be matched to a user, and direct changes go unnoticed.
  2. Look at that event in CloudTrail and confirm where `sub` and `userPoolId` are, and that `requestParameters.userAttributes` of an `UpdateUserAttributes` event is `HIDDEN_DUE_TO_SECURITY_REASONS`. If the attributes (the new address) are in clear, the dead-letter queue holds addresses: it needs its own KMS key and a row in the privacy policy's data inventory.
  3. Set a password through the app, and confirm only one email arrives.
  4. Load the app once, change the account's email with `update-user-attributes` and `verify-user-attribute`, and confirm the old address gets the `emailChanged` email.
  5. Confirm the function logs no `AccessDeniedException` (`reason: error`): DynamoDB Local doesn't enforce the `dynamodb:Attributes` conditions.
- **Deploying.** Deploy the primary region's `domain` stack first (it adds the configuration set, and changes the identity's default to it), then `data`, then `email`. Deploying `email` deploys `data` too, so keep `-c backupCopy=false` until [step 4 of the backup setup](backups.md#setting-it-up) ([why](#the-cloudtrail-trail)):
  ```bash
  npx cdk deploy supply-checkout-prod-us-east-1-domain supply-checkout-prod-us-east-1-email --profile supply-prod -c backupCopy=false
  ```
  Then send a test message to the SES mailbox simulator and check the event reaches the function's log: `aws sesv2 send-email --profile supply-prod --region us-east-1 --from-email-address noreply@supplycheckout.com --destination ToAddresses=bounce@simulator.amazonses.com --configuration-set-name supply-checkout-prod-transactional --content 'Simple={Subject={Data=Bounce test},Body={Text={Data=Test}}}'`. <!-- public-safety: allow -->
  The function's IAM conditions (`dynamodb:Attributes`, `dynamodb:Select`, `dynamodb:ReturnValues`) aren't enforced by DynamoDB Local, so check them once in the deployed stack: create a test invite for `bounce@simulator.amazonses.com` in a test team, send the same message with `--email-tags Name=kind,Value=invite Name=teamId,Value=<team ID> Name=inviteId,Value=<invite ID>`, and confirm the invite item gets `status: failed` and the function logs no `AccessDeniedException`. Then delete the test team's items. <!-- public-safety: allow -->

### Removing an address from the suppression list

Do this only when the address's owner asks, for example after they fixed a full or misconfigured mailbox, or marked an invite as spam by mistake and now can't get sign-in codes. An address on the list gets no invites, notices or Cognito codes. Check it, then remove it (use the address they gave you; don't paste it anywhere else):

```bash
aws sesv2 get-suppressed-destination --profile supply-prod --region us-east-1 --email-address "$ADDRESS" \
  --query 'SuppressedDestination.{reason:Reason,since:LastUpdateTime}'
aws sesv2 delete-suppressed-destination --profile supply-prod --region us-east-1 --email-address "$ADDRESS"
```

A complaint means the person asked not to get our mail, so remove a `COMPLAINT` entry only on their own request. If an invite to the address had failed, the owner sends a new invite; the failed one isn't retried.

**Staging and dev.** Only the prod account exists today, so nothing is delegated yet. When one of those accounts exists (`staging` here):

1. In the staging account, create the zone `staging.supplycheckout.com` (`aws route53 create-hosted-zone --name staging.supplycheckout.com --caller-reference staging-$(date +%s)`) and put its ID in that account's `/supply-checkout/staging/dns/hosted-zone-id`.
2. In the prod account, put the new zone's four name servers in a `StringList` parameter: `aws ssm put-parameter --type StringList --name /supply-checkout/prod/dns/delegation/staging --value 'ns-1.awsdns-01.org,ns-2.awsdns-02.co.uk,…'`.
3. Add `"delegatedEnvs": ["staging"]` to `cdk.json` (it holds names only) and redeploy prod's `domain` stack, which adds the NS record. Keep it in `cdk.json` rather than passing `-c`: a prod deploy without it removes the delegation.
4. Deploy staging with `-c envName=staging` and that account's profile.

## Sign-in

The `identity` stack (`lib/stacks/identity-stack.ts`, [ADR 0007](adr/0007-identity-cognito.md), `supply-checkout-zsm`) holds the Cognito user pool, in the primary region. It's stateful: termination protection, deletion protection on the pool, and a `RETAIN` removal policy.

- **Essentials tier** with **Managed Login** at `auth.<env domain>`, branded with the app's colors (`managedLoginBranding` in `lib/identity.ts`; light or dark follows the browser).
- Sign-in by email with a **one-time code**, a **password** (12+ characters, mixed), or a **passkey**. Passkeys use `auth.<env domain>` as their relying party ID, which Cognito requires with a custom domain. They are bound to that host, so changing it orphans every passkey.
- **Optional TOTP MFA**, no SMS. Owners must turn it on before changing billing (`supply-checkout-8jc.12`). The billing routes enforce that, not the pool: after the membership and role checks they call `GetUser` with the caller's own access token and answer 403 `mfa_required` unless `UserMFASettingList` has `SOFTWARE_TOKEN_MFA` and it's the preferred factor. A Google or Apple user (one who signs in only through the provider, `isFederatedOnly`) passes without it: Cognito never asks them for a second factor, and the provider's sign-in counts for it. A native user with a provider linked must turn TOTP on to pass, but after that a sign-in through Google or Apple isn't asked for the code either (Cognito never asks for MFA on a provider sign-in, and no token says how a session signed in): the provider's sign-in counts, as for a Google or Apple user.
  - **Setting it up** (Account in the app, `src/aws/mfa.js`): with optional MFA, Cognito lets a user with TOTP on sign in only with a password and the code, never an email code or a passkey. So the app first sets a password (`POST /me/password`, Cognito's `ChangePassword`; the current password confirms it, and a passwordless user sends none), then gets a secret (`POST /me/mfa/totp`, `AssociateSoftwareToken`) to show as a QR code, then checks a code from the app (`POST /me/mfa/totp/verify`: `VerifySoftwareToken`, then `SetUserMFAPreference`). All with the user's own token, like the email code routes: no IAM grant.
  - **Why "on the session" holds**: turning it on ends every session the user has (`GlobalSignOut`, tried three times; if it still fails the route answers 503 `signout_failed` and the app finishes it with `POST /me/sign-out-everywhere`), and `GetUser` refuses a revoked access token, so any native session the billing check accepts afterwards began with the password and code. The app then sends the user through Managed Login's `/logout` and back to sign in. Gaps that remain, each only for someone who already holds a session or the provider sign-in: TOTP turned on with direct Cognito calls (the admin scope allows them) doesn't sign anyone out; another browser signed in to Managed Login in the hour before (its session cookie) can get new tokens without the code; and a linked user's provider sign-in (above). Closing the first two needs a trusted record of when TOTP was turned on to compare with the token's `auth_time` (`supply-checkout-8jc.14`).
  - **What it protects**: an owner who has turned it on, against someone with their password or their inbox signing in. It's trust on first use: until they turn it on, whoever gets into the account (an email code from a stolen inbox, say) can set a password and their own authenticator, reach billing, and lock the owner out. A stolen access token can do the same for a passwordless user. So the account's verified address hears of it (`supply-checkout-8jc.15`): after `POST /me/password` succeeds, and after `POST /me/mfa/totp/verify` turns TOTP on (once the sign-out everywhere has run, whether or not it finished), the `account` function emails it what changed and when (UTC), and what to do if it wasn't them (the `passwordSet` and `twoStepOn` templates). The address is the verified one `GetUser` returned for the caller's own token before the change, never one from the request, and the message links only to the app. It's best effort: the change stands if SES refuses the message, takes longer than 3 seconds, or there's no verified address, which is logged (`Security notice not sent`) with the user ID, the kind and the error's name only, and counted in `SecurityNoticeFailures` (sent ones in `SecurityNotices`; both on the dashboard, and any failure in 15 minutes alarms, "Security notices failing", P2). A refused change sends nothing. **Changes made directly against Cognito** (`supply-checkout-8jc.28`, `8jc.29`): the admin scope lets anyone with a session make the same changes with the access token alone, and change the account's email (`UpdateUserAttributes`, then `VerifyUserAttribute` with a code sent to the new address). The email can't be made read-only for the client, because Google and Apple map it and Cognito requires mapped attributes to be client-writable. So the `email` stack's `supply-checkout-<env>-security-notices` rule sends CloudTrail's records of the app pool's `ChangePassword`, `VerifySoftwareToken`, `SetUserMFAPreference`, `UpdateUserAttributes` and `VerifyUserAttribute` calls, whoever made them, to the security notices function (`backend/src/identity/security-notices-handler.ts`). CloudTrail records the user's `sub` for these calls (`additionalEventData.sub`), not the username or the token; the function finds the user by it in the app pool (`ListUsers`, then `AdminGetUser`) and sends the same `passwordSet` notice, or `twoStepOn` when an authenticator is among the user's MFA methods, to the verified address (the same rule as the API's). A change made through the API isn't emailed twice: the `account` function marks the kind sent once SES has taken its notice (`NOTICE#<kind>` in the user's partition; one it couldn't send is left to the function), and the function sends only if no notice of that kind went out in the last 15 minutes, which also keeps the two calls of one TOTP setup to one email. **An email change** is told to the address the account had before (`emailChanged`), and it's checked on every one of these events, so a later event catches a change whose own events were missed. `/me` records the account's first verified address (`NOTICE_ADDRESS`), never for an account being deleted (it checks the `DELETING` mark in the same transaction), with a hash of Cognito's own address as it was. Whether the email changed is decided on that hash: Cognito's verified address only trimmed and lowered, not the app's rules, so a linked user's new address the API doesn't count, one over 254 characters the app can't normalize, or one NFKC would fold into the recorded one all still count, since Cognito sends codes and resets to each. The address told is always the recorded one, which starts only as an address the API trusts. The notice is claimed for the new address and sent, and only then does the record move on (to the new address if it normalizes, otherwise it stays at the old one, marked as told). The claim holds for 45 seconds, just over the function's timeout, and SES calls are bounded (5 seconds per try with `throwOnRequestTimeout`, 2 tries; 10 seconds in all for this notice). If SES refuses it or takes too long, the claim is given up and the event retried. An attempt that finds the claim held but the record not moved throws, and counts it (`pending`) once the claim is 15 seconds old (younger, it's likely another attempt still sending), so an attempt that died holding the claim ends in a retry that sends it (or the dead-letter queue), never in a silent success. An account with no recorded address (it hasn't loaded the app since this shipped, `supply-checkout-8jc.31`) has it recorded at the event, and nobody is told. Failures are logged with the user ID, the kind and the error's name only, and counted in `SecurityNoticeFailures` with a `via: cloudtrail` property and a reason (`not_sent`, `no_address`, `no_user` for an event without a sub, `lookup_failed`, `pending`, `error` for anything else thrown), so they raise "Security notices failing" too. A failed lookup, write or email change notice is retried by Lambda, and an event Lambda or EventBridge gives up on waits 14 days on `supply-checkout-<env>-security-notices-dlq` (SQS-encrypted) to be replayed, which alarms ("Security notices dropped", [journeys.md](journeys.md)). The rule matches this account's events only. See [Transactional email](#transactional-email) for the function's permissions and what to check after deploying.
  - Nothing is logged but the user ID (`Password set`, `Two-step sign-in turned on`): never the password, the secret or a code. There's no way to turn it off in the app, and a lost phone is an administrator's reset for now.
- Email codes come from `noreply@<env domain>` through SES, using the domain identity from the `domain` stack.
- One app client, `web`: a public client (no secret) using the authorization code flow with PKCE. Callback and sign-out URLs are `https://app.<env domain>/`, plus `http://localhost:5173/` outside prod (`-c localhostCallbacks=true|false` overrides). Access and ID tokens last 60 minutes; refresh tokens last 30 days and rotate on every use (a 10-second grace period covers two tabs refreshing at once). Refresh with the `/oauth2/token` endpoint or `GetTokensFromRefreshToken`: rotation turns off `REFRESH_TOKEN_AUTH`.
- **Sign in with Apple** and **Google** are off until their credentials exist (below).
- The web client's **write attributes** are pinned to `email`, `given_name` and `family_name`. Users can never set `email_verified` (or `phone_number_verified`) themselves: the API trusts a verified email for invites. Changing `email` keeps the old, verified address until the new one is confirmed with a code. Cognito requires every attribute an IdP maps to be writable, so Google and Apple **don't map `email_verified`**. They map their `email_verified` claim to `custom:idp_email_verified` instead, and Google maps its `hd` claim to `custom:idp_hd`. The web client can write both, but only while a provider is on. It can never write `custom:linked_email` or `custom:downgrade_pending`.
- **Verified emails from Google and Apple.** With either provider on, three triggers in `backend/src/identity` (`supply-checkout-6v9`, `supply-checkout-0b1`) handle federated users:
  - **One way in** (pre authentication, `sign-in-guard-handler.ts`). The invariant is that a federated-only user signs in only through Google or Apple. A federated-only user is one whose username is `<provider>_<provider user ID>` for a Google or Apple entry in `identities`, or whom Cognito marks `EXTERNAL_PROVIDER`. Cognito runs this trigger for native sign-ins (password, email code, passkey) and not for federated ones, and it refuses every native sign-in by such a user, even one who somehow got a password or a passkey. Native users, including ones with a linked provider (below), are let through: a linked user keeps its native username and `CONFIRMED` status. If who counts as federated ever changes, change `isFederatedOnly()`, the `email_verified` trigger and the linking trigger together. The guard has no AWS permissions.
  - **`email_verified` from the provider** (pre token generation, `email-verified-handler.ts`). For a federated-only user it sets `email_verified` to match the provider's claim with `AdminUpdateUserAttributes`. The value is `"true"` only when the provider says the email is verified (Google sends a boolean, Apple a boolean or `"true"`/`"false"`), and `"false"` otherwise. Users can write `custom:idp_email_verified` themselves, so the trigger reads it only when Cognito has just rewritten it from the provider. That is at a Managed Login token (`TokenGeneration_HostedAuth`, not a refresh) for a federated-only user with status `EXTERNAL_PROVIDER`, and the guard makes every such token a provider sign-in. A failed update is logged and the sign-in goes ahead, and the next sign-in tries again. A failed promotion leaves the user unverified. A failed downgrade leaves them verified until a later sign-in succeeds, and is logged at error level as its own outcome, `downgrade-failed`. Its role can write its own log group and call `cognito-idp:AdminUpdateUserAttributes` on this pool only. The grant is a separate IAM policy attached after the pool exists, because the pool names the function and the function can't name the pool.
  - **Linking to an existing account** (pre sign-up, `account-link-handler.ts`). Cognito runs it the first time a Google or Apple identity signs in (`PreSignUp_ExternalProvider`), before it creates a user. Other sign-ups pass through unchanged, and it never confirms or verifies anyone. It links the identity to an existing native user with `AdminLinkProviderForUser`, so the sign-in lands in the same user (same `sub`) and so the same teams. It links only when all of these hold:
    - The provider says the email is verified. `custom:idp_email_verified` is fresh from the provider here, since the user doesn't exist yet.
    - **The provider is authoritative for the address**, not just someone who once checked it. For Google that's `@gmail.com` or `@googlemail.com`, or a Workspace account whose `hd` claim (mapped to `custom:idp_hd`, read only here) equals the email's domain. For Apple it's a private relay address (`@privaterelay.appleid.com`), `@icloud.com`, `@me.com` or `@mac.com`. A personal Google or Apple account can still carry a work address its owner verified years ago and no longer controls, and linking on that would hand the address's current owner's account to them. Other addresses get a separate account. Linking those is the settings-based flow for a signed-in user (`supply-checkout-b4g`).
    - The email is plain ASCII with no `"` or `\`. Addresses and domains are compared after lowering ASCII letters only, so Unicode case folding can't make two match.
    - ListUsers finds exactly one native (not federated-only) user with that email, on one page. Several matches are refused rather than guessed at.
    - That user is `CONFIRMED`, enabled and has `email_verified` `"true"` (proven with Cognito's own code).
    - It has no identity from the same provider yet.
    - If it already has a Google or Apple identity linked, its `email` still equals `custom:linked_email`, the address recorded when that identity was linked. That attribute is set only by this trigger: no IdP maps it and no client can write it.

    Linking records the email in `custom:linked_email`, then links. Otherwise the sign-up goes ahead and makes a separate federated-only user, as before. After linking, the trigger fails that sign-in on purpose with `ACCOUNT_LINKED:<provider>` (Cognito would otherwise fail it with "Already found an entry for username"). Cognito sends the person back with it in `error_description`, and the web app (`src/aws/session.js`) signs in again once, straight to that provider (`identity_provider`), which lands in the linked user. If a Cognito call fails, the sign-in fails and can be tried again, since going ahead would make a separate account for good. Each call has a 1.5-second timeout, so all three fit in the 5 seconds Cognito gives a trigger.

    Its role can write its own log group and call `cognito-idp:ListUsers`, `cognito-idp:AdminUpdateUserAttributes` and `cognito-idp:AdminLinkProviderForUser` on this pool only. IAM can't limit ListUsers' filter; the code only searches by exact email. Like the `email_verified` trigger's grant, it's a separate policy. A linked user signs in with the provider or natively.
  - **Linked users' `email_verified`** (`supply-checkout-kgw`, the same pre token generation trigger). Cognito applies the provider's attribute mapping to a linked user at every provider sign-in, so a changed provider email overwrites `email` while `email_verified` stays `"true"`. The rule: a linked user's `email_verified` is `"true"` only for the address in `custom:linked_email`, which is always one the person proved with a Cognito code. For a native user with a Google or Apple identity linked, whose email differs from the recorded one while `email_verified` is `"true"`:
    - At a Managed Login token (`TokenGeneration_HostedAuth`), the only kind that follows a provider sign-in, the trigger sets `email_verified` to `"false"` (outcome `linked-unverified`), whatever the provider claims. The person proves the new address with a Cognito code, as for any change of email. We chose this over restoring the recorded address: the trigger only ever takes trust away, never writes an address the provider no longer asserts (and which may be taken or no longer the person's), and Cognito would rewrite a restored address again at every sign-in anyway. Before the downgrade it sets `custom:downgrade_pending` to `"1"`, and the downgrade clears it in the same `AdminUpdateUserAttributes` call, so only a successful downgrade clears the flag (`supply-checkout-0qr8`). If the flag's write fails, the downgrade is still tried. A failed downgrade is tried once more after a 250 ms pause, when there's time left: each call has a 1.2-second timeout, so the flag, two tries and the pause fit in 4 of the 5 seconds Cognito gives a trigger. If both tries fail, that sign-in fails too (`linked-downgrade-failed`, counted in `EmailUnverifyFailures`) and can be tried again. Its log says whether the flag is set (`flagged`) and carries the user's correlation handle (`user`): the first 16 hex digits of an HMAC-SHA256 of the user's `sub`, keyed with a secret the identity stack generates in Secrets Manager. The key reaches the function as an environment variable through a dynamic reference resolved at deploy time, so the role gets no Secrets Manager access. The handle names no one to someone reading the logs; an operator with the key finds the user (runbook in [journeys.md](journeys.md), "Email verification not saved"). A native Managed Login sign-in looks the same to the trigger, so a native change of email that's first followed by a Managed Login sign-in is unverified too and needs its code again.
    - While `custom:downgrade_pending` is set, a downgrade is owed: a Managed Login token with `email_verified` `"true"` downgrades again, even when the email is the recorded one (the address may have been recorded in the moment before the flag). If `email_verified` is already `"false"` (an operator unverified the user), any token clears the flag (`linked-cleared`), since a later `"true"` can only come from a Cognito code; a failed clear (`linked-clear-failed`, counted in `EmailVerifyFailures`) leaves the user untrusted until a later token.
    - At any other token (a refresh, an API sign-in, which never follow a provider sign-in), the trigger records the email in `custom:linked_email` (`linked-recorded`), so the API trusts it and a second provider can still be linked for it, only when it's the address the person last proved with a code in the app (`supply-checkout-ytr2`). A code proves only the address it was sent to (`supply-checkout-cjw7`): once Cognito has sent a code, `POST /me/email/code` reads GetUser again and, if the address is unchanged, writes an `EMAIL_CODE_SENT` item in the caller's own `USER#` partition (the SHA-256 of the address, trimmed and ASCII-lowercased, and the time; otherwise 409 `email_changed`). `POST /me/email/verify` asks Cognito to check the code only if the caller's email is that address and the code is less than a day old; then, if GetUser shows the same address verified, it writes a `VERIFIED_EMAIL` item (the hash and the time) and deletes `EMAIL_CODE_SENT` in one transaction, on the condition that it's still for that address (`backend/src/data/verified-email.ts`). Otherwise it records nothing, deletes the used code's record, and answers 409 `email_changed`. So a provider's rewrite between sending and checking a code gets nothing recorded, even if Cognito accepted the old code for the new address, which it doesn't document either way. Both writes use the function's usual session. The trigger reads the proof (`GetItem`, strongly consistent, 1.2-second timeout) and records the email only when it matches and is less than an hour old (the app refreshes right after the code, and an old proof can't be replayed for an address that comes back later); the same write clears `custom:downgrade_pending`, so a proven address also ends a pending downgrade without a Managed Login sign-in. Any other verified-looking address is left unrecorded (`linked-not-proven`, or `linked-downgrade-pending` while the flag is set), and the API keeps treating it as unverified until the person verifies it in the app. This is a positive signal: nothing has to be written to Cognito for a rewritten address to stay unrecorded, so throttling the pool's shared user-update quota can't get one recorded. A failed read (`linked-lookup-failed`) or recording (`linked-record-failed`), both counted in `EmailVerifyFailures`, lets the refresh go ahead, and the next token tries again. The trigger's role may read only that hash: `dynamodb:GetItem` on the app table where the partition key is `USER#…` (`dynamodb:LeadingKeys`), naming no attributes but `PK`, `SK`, `verifiedEmailHash` and `verifiedAt` (`dynamodb:Attributes`, `VERIFIED_EMAIL_ATTRIBUTES` in `backend/src/data/schema.ts`, with `dynamodb:Select` `SPECIFIC_ATTRIBUTES`), and `kms:Decrypt` on the table's key only through DynamoDB. IAM can't name the user (the trigger has no per-user session) or the sort key, so it could read those two attributes of any user; no other item has them, and it's a hash, not an address. The account function needs no new permission (its session already reaches the caller's own partition) and no `AdminUpdateUserAttributes`. Deleting an account removes both items with the user's other rows (neither sort key is a `LIMIT#` one). The identity stack now deploys after the primary region's data stack, whose SSM output names the table's key.

    The account API applies the same rule to what GetUser returns (`backend/src/api/cognito-user.ts`): a linked user's email counts as verified only while it's the recorded one, and no user's counts while `custom:downgrade_pending` is set, so a rewritten address never lists another person's invites in `/me` or accepts them, even if the trigger's write failed. That relies on the web client reading every attribute (no `ReadAttributes`), which a test checks: GetUser must return `custom:linked_email` and `custom:downgrade_pending`. Reading the flag tells a user only that their own downgrade is pending. The linking trigger also refuses a user whose downgrade is pending. A native change of email counts once the person has verified it in the app and the app's next refresh has recorded it. The linking trigger refuses such a user both ways: its `email_verified` is `"false"`, and its email isn't the recorded one, so a victim's first Google or Apple sign-in with the rewritten address makes its own account. The trigger's role can call `AdminUpdateUserAttributes` on this pool, and read the proven address's hash as above.
  - **Accepted risks.**
    - If a provider sign-in left the claim out, Cognito would keep the attribute's last value, which the user may have written. Google and Apple always send `email_verified` with the `email` scope. A forged verified email would show that address's pending invites (team name and role) in `/me`. Joining still needs the token from the emailed link.
    - Linking trusts Google's `hd` claim for a Workspace address, and so Google's own check that the Workspace tenant owns the domain (DNS verification when the domain is added). A tenant's admin controls every mailbox at the domain anyway. If Google ever let a tenant keep or claim a domain it doesn't own (say, one that lapsed and was re-registered by someone else), that tenant's accounts could be linked to our accounts at that domain. We rely on Google here as every "Sign in with Google" relying party does.
    - If a linked user's downgrade fails after Cognito rewrote the email (even with the flag's write failing too, say because someone flooded the pool's shared user-update quota), the rewritten address keeps `email_verified` `"true"` in Cognito until a later Managed Login sign-in downgrades it. No refresh records it, since no code proved it, and the API doesn't trust it (`supply-checkout-ytr2`); the "Email verification not saved" alarm still reports the failed downgrade. What's left: an address Cognito verified outside the app (a client calling `VerifyUserAttribute` itself, or an operator setting `email_verified`) isn't recorded until the person verifies it in the app again, or the operator also sets `custom:linked_email`.
    - With `keepOriginal` on, a native change of email keeps the old, verified address in `email` until the new one's code is entered, so `/me` shows the old address as verified while the new one waits. The app has no change-of-email flow yet, so there's no pending-address signal; a client that changes its email through Cognito directly verifies it there, and then verifies it in the app before it counts for a linked user.
    - The `email_verified` trigger's log correlation key reaches the function as an environment variable, so anyone allowed `lambda:GetFunctionConfiguration` on it, or who can read CloudFormation drift detection's results for the identity stack, can read the key, and with it turn a handle back into a user by hashing candidate `sub`s. Those are operators who can already read the logs and the user pool; the handle protects only against someone who has the logs alone.

**Verifying an email address in the app** (`supply-checkout-ocjk`). A user whose email isn't verified (a native change of email, or a linked user's address the trigger unverified) verifies it from the web app: `POST /me/email/code` and `POST /me/email/verify` on the account function call Cognito's `GetUserAttributeVerificationCode` and `VerifyUserAttribute` with the caller's own access token (`cognitoEmailCodes()` in `backend/src/api/cognito-user.ts`), which the web client's `aws.cognito.signin.user.admin` scope allows. Like GetUser, they need no IAM permission. They go through the API rather than straight from the browser so that the app keeps talking only to the API: the content security policy's `connect-src` has no Cognito regional endpoint and `config.json` names no region (ADR 0010), the handler checks the token's `sub` against the authorizer's as for every account route, and API Gateway throttles both routes in front of Cognito's own per-user limits on codes and tries. A user can also ask for only 10 codes a UTC day (a counter in their own `USER#` partition, `backend/src/data/email-codes.ts`, like the daily team limit), so one user can't use up the route's shared throttle. A user whose downgrade is pending (`custom:downgrade_pending`) doesn't count as verified, so they can ask for a code; since `supply-checkout-ytr2`, a correct code records the address as proven and the next refresh records it and clears the flag. The app's dialog suggests signing in again when `/me` hasn't caught up. Cognito's refusals come back as `bad_request` with `code_mismatch` or `code_expired`, 429 `quota_exceeded`, or 409 `email_in_use`; only an error's name is ever logged, never the token, the code or Cognito's message. After a code is accepted the account function records the address as proven (a `VERIFIED_EMAIL` item, above) and the app refreshes its tokens, and that refresh is when the pre token generation trigger records a linked user's new address, so `GET /me` then shows `emailVerified: true`. A code counts only for the address it was sent to (above): if the email changed after the code was sent, or while it's checked, or Cognito doesn't show it verified, the route records nothing and answers 409 `email_changed`, and the person sends a new code.

The stack publishes `user-pool-id`, `user-pool-arn`, `web-client-id`, `issuer-url` and `auth-url` under `/supply-checkout/<env>/identity/`. `cognitoJwtAuthorizer()` in `lib/identity.ts` builds the HTTP API's JWT authorizer from them.

**Team isolation**, two layers:

1. **Membership, in the handler.** API Gateway's JWT authorizer checks the token; the handler also requires an unexpired access token and takes the user from `sub`. The team comes only from the path: `authorizeTeam` reads the caller's `MEMBER` item on every request (so a role change applies at once) and issues the `TeamContext` every data function needs. A body that names a team, or any server-owned field, is refused. Then the role (ADR 0007): each route in `routes.ts` names the least role that may call it (`minRole`), checked before anything runs (`roles.ts`). Viewers read; contributors also write sheets and inventory and run the commands; owners also import and manage members. A role below the route's gets 403 `permission_denied` with `reason` `view_only` (the web runtime hands it to the app as view-only access) or `owners_only`, and `backend/test/roles.test.ts` calls every team route as every role.
2. **IAM, `dynamodb:LeadingKeys`.** The data function's own role has no DynamoDB access. For each team it assumes the `DataAccessRole` with the session tag `teamId=<path team>` (cached for up to an hour per team), and that role allows `GetItem`, `PutItem`, `DeleteItem`, `UpdateItem`, `ConditionCheckItem` and `Query` (the last three for the inventory commands' transactions; no `Scan`, no batch writes) only on items whose partition key is `TEAM#${aws:PrincipalTag/teamId}`, or the team's date index partition `TEAM#…#SHEETS`. Every item a team route touches is in one of those two partitions, so a bug that built another team's key would be refused by IAM too.

**First sign-in and teams** (`supply-checkout-l5y`; the app's side is in [docs/api/onboarding.md](api/onboarding.md)). `GET /me` lists the caller's teams (role, plan, trial status) and the live invites for their **verified** email. `POST /teams` creates a team with the caller as owner, `homeRegion` from the serving region and a 14-day trial; it's idempotent per `Idempotency-Key` (the team's ID is derived from the user and the key, and its creation is conditional) and limited to 5 teams per user per UTC day by a counter in the user's partition. `POST /invites/{inviteId}/accept` joins the team that invited the caller's verified email, with `{"token"}` from the emailed link; the transaction checks the token's hash, the address, the expiry and that the invite is unused. Each user can be in at most 20 teams, which also bounds the role sessions one `/me` needs, and the account routes have their own API Gateway throttles (`throttle` in `routes.ts`), as does the CSV import (5 requests a second, burst 10), which can write up to 1,000 items. The email comes from Cognito's `GetUser`, called with the caller's own access token.

These routes write outside any team the caller is in (a new team, or the team they're joining, plus their own `USER#` rows), so the `account` function can't use the `DataAccessRole`. It assumes the **`AccountAccessRole`** with five session tags: `userId` (the token's `sub`), `teamId`, `invitee` (the SHA-256 of the verified email), `member` and `inviteLimit` (the invite limit key of an address being invited: its SHA-256 without a `+tag`, `inviteLimitKey`), unused ones set to `.`, which no key matches. That role allows `GetItem`, `PutItem`, `DeleteItem`, `UpdateItem`, `ConditionCheckItem` and `Query` (no `Scan`, no batch writes) only where the partition key is `USER#<userId>`, `TEAM#<teamId>` or, on `GSI2`, `INVITEE#<invitee>`, and only `UpdateItem` and `DeleteItem` where it's `USER#<member>`, naming no attributes but `PK`, `SK` and `role` (`dynamodb:Attributes`, `MEMBER_ROW_ATTRIBUTES` in `backend/src/data/schema.ts`) and returning nothing (`dynamodb:ReturnValues` `NONE`). The update is conditioned on `attribute_exists(PK)`, so it can't create a row. Where it's `INVITELIMIT#<inviteLimit>`, it allows only `UpdateItem`, naming only `PK`, `SK`, `count`, `type` and `expiresAt` (`INVITE_LIMIT_ATTRIBUTES`) and returning nothing: the address's daily invite counter, and nothing else about it. The handler tags a team only when the request is entitled to it: the ID derived from the caller's own idempotency key, the team of an invite found under their verified email, a team in their own `USER#` rows after the membership check, or the path's team on the members routes (which then check membership and role). It tags a `member` only on a role change or removal, after the caller's owner check and only for a user whose `MEMBER` item is in that team, so the member's team-switcher row changes in the same transaction as their membership. It tags an `inviteLimit` only when an owner creates or re-sends an invite, after the owner check, with the limit key of the invite's address (from the request for a new invite, from the stored invite for a re-send). Residual risk: IAM can't limit the sort key, so a session tagged with a member could still delete any of that member's rows, or change `role` on one that exists (their switcher rows for other teams, or their daily team-creation counter). It can't read them, write any other attribute or create items, and only the members routes set the tag, after the checks above; `backend/test/members-api.test.ts` checks that their writes stay inside that list. The `DataAccessRole` is unchanged.

**Invites** (`supply-checkout-5tp`; the data layer is in [backend.md](backend.md)). Owners invite an address with a role; the `account` function writes the invite and emails the link, and owners list, revoke and re-send invites. Creating and re-sending have the tightest API Gateway throttles (5 requests a second, burst 10), and each team (50), each team for one address (3) and each address (15, from every team together) has a daily limit. Invite addresses must be bare addr-specs, which the mailer checks again. Removing a member revokes their other invites to the team.

**Members and roles** (`supply-checkout-dj6`). Owners list members, change roles and remove members; anyone can leave. The team item's `owners` count moves in the same transaction as every owner membership change, conditioned on `owners > 1` for a decrease, so the last owner can't be removed, demoted or leave (409 `aborted` with `reason: "last_owner"`), even when two owners act at once. Owner actions on someone else also re-check the caller's own `MEMBER` item at write time.

**Sign-in sessions.** The web app keeps access and ID tokens in memory. `/auth/session` redeems the Managed Login code (with its PKCE verifier) at Cognito's `/oauth2/token` and sets the refresh token as `__Secure-sc_refresh` (`HttpOnly; Secure; SameSite=Strict; Path=/auth`, 30 days). `/auth/refresh` redeems it, and because rotation is on, stores the new refresh token each time. `/auth/sign-out` revokes it and clears the cookie. Each checks that `Origin` is the app's (`https://app.<env domain>`, plus `http://localhost:5173` outside prod), and CORS allows only those origins, with credentials.

**Latency.** Functions run Node.js 24 on arm64, bundled by esbuild (ESM, minified, the AWS SDK v3 clients tree-shaken into the bundle) with their clients created once per container. The data function has 1 GB of memory, for CPU. A warm read is a membership check (one `TransactGetItems`) and one `GetItem` or `Query`; a write adds a `PutItem`.

**Deploying.** The api stack reads, from SSM in its region: the `api.` certificate (the domain stack), the table's KMS key ARN (the data stack) and the issuer, web client ID and auth URL (the identity stack). So deploy those first. The synth bundles the handlers, so install the backend's dependencies too. Deploying `api` and `observability` deploys the stacks they depend on (data and audit among them), so keep `-c backupCopy=false` until [step 4 of the backup setup](backups.md#setting-it-up) ([why](#the-cloudtrail-trail)):

```bash
npx cdk diff supply-checkout-prod-us-east-1-api --profile supply-prod -c backupCopy=false
npx cdk deploy supply-checkout-prod-us-east-1-api supply-checkout-prod-us-east-1-observability --profile supply-prod -c backupCopy=false
```

**Account deletion and Cognito.** `DELETE /me` deletes the caller's Cognito user with `DeleteUser` and their own access token (the `aws.cognito.signin.user.admin` scope the web app already asks for), like `GetUser`: the account function has no IAM permission to delete users, so a bug can't delete anyone but the caller. After it, the user's refresh token stops working at once; an access token they still hold passes API Gateway's JWT check until it expires (at most 60 minutes), but the account routes that matter call `GetUser`, which refuses it (401), and they're in no team, so the data routes refuse it too.

## Operators

Platform operators ([ADR 0015](adr/0015-platform-operator-role.md), `supply-checkout-6uw.1`) list and search teams, read one team's account record, comp a team (a free plan for a pilot, say) and read the operator audit. They never read a team's sheets, inventory, invites or receipts: support access with an owner's approval is a later bead.

**The operator pool.** The `identity` stack has a second user pool, `supply-checkout-<env>-ops`, next to the customers' one:

- No self sign-up. Operators are created by an administrator with `npm run operators` or the AWS CLI under an SSO role (below). No Lambda role and no app client can create users or change groups; an `infra` test checks that no policy in any stack grants `AdminCreateUser`, `AdminAddUserToGroup`, `AdminRemoveUserFromGroup` or `CreateGroup`.
- Username and password (16+ characters, mixed), then TOTP, which the pool requires: the first sign-in sets it up, and the pool can't issue a token without it, so every token it issues comes from a session that used MFA. No email codes, passkeys, SMS, Google or Apple, and no email unless an administrator asks for one (`npm run operators -- add --send-email`, which uses Cognito's default sender): a forgotten password is reset by an administrator (`npm run operators -- reset`).
- An `operators` group. Being in the pool isn't enough: the API checks the group.
- Managed Login at `ops-auth.<env domain>` (its certificate is in the `domain` stack in `GLOBAL_SERVICES_REGION`).
- One public client, `ops`: authorization code with PKCE, calling back only to `npm run ops` on `http://localhost:8765/` (`OPS_CLI_CALLBACK` in `lib/identity.ts`). Access and ID tokens last 15 minutes; refresh tokens last 8 hours, with rotation and revocation. It has the `aws.cognito.signin.user.admin` scope so the ops function can call `GetUser` with the operator's token.
- It publishes `ops-user-pool-id`, `ops-user-pool-arn`, `ops-client-id`, `ops-issuer-url` and `ops-auth-url` under `/supply-checkout/<env>/identity/`.

**The ops routes.** The `/ops/*` routes (`OPS_ROUTES` in `backend/src/api/routes.ts`) are on the same HTTP API, in the primary region only, behind their own JWT authorizer for the operator pool (its issuer and the `ops` client). A customer's token fails it, and an operator's token fails the customer authorizer; the team routes never read `cognito:groups`. The `ops` function (`backend/src/operator/`) then checks, on every request: an unexpired access token from the operator pool for the `ops` client whose `cognito:groups` names `operators`; `GetUser` with the token, which Cognito refuses once the token is revoked or the user disabled; and `AdminListGroupsForUser`, which must still list `operators`. So removing someone from the group, disabling them or signing them out globally takes effect on their next request, not when their token expires. Each route has its own throttle (2 to 5 requests a second).

**The operator-access role.** The ops function's own role can reach no table: it may assume `OperatorAccessRole` (tagged with the team a comp changes, or `.`) and call `AdminListGroupsForUser` on the operator pool. The role may:

- `Query` GSI3's `OPS#TEAMS`, `OPS#OWNERS#*` and `OPS#AUDIT#*` partitions, with `dynamodb:Select` limited to `ALL_PROJECTED_ATTRIBUTES` or `SPECIFIC_ATTRIBUTES`. GSI3 is sparse and projects only `OPS_INDEX_ATTRIBUTES` (`backend/src/data/schema.ts`): a team's account record (name, plan, seats, status, trial end, owner count, when it was closed, creation time, Stripe customer, version and comp), an owner's email and join date, and an audit event's action and operator. Team `META` items and owners' `MEMBER#` items carry `GSI3PK`; sheets, products, movements, invites and imports never do.
- `UpdateItem` in the tagged team's partition, naming only `COMP_ATTRIBUTES` (`PK`, `SK`, `type`, `version` and the `comp*` fields; `dynamodb:Attributes`), returning at most those. So it can't change a team's `plan` or `status` (ADR 0009), and it has no `GetItem`, `Query`, `PutItem` or `DeleteItem` on any `TEAM#` partition.
- `PutItem` and `Query` in `OPAUDIT#*` partitions, never `UpdateItem` or `DeleteItem`.
- For stuck imports (`supply-checkout-6uw.2`): `Query` GSI1's `IMPORTS#COMMITTING` partition naming only `STUCK_IMPORT_ATTRIBUTES` (what the scheduled check may read), and `UpdateItem` in the tagged team's partition naming only `IMPORT_INDEX_ATTRIBUTES` (`PK`, `SK`, `GSI1PK`, `GSI1SK`). `POST /ops/teams/{teamId}/imports/{importId}/clear` removes a job's GSI1 keys, on the condition that it's still in that partition and started over an hour ago, with its audit item in the same transaction ("Imports stuck" in [journeys.md](journeys.md)).

Residual risks, accepted: IAM can't require a condition expression, so a `PutItem` in `OPAUDIT#` could overwrite an item with the same key (the code conditions every put on `attribute_not_exists(PK)`, and keys hold a random ID; the operator audit watch below alarms P1 on any overwrite, change or deletion); an `UpdateItem` could create an item in the tagged team's partition holding only comp attributes (the code's `#type = :team` condition prevents it); IAM can't tell `REMOVE` from `SET`, or limit the sort key, so the stuck-import statement would let code set or remove the GSI1 keys of any item in the tagged team's partition (the code's `GSI1PK = IMPORTS#COMMITTING` condition keeps it to a stuck import job, and the route only ever names an `IMPORT#<id>` sort key). The worst case is a closed team's `META` item: removing its GSI1 keys (`TEAMS#CLOSED`) would take it out of the purge queue, so the hourly purge would never find it and the team would never be deleted, silently breaking the promise to delete a closed team's data, with no alarm ("Deletion overdue" counts only teams still in that queue). A test (`backend/test/ops-api.test.ts`, "can't take a closed team out of the purge queue") checks the route can't; a code change could; and `dynamodb:ReturnValues` doesn't cover `ReturnValuesOnConditionCheckFailure`, so code that asked for `ALL_OLD` on a failed condition could read the item it tried to update (the ops code never sets it, and the backend lint config bans `ReturnValuesOnConditionCheckFailure`, `ALL_OLD` and `ALL_NEW` in `src/operator/` and `src/data/operator.ts`). Each would take a change to the ops function's code, which only a deploy can make.

**Reopening a closed team** (`supply-checkout-6uw.6`). The operator-access role has no closure field on purpose: IAM can't tell removing an attribute from setting it, so a role that could reopen a team (remove `closedAt`, `purgeAfter` and the `TEAMS#CLOSED` index keys) could also close one and set a `purgeAfter` in the past, and the hourly purge would delete it. So `POST /ops/teams/{teamId}/reopen` goes through a second function, `OpsReopenFunction` (`backend/src/operator/reopen-handler.ts`), which has no route and which only the ops function may invoke (`lambda:InvokeFunction` on it, unqualified). The ops function verifies the operator as for every route, then invokes it synchronously with plain values (operator `sub`, team ID, reason, `expectedVersion`, `Idempotency-Key`), never expressions. Its own role reaches no table either: per request it assumes `OperatorReopenRole`, tagged with the team, which may `GetItem` and `UpdateItem` only in that team's partition naming only `REOPEN_ATTRIBUTES` (keys, `type`, `version`, `owners`, `closedAt`, `closedBy`, `purgeAfter`, the purge's `purging` mark, `GSI1PK`, `GSI1SK`) and returning nothing, and `PutItem` and `Query` only in that team's `OPAUDIT#` partition. `reopenOpsTeam` (`backend/src/data/operator.ts`) reads the closure, then in one transaction removes it, moves the version (conditioned on the version and closure read, on `purgeAfter` being more than `OPS_REOPEN_CUTOFF_MINUTES` (5) away, on no `purging` mark, and on `owners > 0`), writes the `ops.team.reopen` audit item (before: `closedAt` and `purgeAfter`) and the idempotency record. An operator can restore a disputed closure within its last hour, when an owner no longer can (60 minutes): the purge marks a team `purging` (conditioned on it still being closed and due) before deleting anything, and the reopen's condition refuses that mark, so whichever write lands first wins and a team is never reopened part-deleted. Owners see it in their support actions. Unlike an owner's reopen there's no daily limit and no email to owners. The role's `GetItem`/`UpdateItem` statement also requires `dynamodb:Select` to be `SPECIFIC_ATTRIBUTES` when present, so a `GetItem` without a projection (which names no attributes and would return the whole item) is refused; `reopenOpsTeam` always projects. Residual risks, accepted: the reopen function's code could, with its role, close the one team it's tagged with; `ReturnValuesOnConditionCheckFailure: ALL_OLD` has no IAM control, so code that set it could read the META item it failed to update (the backend lint config bans it in the operator code); the role could `UpdateItem` other items in `TEAM#<tag>` naming only allowed attributes, for example removing a sheet's GSI1 keys; and an administrator with a wildcard `lambda:InvokeFunction` can invoke the reopen function directly with any operator `sub`, which would be attributed to that sub in the audit (CloudTrail still records the real caller). The first three would take a compromised or changed reopen function, which only a deploy makes.

**Comps and the audit.** `PUT /ops/teams/{teamId}/comp` writes `compPlan`, `compSeats`, `compUntil` (at most 12 months ahead), `compReason`, `compBy` (the operator's `sub`) and `compAt` on the team's `META` item, conditioned on the item being a team at the version the operator read, with an operator audit item (`OPAUDIT#<teamId>`, `AUDIT#<ts>#<eventId>`, also in GSI3's `OPS#AUDIT#<yyyy-mm>`) and a record of the `Idempotency-Key` in the same transaction; a retry replays. `DELETE` ends the comp the same way. Reading one team's record is audited too (`ops.team.read`), and so is listing or searching teams (`ops.teams.list`, in `OPAUDIT#PLATFORM`, with the search and the teams returned), since the list shows owners' emails. The list is paged in team ID order (the index's order), and each request reads at most 1,000 teams from the index (`MAX_OPS_TEAMS_READ`) and looks up the owners of the teams it returns 10 at a time, however many teams there are (`supply-checkout-6uw.8`). So a search can return fewer teams than its page size, even none, with a cursor: follow it until there's none. A search for a team ID finds that team directly, on the first page. A closed team can't be comped (409); the check reads the index, which lags a close by a moment, and a comp in that window only sets comp attributes on a team that stays closed. When the purge deletes a team, its `META` and `MEMBER#` items leave GSI3 with it; its operator audit stays for its 2 years. While a comp is live, the team counts as paying for the member cap, keeps getting live updates even if its Stripe status has ended, and `/me` shows it (`liveComp` in `backend/src/data/model.ts`). Audit items expire after 2 years. Owners read their team's operator audit at `GET /teams/{teamId}/support-actions`, attributed to "Supply Checkout support": the data-access role may `Query` its team's `OPAUDIT#` partition only for `OWNER_OPERATOR_AUDIT_ATTRIBUTES`, which don't include the operator's `sub`. The ops function logs one line per request with the route, team ID, operator `sub` and status, never emails or tokens.

**The CLI.** `npm run ops` (`scripts/ops.mjs`) is the operators' client until the ops page (`supply-checkout-8jc.8`):

```bash
npm run ops -- reopen <teamId> --reason "Owner disputes the closure"
npm run ops -- audit --team <teamId>           # or --month 2026-09 for everyone's

```

The first command opens `ops-auth.<env domain>` in the browser (username, password, TOTP) and takes the redirect on `http://localhost:8765/`, listening on the loopback addresses only. It keeps only the access token, for its 15 minutes, in `~/.config/supply-checkout/ops-<env>.json` (mode 600); no refresh token is stored. The ops client ID comes from `--client-id`, `SUPPLY_OPS_CLIENT_ID`, or SSM with the AWS CLI (`--profile`, default `supply-prod`). `--env staging` points it at another environment, `--json` prints the API's answers. `comp` reads the team first and sends its `version` with a new `Idempotency-Key`, so a comp never overwrites a change it didn't see.

**The alerts.** The primary region's `observability` stack has fourteen EventBridge rules on CloudTrail's management events that send the P1 topic a message naming the CloudTrail event, not the person. Each operator rule has a fixed name, `supply-checkout-<env>-operator-<suffix>` (`OPERATOR_RULE_SUFFIXES` in `lib/stacks/observability-stack.ts`). EventBridge allows an event pattern 2,048 characters (the "Event pattern size" quota; the `PutRule` API's own 4,096 isn't the limit that applies), so the calls are spread over rules small enough to stay well inside it, and `test/observability.test.ts` checks every pattern in every stack with each name or ARN as long as a real one (`supply-checkout-pbp.17`):

- `OperatorPoolChanges`: calls on the operator pool, in two lists in `lib/stacks/observability-stack.ts`. `OPERATOR_USER_EVENTS` change who is an operator or how they sign in (`AdminCreateUser`, `AdminDeleteUser`, `AdminAddUserToGroup`, `AdminRemoveUserFromGroup`, `AdminSetUserPassword`, `AdminResetUserPassword`, `AdminEnableUser`, `AdminSetUserMFAPreference`, `AdminUpdateUserAttributes`, `AdminLinkProviderForUser`) and always alert, even when CloudFormation makes them, so a deploy can't add an operator silently. `OPERATOR_POOL_CONFIG_EVENTS` configure the pool, its client, domain, groups and identity providers (`CreateGroup`, `UpdateGroup`, `DeleteGroup`, `UpdateUserPool`, `SetUserPoolMfaConfig`, `CreateUserPoolClient`, `UpdateUserPoolClient`, `DeleteUserPoolClient`, `UpdateUserPoolDomain`, `DeleteUserPoolDomain`, `CreateIdentityProvider`, `UpdateIdentityProvider`, `DeleteIdentityProvider`) and alert unless CloudFormation made them for a deploy. Deleting or changing the ops client or domain locks every operator out; identity provider changes are watched so one can't be added and repointed unseen (the ops client supports only `COGNITO`, so they aren't themselves a lockout) (`supply-checkout-6uw.19`). Unlike the other rules, its state is `ENABLED_WITH_ALL_CLOUDTRAIL_MANAGEMENT_EVENTS` (`OPERATOR_POOL_RULE_STATE`), in case EventBridge counts some of these calls as read-only (see "Why group changes have their own watch" below). `OPERATOR_LOCKOUT_EVENTS` (`AdminDisableUser`, `AdminUserGlobalSignOut`) lock an operator out without deleting them, and alert unless CloudFormation made them (no template does). Deleting, disabling or signing out every operator would lock responders out, so each alerts (`supply-checkout-6uw.16`); the operator group watch also sees a deletion or a disable within 5 minutes.
- `OperatorSelfServiceChanges`: what an operator's own token can change: `AssociateSoftwareToken`, `VerifySoftwareToken`, `SetUserMFAPreference`, `UpdateUserAttributes`, `DeleteUser`. CloudTrail records these with the pool ID in `requestParameters` or `additionalEventData`, so the rule matches either.
- `OperatorAuditWatchChanges` (`supply-checkout-6uw.11`): deleting the operator audit watch's event source mapping, or its function or the operator group watch's (`supply-checkout-3sv.5`), or removing a permission from either function (`RemovePermission`, such as EventBridge's permission to invoke the group watch, which would otherwise stop every run with only the P2 silent alarm 15 minutes later: `supply-checkout-3sv.9`), whoever does it; and, outside a deploy, updating the mapping (disabling it or changing its filter), the function's code or configuration, or its concurrency (zero stops it). Lambda's event names carry an API version (`UpdateEventSourceMapping20150331`), so the rule matches them by prefix; the mapping by its UUID (`uUID`), the function by its name or ARN.
- `OperatorAuditWatchRoleChanges`: deleting the watch's role, or its role policies, whoever does it (`DeleteRole`, `DeleteRolePolicy`, `DetachRolePolicy`); and, outside a deploy, changing its policies, trust policy or permissions boundary. The same for the operator group watch's role (`supply-checkout-3sv.5`), and, outside a deploy, `CreateFunction` or `UpdateFunctionConfiguration` giving any function that role (matched by prefix for Lambda's versioned event names). `requestParameters.role` matches the role's ARN exactly, or any ARN ending in `:role/` and then anything ending in the role's name (`supply-checkout-3sv.9`), in case CloudTrail records the ARN spelled differently from the template's. That wildcard also matches another role whose name ends in this one, which only over-alerts. EventBridge can't match a wildcard and ignore case at once, so an ARN with the name in another case wouldn't match. The drill below confirms what CloudTrail records in `requestParameters.role`.
- `OperatorAuditWatchLogChanges`: the watch's log group. `DeleteLogGroup` on it whoever calls it (its role can't recreate the group, and its metrics are embedded in its log lines, so nothing would arrive); `PutTransformer`, `DeleteTransformer` or `PutDataProtectionPolicy` on that group outside a deploy (a transformer could strip the metric from its lines); and `PutAccountPolicy` for a `TRANSFORMER_POLICY` or `DATA_PROTECTION_POLICY`, which reach every log group, whoever calls it (this app never makes one).
- `OperatorAuditWatchTableChanges`: the rest of the watch's data path. `PutResourcePolicy` or `DeleteResourcePolicy` on the table or its stream outside a deploy (a Deny on `GetRecords` cuts the watch off without an error); `UpdateTable` on the table outside a deploy, and `UpdateTable` turning its stream off whoever calls it; and `DisableKey` or `ScheduleKeyDeletion` on the table key whoever calls them, and `PutKeyPolicy` on it outside a deploy.
- `OperatorAlarmChanges`: `DisableAlarmActions` or `DeleteAlarms` on the four operator audit alarms whoever calls them, and `PutMetricAlarm` on them outside a deploy.
- `OperatorGroupWatchAlarmChanges` (`supply-checkout-3sv.5`): the same calls on the operator group watch's two alarms, **Operator group changed** and **Operator group watch silent**, in a rule of its own because `OperatorAlarmChanges` has no room left inside the pattern limit.
- `OperatorGroupSnapshotChanges` (`supply-checkout-3sv.5`): `PutParameter`, `DeleteParameter`, `DeleteParameters`, `LabelParameterVersion` or `UnlabelParameterVersion` on the operator group watch's snapshot parameter, by name or ARN, unless the watch's own role (`userIdentity.sessionContext.sessionIssuer.arn`) or CloudFormation made the call. A deploy that changes the parameter doesn't alert here, but the watch's next run pages (below).
- `OperatorAlertRouteChanges`: `DeleteTopic` or `RemovePermission` on either alarm topic whoever calls them, and `SetTopicAttributes` (its policy or key) outside a deploy; `PutDataProtectionPolicy` on either topic whoever calls it (a policy that denies every inbound message makes the topic refuse every publish; CloudTrail names the topic in `resourceArn`, not `topicArn`, and neither topic has one); and `Unsubscribe` or `SetSubscriptionAttributes` on a subscription to either topic outside a deploy.
- `OperatorAlertKeyAndTrailChanges`: `DisableKey` or `ScheduleKeyDeletion` on the topics' key or the [trail's](#the-cloudtrail-trail) key whoever calls them, and `PutKeyPolicy` on either outside a deploy, matched by the key's ARN in the event's `resources` so a call made through an alias still matches (the trail key's ARN comes from the audit stack's SSM parameter); `CreateAlias` or `UpdateAlias` pointing any alias at that key (`targetKeyId`), whoever calls them, since nothing ever makes one for it; and `StopLogging`, `DeleteTrail`, `UpdateTrail`, `PutEventSelectors` or `PutAdvancedEventSelectors` on any trail in the account, the audit stack's included. This one and the one above tell **both** topics (P1 and P2), so deleting or breaking one still reaches the other.
- `OperatorTrailBucketChanges` (`supply-checkout-3sv.4`): on the [trail's](#the-cloudtrail-trail) bucket (by the name the template builds), `DeleteBucket`, `DeleteBucketPolicy` or `DeleteBucketEncryption` whoever calls them, and `PutBucketPolicy`, `PutBucketLifecycle` (CloudTrail's name for `PutBucketLifecycleConfiguration`), `DeleteBucketLifecycle`, `PutBucketVersioning`, `PutBucketEncryption` or `PutBucketLogging` outside a deploy (`TRAIL_BUCKET_EVENTS`); on the trail's key, `CreateGrant` or `DisableKeyRotation` whoever calls them (`TRAIL_KEY_EVENTS`, by the key's ARN in `resources`; nothing here makes either). A one-day lifecycle rule or a policy that denies CloudTrail would otherwise destroy or cut off the log archive with no alert. P1 only: these break the archive, not the alerts. Stronger options, for the owner to decide: Object Lock on the trail bucket, or an organization trail to a log archive account (ADR 0003).
- `OperatorRuleTampering` and `OperatorRuleTamperingWatch`: `DeleteRule`, `DisableRule` or `RemoveTargets` on any rule whose name starts with `supply-checkout-<env>-operator-` (every rule above, these two, and any operator rule added later) or on `DeletionsRuleTampering` (below), whoever calls them (a stack update that drops a rule or its target alerts too, which is intended), and `PutRule` or `PutTargets` on them outside a deploy. Matching the names by prefix keeps their patterns short however many rules there are; it also alerts on a new rule someone makes with that prefix outside a deploy, which nothing should. A rule can't report its own deletion, so there are two, each matching the other's name: whichever is deleted or disabled first, the other alerts.
- `DeletionsRuleTampering` (`supply-checkout-<env>-deletions-rule-tampering`, bead `supply-checkout-72d.17`): the same calls on the deletion records watch's two rules, its S3-event rule and its bucket-changes rule ([backups.md](backups.md#when-the-deletion-records-bucket-is-changed)), by reference. The two above watch it by its fixed name, which isn't under their prefix.

Residual risks, accepted (`supply-checkout-6uw.11`). Each needs the `supply-prod` administrator's rights (or the management account's), and each call is still in CloudTrail:

- **The key.** One KMS key (`AlarmTopics` in `lib/observability/alarm-topics.ts`) encrypts **both** alarm topics, P1 and P2. So `DisableKey`, or a `PutKeyPolicy` that takes away EventBridge's, CloudWatch's or SNS's use of it, breaks P1 and P2 at once: every alarm and alert goes undelivered, including the alert on that very call, which travels through the same key. The alarms still change state in CloudWatch, and the call is in CloudTrail, but nobody is told. `ScheduleKeyDeletion` leaves the key working for its 7 to 30 days, so that alert arrives. A separately keyed path for these alerts (a second key for one topic, or a CloudWatch Logs target with its own alarm) would close this; it isn't built.
- **Both topics at once.** Deleting or unsubscribing everyone from one topic reaches the other; doing both, the first call's alert should go out through the topic still there, but a second call made before EventBridge delivers the first can beat it.
- **CloudTrail itself.** These rules only see calls CloudTrail records, and only while a trail is logging in the account: the audit stack's ([The CloudTrail trail](#the-cloudtrail-trail)). Stopping or deleting it alerts through the rule above (that call itself is recorded), but every rule is blind after that until it's turned back on. Changes to the trail bucket's policy, lifecycle, versioning, encryption or logging, and grants on its key, alert P1 through `OperatorTrailBucketChanges` (above); a policy change that cuts CloudTrail off also shows as a delivery error in `get-trail-status`. An organization trail is managed from the management account (`supply-mgmt`), where nothing here watches; the rule above catches trails in this account only.
- **Deleting the whole stack.** A `DeleteStack` on the observability stack deletes every rule, topic and alarm in one go; the first `DeleteRule` alerts only if the other tampering rule and a topic are still there when EventBridge delivers it.
- **Deploys, including other stacks'.** The `outsideDeploys` calls are exempt when CloudFormation makes them (`userIdentity.invokedBy` is `cloudformation.amazonaws.com`). That's true of a call made through **any** CloudFormation stack, not just this app's: someone who can create a stack could, for example, put a key policy or a table resource policy in a stack of their own and it wouldn't alert. The heartbeat below still catches one that cuts the watch off; one that only breaks alerting (a topic policy) it doesn't.
- **Email unsubscribe links.** Every SNS email has an unsubscribe link, and an email subscription confirmed by clicking the link in AWS's confirmation message can be unsubscribed by anyone holding one of those emails, without signing in. `Unsubscribe` from the link may not be recorded as a normal CloudTrail call, so the rule above may not see it. CDK and CloudFormation can't set `AuthenticateOnUnsubscribe`; to require it, confirm each email subscription with the CLI instead of the link (see "Alarm recipients" in [observability.md](observability.md#alarm-recipients)).
- **What the rules don't list.** `SetAlarmState` (sets an alarm to OK until its next evaluation); purging or deleting the watch's dead-letter queue (it only holds positions of batches already given up on; the dropped-records alarm fires first); the heartbeat schedule (`UpdateSchedule`, `DeleteSchedule`), grants on the table key (`RevokeGrant`, `RetireGrant`), and a log transformer or table change made in a deploy of any stack: each of these stops the heartbeat, so **Operator audit watch silent** (P2) fires within 30 minutes instead of a P1 message at once; and anything a new EventBridge, Lambda, IAM, CloudWatch Logs, DynamoDB, KMS or SNS API adds later.
- **A stronger control, for the owner.** A service control policy in the organization could deny `events:DeleteRule`, `DisableRule`, `RemoveTargets` and `PutRule` on the operator rules, and the watch, topic and key calls above, to everyone but the CloudFormation execution role. SCPs are set in the management account, so that's the owner's decision, outside this repository.

**The operator audit watch.** Operator audit items (`OPAUDIT#`, both the `AUDIT#` entries and the `REQUEST#` idempotency records) are append-only, and nothing in the app changes or deletes one. The primary region's `observability` stack runs `supply-checkout-<env>-operator-audit-watch` (`backend/src/ops/operator-audit-watch-handler.ts`, `lib/observability/operator-audit-watch.ts`) on the table's stream. Its event source mapping passes only `MODIFY` and `REMOVE` records whose partition key starts with `OPAUDIT#`, the `INSERT`s below and its own heartbeat item, so it never sees team data, and its role can read the stream and nothing in the table. Each change counts in `OperatorAuditChanged` unless it's a TTL expiry: a `REMOVE` by DynamoDB's TTL process, or of an item whose `expiresAt` had already passed (another replica's TTL deletion can arrive without the TTL identity; making a live item look expired takes a `MODIFY`, which counts). It also reads `INSERT`s of `AUDIT#` entries (never the `REQUEST#` records, which live 24 hours by design) and counts one whose `expiresAt` is more than 7 days short of 2 years after the write (`SHORT_RETENTION_SLACK_DAYS`): the TTL would delete it early as an "expiry", which a `REMOVE` alone can't tell apart. **Operator audit changed** (P1) fires on any in 5 minutes, and **Operator audit watch failing** (P2) when the function throws. After five retries the mapping gives the batch up and records its shard and sequence numbers (never the items) in the watch's dead-letter queue, and **Operator audit watch dropped records** (P2) fires: read the message, then the records from the stream while they're still there (24 hours) or compare the audit with point-in-time recovery for that time. The log line has the item's keys, the event name and the stream event ID, never its attributes. It's the stream's second consumer, after the live-update publisher; DynamoDB advises no more than two per shard, so a third needs a fan-out.

**The heartbeat** (`supply-checkout-6uw.11`). Every alarm above needs the watch to read the stream and its metrics to reach CloudWatch, and many things stop that without an error: a disabled mapping, zero concurrency, a stream or key policy, the stream turned off, a deleted or transformed log group. So an EventBridge Scheduler schedule rewrites one item, `OPWATCH#HEARTBEAT` / `HEARTBEAT` (`OPERATOR_AUDIT_HEARTBEAT` in `backend/src/data/schema.ts`), every 10 minutes with DynamoDB's `PutItem` directly, no function; the item holds only its keys and `at`, the scheduled time. Its role may `PutItem` only that partition, naming only those three attributes, and use the table key through DynamoDB. The watch counts each write of it in `OperatorAuditWatchHeartbeat`, and **Operator audit watch silent** (P2) fires when none arrives in 30 minutes (missing data breaches). An alarm on the mapping's `IteratorAge` was the other choice, but Lambda sends it only when it invokes the function, and the filter means it's rarely invoked, so a stalled read would look like a quiet night. If it fires: check the mapping is enabled (`aws lambda get-event-source-mapping`), the function's concurrency, its log group exists (if it was deleted, recreate it with the same name and retention: the role can only write to it, and a redeploy doesn't recreate it) and has no transformer (`aws logs get-transformer`), the table's stream is on and has no resource policy (`aws dynamodb get-resource-policy`), the table key is enabled with its policy as deployed, and the schedule is enabled; then look for the CloudTrail event that changed it.

**Why group changes have their own watch** (`supply-checkout-3sv.5`). In the 2026-09-27 drill, after the trail started logging (21:29 ET), the owner added a test operator (`AdminCreateUser` 21:30:35, `AdminAddUserToGroup` 21:30:36), then removed it (`AdminRemoveUserFromGroup` 21:33:40, `AdminDisableUser`, `AdminUserGlobalSignOut`, `AdminDeleteUser` 21:33:43). Only `AdminCreateUser` alerted. What was checked, read-only:

- All six calls are in the trail's S3 log files (the create, the add and the remove in the same file), and in `lookup-events`. The trail logs all management events, read and write, with no advanced selectors.
- CloudTrail classifies all six the same way: `eventType` `AwsApiCall`, `readOnly: false`, `managementEvent: true`, `eventCategory` `Management`, `eventSource` `cognito-idp.amazonaws.com`, `awsRegion` `us-east-1`, the same caller (an SSO role session, `userIdentity.type` `AssumedRole`, no `invokedBy`), the same user agent apart from the command, and `requestParameters.userPoolId` set to the operator pool's ID in plain text (only `username` and `userAttributes` are `HIDDEN_DUE_TO_SECURITY_REASONS`). Apart from the event name and request fields, the add differs from the create only in `responseElements`, which is `null`.
- The deployed rule's pattern (`aws events describe-rule`, last changed by a deploy hours before) matches the create, the add and the remove, tested with `aws events test-event-pattern` on each record from S3 wrapped as EventBridge wraps it. `AdminDeleteUser` didn't match: it wasn't in the pattern then (it is since `supply-checkout-6uw.16`, with `AdminDisableUser` and `AdminUserGlobalSignOut`).
- The rule's `MatchedEvents`, `TriggeredRules` and `Invocations` were 1 each, all in the 21:30 minute, with no `FailedInvocations`; account-wide, no other rule matched anything in 21:30–21:35 but the scheduled checks. So the add and the remove never reached the rule: EventBridge didn't match them, or never got them.
- AWS documents no exception. EventBridge's reference for Cognito user pools says CloudTrail sends its events to EventBridge ([Amazon Cognito user pools events](https://docs.aws.amazon.com/eventbridge/latest/ref/events-ref-cognito-idp.html)), once a trail is logging them ([AWS service events delivered via AWS CloudTrail](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-service-event-cloudtrail.html)); Cognito logs every user pool API action as a management event ([Amazon Cognito logging in AWS CloudTrail](https://docs.aws.amazon.com/cognito/latest/developerguide/logging-using-cloudtrail.html)). EventBridge's list of read-only events that don't start with `Describe`, `Get` or `List` names only Cognito's `AdminGetDevice`, `AdminGetUser`, `AdminListDevices`, `AdminListGroupsForUser`, `AdminListUserAuthEvents`, `IntrospectToken` and some managed login pages ([Management events generated by AWS services](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-service-management-event-list.html)). Delivery from CloudTrail is best effort, and that's all AWS says.

So the cause is on AWS's side of CloudTrail and EventBridge and isn't confirmed: the best explanation is that these Cognito calls don't reach the default bus, or reach it classed as read-only, which a rule in the default `ENABLED` state doesn't match. The owner's diagnostic below tells the two apart. Either way, an alert on who is an operator can't rest on it, so:

- `OperatorPoolChanges` now matches read-only management events too (above). If the diagnostic shows the group calls arriving classed as read-only, that alone fixes the rule.
- **The operator group watch** (`lib/observability/operator-group-watch.ts`, `backend/src/ops/operator-group-watch-handler.ts`) doesn't use CloudTrail at all. Every 5 minutes (`GROUP_WATCH_EVERY_MINUTES`), `supply-checkout-<env>-operator-group-watch` lists the `operators` group (`ListUsersInGroup`) and compares each member's `sub` and enabled flag with what it saved last in the SSM parameter `/supply-checkout/<env>/observability/operator-group-snapshot`. A snapshot it has to start again, whether it finds the deploy's initial value `none` or one it can't read (including an empty value), is logged as an error, counts in `OperatorGroupBaselineReset` and fires **Operator group changed** too, since a reset can't be told from someone putting the parameter back to hide a change. So the first deploy pages once, 5 to 10 minutes after it, and so does every deploy that changes the parameter's properties (CloudFormation writes `none` again); a deploy that leaves the parameter alone doesn't. It writes the parameter only when something changed, after counting, so a failed write alerts again at the next run. Every run that finishes sends the group's size, `OperatorGroupMembers`, and **Operator group watch silent** (P2) fires when none arrives in 15 minutes (three runs; missing data breaches). Its schedule rule is `supply-checkout-<env>-operator-group-watch`, under the operator prefix, so disabling, deleting or retargeting it alerts through the rule-tampering rules. Both alarms are on the dashboard, and both metrics in its last row.
- The watch is under the tampering rules like the audit watch: its function (`OperatorAuditWatchChanges`), role (`OperatorAuditWatchRoleChanges`) and log group (`OperatorAuditWatchLogChanges`) alert when deleted, or changed outside a deploy; its alarms through `OperatorGroupWatchAlarmChanges`; its parameter through `OperatorGroupSnapshotChanges`; its schedule rule through the rule-tampering rules.
- What the watch doesn't see: an operator added and removed again between two runs (the calls are still in CloudTrail, and `OperatorPoolChanges` may still alert on them); a `PutParameter` made from the watch's own function (changing its code or configuration outside a deploy alerts through `OperatorAuditWatchChanges`, but credentials taken from a running copy of it would work until they expire; another function with its role is refused by the `lambda:SourceFunctionArn` condition, and giving one the role alerts) or through a CloudFormation stack (any stack's, like the other `outsideDeploys` exemptions; the watch then pages on the reset if it's `none`, but not if the stack wrote a real-looking snapshot); and anything the rules' own gaps above leave open (a deploy of any stack changing its function, role or log group).

### Backfills

One-off migrations for items written before a change, in `backend/src/data/backfill.ts`, run with `npm run backfill` from `backend/` (`backend/scripts/backfill.ts`). They run with your SSO credentials, not a Lambda role: no Lambda may `Scan` the table, and `index.ts` doesn't export them. Each mode scans the whole table (strongly consistent), is a dry run unless given `--apply`, prints counts only (never emails, names or user IDs), and conditions every write so it never overwrites a newer value and never re-creates an item the purge deleted in the meantime. Each is idempotent: run it again and it finds nothing. Two guards against pointing it at the wrong place: `--table` must be an app table's name (`supply-checkout-<env>-app`), and `--profile` is required. Before it reads or writes anything, it asks STS which account the profile signs in to and prints it in its first line (`members on supply-checkout-prod-app in us-east-1 in account <account ID> (profile supply-prod)`): check it's the account you mean before you run it with `--apply`. With `--endpoint` (DynamoDB Local), it needs no profile and takes any table name. If one stops partway (a throttle, an expired session), run it again.

| Mode | What it changes | Why |
| --- | --- | --- |
| `stray-ops-keys` | Removes `GSI3PK` and `GSI3SK` from items that shouldn't have them, or have other values than they should, on the condition that they're still the values it read (and, for a member, that they haven't been made an owner since). | Nothing customer-written may reach the operators' index (above). |
| `ops-index` | Sets GSI3 keys on every team `META` item and owner `MEMBER#` item without them, on the condition that they're still absent (and that the member is still an owner). Closed teams too: they stay in the index until the purge deletes them, as a team made today does. | Teams made before PR #99 aren't in the ops team list. |
| `members` | Sets the `members` count on every team `META` item without one, from a strongly consistent count of its `MEMBER#` items, on the condition that it's still absent. A membership change that commits after the count sets the count itself (`teamCounts`), so the backfill's write fails and it leaves that team alone. | Teams made before PR #93 have no count, so the join-during-deletion guard (PR #103) can't protect them until their next membership change. |

Run them after the deploy that adds GSI3 is `ACTIVE`, in this order (`ops-index` after `stray-ops-keys`, so a team whose keys were wrong gets them back correctly), each as a dry run first:

```bash
aws sso login --profile supply-prod
cd backend && npm ci
B="--table supply-checkout-prod-app --region us-east-1 --profile supply-prod"
npm run backfill -- stray-ops-keys $B            # dry run: expect 0; check the account in the first line
npm run backfill -- stray-ops-keys $B --apply    # only if it found some, after looking at them
npm run backfill -- ops-index $B                 # dry run: team META and owner MEMBER items without keys
npm run backfill -- ops-index $B --apply
npm run backfill -- members $B                   # dry run: teams without a count
npm run backfill -- members $B --apply
npm run backfill -- ops-index $B && npm run backfill -- members $B   # both find 0
npm run ops -- teams                             # every team is listed
```

A line such as `changed by something else first, left alone: 1` is a race the condition caught (a membership change, a promotion, a purge): the item already has a current value, or no longer exists. `keys that aren't valid IDs, left alone` shouldn't happen; such an item is worth a look. The tests (`backend/test/backfill.test.ts`) run every mode, its races and the CLI against DynamoDB Local.

The role's IAM conditions (`dynamodb:Attributes`, `dynamodb:Select`, `dynamodb:LeadingKeys` patterns) aren't enforced by DynamoDB Local, so after the first deploy, and after any change to the role or to `backend/src/data/operator.ts`, list teams, read a test team, comp it and end the comp, and confirm `/aws/lambda/<ops function>` logs no `AccessDeniedException`.

It prints what the operator does next. Then run `npm run operators -- list` and check it shows them with `no TOTP`. By hand:

3. The operator deletes the old entry from their authenticator app, signs in with the new temporary password, and sets up TOTP again.

**Keys.** The Stripe secret key lives only in Secrets Manager, in each region the api stack runs in: `supply-checkout/<env>/stripe/test-secret-key` for the sandbox and, later, `supply-checkout/<env>/stripe/live-secret-key` (`stripeSecretName` in `backend/src/billing/names.ts`), a plain string or a JSON object with one field holding the key. The owner stores them; nothing in the repo does. Which one an environment uses is `stripeMode` in CDK context (`test` unless `-c stripeMode=live`), and the functions refuse a key of the other mode (`STRIPE_MODE`). A function reads the key the first time it needs Stripe and keeps the client for an hour (`backend/src/billing/stripe.ts`), so a rotated key is picked up without a deploy. Neither the key nor Stripe's error messages are ever logged: only Stripe's error type, code, status and request ID.

**Products and prices.** `backend/src/billing/catalog.ts` is the catalog, **provisional** until the pricing decision (`supply-checkout-akz`): ADR 0009's proposal, Starter at $9 a month including 3 seats then $3 a seat, and annual at 10 months' price. Each plan is one Stripe product with an ID we choose, and one graduated tiered price per interval (a flat amount for the included seats, then per seat; the subscription's quantity is the seat count), found by its **lookup key**. No price ID is written down anywhere: the billing function looks prices up by lookup key and keeps them for 10 minutes. `npm run stripe-catalog` (`backend/scripts/stripe-catalog.ts`) makes Stripe match the catalog. It's idempotent: a product or price that matches is left alone, a product's name or description is updated in place, and a price whose amounts changed (Stripe can't edit those) is replaced by a new one that takes over the lookup key, with the old one archived. So running it twice leaves one product per plan and one price per plan and interval. Without `--apply` it's a dry run. Without `--live` it reads the test secret and refuses anything but a test-mode key; with `--live` it reads the live secret and refuses anything but a live key.

```bash
aws sso login --profile supply-prod
cd backend && npm ci
npm run stripe-catalog -- --profile supply-prod --region us-east-1            # dry run: what would change in the sandbox
npm run stripe-catalog -- --profile supply-prod --region us-east-1 --apply    # make the sandbox match
# Live mode, once the live key is stored (supply-checkout-dri) and the prices are final (akz):
npm run stripe-catalog -- --profile supply-prod --region us-east-1 --live           # dry run against the live account
npm run stripe-catalog -- --profile supply-prod --region us-east-1 --live --apply
```

After changing the catalog, run it before deploying code that sells the new prices, or checkouts fail with a price the billing function can't find (the Checkout broken alarm).

The same script then makes the **Customer Portal configuration** match `backend/src/billing/portal.ts` (`supply-checkout-121`): one configuration of ours per Stripe mode, found by its metadata (`app: supply-checkout`, `portal: owners`), created if there's none, updated (and reactivated) if its features differ or it names other prices, otherwise left alone; its line in the output is `portal owners`. It lets owners update their card and billing details (name, email for receipts, address, tax ID), see and download invoices, switch the plan's price between the catalog's monthly and annual prices (not the seat count, which follows the team's members, `supply-checkout-l50`; a switch during the free trial keeps the trial, with prorations otherwise), and cancel at the end of the period, with a reason and no refund. The billing function finds the configuration by the same metadata (kept for 10 minutes) and passes it on every session, so the Dashboard's default portal configuration is never used. Without ours, the portal fails with `BillingPortalErrors` (the Billing portal broken alarm): run the script with `--apply` in that mode before deploying, and again whenever the catalog's prices change. A price replaced by a new one is swapped in the portal by the same run.

**Checkout.** `POST /teams/{teamId}/billing/checkout` ([openapi.yaml](api/openapi.yaml)) is served by the `billing` function (`backend/src/api/billing-handler.ts`), in every region. Owners only (checked before the body is read or Stripe is called). The body is only the plan and interval: the seat count is the server's, so a team with viewers isn't billed for them and its first invoice isn't prorated down by the seat sync right after Checkout. It makes the team's Stripe customer the first time (named after the team, `metadata.teamId`) and links it to the team (`linkStripeCustomer`: the `STRIPE#<customerId>` link and the team's `stripeCustomerId`, in one transaction, so a customer can never move to another team), then creates a Checkout Session in subscription mode for that customer, which requires a billing address and lets a business add its name and tax ID (`billing_address_collection: required`, `tax_id_collection`; Stripe saves them on the customer and prints them on every invoice): the plan's price, `quantity` = the team's billed members as they are now (`countBilledMembers`, at least 1; `supply-checkout-8jc.20`), `client_reference_id` and `metadata.teamId` the team. A team with at least two days of its free trial left keeps it: the subscription's `trial_end` is the team's `trialEndsAt`, Checkout asks for no card (`payment_method_collection: if_required`), and if no card is added by then Stripe cancels the subscription (`trial_settings.end_behavior.missing_payment_method: cancel`). Otherwise Checkout asks for a card. A closed team (403 `team_closed`) or one whose subscription hasn't ended (409 `already_subscribed`) can't start a checkout. Every Stripe create has an idempotency key (the customer's from the team and its name; the session's from the request's `Idempotency-Key`, the customer, the price, the seats and the trial end), so a retry answers the same page. Nothing about the team's plan, seats or status changes here: the webhook (`supply-checkout-2kl`) applies what Stripe records, and the billing worker then keeps the subscription's quantity at the team's billed members (Seats, below), which is where Checkout started it unless someone joined or left in between. A failure on our side or Stripe's counts `CheckoutSessionErrors` (the Checkout broken alarm).

**Customer Portal** (`supply-checkout-121`). `POST /teams/{teamId}/billing/portal` ([openapi.yaml](api/openapi.yaml)) is served by the same `billing` function, in every region. Owners only, checked first (`authorizeTeam` on the path's team, then `requireRole`), exactly as for Checkout: the team comes only from the path and the caller's membership in it, read on a billing-access role session tagged with that team, and the customer only from that team's `META` item (`stripeCustomerId`, which only `linkStripeCustomer` writes, together with the `STRIPE#` link, so a customer can never belong to two teams). The body must be empty or `{}`: nothing in the request reaches Stripe. The session is made for that customer with our portal configuration and `return_url` `https://app.<env domain>/?billing=portal&team=<teamId>` (`APP_URL`, set by the stack, never from a request header). A closed team is 403 `team_closed`; a team with no Stripe customer yet (no checkout started) is 409 `no_billing_account`; a team whose subscription ended can still open it, for its invoices and card. It reads the team and writes nothing: no new IAM, since the function's own role already reads the Stripe secret key, and the billing-access role's `GetItem` in `TEAM#<teamId>` covers the reads. Logged: `Billing portal opened` with the team ID; a failure logs `Billing portal failed` with Stripe's error fields only, and counts `BillingPortalErrors`. `GET /me` gives each team `billingAccount` (it has a Stripe customer, so the web app shows owners **Billing** in the team bar) and `cancelsAt` (the end of the period a canceled subscription still runs to; the team bar says so to everyone). What an owner changes in the portal comes back through the webhook: `customer.subscription.updated` records a switch of price (plan and interval), a new card, or a cancellation (`cancelAtPeriodEnd`, set from Stripe's `cancel_at_period_end`, or a `cancel_at` date), and `customer.subscription.deleted` ends it at the period's end, turning the team read-only and emailing its owners, all within a minute. The trial-ending and payment-failed emails send owners to the app, where Billing is how they add or fix a card. Both routes need two-step sign-in (Sign-in, above): an owner without it gets 403 `mfa_required`, and the app opens the setup.

**Webhook, queue and worker** (`supply-checkout-2kl`). `POST /billing/webhook` is Stripe's endpoint, in every region, with no authorizer: the `billing-webhook` function (`backend/src/billing/webhook-handler.ts`) checks the `Stripe-Signature` header against the endpoint's signing secret (5-minute tolerance), puts the event on the billing queue, and only then answers 200. A bad or missing signature is 400 and counts `WebhookSignatureFailures` (the Webhook signature failures alarm); a queue that won't take the event is 500, so Stripe retries. Events we don't handle, and events from the other Stripe mode, are answered 200 and dropped. The message holds only IDs, the event's type and time, and the statuses and dates the owner emails need, never a name, email or address. The queue (`supply-checkout-<env>-billing-events.fifo`) is FIFO, grouped by Stripe customer (one team, one customer) and deduplicated by event ID; a message that fails 5 times goes to `supply-checkout-<env>-billing-events-dlq.fifo` (the Billing events stuck alarm, P1; Billing events late, P2, when the oldest message is over 5 minutes old). The `billing-worker` function (`backend/src/billing/worker.ts`) takes one event at a time: it skips an event already recorded, finds the team from our own `STRIPE#` link (never from the event), fetches the subscription's latest state from Stripe and applies it to the team's `META` item (`plan`, `seats`, `status`, `billingInterval`, `currentPeriodEnd`, `cancelAtPeriodEnd`, `stripeSubscriptionId`) with `applySubscription`, emails owners when that's called for, and only then records the event (`WEBHOOK#<eventId>`, kept 30 days). Replaying an event changes nothing. The write is conditioned on the item existing (a purged team is never recreated), on no `closedAt` and no `purging` (a closed team changes no more; see "Closing a subscribed team" below for its subscription), on the customer being the team's, and on the subscription being the team's, or the new one when the team's has ended. A second live subscription for a team that has one (two Checkout pages finished before the first webhook) isn't applied: the worker cancels it at once, and logs it (a second one that was already paid needs a refund by hand). Checkout also refuses a team whose customer has a live subscription the webhook hasn't recorded yet.

**Invoices** (`supply-checkout-eja`). Stripe makes, emails and keeps the invoices; the app only lists them. `GET /teams/{teamId}/billing/invoices` ([openapi.yaml](api/openapi.yaml)) is served by the same `billing` function, with exactly the portal's checks (owners only, two-step sign-in, `team_closed`, `no_billing_account`) and for the same customer, the one on the path's team's `META` item: it lists that customer's latest 24 invoices from Stripe (`invoices.list`, newest first), so the list is always Stripe's. Drafts are left out (Stripe hasn't sent them); `hasMore` says older ones are in the Customer Portal. Each has its number, status, date, amounts and currency, and links to Stripe's hosted invoice page and PDF, passed on only if they're `https` pages on `stripe.com`. Nothing from the request reaches Stripe, it writes nothing, and it needs no new IAM (the same `GetItem`s as the portal, and the Stripe key the function already reads). Logged: `Invoices listed` with the team ID and the count; a failure logs `Invoices failed` with Stripe's error fields only and counts `InvoiceListErrors` (on the dashboard's billing errors graph, with no alarm: the portal lists invoices too). The billing details on an invoice (the billing name, address, and a business's tax ID) are the customer's: Checkout collects them, and owners change them in the portal (name, email for receipts, address, tax ID).

**Invoice and receipt emails.** Stripe sends them, not us: there's no second email path. They're account settings in the Stripe Dashboard, not something the API or the catalog script sets, so the owner turns them on once per mode (the sandbox emails only addresses on the Stripe account's own team, so test with one of those): in Settings, **Customer emails**, "Successful payments" (receipts); in Settings, **Billing, Subscriptions and emails**, "Send finalized invoices and credit notes to customers" (with links to the hosted page and PDF), and the renewal and failed-payment reminders as wanted. The address is the customer's email, which Checkout saves on the customer the first time (the customer is made without one) and the owner changes in the portal. The invoice's header and footer come from **Settings, Business, Public details** (the business name, address and support email) and **Billing, Invoice template**: fill those in before going live.

**Closing a subscribed team** (`supply-checkout-t0en`, `backend/src/billing/closing.ts`). Closing a team never calls Stripe: the closure is one DynamoDB transaction, so a Stripe outage can't refuse a closure or leave it half done, and the closed team itself is the pending cancellation. The hourly closed-team purge carries it out: at the start of each run it lists every closed team (GSI1's `TEAMS#CLOSED` partition) that has a `stripeSubscriptionId` and no `stripeCancelledFor` equal to its `closedAt`, re-reads each one (consistent), fetches the subscription from Stripe, ends it, and then records `stripeCancelledFor = closedAt` on the `META` item, conditioned on the same `purgeAfter` (still this closure). Ending it means `cancel_at_period_end` for a `trialing`, `active` or `past_due` subscription (nothing more is charged, and a trial ends at its trial end uncharged), cancelling at once one that's `unpaid`, `paused` or `incomplete` (nothing is being paid for), and nothing for one that's ended or already set to cancel, or that Stripe no longer has (logged as a warning). Each Stripe call has an idempotency key hashed from the action, the team, `closedAt` and the subscription, so a retry sends the same request; a team reopened and closed again is a new closure with new keys. A team that fails (Stripe down, say) isn't recorded, is tried again the next hour, and makes the run throw, which the Functions failing alarm sees; the run still purges and still sends its gauge. The subscriptions part starts no new team after half the run's 4-minute budget. So a closed team's subscription is set to cancel within about an hour of the closure: a renewal or trial conversion in that hour is charged. The purge logs it (`Closed team's subscription renewed after it closed`) and counts it in `ClosedTeamRenewalsCharged`, and the "Closed team charged" alarm fires, so the invoice gets refunded by hand. The window isn't closed by ending the subscription at close time, because a reopen doesn't resume a subscription yet (`supply-checkout-85qp`): the purge's hour is what lets a team closed by mistake be reopened with its subscription untouched. The billing worker also ends a live subscription on a closed team when an event for it arrives (a checkout that finished just after the team closed, whose subscription the team never recorded), with the same keys; it never writes to a closed team. A team reopened while the purge or the worker was calling Stripe is logged as an error (`Team reopened while its subscription was being ended`), counted in `ReopenedTeamSubscriptionsEnded` (the "Reopened team's subscription ended" alarm), and fails the run or the event: its subscription is set to cancel and needs resuming (`supply-checkout-85qp`). The purge finds it when recording `stripeCancelledFor` fails its condition; the worker, after any change it asked Stripe for, re-reads the team (consistent, the same `GetItem` on `META` it already makes) and finds it open, or closed again with another `closedAt`. A team purged meanwhile is fine: deleting its customer ends the subscription anyway. When the purge deletes a team, it first deletes the team's Stripe customer (`customers.del`: its name, email, address and saved cards, and any subscription still on it ends at once; Stripe keeps the invoices and payments). A customer already deleted counts as done; any other Stripe failure leaves the whole team for the next run, so its data never goes while its customer stays, and after a day of that "Deletion overdue" alarms. `ClosedTeamSubscriptionsEnded` and `StripeCustomersDeleted` count both. The purge's role may read the one Stripe secret key for the environment and mode (`secretsmanager:GetSecretValue` on its ARN only), and its table grants gained only `stripeSubscriptionId` and `stripeCancelledFor` ([Observability](observability.md)).

**Read-only after a subscription ends.** A team whose `status` is `canceled`, `unpaid` or `incomplete_expired` and that has no live comp is read-only (`isReadOnlyForBilling`): `authorizeTeam` puts it on the context (`subscriptionEnded`) and `writable` refuses a write with `SubscriptionEndedError` (403 `permission_denied`, `reason: "subscription_ended"`), except what a closed team allows (leaving, removing members, revoking invites, closing) and a member keeping their own email current and an owner linking the customer to subscribe again. So a team whose trial ended without a card turns read-only when Stripe cancels its subscription. `GET /me` says so (`subscriptionEnded`), and the web app shows a banner, keeps the app view-only, and gives owners a Subscribe button that starts Checkout (Starter, monthly, a seat per member) and then a link to it. The 7-day grace period for `past_due` and deleting canceled teams are bead `supply-checkout-qdx`.

**Owner emails** (`sendTeamNotice`, the existing `trialEnding`, `paymentFailed` and `readOnly` templates): a trial ending with no card on the subscription (`customer.subscription.trial_will_end`), a failed payment (`invoice.payment_failed`, with the next try), and the subscription ending (`customer.subscription.deleted`, or `.updated` into `canceled`, `unpaid`, `incomplete_expired` or `paused` from another status), unless a comp keeps the team going. Each owner is emailed at most once per event: the worker claims `WEBHOOK#<eventId>` / `NOTICE#<userId>` before sending, so a retried event never emails twice, and an email that fails after the claim is counted (`BillingNoticeFailures`) rather than retried. Closed teams get none.

**Seats** (`supply-checkout-l50`). A subscription's quantity is the team's **billed members**: owners and editors (`contributor`); viewers are free (owner decision, 2026-09-28). That rule is one list, `BILLED_ROLES` in `backend/src/data/seats.ts`. The quantity is just that count (at least 1): the price is graduated, so the plan's included seats are in its flat first tier and nothing here adds or subtracts them. The sync is **asynchronous, through a queue of its own**, so a membership change never waits on Stripe or fails because Stripe is down:

- After a membership change commits (an invite accepted, a role changed, a member removed or leaving, an account deleted, a team reopened), the account function puts a seat sync on the seat sync queue for the team's Stripe customer, taken from the team's own `META` item (`queueSeatSync` in `backend/src/api/account-handler.ts`, `sqsSeatSyncQueue` in `backend/src/billing/seat-queue.ts`). Only for an open team with a Stripe customer. The ops function does the same after an operator reopens a team (`POST /ops/teams/{teamId}/reopen`), reading the customer from the operators' index (`opsTeamStripeCustomer`), since members may have left while it was closed (`supply-checkout-8jc.21`). It's best effort: a sync that couldn't be queued is logged (`Seat sync not queued`, the error's name) and counted (`SeatSyncQueueFailures`), and the membership change or reopen stands.
- The queue (`supply-checkout-<env>-seat-syncs.fifo`, in every region) is FIFO, grouped by the customer, so one team's syncs are handled one at a time, and deduplicated by the message's own ID; a message that fails 5 times goes to `supply-checkout-<env>-seat-syncs-dlq.fifo` (the Seat syncs stuck alarm, P2). The message is `{kind: "seats", id, customer, reason, created}`. It names no team: the worker finds the team from our `STRIPE#` link, as for an event. It's a queue of its own, not the billing queue, so only the webhook ever sends Stripe events: the billing worker reads both, and takes only seat syncs from this one (it knows it by `SEAT_QUEUE_ARN`) and only Stripe events from the other. Ordering with the customer's Stripe events doesn't matter: the quantity is always recomputed, and Stripe's own update event records it.
- The worker (`createSeatSync`) skips a closed, purging or purged team, a team whose own `stripeCustomerId` isn't the message's customer (`not_ours`, logged as `Seat sync skipped: the team has another Stripe customer`), a team with no subscription (a trial that never went through Checkout), a team or subscription that has ended, an `incomplete` subscription, one that isn't the customer's (`not_ours`, logged too), and one that isn't exactly one item on a catalog price. More billed members than a team can have (`MEMBERS_PER_TEAM`, 100) means something is wrong elsewhere: it changes nothing, logs `Seat sync skipped: more billed members than a team can have` with both numbers, and counts `SeatQuantityDrift`, so the Seat counts drifting alarm brings a person (outcome `over_cap`). Otherwise it counts the billed members **as they are when it runs** (a strongly consistent query of the `MEMBER#` items' roles), and if the seat item's quantity differs it calls `subscriptionItems.update` with that quantity and `proration_behavior: create_prorations`. It never adds or subtracts, so two changes that race converge on the same number, and a late or repeated message does no harm. The Stripe idempotency key is `seats-<teamId>-<sha256 of the message ID, the SQS message ID that delivered it, the item, the current quantity and the target>`: a queue retry of the same message has the same SQS message ID and sends the same key, and a retry after Stripe applied the update finds the quantity right and sends nothing. Every new delivery gets a new key, so a message ID used again (the reconciliation's is fixed per customer per day, and a Stripe event can be redelivered) never replays an update Stripe cached earlier and logs `updated` for a change that wasn't made. The seat sync queue's event source mapping runs at most 5 workers at once (`SEAT_SYNC_MAX_CONCURRENCY`), so the nightly fan-out stays near 20 Stripe requests a second, under Stripe's rate limit (25 a second in test mode). A Stripe failure throws, so the message is retried (5 tries, then the seat syncs dead-letter queue). Stripe's `customer.subscription.updated` then records the new `seats` on the team.
- After applying (or re-seeing) any Stripe event about a subscription, the worker runs the same sync, so the quantity chosen at Checkout follows the billed members from the start. It runs after the event is recorded, so a failure there retries only the sync (the event is a duplicate then); but if Stripe stays unreachable for all 5 tries, the event itself lands in the billing dead-letter queue (Billing events stuck) although it was applied. Replaying it is safe.
- **Nightly reconciliation.** `supply-checkout-<env>-seat-reconcile` (`backend/src/ops/seat-reconcile-handler.ts`, primary region, 07:00 UTC) lists the open teams with a Stripe customer, whether or not their subscription has ended, from the operators' index and queues a seat sync with reason `reconcile` on the seat sync queue for each (one message per customer per day, batches of 10). When one finds the quantity wrong the worker counts `SeatQuantityDrift` (the Seat counts drifting alarm), logs `Seat quantity drift` with the team and subscription IDs, the Stripe quantity and the billed members, and fixes it. So a sync that was never queued, went to the dead-letter queue, or a change made outside the account and ops APIs (a restore removing a deleted user, see [backups](backups.md#8-writes-back-on)) is put right within a day, and noticed. It runs in the primary region only, and that's enough once `us-west-2` serves teams too (phase 2, ADR 0010): the table is a global table, so the operators' index lists every region's teams, and their syncs go on the primary region's seat sync queue, whose worker reads the same table and calls Stripe, which has no region. It converges because the quantity is always recomputed, never incremented: a primary-region sync that read a replica a moment behind a `us-west-2` membership change, and landed after that region's own sync, is put right by the team's next sync or the next night's run. The run sends `SeatReconcileTeams` (how many it queued); none for two days is the Seat reconciliation not running alarm. The same message carries the entitlement check, below.
- **Nightly entitlement check** (`supply-checkout-8jc.9`, `backend/src/billing/entitlements.ts`). For each seat sync with reason `reconcile`, the worker first checks the team's billing against Stripe, so a webhook that was lost (Stripe gave up, the endpoint or its secret was wrong) or is sitting in the billing dead-letter queue is put right within a day. No schedule, queue or IAM of its own: it rides on the seat reconciliation's message and the worker's existing Stripe key and `BillingWorkerRole` grants. It finds the team from our `STRIPE#` link (skipping a closed, purging or gone team), retrieves the team's recorded subscription, and when there's none or it has ended, lists the customer's subscriptions (`status: all`, the newest 10) for a live one (not `incomplete`) the team never recorded (a lost checkout or resubscription) that's over an hour old (`UNRECORDED_GRACE_SECONDS`, so one being made as the check runs has time for its own events). It compares Stripe's subscription ID, status, plan and seat quantity with the team's `stripeSubscriptionId`, `status`, `plan` and `seats` (`entitlementDrift`; a price we don't sell leaves the plan alone). Any difference is fixed with `applySubscription`, conditioned (`asRead`) on the team's status, plan, seats and subscription still being what the check read, so an event the worker applied meanwhile is almost never overwritten with older state: that conflict throws, and the retry finds the team in sync. The condition compares those values, not a version, so a change and back (A to B to A) between the read and the write, or a change only to `cancelAtPeriodEnd` or `currentPeriodEnd`, isn't seen; the next event for the subscription, or the next night, corrects it. Once the fix is written it counts `EntitlementDrift` (the Entitlements drifting alarm, P2, primary region) and logs `Entitlement drift` with the team and subscription IDs, the fields, and both sides' subscription ID, status, plan and seats. A recorded subscription, or a customer, Stripe doesn't have (`resource_missing`) is counted and logged (`Entitlement drift: subscription missing in Stripe`, `... customer missing in Stripe`) but changes nothing, and that team's seat sync is skipped, so it doesn't reach the dead-letter queue every night. No owner email is sent for a fix; replaying the lost event does that ([runbook](runbooks/billing-dlq-replay.md)). A seat sync after a membership change never runs the check.

**The Stripe endpoint.** In the sandbox, the event destination `supply-checkout-prod-billing` sends to `https://api.supplycheckout.com/billing/webhook` on API version `2026-08-26.dahlia` (the `stripe` package's), subscribed to exactly: `checkout.session.completed`, `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `customer.subscription.trial_will_end`, `invoice.paid` and `invoice.payment_failed` (`BILLING_EVENTS` in `backend/src/billing/names.ts`). Its signing secret (`whsec_…`) is stored as a plain string at `supply-checkout/prod/stripe/test-webhook-secret` in us-east-1. If the secret is missing or wrong, every webhook fails (500 without it, 400 and the Webhook signature failures alarm with the wrong one), and Stripe retries for 3 days. Another environment, or live mode, needs its own destination and secret (`supply-checkout/<env>/stripe/<mode>-webhook-secret`), subscribed to the same events. Rotating: roll the secret in Stripe and update the stored value; functions pick it up within an hour, so keep Stripe's overlap window at least that long. Adding an event to `BILLING_EVENTS` means adding it to the destination too.

**Testing after a deploy** (sandbox):

1. In the Stripe Dashboard, on the destination, send a test `customer.subscription.updated` event. It should be answered 200, and the billing worker's log should show `Billing event` with outcome `unknown_customer` (the test event's customer isn't ours).
2. In the web app, as the owner of a test team, start a checkout (`POST /teams/{teamId}/billing/checkout`, or the Subscribe button on a read-only team) and finish it with Stripe's test card `4242 4242 4242 4242` or with no card during the trial. Within a minute `GET /me` shows the team's plan `starter` and status `trialing` (or `active` without a trial).
3. As that owner, press **Billing** in the team bar, then Continue to billing: Stripe's Customer Portal opens for the team, with the test card, invoices and "Cancel subscription". Switch to annual, add a card, and cancel. Back in the app (the portal's return link), within a minute the team bar says when the subscription ends (`cancelsAt` on `GET /me`), and "Renew" in the portal clears it. As a contributor of the same team there's no Billing, and `POST /teams/{teamId}/billing/portal` answers 403 `owners_only`.
4. In the Dashboard, cancel that subscription now. The team turns read-only (`subscriptionEnded: true`, the banner in the app), and each owner gets one "is now read-only" email.
5. Seats: on a subscribed test team, invite someone as an editor and accept. Within a minute the billing worker's log shows `Seat sync` with outcome `updated`, and the subscription's quantity in the Dashboard is the team's owners and editors. Change them to viewer: the quantity goes down again, with a proration on the upcoming invoice. Then invoke the reconciliation once by hand (`aws lambda invoke --function-name supply-checkout-<env>-seat-reconcile /dev/null`): its log says how many teams it queued, and the worker's `Entitlement check` and `Seat sync` lines say `in_sync`. To see the entitlement check catch drift, force a mismatch on a test team (Dry run 2 in the [runbook](runbooks/billing-dlq-replay.md)). (Running it once after the first deploy also keeps Seat reconciliation not running from firing before the first night.)
6. Check that the billing and seat sync dead-letter queues are empty, and that no Webhook signature failures, Billing events stuck, Billing events late, Billing portal broken, Seat syncs stuck, Seat counts drifting or Entitlements drifting alarm fired (other than the one forced in step 5).

**IAM.** The billing function's own role can't reach the table. It may `secretsmanager:GetSecretValue` on the one secret for its environment and mode (`arn:…:secret:supply-checkout/<env>/stripe/<mode>-secret-key-??????`, built by `stripeSecretArn` in `infra/lib/config.ts`: Secrets Manager's six random characters and nothing else; it's encrypted with Secrets Manager's AWS managed key, which needs no KMS grant), and assume the **`BillingAccessRole`** with two session tags: `teamId` (the path's team) and `stripeCustomer` (`.` until Stripe has made the team's customer). That role allows `GetItem` in `TEAM#<teamId>` (the membership check and the team), `Query` there on the table only, naming only `PK`, `SK` and `role` (`MEMBER_SEAT_ATTRIBUTES`) with `Select` `SPECIFIC_ATTRIBUTES` required (the billed member count for Checkout's quantity, so it reads no names or emails), `UpdateItem` there naming only `PK`, `SK` and `stripeCustomerId` (`CUSTOMER_LINK_TEAM_ATTRIBUTES`) and returning nothing, and `PutItem` only in `STRIPE#<stripeCustomer>`, naming only the link's attributes (`STRIPE_LINK_ATTRIBUTES`) and returning nothing. No other `Query`, and no `Scan` or `DeleteItem`. The handler tags a customer only with the ID Stripe returned for that team. The update also names `closedAt` (its condition, so a team closed after the membership check isn't linked), and IAM can't limit the sort key, so the grant covers updating those three attributes on any item in `TEAM#<teamId>`: the code only ever updates `META`, on the condition `attribute_exists(PK)`, and a stray `closedAt` could make a team read-only but never put it in the purge's index (`purgeAfter` and the GSI1 keys aren't allowed). No other function may assume the role. `backend/test/billing-api.test.ts` runs the handler against a check that mirrors the role (`backend/test/billing-policy.ts`).

The webhook function may only read its signing secret (`supply-checkout/<env>/stripe/<mode>-webhook-secret-??????`) and `sqs:SendMessage` to the billing queue: no table and no Stripe API key. The worker's own role may read the Stripe secret key, send owner emails (`grantSendEmail`) and assume the **`BillingWorkerRole`**, tagged with the event, its customer and (once the link is read) the team, whose policy allows `GetItem` and `PutItem` in `WEBHOOK#<eventId>` naming only the event records' attributes (`WEBHOOK_RECORD_ATTRIBUTES`), `GetItem` in `STRIPE#<customer>` naming only `teamId`, `GetItem` and `Query` in `TEAM#<teamId>` naming only `BILLING_READ_ATTRIBUTES` (the `META` item's billing, closure and comp fields, and an owner's role and email: never documents), and `UpdateItem` there naming only `BILLING_UPDATE_ATTRIBUTES`, returning nothing. Like the billing function's, the update's attributes include `closedAt` and `purging` (its condition's) but never `purgeAfter` or the GSI1 keys. `backend/test/billing-worker.test.ts` runs the worker behind a mirror of that role, and `backend/test/billing-seats.test.ts` the seat sync, whose billed-member count is a `Query` of `MEMBER#` items naming only `SK` and `role`, inside the same grant.

Seats add the seat sync queue, which the worker reads (its event source mapping's grant), and three senders to it and nothing else: the account function's own role and, in the primary region, the ops function's may `sqs:SendMessage` to it (`QueueSeatSyncs`, with `SEAT_QUEUE_URL`; the ops function reads the team's customer through the operator-access role's GSI3 grant it already has), and the seat reconciliation's role may `sqs:SendMessage` to it (by its name, from the observability stack), `Query` GSI3's `OPS#TEAMS` partition naming only `SEAT_RECONCILE_ATTRIBUTES` (`PK`, `SK`, the GSI3 keys, `stripeCustomerId`, `closedAt`, `status`; `dynamodb:Select` `SPECIFIC_ATTRIBUTES`), and decrypt the table key through DynamoDB. None of them can read a team's partition or the Stripe key, or send to the billing queue. A seat sync can only make the worker recompute a quantity from the team's own members and, for the nightly reconciliation's, re-apply the state Stripe has for the team's own customer (the entitlement check), with the grants it already has.

## Live updates

The `realtime` stack (`lib/stacks/realtime-stack.ts`, [ADR 0006](adr/0006-api-and-realtime-sync.md), [ADR 0016](adr/0016-per-member-live-update-channels.md), `supply-checkout-dpc`, `supply-checkout-4zn`) is an AppSync Events API with one channel per user, `/users/<sub>`, at `realtime.<env domain>`. [docs/api/realtime.md](api/realtime.md) is the client contract: how to connect, the event shape, reconnecting and the polling fallback.

- **Subscribing.** Clients connect and subscribe with their Cognito access token. A Lambda authorizer (`backend/src/realtime/authorizer-handler.ts`) verifies the token (signature, issuer, expiry, the web client, `token_use=access`) and allows a subscription only to exactly `/users/<sub>` for the token's own user. It reads no data and has no table or KMS access. Nothing is cached. Publishing takes IAM, and only the stream consumer's role may, on the `users` namespace.
- **Publishing.** A consumer (`backend/src/realtime/publisher-handler.ts`) reads the table's stream, filtered to `PRODUCT#` and `SHEET#` items (the changes) and to `META` and `MEMBER#` items (who gets them), and publishes `{teamId, collection, id, op, version}` for each document write to the channel of each current member of the team, with no document data: clients fetch through the data API, which checks membership on every request.
- **Cutting off removed members, and canceled and closed teams.** The consumer reads a team's members, billing status and closure with `liveUpdateRecipients` and caches them for 30 seconds, forgetting them as soon as the stream shows a `META` or `MEMBER#` write for that team. So a removed member, or every member of a team whose status is `canceled`, `unpaid` or `incomplete_expired`, stops getting notices at once in practice and within 30 seconds at worst. Its table permission is `GetItem` and `Query` on `TEAM#*` partitions for `LIVE_AUDIENCE_ATTRIBUTES` only (`PK`, `SK`, `userId`, `role`, `status`, `closedAt`, `compPlan`, `compUntil`; `dynamodb:Attributes`), so it can't read documents or emails through the table. It does see whole items in the stream images it's handed (a `MEMBER#` item has the member's email), and it never logs a record, an image or an event: its logs have team IDs, counts and error messages only (`backend/test/realtime-publisher.test.ts` checks). It reads a team's members again before each chunk of 5 events (from its cache, normally), so the 30-second bound holds however long an invocation runs; a read that takes over 2 seconds fails and is retried with the batch (`AUDIENCE_READ_TIMEOUT_MS`), and each DynamoDB request has a 1-second timeout (`CONSUMER_DB_REQUEST_TIMEOUT_MS`). A batch with more than 10 changes to one team's collection (`COLLECTION_EVENT_AFTER`, an import) publishes one "re-list" event for them instead ([docs/api/realtime.md](api/realtime.md#collection-events)). Partial batch failures are retried from the first unsent record; a batch that keeps failing goes to `supply-checkout-<env>-live-updates-dlq`. Batches are 25 records (`STREAM_BATCH_SIZE`), and one invocation makes at most 2,500 publish requests and starts them for at most 5 seconds, each with a 3-second timeout, inside the function's 10 seconds (`PUBLISHES_PER_INVOCATION`, `PUBLISH_BUDGET_MS`, `PUBLISH_TIMEOUT_MS` in `backend/src/realtime/channels.ts`). Past the budget it stops and reports the earliest unfinished record, and Lambda carries on from there, so a big, busy team can't hold up the other teams on its shard for longer than that. Requests go out earliest record first, and the batch's first chunk (the earliest document record's team, up to 5 events) always goes to every member at once, outside the budget and the concurrency limit, so it finishes within one publish timeout and every invocation moves the shard forward by at least one record, however big the team or slow AppSync. A full batch of teams at the member cap (100) fits the budget; a budget stop is logged as a warning, in the `Batch` line's `deferred` and in the `LiveUpdatesDeferred` metric, not counted in `LiveUpdateFailures`. **Retries and budget stops.** A response that reports a record is, to the event source mapping, a failed invocation: AWS retries "up to the retry limit" and doesn't document the count resetting when the checkpoint moves forward (only bisecting a batch is said not to use it), so we assume every budget stop spends one of the mapping's `MaximumRetryAttempts`. That's why it is `STREAM_RETRY_ATTEMPTS` (25, at least `STREAM_BATCH_SIZE`): each stop moves at least one record, so stops alone always drain a batch before its retries run out. Real failures retry that many times too, inside the one-hour maximum record age, then go to the dead-letter queue. Alarms: Live updates failing, delayed, dropped and deferred ([docs/journeys.md](journeys.md)).
- **Regions.** The custom domain is added where its certificate is (`GLOBAL_SERVICES_REGION`). The consumer runs in the primary region, which has the table's stream; the second region's consumer is phase 2.

**Deploying.** The realtime stack reads, from SSM in its region: the table's stream and key ARNs (data stack), the user pool ID and web client ID (identity stack) and the `realtime.` certificate (the domain stack in `GLOBAL_SERVICES_REGION`). Deploy it after those, and before observability. Deploying it deploys the data stack too, so keep `-c backupCopy=false` until that environment has done [step 4 of the backup setup](backups.md#setting-it-up) ([why](#the-cloudtrail-trail)):

```bash
npx cdk diff supply-checkout-staging-us-east-1-realtime --profile <staging profile> -c backupCopy=false
npx cdk deploy supply-checkout-staging-us-east-1-realtime supply-checkout-staging-us-east-1-observability --profile <staging profile> -c backupCopy=false
```

Then measure the 2-second p95 and the reconnect behavior in staging as described in [docs/api/realtime.md](api/realtime.md#measuring-after-a-deploy).

## Template snapshots

`test/stacks.test.ts` snapshots every stack's synthesized template, one file per stack in `test/__snapshots__/<stack name>.json` (for example `supply-checkout-prod-us-east-1-api.json`), so a change to one stack only touches that stack's file. Lambda asset hashes and the function version IDs made from them are masked, because they depend on the checkout's path. When a change to a stack is intended, review the test's diff, then accept it and commit the changed files:

```bash
cd infra
npm run test:update
git diff --stat test/__snapshots__
```
