# Releases

How releases are cut is in the [README](../README.md#releases).

## Deploying a release

A release deploys to prod through `.github/workflows/deploy.yml` ([ADR 0012](adr/0012-cicd-releases-rollbacks.md), beads `supply-checkout-pbp.26`, `pbp.27` and `pbp.28`). It plans first and applies after, so the owner reads the diff before approving any change. From merge to prod:

1. **The release pull request.** release-please keeps `chore(main): release x.y.z` open. GitHub Actions opened it, so CI doesn't start on its own: the release workflow's `release-pr-checks` job starts CI on its branch after each update. It needs the owner's approval to merge, like every bot-opened pull request (`npm run land` prints the `gh pr review <pr> --approve` command). `npm run land` merges it only once `main`'s CI passed on `main`'s head, the commit the release will tag, and then holds a release window: no other PR lands until this release's `Deploy vX.Y.Z` run has completed, or the lead runs `npm run land -- --release-done` (see [Contributing to main](../README.md#contributing-to-main)).
2. **The release.** Merging it makes release-please tag `vX.Y.Z` and publish the GitHub Release. The release workflow re-runs the full CI suite on it (`checks`).
3. **The deploy starts.** Once `checks` passes, the release workflow's `deploy` job runs `gh workflow run deploy.yml --ref main -f tag=vX.Y.Z`. A release or tag that `GITHUB_TOKEN` creates triggers no workflows, but a dispatch does. That job has no AWS access.
4. **`release`** (no credentials) first checks that both deploy environments, `production` and `production-stateful`, are locked down (`scripts/check-environments.mjs`): each exists, administrators can't bypass it, its deployment branches are custom with exactly one policy, `main` (branch), and it has a required reviewer. GitHub creates an environment with no protection the first time a job names one that doesn't exist, and the deploy role trusts both, so this runs before any job names them, dry runs included, and fails the run otherwise. It checks the journey tests' environment too ([The production-journeys environment](#the-production-journeys-environment): `main` only, no admin bypass, no reviewer needed) with `--journeys`, which adds it without `deploy.yml` naming it: `--journeys required` once the journey tests are switched on (the repository variable `JOURNEYS_ENABLED` is `true`), so it must exist; `--journeys if-present` until then, so a missing one passes but one that exists must still be locked down. Then it checks the run is on `main` (every job refuses any other ref: a run dispatched on a tag would use that tag's own copy of the workflow, which could leave these checks out) and checks the tag: it looks like `vX.Y.Z`, has a published GitHub Release, is not a pre-release (a release whose journey tests failed in prod; see [When the journey tests fail](#when-the-journey-tests-fail)) unless the run says **allow-bad-release**, and its commit is on `main` and passed CI in a real run on `main`: a `ci.yml` run for the push to `main` that succeeded, or the release workflow's run for that push whose `checks / CI passed` job succeeded. Every commit on `main` gets its own CI run that nothing cancels ([CI](../README.md#ci)), so the release commit has one. A check run that merely has the right name doesn't count (any workflow with `checks: write` could post one). Anything else stops the run before it asks for approval.
5. **`trust`** (no environment) asks AWS for the deploy role with this job's OIDC token, whose subject has no environment, and passes only if AWS refuses with `Not authorized to perform sts:AssumeRoleWithWebIdentity`. It never prints the call's output if it succeeds; it fails the run instead, because the role's trust is too wide. It needs the repository secret `AWS_DEPLOY_ROLE_ARN` (below); without it, it warns and skips (a dry run fails instead), though `synth` needs the secret too and fails without it.
6. **`build`** (no environment, no `id-token` permission, no AWS access) builds the web app, the demo and the operator page once from the release commit (`npm ci --ignore-scripts`, `npm run build:web`, `npm run build:demo`, `npm run --if-present build:ops`), since the build runs the release commit's vite config, plugins and dependencies; hashes `dist/web`, `dist/demo` and `dist/ops`; and keeps them as the run's `web-build` artifact for 30 days, longer than an approval can wait. A release from before the operator page (v1.9.0 and older, which have no `build:ops`) builds without it, so it still deploys, and `apply` leaves the `ops` channel as it is, with a warning. They hold no configuration (the app's `config.json` and the page's `ops-config.json` are written when they're published) and they're public once live anyway. It restores and saves no cache. CodeQL's untrusted-checkout and cache-poisoning queries flag a job like this; the commit it checks out is the one `release` proved is a released, CI-passed commit on `main`, not pull request code.

   **`synth`** (no environment, no `id-token` permission, no AWS access) synthesizes the stacks from the release commit, since the synth runs the release commit's CDK app, its dependencies (`npm ci --ignore-scripts` in `backend/` and `infra/`) and the Lambda bundling, and keeps the cloud assembly as the run's `cloud-assembly` artifact for 30 days. It synthesizes twice, with the backup copy and with `-c backupCopy=false` (like `scripts/deploy.sh`, until the copy vault's parameter exists), because only `plan` can read which applies, and seals each one's hash (templates, asset manifests and `manifest.json`: `scripts/assembly-hash.sh`; CI checks two synths of a commit match) into the artifact with it, never into a job output or the log: a hash over templates that name the account could be brute-forced back to it, since the source is public and the synth deterministic, and GitHub prints every step's `env` in the log, masking only secrets. The stacks name the account, which an apply job's synth gets from its credentials; this job has none, so it takes the account ID from the repository secret `AWS_DEPLOY_ROLE_ARN` (masked in the log). The account ID isn't secret from the release commit, which deploys into it, but artifacts of a public repository are public, so the uploaded copy has it swapped for a placeholder (`scripts/assembly-pack.sh`), which refuses to pack any other 12-digit number standing alone. The placeholder alone isn't enough: the asset manifests' keys and object keys, each stack's `stackTemplateAssetObjectUrl` and nested templates' names are SHA-256 hashes of templates that held the account, and a 12-digit ID can be brute-forced from one in GPU-hours. So both packed assemblies are **sealed** into one file (`scripts/assembly-seal.mjs`: AES-256-GCM under a key derived with scrypt from the repository secret `DEPLOY_ASSEMBLY_KEY`, passed through the environment, never argv), and the artifact shows neither the account, nor a hash, nor even the file names. The placeholder swap and the 12-digit check stay, in case the key ever leaks. The job checks the secret is set before any release code runs, and fails with an error naming it otherwise. The key hides the assembly from the public, not from the release's code: code in the release (a dependency, its CDK app) runs in this job and could read `DEPLOY_ASSEMBLY_KEY` (through `$GITHUB_ENV` or `BASH_ENV`, say), and the apply jobs hold it after running release code too. It knows the account anyway, but whoever holds the key can open every `cloud-assembly` artifact still kept (30 days) and check guesses against the HMACs in past runs' logs. So after a release you suspect, **rotate the key**: `openssl rand -base64 32 | gh secret set DEPLOY_ASSEMBLY_KEY`. Only the assembly's top-level files go: `cdk diff --method template` reads none of the asset folders. Same CodeQL note as `build`.

7. **`plan`** (in `production`: **approval 1**; it deploys nothing) **runs no code from the release commit** (`supply-checkout-pbp.39`): it checks out only `main`'s own commit (the deploy tooling, `scripts/`, and `infra/` for `main`'s locked CDK CLI and `cdk.json`), so an older release is planned and deployed with today's checks, and installs `main`'s CDK CLI before any credentials exist, without install scripts. It takes only well-formed hashes and artifact IDs from the `synth` and `build` jobs, downloads the `synth` job's sealed assemblies by that ID and opens them with `main`'s `scripts/assembly-seal.mjs` before any credentials exist (GCM's tag must check out first, so a wrong key or a changed byte fails closed, and it takes only folders of plain files), signs in with the deploy role (the role ARN a secret, the account ID masked in the log), checks it's the deploy role, then **drops to CDK's read-only lookup role** (`ReadOnlyAccess`) for the rest. It reads whether the backup copy vault exists, unpacks the matching assembly with this account's ID put back (byte for byte what `synth` wrote, so it must reach the hash sealed with it; that's the plan's hash, and it hands the apply jobs only `HMAC-SHA256(DEPLOY_ASSEMBLY_KEY, hash)` (`assembly-seal.mjs hmac`), as its `hash-hmac` output), and posts each group's `cdk diff --method template` to the job summary, account IDs scrubbed, run with `main`'s `cdk` from a folder holding nothing but the assembly (no `cdk.json`, so no app or plugin of the release's; `--app <folder>` runs no app). Then the **no-replacement check** (`scripts/check-replacements.mjs`): it fails the plan if the stateful stacks' diff replaces, may replace, deletes or orphans a table, user pool or client, KMS key, bucket, hosted zone, log group, backup vault, trail, SES identity or secret, or orphans anything.
8. **Read the plan's summary**, then approve what's next:
   - **`apply-stateful`** (in `production-stateful`: **approval 2**), only if the stateful stacks' diff isn't empty, deploys `domain`, `data`, `identity`, `email`, `backup` and `audit`. It checks out the release commit, installs its dependencies before signing in, synthesizes again with the deploy role's credentials and refuses to deploy unless the template hash is the plan's (it hashes its own synth and compares HMACs under the key in one step, so no raw hash leaves it), diffs and checks for replacements again (prod may have changed since), then deploys. Termination protection stays on.
   - **`apply`** (in `production`: **approval 3**, every release), after `apply-stateful` succeeded or was skipped:
     1. Downloads the `build` job's web build by its artifact ID (so a re-run never picks up another) and refuses it unless it matches that job's hash, before anything deploys. A build that's gone (more than 30 days) stops the job with a message to run the deploy again.
     2. With the same template hash check, deploys the stateless stacks, `web`, `api`, `realtime` and `observability`, if their diff isn't empty (CDK orders them: web before observability). The groups are in `scripts/deploy-stacks.mjs`, shared with `npm run deploy`.
     3. Switches to the web stack's **publisher role** (`supply-checkout-prod-web-publisher`, `infra/lib/web/publisher.ts`). CDK's bootstrap roles can't publish: the file-publishing role writes only to CDK's staging bucket, the deploy role only drives CloudFormation, and the lookup role only reads. The publisher role may read publish-web's parameters, list, read and write the releases bucket under `releases/` (no delete), get and put keys in the live-version store, read the distribution's config, and describe and test the router. Only the GitHub deploy role can assume it.
     4. Notes what's live on each channel (`publish-web.mjs live`), then publishes `app-vX.Y.Z` (with its `config.json`), `demo-vX.Y.Z` and the operator page's `ops-vX.Y.Z` (with its `ops-config.json`, as `npm run publish:ops` writes it; `supply-checkout-8jc.47`) and makes them live (`publish-web.mjs publish --reuse`: a release that's already uploaded, from deploying the same tag again or an older one, is made live again, never uploaded over).
     5. Checks the live routers (`publish-web.mjs check-router`, the check from the qk1.1 outage, which runs the web app's router and the operator page's) and the live sites (`scripts/check-web.mjs`): `https://app.supplycheckout.com/` serves exactly the `index.html` just published, with a Content-Security-Policy and HSTS; its `config.json` has every key; `https://supplycheckout.com/demo/` serves the demo's `index.html`; and `https://ops.supplycheckout.com/` serves the operator page's `index.html` with its strict CSP (`default-src 'none'`), HSTS and `Cache-Control: no-store`, its `ops-config.json` has every key and is `no-store`, and a path it doesn't serve (`/config.json`) is a `no-store` 404. It tries for up to two minutes while the edges pick up the new version.
     6. Runs the **post-deploy checks** (`scripts/smoke-checks.mjs`, below).
     7. If the publish, the router check or the site check fails after publishing started, or the run is cancelled or times out, it **rolls every channel back** (`app`, `demo` and `ops`) to what was live before (a channel with nothing live before is left as it is, with a warning), checks the router again, and fails the deploy. The summary says which channels were rolled back, and says so only when that worked. Each check-web request times out after 15 seconds. A failed post-deploy check doesn't roll the web app back (below).
     8. Ends with a **Deploy summary** in the job summary, whatever happened: each step's outcome (stacks, publish, router, site, post-deploy checks, web rollback) and one line saying what to do next.
9. **`journeys`** (no approval, no environment, no `id-token`, no secrets; `contents: read` and `actions: write` only), only after `apply` succeeded (post-deploy checks included), **dispatches** `.github/workflows/journeys.yml` on `main` (`gh workflow run journeys.yml --ref main -f tag=<tag> -f deploy-run=<run id>-<attempt>`, the way the release workflow starts the deploy) and waits for that run: the customer journeys walked against prod as test accounts in test teams ([Journey tests against prod](testing.md#journey-tests-against-prod), bead `supply-checkout-o60.6`). Until the journey tests are switched on it dispatches nothing, and its summary says they didn't run. The dispatched run is titled `Journeys after deploying <tag> (deploy run <run id>-<attempt>)` (its `run-name`), and the job finds it by that exact title among the workflow's `workflow_dispatch` runs on `main` started by `github-actions[bot]` (as a dispatch with `GITHUB_TOKEN` is), never by taking the latest run (two can start close together), waiting up to 5 minutes for it to appear and refusing if two have the title. It then waits up to 95 minutes for the run to finish (the job's own timeout is 110, and a test keeps the 5 and 95 minutes under it, and the dispatched run's job timeouts under the 95), cancelling it if it doesn't, lists the runs with that title again and refuses unless that run is still the only one, and cancels it too if the job itself is cancelled (`scripts/journeys/workflow.mjs follow` and `cancel`). In the dispatched run, the `check` job (no credentials) checks the inputs' shapes, checks the environment again, checks the deploy run it names is a deploy of `main` still going, and waits for any other run of the journey tests to finish; the `suite` job, which installs its browsers cold (no cache), in `production-journeys`, checks every secret is set, signs in with the journeys role (the account ID masked), runs the suite in desktop Chrome and iPhone Safari, and then, whatever happened, cleans up, writes the summary (every registry step's result per browser) and uploads the traces, videos and report to the private results bucket; the `results` job (no environment, no permissions) uploads the failed steps, only entries shaped like `J4.2 (desktop-chrome)`, as the `journeys-verdict` artifact, the one Actions artifact the run makes, since another run's job outputs can't be read. The deploy's job reads the suite step's outcome from the run's jobs and, on a failure, the failed steps from that artifact, checking each against a fixed shape. The suite failing, or the run not succeeding, fails the deploy. Only `journeys.yml` names the environment, and the deploy passes it nothing but the two inputs.

   **Why a dispatch, not a call** (bead `supply-checkout-o60.15`). Until 1.10.0 the deploy called `journeys.yml` as a reusable workflow (`uses:`) with no `secrets:`. GitHub gives a called workflow's job the secrets of the environment it names only when the caller passes `secrets: inherit` ([actions/runner#4453](https://github.com/actions/runner/issues/4453), [github/docs#44458](https://github.com/github/docs/issues/44458)), so in the 1.10.0 deploy every `JOURNEYS_*` secret was empty, while a run by hand got them all. `secrets: inherit` would also hand `journeys.yml` the deploy's own secrets (`AWS_DEPLOY_ROLE_ARN`, `DEPLOY_ASSEMBLY_KEY`), and a called workflow runs under the calling job's permissions. A dispatched run is a run of its own, on `main`, with the journey tests' environment secrets and nothing of the deploy's. A dispatch made with `GITHUB_TOKEN` does start a run (`workflow_dispatch` is one of the documented exceptions to the rule that `GITHUB_TOKEN` events start no workflows), as the release workflow already relies on. One difference: the dispatched run uses `main`'s head when it starts, not the deploy run's commit of `main`, so a change merged to `tests/prod/` during a deploy is in its run. `scripts/check-deploy-workflow.mjs` refuses any job-level `uses:` or `secrets:` in `deploy.yml`, and `scripts/check-workflow-environments.mjs` refuses a `workflow_call` trigger in `journeys.yml`.
10. **`verdict`** (no environment, no AWS, `contents: write` only) notes the result on the GitHub Release (`scripts/release-verdict.mjs`): on a pass, "Journey tests passed in prod" and the dispatched journeys run's link; on a failure, the failed steps and browsers, and the release becomes a **pre-release**. When the suite didn't run or didn't finish (switched off, a set-up step failed, cancelled, the run not found or not finished in time), the release is left as it is.

**What approving runs.** No job that runs the release commit's code (its dependencies, its CDK app, its build) can request the production OIDC token before an apply approval (`supply-checkout-pbp.39`). `build` and `synth` run it with no environment and no `id-token` permission, and hand on only files (artifacts, by ID) and outputs that must look like a hash or an ID. `plan`, which can request the token and so the deploy role, runs only `main`'s scripts and `main`'s CDK CLI, on those files as data: approving it shows the diff and deploys nothing. Blanking `ACTIONS_ID_TOKEN_REQUEST_*` for the synth step alone, inside a job with the token, wouldn't do: a step reaches the later ones through `$GITHUB_ENV`, `$GITHUB_PATH`, `BASH_ENV` or a process left running. `scripts/check-deploy-workflow.mjs` (in CI) keeps it so: in `deploy.yml`, no job calls another workflow, and a job that can request the token checks out only `main`'s commit, except `apply-stateful` and `apply`, which must come after an apply approval. (`journeys` has no `id-token` permission at all: it only dispatches the journeys workflow.) Approving an apply job runs the release commit's code with the deploy role throughout: its synth and its CDK deploy, and in `apply` the web publish too, which is no escalation, since that job already holds the deploy role (the publisher role is narrower). Deploying the release needs that anyway; the real control is that only a reviewed, released commit on `main`, which passed CI, gets this far, and the approvals decide when, and whether the diff is wanted. Approving an apply job is the approval for everything in it, IAM and security group changes included (`--require-approval never`: CDK doesn't ask). Rejecting it stops there. Each apply job synthesizes again rather than deploying the uploaded assembly (which `synth`, without credentials, made), and a synth that doesn't reach the plan's hash fails; the deploy is to be run again.

**What the split doesn't cover, and how `plan` reads the assembly.** The release's assembly isn't inert to the CDK CLI: `manifest.json` names the files `cdk` reads (a stack's `templateFile`, an asset manifest's `file`, a nested stack's `aws:asset:path`), and its `missing` entries make `cdk` run context lookups (SSM, Cloud Control) with the job's credentials, whose answers could reach the public diff. So before the diff, `scripts/check-assembly.mjs` (`main`'s) refuses any `missing` entry, any artifact that isn't a stack, an asset manifest, the tree or the feature flag report, any file the manifest or a template names that isn't a plain name of a regular file in the folder (nested stacks' templates are checked in turn), any asset with an `executable` source, any control character (a newline, say, or a Unicode bidi control) in the manifest's identifiers, the asset manifests or a template's logical IDs, and any stack that isn't the one it says, in this account and the release's region: its `stackName` (if any) must be its artifact ID, its `environment` `aws://<account>/<region>`, and its roles (`assumeRoleArn`, `cloudFormationExecutionRoleArn`, `lookupRole`), template URL, bootstrap version parameter and every asset destination's role, bucket and region the standard CDK bootstrap ones for `main`'s qualifier, with no external ID or other assume-role options. Its problems quote every name from the assembly as escaped JSON and never name the account. And the diff runs with `--no-lookups`, and is printed with workflow commands stopped (`::stop-commands::` with a random token) and fenced in the summary with more backticks than any run in it, so the release's text can't act as a workflow command or as markdown. `main`'s CLI may still try a role the manifest names to read the deployed templates, as the read-only lookup role. A release can still choose what the diff shows; the hash check in each apply job is what ties that to what deploys. `scripts/check-deploy-workflow.mjs` is a tripwire, not a proof: it can't see every way a `run` step could fetch the release's code, so review `deploy.yml` changes with this in mind. The `trust` job, which has the token and no environment, runs no release code at all.

**No caches where the token is.** Never add `actions/cache`, or `cache:` on `setup-node`, to `plan`, `apply-stateful` or `apply` (`scripts/check-deploy-workflow.mjs` refuses it), and keep `package-manager-cache: false` on every `setup-node` in `deploy.yml` (it refuses one without it), since `setup-node` caches npm by itself when `package.json` names a `packageManager`: `build` and `synth` run release code, which could poison a cache (through `NODE_OPTIONS` in `$GITHUB_ENV`, say) that a job holding the token would restore. And don't use `PhysicalName.GENERATE_IF_NEEDED` in the stacks (CI refuses it): the name it generates hashes in the account, and it would show in the public diff, which scrubs only 12-digit runs.

**No raw template hashes in the log.** GitHub prints each step's `env` in its header, and its `run` with expressions filled in, masking only secrets. An assembly's hash is over templates that name the account, and the source is public and the synth deterministic, so a printed hash would let anyone brute-force the 12-digit account. So `synth` seals its hashes with the assembly, and `plan` passes on only `hash-hmac`, an HMAC under `DEPLOY_ASSEMBLY_KEY`. `scripts/check-deploy-workflow.mjs` refuses any `deploy.yml` job output with `hash` in its name that doesn't end in `-hmac`, and any `${{ needs.….outputs.…hash… }}` or `${{ steps.….outputs.…hash… }}` in an `env`, `outputs`, `with` or `run`, unless it ends in `-hmac`. The one exception is the `build` job's `hash` of the web build, whose files are public. It can't see a `run` step that echoes a hash it computed itself, so review those by eye.

**Data changes and the override.** Follow expand/contract ([ADR 0012](adr/0012-cicd-releases-rollbacks.md)): add the new field, index or resource and read both shapes in one release, remove the old one in a later release, and never change a property that replaces a table, pool, key or bucket. When a replacement or deletion is planned (a migration that has moved the data first), run the deploy by hand with **allow-replacement** checked: the check still reports what it found, in the plan's summary, and lets it through, and the plan always shows a warning and a summary line saying it's on.

**What the check can't see.** `cdk diff --method template` compares templates. A replacement that depends on a value only known at deploy time (a parameter, an SSM value or another stack's export that changes) doesn't show as one. The backstop is in the stacks: stateful resources have `RETAIN` removal policies, the table has deletion protection, and the stacks have termination protection, so a missed replacement leaves the old resource in place instead of deleting it.

**The diff is public.** The repository is public, so its Actions logs and job summaries are too, and the diff shows resource names, policy documents and other settings of the stacks. That's accepted: the same templates come from the public source with `cdk synth`. Account IDs aren't in it: every run of 12 digits becomes `<account>` (`scripts/scrub-account-ids.sed`), which over-redacts on purpose, so other accounts' IDs (the backup account, say) go too.

**Post-deploy checks** (`supply-checkout-pbp.30`). After the web checks, which already prove `app.` answers 200 with the new `index.html`, a CSP and HSTS, that its `config.json` has every key, that the demo is live and that the live router works, `apply` runs `scripts/smoke-checks.mjs`, read-only and making no AWS calls, over HTTPS as anyone would:

- `https://api.supplycheckout.com/me` and `/ops/teams` answer **401** without a token: the API is up and both authorizers refuse an anonymous caller. A 200 or a 5xx fails.
- `realtime.supplycheckout.com` and `auth.supplycheckout.com` **resolve** in DNS and **answer HTTPS below 500**: the live updates and sign-in custom domains are in place and their services answer.

Each check is tried 3 times, 5 seconds apart, with a 15-second timeout per request, to ride out a cold start. The job summary gets a table of every check, what it expected and what came back. You can run it from a laptop at any time: `node scripts/smoke-checks.mjs`.

**When a post-deploy check fails.** The deploy fails and says so in the summary. The web app is **not** rolled back: a failure there is the stacks', and the new app is the one that matches the new API. The stacks aren't rolled back automatically either (that's `supply-checkout-9lj`). Then:

1. Read the table: which check, and what came back. A 5xx from `api.` or a `realtime.`/`auth.` that doesn't answer points at the stacks this release changed (the plan's diff says which).
2. If users are affected, deploy the previous release again: Actions, Deploy, **Run workflow** from `main` with the previous tag. That runs the same plan and approvals, puts its stacks back, and makes its web app live again (`publish --reuse`). Stateful changes follow expand/contract, so the previous release's code reads the data as it is now. Don't roll a stateful stack back without reading its diff.
3. Otherwise, fix forward with a new release.

**Hook for the core journey canary** (`supply-checkout-pkt`, after the pilot). ADR 0012 runs the canary once after each prod deploy, whatever the hour. It goes in `apply` right after **Post-deploy checks** (there's a comment there), and should fail the deploy the same way, without rolling the web app back. Starting a CloudWatch Synthetics canary needs `synthetics:StartCanary` (or `StartCanaryDryRun`), and none of the roles the deploy role may assume has that today. pkt adds a narrow permission for that one canary, for example on the web publisher role or a role of its own.

**By hand.** Actions, Deploy, **Run workflow**, from `main`, with the tag: to deploy a release again, to roll the stacks back to an older release (its commit must still be on `main`; the replacement check still applies), for a planned migration (**allow-replacement**), or for a **dry run** (the plan only). Only one deploy runs at a time (concurrency group `deploy-production`, never cancelled once started); a run started while another is going waits, and a newer waiting run replaces an older waiting one. Dry runs deploy nothing and have their own group (`deploy-production-dry-run`), so a dry run never replaces a release deploy that's waiting for approval. A dry run can also run while a real deploy is executing; its diff may then fail or show changes that are mid-deploy, which is harmless: run it again afterwards.

**What it doesn't do yet.** Automatic rollback after failed journey tests (`supply-checkout-9lj`), the core journey canary (`supply-checkout-pkt`, after the pilot; its hook is below), alarm checks, and automatic rollback of the stacks (`supply-checkout-9lj`). The claude.ai artifact is retired: nothing is published to claude.ai. `npm run deploy` ([Deploying](infrastructure.md#deploying)) and `npm run publish:web` ([Web hosting and releases](web-app.md#web-hosting-and-releases)) stay the break-glass path.

**Settings it needs (the owner, once).**

- Environment `production`: deployment branches `main` only (no tags), the owner as required reviewer, no admin bypass, and the environment **secret** `AWS_DEPLOY_ROLE_ARN` (the deploy role stack's `DeployRoleArn` output).
- Environment `production-stateful`, **before the deploy role stack is deployed again**: the same rules (deployment branches `main` only, the owner as required reviewer, administrators can't bypass); optionally prevent self-review or add a wait timer. No secrets of its own are needed: it uses the repository secret.
- Repository secret `AWS_DEPLOY_ROLE_ARN` with the same value, for the `trust` job, the `synth` job (the account ID for the synth; it fails without it) and `production-stateful`. Secrets, not variables, so the ARN and the account ID in it are masked in the public run logs.
- Repository secret `DEPLOY_ASSEMBLY_KEY`, the key `synth` seals the `cloud-assembly` artifact with and `plan` opens it with; both fail without it. Make it without ever seeing it: `openssl rand -base64 32 | gh secret set DEPLOY_ASSEMBLY_KEY`. To rotate it, run that again between deploys, and after any release you suspect (a run that's waiting for approval when it changes can't open its artifact or match the plan's HMAC: run the deploy again).
- The deploy role stack deployed again after this change ([GitHub Actions deploy role](infrastructure.md#github-actions-deploy-role)): its trust now accepts `production-stateful` too. Until then, `apply-stateful` fails closed in its sign-in step. `npm run deploy:github-deploy` runs `scripts/check-environments.mjs` first (with your `gh` login) and refuses to deploy the trust unless both environments are locked down.
- **This change adds a second permission to the deploy role** (assume the web publisher role), so the deploy role stack must be deployed again after it merges, as above. Until then, the `apply` job fails at **Switch to the web publisher role**, after deploying the stacks and before publishing anything. The publisher role itself comes with the web stack, which the first release's `apply` job deploys.
- Both checks need `production` on `main` only: remove its `v*` tag policy, or every deploy stops at the `release` job.
- A tag ruleset on `refs/tags/v*` that lets only the owner and GitHub Actions (release-please) create, update or delete release tags.

### When the journey tests fail

The journey tests run after the release is already live for everyone, so there's nothing to hold back: a failure ([the plan](journey-tests-plan.md), "When the suite fails", owner decision 4) means

1. **The deploy run fails.** The deploy's `journeys` job links the journeys run it dispatched (titled `Journeys after deploying <tag> (deploy run …)`, under Actions, Journeys), whose summary lists every step's result in each browser, with each failure's message (masked); its traces and videos are in the results bucket under `runs/<journeys run id>-<attempt>/` (the summary names the keys, never presigned links). Re-running the deploy's `journeys` job dispatches a new journeys run; re-running the journeys run alone marks no release.
2. **The release is marked.** The `verdict` job makes it a pre-release and adds the failed steps to its notes. The deploy's release check then refuses to deploy it again: a bad release can't go out again by accident, and the releases page shows which releases were good.
3. **A critical journey failing is a P1** (J0, J1, J4, J7, J8, J13, J14, failed on both tries; the summary and the release notes say "Critical journeys failed"): follow the runbook, `docs/runbooks/journey-tests-failed.md` (bead `supply-checkout-o60.11`). If customers are affected, deploy the previous release again (Actions, Deploy, **Run workflow** with the previous tag), which puts back its stacks and its web app. A non-critical journey failing is a P2: fix forward the same business day.
4. **No automatic rollback yet.** That waits for `supply-checkout-9lj`; until then the web app and stacks stay on the new release.

**The override, allow-bad-release.** Deploy a pre-release again only when the tests themselves were wrong and have been fixed on `main` (the deploy runs `main`'s journeys workflow and specs): Actions, Deploy, **Run workflow** with the tag and **allow-bad-release** checked. The release check warns and notes it in the summary. A pass then adds "Journey tests passed" to the notes but leaves the pre-release mark: once you're satisfied the release is good, clear it by hand with `gh release edit vX.Y.Z --prerelease=false` (and set it as latest if it's the newest). Redeploying an older release (a rollback) runs today's specs, so a step added since may fail on it; read the summary before treating that as a regression.

**By hand, the journey tests alone.** Actions, Journeys, **Run workflow**, from `main`: to check prod after a change to `tests/prod/`, an incident, or a Stripe or AWS change outside a deploy (after merging a change to `tests/prod/`, run it before the next release). Leave both inputs, **tag** and **deploy-run**, empty: they're for the deploy, and the `check` job refuses a run whose deploy-run doesn't name a deploy of `main` that's still going. Runs by hand go one at a time in a concurrency group of their own (`journeys-manual`); a deploy's run takes a group of its own per deploy run and attempt (`journeys-deploy-<id>-<attempt>`), so a waiting run can never replace another's waiting run. Two runs against prod at once would break each other (each signs the test accounts out everywhere when it ends), so a run by hand's `check` job refuses while a deploy is queued, waiting or running, or while a deploy's run of the journey tests (titled `Journeys after deploying …`) hasn't completed (a deploy cancelled before it followed its run, or a cancel that failed, can leave one testing prod), and a deploy's run waits up to 30 minutes for any other journeys run to finish, then fails (`scripts/journeys/workflow.mjs wait-for-prod`). It marks no release.

### The production-journeys environment

The prod journey tests ([the plan](journey-tests-plan.md), "Credentials and secrets"; bead `supply-checkout-o60.4`) run in a GitHub environment of their own, `production-journeys`. The journeys role ([Journey tests](infrastructure.md#journey-tests)) trusts any job in it, and its secrets reach any job that names it, so it must be locked down before the role exists. GitHub creates an environment with no protection the first time a job names one that doesn't exist. Only the journeys workflow (`.github/workflows/journeys.yml`, `supply-checkout-o60.6`) names it, and its job that does runs only once the journey tests are switched on (step 9 below) and the environment passes the check.

**Guards in the repository.**

- `scripts/check-environments.mjs --environment production-journeys` (or `--journeys required`, which adds it without naming it: the deploy's release job uses that, or `--journeys if-present` while the journey tests are switched off) refuses unless it exists, administrators can't bypass it, and its deployment branches are custom with exactly one policy, `main` (branch). Unlike `production` and `production-stateful` it needs no required reviewer (owner decision 5 in the plan): the owner already approved the deploy it follows, and it deploys nothing.
- `npm run deploy:journeys` (in `infra/`, `scripts/deploy-journeys.mjs`) runs that check first and deploys nothing unless it passes, with the same repository-context and ID checks as `deploy:github-deploy`.
- CI's lint job runs `scripts/check-workflow-environments.mjs`, which parses every workflow as YAML (one that doesn't parse fails): only `.github/workflows/journeys.yml` may name `production-journeys` (in any letter case, after YAML's escapes are decoded, and anywhere in the raw text, comments included); a workflow that names it, dispatches `journeys.yml` (mentions the file anywhere in it, `on:` included, such as an input's default, but not in an event filter like `paths` or workflow_run's `workflows`, as `gh workflow run journeys.yml` does), dispatches a workflow that reaches it (mentions that workflow's file, as `release.yml`'s `gh workflow run deploy.yml` does), or calls one that reaches it, followed through every chain, may only be started by `workflow_call`, `workflow_dispatch`, `push` or `schedule`, never by `pull_request`, `pull_request_target` or any other event someone without write access can cause; `journeys.yml` has no `workflow_call` trigger, so nothing can call it (it's dispatched: [step 9 of the deploy](#deploying-a-release), "Why a dispatch, not a call"); no job sets its environment from an expression; a job calls a reusable workflow only as `./.github/workflows/<file>.yml` (a called workflow runs with the caller's OIDC subject and secrets, so never one from another repository or ref); no step calls into this repository by a remote reference; and no workflow uses a YAML merge key (`<<`). A change to this check or to `check-environments.mjs` gets the security review, since a PR runs its own copy.
- `deploy:journeys` and `deploy:github-deploy` refuse `--app`, `-a`, `--output`, `-o`, `--all`, grouped short options (`-ra`) and stack names, so they deploy only their own app's stack. The environment's `main`-only rule doesn't stop a `pull_request_target`, `issue_comment` or `workflow_run` run, which is on `main` too.

**Setting it up (the owner, once), in this order.**

1. **Create the environment.** Settings, Environments, **New environment**, name `production-journeys`, then on its page:
   - **Required reviewers**: off. **Wait timer**: off.
   - **Allow administrators to bypass configured protection rules**: unchecked.
   - **Deployment branches and tags**: **Selected branches and tags**, then **Add deployment branch or tag rule**: ref type **Branch**, name pattern `main`. No other rule, and no tag rule.
   - No secrets or variables yet.

   Or with `gh` (the same settings):

   ```bash
   gh api -X PUT repos/davetashner/supply-checkout/environments/production-journeys \
     -F can_admins_bypass=false \
     -F 'deployment_branch_policy[protected_branches]=false' \
     -F 'deployment_branch_policy[custom_branch_policies]=true'
   gh api -X POST repos/davetashner/supply-checkout/environments/production-journeys/deployment-branch-policies \
     -f name=main -f type=branch
   ```

2. **Check it**, with your `gh` login:

   ```bash
   node scripts/check-environments.mjs --environment production-journeys
   ```

   It prints `check-environments: production-journeys: each exists, main only, no admin bypass`. Anything else lists what to fix.
3. **Deploy the journeys stack** with `npm run deploy:journeys -- --profile supply-prod`, following [Journey tests](infrastructure.md#journey-tests), "Deploying it", steps 1 to 5 (the data stack first, then the checks that no receipt rule set is active and nothing exists at `e2e.`).
4. **Activate the SES receipt rule set and check the mailbox end to end**: the same section's steps 6 and 7.
5. **Add the environment secret `JOURNEYS_AWS_ROLE_ARN`**: the stack's `JourneysRoleArn` output (step 8 there).
6. **Make the long-lived accounts and teams** (the plan's "Long-lived test accounts"):
   - Sign up three accounts, `owner`, `crew` and `viewer`, each at the test subdomain (`e2e.` the app's domain), each with its own password of 32 random characters stored nowhere but the secrets below. The sign-up code arrives in the mail bucket under `inbox/`: `aws s3 ls` it and `aws s3 cp "s3://<bucket>/inbox/<key>" -` to read it (the bucket name is in SSM, `/supply-checkout/prod/journeys/mail-bucket-name`).
   - As `owner`, turn on two-step sign-in and keep its secret key (base32) for `JOURNEYS_OWNER_TOTP`.
   - As `owner`, make two teams, **Journeys desktop** and **Journeys phone**, and invite `crew` as a contributor and `viewer` as a viewer to both.
   - Comp each team for 12 months as an operator: `npm run ops -- comp <teamId> --months 12 --reason "Journey tests"`.
   - Sign in as each account and check that `/me` lists exactly the two journey teams, and that `npm run ops -- teams` shows both with the **Test** badge.
7. **Add the other environment secrets**: `JOURNEYS_OWNER_PASSWORD`, `JOURNEYS_CREW_PASSWORD`, `JOURNEYS_VIEWER_PASSWORD`, `JOURNEYS_OWNER_TOTP`; the three accounts' addresses, `JOURNEYS_OWNER_EMAIL`, `JOURNEYS_CREW_EMAIL` and `JOURNEYS_VIEWER_EMAIL`; the two teams' IDs, `JOURNEYS_DESKTOP_TEAM_ID` and `JOURNEYS_PHONE_TEAM_ID` (from `/me`, or `npm run ops -- teams`); the two bucket names, `JOURNEYS_MAIL_BUCKET` and `JOURNEYS_RESULTS_BUCKET` (the stack's `MailBucketName` and `ResultsBucketName` outputs: the journeys role can't read SSM, and as secrets the account ID in them is masked in the logs); and `JOURNEYS_STRIPE_SANDBOX_KEY` (a restricted **sandbox** key: Subscriptions write, Customers read, Payment methods write; never a live key). Rotation is in the plan's secrets table. Environment secrets, never repository secrets or variables, so only a job on `main` in this environment can read them.
8. **Check it again** (step 2) after any change to the environment's settings.
9. **Switch the journey tests on**: Settings, Secrets and variables, Actions, **Variables**, new repository variable `JOURNEYS_ENABLED` with the value `true` (or `gh variable set JOURNEYS_ENABLED --body true`). Until then the deploy dispatches no journeys run and passes without them (its `journeys` job warns "The journey tests are switched off", and its summary says they didn't run), and a run by hand's `check` job warns the same and skips the suite. From then on, every deploy and every run by hand requires the environment to exist and be locked down, and the suite job requires every secret above (it fails, naming the missing ones, before signing in). Then run it once by hand (Actions, Journeys, **Run workflow** from `main`) and read the run's public log for anything that should have been masked; the plan asks for that first real run to include a deliberately failing test, to check the upload redacts and doesn't refuse. To switch them off again, delete the variable or set it to anything but `true`.

**What runs with AWS credentials.** In `journeys.yml`, only the `suite` job, in `production-journeys`, with the journeys role (two buckets, nothing else): it restores no cache of any kind (main's caches are written by ordinary CI runs, whose `npm ci` runs every dev dependency's install scripts, and a browser runs here with every secret), installs its dependencies with `--ignore-scripts` and the browsers cold, before any credential or secret is in a step's environment. In `deploy.yml`, only `plan` (the lookup role after its sign-in steps, whose deploy-role session lasts 15 minutes), `apply-stateful` and `apply` (the publisher role for publishing), each only after the owner's approval, only in `production` or `production-stateful` (both `main` only), only in a run on `main`, and only code from a release commit on `main` that passed CI. No dependency cache is restored in them, no pull request event starts the workflow, and every third-party action is pinned by commit SHA.

## What's New notes

The app's What's New banner ([web-app.md](web-app.md#the-web-app-on-aws), `supply-checkout-005.17`) shows a short note for each user-facing change released in the last 14 days. The notes are written by hand, in `src/whats-new.json`, because commit titles are written for developers. The banner is drawn from that file, and the file is shipped with the app.

**The check.** `scripts/check-whats-new.mjs` (in `npm run lint`) reads the newest release in `CHANGELOG.md`. Every entry under its **Features** must have a note, or an explicit skip with a reason. Fixes don't need one, but a fix users will notice deserves a note. On an ordinary pull request, `CHANGELOG.md` is main's, and its newest release already has notes, so the check passes. It only fails on release-please's pull request, whose `CHANGELOG.md` adds the next release. The error names each `feat:` entry that has neither a note nor a skip. The check also refuses a malformed file: an unknown field, a bad date, releases out of order, a title over 60 characters or text over 200, a note without `prs`, or a pull request that is both noted and skipped. Its tests are in `scripts/check-whats-new.test.mjs`.

**Writing them.** When the release pull request's CI fails the check (or before, if you know what's in it), open a pull request to main that adds the release at the top of `src/whats-new.json`. release-please then carries the notes into its own pull request when it updates it. Don't push to release-please's branch, because it rewrites that branch.

```json
{
  "version": "1.10.0",
  "date": "2026-10-08",
  "notes": [
    { "title": "See who's signed in", "text": "The bar under the header shows your name and your role in the team.", "prs": [605] }
  ],
  "skip": { "564": "Behind the scenes: test infrastructure" }
}
```

- `version` is the release's version, and `date` is the day it's deployed to prod. The banner shows a release from that day until 14 days later, so a date later than the deploy holds the notes back until then. Releases go newest first.
- A note says what someone using the app can now do, or what's different, in a sentence or two. Write for the people using the app, not the people who built it. Don't use pull request titles, and don't name internals ("the API", "DynamoDB", "a migration"). Use the app's own words (projects, inventory, checkout, Account), and keep the title under 60 characters and the text under 200. One note can cover several pull requests (`prs`), for example a feature built in a backend PR and an app PR.
- Skip a `feat:` entry that users won't see, such as a support tool, the marketing site, infrastructure, metrics or a migration, and give a short reason. The reason isn't shown in the app, but reviewers read it.
- The owner reviews the notes as part of the release pull request, before approving it. They're the words customers will read.

## Real-device check

Playwright can't open a phone's camera (its tests use a stand-in camera, `tests/camera.js`), so before publishing a release, check scanning on a real iPhone and a real Android phone: your own phones, or a real-device cloud such as BrowserStack Live. A Scan button opens the camera in a scanner (`src/live-scan.js`), which reads each frame with the browser's `BarcodeDetector` where there is one (Chrome and Samsung Internet on Android) and ZXing otherwise (Safari on iPhone and iPad, Firefox), and takes a code once two frames agree. **Take a photo instead** (and a browser without a camera) takes a photo through the file input (`capture="environment"`), decoded the same way.

1. **iPhone, Safari** (current iOS): open a project and tap **Scan to check out**. Allow the camera, and hold a real barcode in the frame: the scanner closes and the checkout dialog opens with the right item, and the camera light goes off. Scan a code turned on its side, and a small shelf or bin label too. Tap **Scan to check out** again, then **Take a photo instead**, and photograph the barcode: the same dialog opens. Then, on the project list, tap **Scan receipt**, photograph a paper receipt, and check the review screen lists its lines.
2. **Android phone, Chrome** (current Android): repeat step 1.
3. **Android phone, Samsung Internet** and **Firefox for Android**: open a project and scan one barcode in each.
4. On both phones, photograph something that isn't a barcode: the app says no barcode was found and suggests typing the number. And open the scanner, then switch to another app and back: the camera light goes off and the scanner says it's paused, with **Try again**.
5. On both phones, turn to landscape and back on the project and receipt screens: nothing scrolls sideways and no button is cut off.

Note the devices and OS versions in the release PR before merging it.

## Journey evidence pack

Each GitHub Release also gets a journey evidence pack, built by the `evidence` and `evidence-upload` jobs in `.github/workflows/release.yml` after the full check suite passes:

- `journey-evidence.html`: for every journey, each step with its result, the tests that prove it and their results, the time in the video where each shows the step, a screenshot at the step's end, and the alarms that watch the journey.
- `J<n>-<name>.webm`: one video per journey, J0 to J11 (phase 2 journeys have nothing built to show), recorded on desktop Chromium.
- `journey-traces.zip`: each test's Playwright trace.

It's recorded from the release tag against the test suite's fakes and demo data, never production or a real account: the job has no secrets or cloud credentials and only a read-only token, and a separate job with `contents: write` uploads the files. Release assets are public. A test that fails while recording doesn't stop the upload: the report shows it failed, and the workflow run has a warning. A recording that can't run at all (a build, the test listing or the run itself fails: `record.mjs` exits 2) fails the `evidence` job at **Record the journeys**, with the reason in its log, and nothing is uploaded. How it works: [Journey videos](testing.md#journey-videos).

To check it, open the release on GitHub and look for those assets. Download the report, the videos and `journey-traces.zip` into one folder and unzip the traces there; then the report plays each video in the page, its timestamps seek to the step, and its trace links open the files (`npx playwright show-trace <file>`, or drop one on trace.playwright.dev).
